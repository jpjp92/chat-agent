# DEV 2026-05-18

## 멀티 프로바이더 연동 아키텍처 확장 기획 (OpenAI / Anthropic)

현재 Google Gemini (`@google/genai` SDK)에 강하게 결합되어 있는 시스템에 향후 OpenAI(GPT-5.2, GPT-5-mini 등)나 Anthropic(Claude 4.6 Sonnet, Claude 4.5 Haiku 등) 타 프로바이더 모델을 도입하기 위해 필요한 아키텍처 개선 방향을 기획했습니다. (TODO 백로그의 M1~M4, M6 항목 대응)

### 1. Provider 추상화 레이어 도입 (M1)

현재 `generator.ts` 등에서 SDK를 직접 호출하는 구조를 프로바이더 독립적인 공용 인터페이스로 래핑합니다.

```text
api/_lib/providers/
  ├── index.ts        # 통합 인터페이스 (Unified Provider)
  ├── types.ts        # 공통 Message, Request, Response 타입 정의
  ├── gemini.ts       # 기존 Gemini SDK 로직 래핑
  ├── openai.ts       # OpenAI SDK 래핑 (`openai` 패키지)
  └── anthropic.ts    # Anthropic SDK 래핑 (`@anthropic-ai/sdk`)
```

- 호출부를 `getProvider(modelId).streamResponse(...)` 형태로 단순화.
- 각 프로바이더 파일 내부에서 공통 포맷을 자체 포맷으로 Mapping 하여 API 호출 수행.

### 2. 모델 메타데이터 레지스트리 확장 (M3)

프론트엔드(`src/lib/models.ts`)와 백엔드(`api/_lib/models.ts`)의 모델 레지스트리를 확장하여 모델별 소속 프로바이더와 지원 기능(Capability)을 명시합니다.

```typescript
// api/_lib/models.ts 예시
export const MODELS = {
  // Gemini
  FLASH:        { id: 'gemini-2.5-flash', provider: 'google', vision: true, tools: true, search: true },
  FLASH_LITE:   { id: 'gemini-2.5-flash-lite', provider: 'google', vision: false, tools: false, search: false },
  FLASH_3_1_LITE: { id: 'gemini-3.1-flash-lite', provider: 'google', vision: false, tools: false, search: false },
  // OpenAI
  GPT_5_2:      { id: 'gpt-5.2', provider: 'openai', vision: true, tools: true, search: false },
  GPT_5_MINI:   { id: 'gpt-5-mini', provider: 'openai', vision: true, tools: true, search: false },
  GPT_5_4_MINI: { id: 'gpt-5.4-mini', provider: 'openai', vision: true, tools: true, search: false },
  // Anthropic
  CLAUDE_SONNET:{ id: 'claude-4.6-sonnet', provider: 'anthropic', vision: true, tools: true, search: false },
  CLAUDE_HAIKU: { id: 'claude-4.5-haiku', provider: 'anthropic', vision: true, tools: true, search: false }
} as const;
```

이를 통해 선택된 모델의 Vision/Tool 지원 여부를 동적으로 파악하여 라우팅할 수 있습니다.

### 3. 공통 메시지 및 페이로드 정규화 (M4)

프로바이더별로 다른 멀티모달 및 시스템 프롬프트 형식을 통합 관리합니다.

- **멀티모달(이미지/영상) 처리 차이**:
  - **이미지**: Gemini는 `inlineData`/`fileData` 사용, OpenAI/Anthropic은 base64 URL 방식 사용.
  - **영상(Video)**: 네이티브 영상 분석 기능은 현재 **Gemini 모델만 지원**합니다. OpenAI(GPT)와 Anthropic(Claude)은 텍스트 및 이미지만 처리 가능하므로, 해당 모델 선택 시 영상 첨부 및 직접 분석 기능은 제한되거나 폴백이 필요합니다.
- **시스템 프롬프트**: Gemini는 `systemInstruction`, OpenAI는 `role: "system"`, Anthropic은 `system` 파라미터.
- **특화 기능 폴백**: 타 모델에서 미지원하는 YouTube URL 직접 분석이나 Google Search Grounding은 자막 스크래핑 폴백(`fetch-transcript`)이나 DuckDuckGo 기반 `searchWebTool`로 대체되도록 내부 로직 분기.

### 4. API 키 및 에러 관리 통합 (M2)

`api/_lib/config.ts`를 확장하여 다중 키를 관리합니다.

- `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` 환경변수 추가.
- Rate Limit(429)이나 토큰 소진 등 프로바이더별 에러 포맷을 파싱하여, 프론트엔드에 기존 규격화된 에러 객체 형태로 통일하여 전달.

### 6. Provider별 Rate Limit 및 Quota 관리 정책 (M2 확장)

API 호출 시 각 프로바이더의 Rate Limit(속도 제한)을 고려하여 다중 키 로테이션 및 백오프(Backoff) 처리를 고도화해야 합니다.

**[Anthropic (Claude) Rate Limit 기준]**
- **Claude 4.6 Sonnet**: 50 RPM / 30K TPM (Input) / 8K TPM (Output)
- **Claude 4.5 Haiku**: 50 RPM / 50K TPM (Input) / 10K TPM (Output)
- **Claude Opus 계열**: 50 RPM / 500K TPM (Input) / 80K TPM (Output)
- **공통 제한**: 
  - 배치 요청: 전체 모델 합산 50 RPM
  - 웹 검색 도구: 전체 모델 합산 30 RPS (초당 요청)
  - *참고*: 입력 토큰(TPM) 산정 시 '캐시 읽기(Cache Reads)'는 제외됩니다.

**[OpenAI (GPT) Rate Limit 기준]**
- **GPT-5.2**: 500 RPM / 500K TPM / 900K TPD (일일 토큰)
- **GPT-5-mini**: 500 RPM / 500K TPM / 5M TPD
- **GPT-5.4-mini**: 500 RPM / 200K TPM / 2M TPD
- **공통 특징**: 주요 타겟 모델들의 분당 요청수(RPM)는 500회로 넉넉하지만, 일일 토큰 한도(TPD) 차이가 크므로 트래픽 관리에 유의해야 합니다.

**[Google (Gemini) Rate Limit 기준]**
- **Gemini 2.5 Flash**: 1K RPM / 1M TPM / 10K RPD (일일 요청 수)
- **Gemini 2.5 Flash Lite**: 4K RPM / 4M TPM / RPD 무제한
- **Gemini 3.1 Flash Lite**: 4K RPM / 4M TPM / 150K RPD
- **Gemini 2.5 Flash TTS** (음성 생성): 10 RPM / 10K TPM / 100 RPD
- **Imagen 4 Generate** (이미지 생성, 백로그): 10 RPM / 70 RPD (TPM 미적용)

> [!TIP]
> 위에서 정리된 3대 프로바이더(Google, OpenAI, Anthropic)의 상세 Rate Limit 정책을 바탕으로, `api/_lib/config.ts`의 `markKeyRateLimited` 쿨다운 시간(현재 일괄 60초)과 에러(429) 처리 로직을 프로바이더별 한도에 맞춰 정교하게 최적화할 계획입니다. 특히 TTS나 이미지 생성(Imagen) API는 RPM 한도가 10회로 매우 낮아 별도의 백오프(Backoff) 및 큐(Queue) 관리가 중요합니다.
