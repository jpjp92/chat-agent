## 1. URL 수집 Jina Reader fallback 적용

### 배경

- Wikidocs 블로그 URL 요약에서 원문 기반 요약이 아니라 검색 기반 요약처럼 다른 내용이 섞이는 케이스를 확인.
- 테스트 대상: `https://wikidocs.net/blog/@jaehong/8007/`
- Node 서버 사이드 `fetch`는 `403 Forbidden`과 `Just a moment...` Cloudflare challenge HTML만 수신.
- 기존 selector/본문 추출 로직은 실제 본문 HTML을 받지 못하므로 개선해도 효과가 없음.
- Cheerio는 이미 받은 HTML을 파싱하는 도구라 403/challenge 응답 자체를 해결하지 못함.

### 테스트

- `scripts/test-url-extract.mjs` 추가.
- 테스트 항목:
  - 직접 Node fetch 상태 코드, content-type, HTML 길이, challenge 감지.
  - 기존 `fetch-url` 스타일의 메타/본문 추출 결과.
  - Wikidocs 전용 selector 후보.
  - 선택적 Cheerio 후보.
  - Jina Reader 후보.
- 결과:
  - 직접 fetch: `403 Forbidden`, title `Just a moment...`, 본문 추출 길이 16.
  - Cheerio: challenge HTML만 파싱 가능하므로 우회 효과 없음.
  - Jina Reader: `200 OK`, 약 4.4KB Markdown 텍스트 확보, 실제 본문 키워드 `ACE-Step` 포함.

### 수정

- `api/fetch-url.ts`
  - 직접 수집 결과가 `403`, Cloudflare challenge, `Just a moment...`, `cf-chl`, `challenge-platform` 패턴이면 실패로 판단.
  - 직접 수집이 막히면 `https://r.jina.ai/http://{targetUrl}`로 Jina Reader fallback 실행.
  - 직접 수집은 성공했지만 추출 본문이 너무 짧으면 Jina Reader를 한 번 시도하되, Jina 실패 시 기존 짧은 본문은 버리지 않음.
  - Jina Reader 결과는 기존 URL 컨텍스트와 동일하게 `content`로 반환.
  - 사용자-facing 원문 수집 실패 안내 문구는 추가하지 않음.

### 검증

- `npx tsc --noEmit` 성공.
- `node scripts/test-url-extract.mjs https://wikidocs.net/blog/@jaehong/8007/` 성공.
- 확인 결과:
  - 직접 fetch는 Cloudflare challenge로 실패.
  - Jina Reader는 실제 본문 Markdown 확보.

### 남은 판단

- Jina Reader도 실패하면 기존처럼 `[FETCH_ERROR]`가 반환되고, 채팅 생성 경로는 URL 컨텍스트 없이 검색/일반 응답 경로로 진행될 수 있음.
- Jina Reader는 외부 서비스 의존성이므로 향후 사용량/지연시간/장애율이 커지면 timeout, 도메인별 allowlist, 별도 환경변수 on/off 스위치를 검토.

## 2. Jina Reader URL 이중 프로토콜 버그 수정

### 증상

- 네이버 뉴스(`https://n.news.naver.com/...`) URL 요약 시 실제 기사와 전혀 다른 내용이 반환됨.
- 예: AI 에이전트 관련 기사 요청 → 의대 정원 관련 기사 내용으로 응답.

### 원인

`fetchJinaReaderContent`에서 Jina Reader URL을 생성할 때 프로토콜을 중복 삽입.

```ts
// 버그: targetUrl에 이미 https://가 포함되어 있는데 http://를 추가로 붙임
const readerUrl = `https://r.jina.ai/http://${targetUrl}`;
// → https://r.jina.ai/http://https://n.news.naver.com/...  (잘못된 URL)
```

Jina Reader가 잘못된 URL을 받아 캐시된 무관한 기사 내용을 반환하는 것이 원인.

### 수정

```ts
// 수정: targetUrl 그대로 사용 (이미 https:// 포함)
const readerUrl = `https://r.jina.ai/${targetUrl}`;
// → https://r.jina.ai/https://n.news.naver.com/...  (올바른 URL)
```

- `api/fetch-url.ts` 72번째 줄 수정.

## 3. isBlockedOrChallenge 오탐 수정 및 Jina fallback 우선순위 재설계

### 증상

- Jina Reader URL 이중 프로토콜 버그 수정 후에도 일부 뉴스 URL에서 완전히 다른 기사 내용이 반환되는 케이스 지속 보고.

### 원인 1 — isBlockedOrChallenge 오탐

`isBlockedOrChallenge` 함수의 `lower.includes('cloudflare')` 단순 포함 체크가 오탐 원인.

```ts
// 문제: Cloudflare를 CDN으로 사용하는 정상 사이트의 HTML에도
// cdnjs.cloudflare.com 등 스크립트 경로가 포함될 수 있어 오탐 발생
|| lower.includes('cloudflare')
```

Cloudflare CDN을 사용하는 정상 언론사 페이지가 challenge 페이지로 잘못 분류되면:
1. 직접 fetch 결과가 정상임에도 `isBlockedOrChallenge` → `true`
2. Jina Reader fallback 불필요하게 실행
3. Jina 실패 시 `[FETCH_ERROR]` → Google Search 활성화 → 다른 기사로 응답

또한 `lower.includes('just a moment')`도 본문에 해당 문구가 포함된 정상 사이트에서 오탐 가능.

### 원인 2 — 직접 fetch 성공 후 Jina 호출 경로

`content.length < 300` 조건으로 Jina fallback을 추가로 호출하는 경로가 존재했음.

```ts
// 문제: 직접 fetch 성공(짧은 내용)→ Jina 호출 → Jina가 캐시된 엉뚱한 기사 반환
if (content.length < 300) {
    content = await fetchJinaReaderContent(targetUrl);
}
```

직접 fetch가 정상적으로 내용을 반환했음에도 Jina가 이를 덮어쓰고 전혀 다른 기사를 반환하는 것이 근본 원인.

### 수정

```ts
// isBlockedOrChallenge: 오탐 범위 축소
// 'just a moment' → <title> 태그 한정
// 'cloudflare' 단독 → 'checking your browser'와 AND 조합
return status === 403
    || !!html.match(/<title[^>]*>\s*just a moment/i)
    || lower.includes('cf-chl')
    || lower.includes('challenge-platform')
    || (lower.includes('cloudflare') && (lower.includes('checking your browser') || lower.includes('enable javascript and cookies')));
```

```ts
// Jina fallback 우선순위 재설계
// 직접 fetch 성공 시 → 내용 길이와 무관하게 무조건 사용
// Jina Reader → 직접 fetch가 완전히 실패(타임아웃, 연결 오류, 차단)할 때만 사용
// content < 300 보완 목적의 Jina 호출 제거
```

- `api/fetch-url.ts` `isBlockedOrChallenge` 함수 수정.
- `content.length < 300` → Jina 호출 경로 제거.
- `scripts/test-url-extract.mjs`의 동일 패턴도 로컬 수정 (`.gitignore` 대상).

### 검증

- `npx tsc --noEmit` 성공.
- 네이버 뉴스 URL 직접 fetch: 200 OK, 2019자 정상 추출, challenge 오탐 없음 확인.
- Jina Reader 올바른 URL(`https://r.jina.ai/https://...`) 다수 Naver URL 응답 정상 확인.

### 현재 동작 흐름

```
직접 fetch 성공(내용 있음) → 그대로 반환 (Jina 미호출)
직접 fetch 완전 실패        → Jina Reader fallback
Jina도 실패                 → [FETCH_ERROR] → Google Search fallback
```

## 4. generator.ts hasUrlContent 조건 수정 (근본 원인)

### 증상

- 로컬(`npx vercel dev`, 한국 IP)에서는 URL 요약이 정상 동작.
- 배포 후 웹(Vercel 서버, 해외 IP)에서는 계속 전혀 다른 기사를 요약.

### 원인

`api/_lib/agent/nodes/generator.ts`의 `hasUrlContent` 판단 조건이 문제.

```ts
// 기존: 내용 길이 300자 이상일 때만 Google Search 비활성화
const hasUrlContent = !!(urlContentMatch && urlContentMatch[1].trim().length >= 300);
```

- **로컬(한국 IP)**: Naver가 본문 포함 2199자 반환 → `hasUrlContent = true` → Google Search 비활성 → 정상 요약
- **Vercel(해외 IP)**: Naver가 JS 렌더링 없이 짧은 HTML 반환 → 추출 내용 < 300자 → `hasUrlContent = false` → **Google Search 활성화 → 전혀 다른 기사 요약**

직접 fetch, Jina fallback 우선순위를 아무리 수정해도, generator 단에서 Google Search를 켜버리면 의미가 없었던 구조.

### 수정

```ts
// 수정: [URL_CONTENT:] 태그 존재 여부로만 판단 (길이 체크 제거)
const hasUrlContent = state.webContent.includes('[URL_CONTENT:');
```

- `useChatStream.ts`에서 fetch 완전 실패 시 `[URL_CONTENT:...]` 태그를 추가하지 않으므로, 태그 존재 자체가 "URL fetch 완료" 신호로 충분.
- URL이 제공된 이상 내용이 짧아도 해당 URL 기반으로만 요약. og:title + og:description만으로도 올바른 기사 요약 가능.

### 검증

- `npx tsc --noEmit` 성공.
