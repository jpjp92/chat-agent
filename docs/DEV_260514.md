# DEV 2026-05-14

## 1. URL 수집 Jina Reader fallback 적용

### 배경

- Wikidocs 블로그 URL 요약에서 원문 기반 요약이 아니라 검색 기반 요약처럼 다른 내용이 섞이는 케이스를 확인.
- 테스트 대상: `https://wikidocs.net/blog/@jaehong/8007/`
- Node 서버 사이드 `fetch`는 `403 Forbidden`과 `Just a moment...` Cloudflare challenge HTML만 수신.
- 기존 selector/본문 추출 로직은 실제 본문 HTML을 받지 못하므로 개선해도 효과가 없음.
- Cheerio는 이미 받은 HTML을 파싱하는 도구라 403/challenge 응답 자체를 해결하지 못함.

### 테스트

- `scripts/test-url-extract.mjs` 추가.
- 테스트 항목:
  - 직접 Node fetch 상태 코드, content-type, HTML 길이, challenge 감지.
  - 기존 `fetch-url` 스타일의 메타/본문 추출 결과.
  - Wikidocs 전용 selector 후보.
  - 선택적 Cheerio 후보.
  - Jina Reader 후보.
- 결과:
  - 직접 fetch: `403 Forbidden`, title `Just a moment...`, 본문 추출 길이 16.
  - Cheerio: challenge HTML만 파싱 가능하므로 우회 효과 없음.
  - Jina Reader: `200 OK`, 약 4.4KB Markdown 텍스트 확보, 실제 본문 키워드 `ACE-Step` 포함.

### 수정

- `api/fetch-url.ts`
  - 직접 수집 결과가 `403`, Cloudflare challenge, `Just a moment...`, `cf-chl`, `challenge-platform` 패턴이면 실패로 판단.
  - 직접 수집이 막히면 `https://r.jina.ai/http://{targetUrl}`로 Jina Reader fallback 실행.
  - 직접 수집은 성공했지만 추출 본문이 너무 짧으면 Jina Reader를 한 번 시도하되, Jina 실패 시 기존 짧은 본문은 버리지 않음.
  - Jina Reader 결과는 기존 URL 컨텍스트와 동일하게 `content`로 반환.
  - 사용자-facing 원문 수집 실패 안내 문구는 추가하지 않음.

### 검증

- `npx tsc --noEmit` 성공.
- `node scripts/test-url-extract.mjs https://wikidocs.net/blog/@jaehong/8007/` 성공.
- 확인 결과:
  - 직접 fetch는 Cloudflare challenge로 실패.
  - Jina Reader는 실제 본문 Markdown 확보.

### 남은 판단

- Jina Reader도 실패하면 기존처럼 `[FETCH_ERROR]`가 반환되고, 채팅 생성 경로는 URL 컨텍스트 없이 검색/일반 응답 경로로 진행될 수 있음.
- Jina Reader는 외부 서비스 의존성이므로 향후 사용량/지연시간/장애율이 커지면 timeout, 도메인별 allowlist, 별도 환경변수 on/off 스위치를 검토.
