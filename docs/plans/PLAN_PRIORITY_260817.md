## 1순위 — S등급: 조용히 틀린다

### 1-1. CGV 스크래핑 실패가 "상영 없음"으로 보인다 — [BACKLOG A3](PLAN_BACKLOG_260801.md)

스크래핑이 실패했는데 카드는 **"상영작 없음"** 을 정상 결과처럼 그린다. 사용자는 극장이 쉬는 줄 안다.
CGV만 browserless(Cloudflare 우회)라 **셋 중 하나만 조용히 비는** 구조다.
→ 실패와 "정말 없음"을 **구분해서** 렌더해야 한다(에러 상태 + 재시도).

### 1-0. 🔴 **열린 업로드 엔드포인트** — IDOR-3 재평가 (2026-08-17)

**[TODO](../TODO.md) 의 기술이 실제보다 약하다.** IDOR-3 는 *"admin 클라이언트 + 형식 검증뿐"* 이라
적혀 있는데, 이는 "인증은 되는데 소유권 검증이 없다"로 읽힌다. **인증 자체가 없다:**

```
$ grep -c "Authorization\|createRouteClient\|unauthorized\|getUser" <3개 라우트>
upload 0 · create-signed-url 0 · parse-document 0
```

클라이언트도 `authedFetch` 가 아닌 **평범한 `fetch`** 로 부른다(`services/geminiService.ts`).
`/api/sessions` 는 Bearer 토큰을 붙이는데 스토리지 3종만 안 붙인다.

**IDOR 가 아니라 열린 업로드다** — IDOR 는 "로그인한 A 가 B 의 파일에 접근"이지만 여기는 로그인이 필요 없다.

- 누구나 `POST /api/upload` 로 Supabase 에 파일을 쌓을 수 있다
- 버킷이 공개라 **이 서비스 도메인에서 서빙된다** — 불법 콘텐츠 호스팅에 악용되면 계정 문제로 번진다
- 스토리지 용량·대역폭 비용이 그대로 청구된다
- `upsert: true` 라 경로를 맞히면 덮어쓸 수 있다

> 🔴 **CGV·폴백 크래시보다 위다.** 그것들은 *사용자가 겪는* 문제지만 이건 *제3자가 악용하는* 문제라
> **노출 시간이 곧 위험**이다. dev 에 이미 배포돼 있다.

**조치는 2단계로 나눈다 — Phase 2 에 이관 문제가 있기 때문이다:**

| | 내용 | 막는 것 |
|---|---|---|
| **Phase 1** | `authedFetch` 전환 · JWT `sub` 로 `${uid}/` prefix · user-scoped 클라이언트 · `storage.objects` RLS · 버킷은 **공개 유지** | 무인증 업로드 · 타인 파일 덮어쓰기 · 열거 |
| **Phase 2** | 버킷 비공개 + 서명 다운로드 URL + 기존 객체 이관 + `attachment_url` 백필 | URL 을 아는 제3자의 읽기 |

> 🔴 **Phase 2 가 미뤄져 온 진짜 이유**: `chat_messages.attachment_url` 에 `getPublicUrl` 결과가
> **저장돼 있다.** 버킷을 비공개로 돌리는 순간 기존 메시지의 이미지가 전부 400 이 된다.
> 렌더러가 매번 서명 URL 을 받도록 바꾸고 기존 행을 백필해야 한다 — 별개 작업이다.

**기존 파일은 그대로 둔다**(2026-08-17 결정). 소유자를 알 수 없어 이관이 불가능하고,
공개 URL 로는 계속 보이므로 **과거 대화가 깨지지 않는다.** 새 파일부터 안전해진다.
