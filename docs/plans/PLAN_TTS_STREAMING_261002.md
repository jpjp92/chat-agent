| 피드백 항목 | 판정 | 근거 |
|---|---|---|
| 채팅은 Gemini 유지, TTS만 분리 | ✅ 채택 | 영향 범위 최소, TTS 장애가 텍스트 채팅에 번지지 않음 |
| 버튼 재생이면 전체 텍스트 1회 요청 + 오디오만 스트리밍 | ✅ 채택 | 현재 UX 가 버튼 방식 |

| **OpenAI 로 교체가 해법** | ⚖️ 수정 | Gemini TTS 도 `generateContentStream` 으로 PCM 청크 스트리밍 가능 — 대안이 빠졌다. **측정으로 결정** |
| `AudioWorklet` 재생 큐 | ⚖️ 수정 | 과함. 청크별 `BufferSource` 를 `nextStartTime` 에 예약하면 끊김 없이 이어진다 |
| 키·비용·인증 | ❌ 누락 | 무인증 라우트 + 유료 키 조합(위 선행 조건) |

## 3. 피드백이 놓친 것

1. **홀수 바이트 경계.** 네트워크 청크가 홀수 바이트로 끊기면 Int16 변환이 1바이트 밀려 잡음이 난다.
   남은 1바이트를 다음 청크로 이월한다.
2. **fallback 은 첫 바이트 전까지만.** 스트림이 열린 뒤에는 키·공급자를 바꿀 수 없다. 현재 키 루프는
   "첫 청크 수신" 시점까지만 돈다.
3. **텍스트 전처리.** 코드블록·표·URL·LaTeX 가 그대로 읽힌다. 공급자와 무관하고 비용이 작다.
4. **`gain 1.8` 클리핑.** 공급자마다 출력 레벨이 달라 고정 증폭은 찢어질 수 있다. 공급자별 값.
5. **OpenAI `instructions` 파라미터.** 톤 지정(예: 차분한 한국어) 가능 — A/B 대상에 넣는다.
6. **비용.** `gpt-4o-mini-tts` 는 유료(대략 분당 $0.015 수준, 착수 시 공식 가격 재확인).
   `OPENAI_API_KEY_TIER1` 은 env 에 이미 있다.
7. **Vercel 응답 4.5MB 제한은 스트리밍엔 해당 없음** — 다만 2000자 상한은 유지한다.

### 4-1. 0단계 1차 결과 (2026-10-03, n=2, `probe-tts-latency.mts`)

중앙값, 성공 건만. short ≈ 17자, medium ≈ 200자, long = 2000자(route 상한).

| 텍스트 | gemini-batch | gemini-stream | openai-stream TTFB / 전체 |
|---|---|---|---|
| short | 3.78s | 4.04s | **2.36s** / 5.99s |
| medium | 14.76s (1/2 실패) | 16.42s (1/2 실패) | **2.19s** / 14.59s |
| long | **0/2 성공** | 137.61s (TTFB=전체) | **1.40s** / 7.98s ⚠️ |

1. **Gemini TTS 는 실제로 스트리밍되지 않는다.** `generateContentStream` 도 TTFB ≈ 전체 —
   오디오가 청크 하나로 온다. §2 의 "Gemini 스트리밍 대안"은 **기각**. 남는 선택지는 OpenAI 뿐이다.
2. **현행 경로는 2000자에서 실패한다**(batch 0/2, medium 도 1/2). 현재 사용자가 긴 답변을 들을 때
   이미 깨져 있을 가능성이 높다 — "느리다"보다 큰 문제.
3. 🔴 **OpenAI long 은 잘렸다.** 2000자 입력에 오디오 15~18s — medium(200자)의 27~31s 보다 짧다.
   원인 미확인(입력 토큰 상한 추정). **긴 텍스트는 서버에서 분할 요청 → 하나의 스트림으로 이어 붙이기**가
   2단계에 추가된다. 분할 크기는 잘리지 않는 최대치를 먼저 잰다.
4. n=2 라 지연 수치는 방향만 본다. 1·2 는 크기가 커서 판정을 바꾸지 않는다.

### 4-2. 긴 텍스트 분할 측정 (2026-10-03, n=1, `probe-tts-chunking.mts`)

정상 발화 속도는 **약 13.6초/100자**(300~800자 단일 요청에서 일정). 판정은 이 비율을 주 지표로 한다 —
전사 비율·표지어는 STT 오류가 섞여 보조 지표다(500자 ❌ 는 STT 가 "바나나"를 "단 하나"로 받아 적은 것).

| 구성 | 오디오 | 초/100자 | 판정 |
|---|---|---|---|
| 단일 300·500·800 | 37.5·64.7·105.6s | 13.6~13.7 | 정상 |
| 단일 1200 | 232.7s | 19.4 | 🔴 **반복 생성**(전사 142%) |
| 단일 1600·2000 | 143.8·194.8s | 9.2~9.8 | 🔴 **중간 생략** — 끝 문장은 읽어서 표지어로는 못 잡는다 |
| 분할 300/500 (첫 조각 80자) | 279~283s | ≈14 | 정상 |

- **단일 요청은 ~800자까지만 안전**, 1200자부터 반복·생략이 생긴다. 잘림은 "끝이 끊긴다"가 아니라
  **중간이 빠지거나 반복된다** — 표지어 방식으로는 못 잡는 형태라 오디오 길이 비율이 필요했다.
- 분할하면 첫 소리 **0.9~1.1s**(단일 2.1s). 선행 2개(`p2`) 가 전체 23s 로 가장 빠르다.
  `500-p1`·`500-p2` 에서 끊김 1회 — 첫 조각(80자 ≈ 11s 재생)이 다음 500자 조각 생성보다 빨리 끝난 것.
  → **조각 크기를 점증**(80 → 200 → 400…)시키면 해소될 것으로 본다(미측정).
- 0단계 1차의 "2000자 → 15s" 는 **같은 문장 반복 입력**이 원인이었다(모델이 반복을 접음) — 이번엔 문장을 다양화했다.
- 2단계 설계 확정: 문장 경계 분할 · 조각 ≤ 400자 · 첫 조각 짧게 · 선행 2개.

### 4-2c. 유료 키 분할 비교 + 700자 조각 (2026-10-03)

2000자 정상 오디오 기준 ≈ **280s**(300·500자 분할 전 건의 값).

| 구성 | OpenAI 오디오 | Gemini 3.1 오디오 |
|---|---|---|
| 단일 | 198s 🔴 | 132s 🔴 |
| 500자 조각 | 279s | 279·281s |
| 700자 조각 (4회씩) | 225 🔴 · 279 · 273 · 250 🔴 | 291 · 291 · 273 · (연결 끊김 1) |

- **700자는 OpenAI 에서 4회 중 2회 생략**(-20%·-11%). "800자까지 정상"은 n=1 이었고 경계가 그보다 낮다.
  Gemini 는 700자에서 280s 를 넘는 쪽(반복 의심)으로 흔들린다 → **조각 상한은 500자**로 둔다.
- 전체 시간은 OpenAI 가 빠르다(500·p2: 23s vs 43s). 첫 소리는 둘 다 ~1s.
- 모든 분할 구성에서 끊김 1회 — 이 측정은 조각을 **다 받은 뒤** 재생한다고 가정하므로 비관적이다.
  실제 구현은 조각도 스트리밍 재생하므로 줄어들 것이다(미측정).

**500자·선행 2 반복 (4회씩)** — 오디오 OpenAI 275·280·278·271s, Gemini 284·282·273·279s.
8/8 이 280s ±3% 안 — 700자의 -20% 와 대비된다. **조각 상한 500자 확정.**
첫 소리 OpenAI 0.66~1.87s · Gemini 1.29~1.51s, 전체 OpenAI 25~37s · Gemini 43~44s.
전사 비율 72~73% 가 완전한 오디오에서도 반복되므로 긴 오디오에서 **STT 쪽 상한**으로 본다 — 판정에 쓰지 않는다.

실호출(`tests/manual/probe-speech-route.mts`, 핸들러 직접 호출 — 이 환경에서 `next dev` 가 stdin 종료로 바로 꺼져 dev 서버는 못 띄웠다):

| | 첫 소리 | 2000자 전체 | 2000자 오디오 | 문장 누락 (medium, 전사) |
|---|---|---|---|---|
| Gemini 3.1 | 0.94~1.49s | 37~40s | 248 🔴·278s | **1/7** — 둘째 조각의 마지막 문장 |
| OpenAI | 0.55~1.42s | 22~27s | 276~281s (4/4) | 0/7 |

- 🔴 **Gemini 는 짧은 조각에서도 문장을 간헐적으로 빠뜨린다.** 오디오 길이 판정(±3%)으로는 한 문장(2000자의 ~1.5%)을
  못 잡는다 — §4-2c 의 "8/8 정상"은 **문장 단위로는 검증되지 않은 것**이다. 프로브에 전사 기반 문장 누락 판정을 넣었다.
- 🔴 **OpenAI 는 첫 ~0.4s 를 몰아 보낸 뒤 최대 225ms 멈춘다**(3/3) → 시작 직후 1회 끊김. 클라이언트 지터 버퍼를
  OpenAI 300ms·Gemini 50ms 로 둬 short·medium 끊김 0, long 은 2회 중 1회 남음.
- **언마운트 cleanup 버그(기존):** `useEffect(..., [isPlaying])` 의 cleanup 이 true→false 전환마다 전역 `stopAudio()` 를 불러,
  A 재생 중 B 를 누르면 A 의 상태 전환이 **B 의 재생을 죽였다**. 언마운트 전용으로 바꿨다.
- 🔴 **브라우저 재생은 아직 사람이 들어보지 않았다** — 스케줄링·iOS 잠금 해제·증폭(OpenAI 1.0 은 미측정 기본값)은 로컬 앱에서 확인 필요.

**재시도 (`server/tts/retry.ts`, 하니스 `tests/test-tts-retry.mts`)** — 조각 단위, **첫 바이트 전까지만**, 상한 3회.
429·408·5xx·네트워크·빈 오디오는 재시도, 그 외 4xx 와 사용자 취소는 즉시 실패. Gemini 는 시도마다 다음 키, OpenAI 는 같은 키로 0.5s·1s 대기.
🔴 초판 문제 둘을 고쳤다: OpenAI 는 재시도가 **없었고**, Gemini 는 400 에도 키 12개를 다 돌아 최악 60s×12 로 maxDuration(120s)을 넘었다.
재생 시작 후 스트림이 끊기면 클라이언트는 받은 만큼 재생하고 정상 종료한다(그전엔 버튼만 대기로 돌아가고 소리는 계속 나와 멈출 수 없었다).

**로컬 실사용 1차 (2026-10-03, `npm run dev`, 기본 gemini·무료 풀)** — 🔴 **61초 뒤 500.**
키 3개가 3.1 TTS 일일 한도(10회/키)로 소진(측정 프로브가 같은 풀을 쓴 영향 포함)되고, 남은 시도 하나가 응답 없이 걸려
조각 타임아웃 60s 를 다 기다렸다. 수정: **첫 바이트 타임아웃 12s**(걸린 시도만 끊고 재시도, abort 를 무시하는 SDK 도 경주로 탈출),
**`TTS_USE_TIER1=true`** 면 Gemini 를 유료 `API_KEY_TIER1` 로만. 둘 다 하니스·실호출 확인.
→ 무료 풀은 Gemini TTS 운영 경로가 될 수 없다는 §4-2b 판단이 실사용으로 확인됐다.

**로컬 실사용 2차 (2026-10-03, TIER1)** — 🔴 **단어를 한 글자씩 철자로 읽고, 20초 뒤 "failed to pipe response"(500).**
원인: 그 답변이 날씨 카드라 본문이 ```` ```json:weather {...}``` ```` 이었다. 기존 전처리(`[#*`_~]` 제거)가 JSON 을 그대로 보내
4조각 모두 JSON — 모델은 철자로 읽었고, 기호뿐인 조각엔 오디오를 안 줘 재시도 3회 후 스트림이 중간에 끊겼다.
**1단계(전처리)를 건너뛴 대가였다.** 수정:
- `server/tts/speakable.ts` — 코드 펜스(카드 JSON 포함)·수식·HTML·이미지·URL·인용 번호 제거, 링크는 글자만, 표는 칸을 쉼표로,
  글머리표 줄마다 문장 경계. 서버가 원문을 받아 정리 **후** 2000자 상한. 하니스 `tests/test-tts-speakable.mts`
- 읽을 것이 없으면 **422**, TTS 호출 없음(클라이언트는 조용히 종료)
- 첫 조각 이후 조각이 재시도까지 실패하면 **그 조각만 건너뛴다**(스트림 유지)
- 실제 두 메시지로 재확인: 카드 → 422, 본문 → 2조각 34s, 전사상 전 문장·정상 발음

**판단:** 속도(전체 1.6배)·충실도(누락 0/7 vs 1/7) 모두 OpenAI 가 앞선다. 단 OpenAI 기본 승격은 하드닝 1순위(인증) 뒤.

## 7. 인증·한도·예산 (2026-10-03) — 코드 구현, **SQL 미적용**

유료 키(`TTS_USE_TIER1` / OpenAI)를 붙이므로 [하드닝 §6-1 1순위](PLAN_HARDENING_260822.md#6-1-우선순위와-완료-조건)를 TTS 에 한해 먼저 한다. 세 겹:

| 겹 | 구현 | 막는 것 |
|---|---|---|
| 1. 토큰 | `createRouteClient` + 클라이언트 `authedFetch`. 토큰 없음·위조 → 401 | 앱 밖 직접 호출 |
| 2. 게스트·회원 한도 | RPC `consume_tts_quota` ([tts-quota.sql](../guide/db/tts-quota.sql)) — 게스트 403, 회원 **20,000자/일(KST)** 초과 429. 글자 수로 센다(비용 ∝ 오디오 길이). 공급자 호출 **전에** 원자적 소비, RPC 실패 시 fail-closed | 로그인 사용자의 반복 호출 |
| 3. 공급자 월 상한 | AI Studio Project Spend Cap · OpenAI project hard limit (콘솔) | 1·2 가 뚫렸을 때의 최대 피해 |

- 실측: 토큰 없음·위조 토큰 → 401, **공급자 호출 0회**. 게스트·회원 경로는 SQL 적용 후 확인 필요.
- 🔴 **배포 순서: SQL 적용 → 앱 배포.** 반대면 TTS 가 500(fail-closed).
- 한도 소비는 합성 전이라, 합성이 실패해도 차감된다(보수적으로 둔다).
- 거부 시 클라이언트는 `custom-toast` 로 안내(게스트: 로그인 필요, 회원: 오늘 한도 소진).
- `probe-speech-route.mts` 는 이제 `TTS_PROBE_BEARER`(회원 access token)가 필요하다.

비용 근거(2026-10 공개 가격, 착수 시 재확인): Gemini 3.1 Flash TTS 오디오 출력 $20/1M 토큰(≈25 토큰/초) → 2000자(≈280s) ≈ **$0.14**.
회원 한도 20,000자/일 ≈ 최악 $1.4/일/회원.

## 8. 사용자 노출 예외 처리 (2026-10-03)

원칙: **사용자에게는 종류별 안내만, 상태 코드·원문은 `console.warn` 에만.** (`console.error` 는 dev 오버레이에 원문을 띄운다)

| kind | 조건 | ko 문구 | 토스트 |
|---|---|---|---|
| guest | 403 | 음성 읽기는 로그인한 회원만 사용할 수 있습니다. | info |
| quota | 429 | 오늘 음성 읽기 한도를 모두 사용했습니다. 내일 다시 이용해주세요. | info |
| auth | 401 · 세션 없음 | 로그인이 만료되었습니다. 다시 로그인한 뒤 시도해주세요. | error |
| network | fetch 자체 실패 | 네트워크 연결이 불안정합니다. 연결을 확인한 뒤 다시 시도해주세요. | error |
| server | 그 밖(500 · 오디오 초기화 실패 등) | 음성을 만들지 못했습니다. 잠시 후 다시 시도해주세요. | error |

- 문구는 ko/en/es/fr 4개 언어(`ChatMessage.tsx` `TTS_ERROR_MESSAGES`). 버튼 툴팁·aria-label 도 상태별(읽기/중지/준비 중) 4개 언어.
- 조용히 끝내는 경우: 사용자 중지(AbortError) · 읽을 것 없음(422) · 재생 시작 후 스트림 끊김(받은 만큼 재생).

- ⚠️ 토스트 표시는 브라우저에서 아직 확인하지 않았다.

## 9. 1순위 3.8 Lite + OpenAI 폴백 (2026-10-04)

**가격**(공개 단가, 오디오 25 토큰/초 = 1,500 토큰/분):

| 모델 | 오디오 출력 | 분당 | 2000자(≈4.7분) |
|---|---|---|---|
| Gemini 3.8 Flash Lite TTS | $6/1M (2026), **2027-01-01 부터 $12** | ≈$0.009 → $0.018 | ≈$0.04 → $0.08 |
| OpenAI `gpt-4o-mini-tts` | $12/1M (대시보드 역산 ≈$0.016/분) | ≈$0.015 | ≈$0.07 |
| Gemini 3.1 Flash TTS | $20/1M | ≈$0.03 | ≈$0.14 |

→ 2026 년 안에는 Lite 가 OpenAI 보다 ~40% 싸고, 2027 부터 비슷하다. 3.1 의 1/3.

**폴백 규칙**(`server/tts/synth.ts`):
- 1순위 = `TTS_PROVIDER`(미설정 gemini), 폴백 = 다른 공급자 — 키가 있으면 자동, `TTS_FALLBACK=off` 로 끔
- 폴백은 **조각의 첫 바이트 전** 실패에만. 첫 조각이 실패하면 이후 조각도 폴백부터(목소리 하나), 이후 조각만 실패하면 그 조각만 폴백(목소리 바뀜 — 내용 누락보다 낫다, 경고 로그)
- 실측: 정상 → gemini 첫 바이트 1.40s · Gemini 무효 키 → **openai 가 요청 전체를 읽음**(첫 바이트 2.20s) · `TTS_FALLBACK=off` → 0.3s 에 실패

**음량을 서버로 옮겼다** — 폴백으로 한 스트림에 두 공급자가 섞이면 클라이언트의 공급자별 증폭이 틀린다.
🔴 실측에서 **3.8 Lite 원음이 이미 풀스케일**(피크 32768, RMS -14.9 dBFS)이라 예전 1.8(2.5 용)을 두면 **찌그러졌다**.
OpenAI 는 RMS -18.2 dBFS·피크 22152. → **gemini 1.0 · openai 1.4**(RMS ≈5899 vs ≈5640).

⚠️ 남은 것: Gemini 쪽 재시도(3회 × 첫 바이트 12s)를 다 쓴 뒤에야 폴백하므로 Gemini 가 **걸리는** 장애에서는 폴백까지 최대 ~37s.
Preview 환경엔 `TTS_USE_TIER1` 이 없어 Gemini 무료 풀을 쓴다(3.8 Lite 무료 한도 미확인) — 실패하면 OpenAI 가 받는다.
