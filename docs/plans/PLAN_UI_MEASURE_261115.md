## 1. 검토안 대조

**확인한 것(우리 코드)** — [SourceBar.tsx](../../components/SourceBar.tsx) 선언값이 검토안 표와 일치한다: 접힘 기준 3개(`COLLAPSE_AT`), 접힌 버튼 `min-h-[44px]`·`px-4`·`gap-2`·`rounded-full`, 시트 `max-h-[85dvh]`·`sm:max-w-md`·`rounded-t-2xl`·하단 `env(safe-area-inset-bottom)`, 닫기 `w-11 h-11`(44px).

**검토안이 놓친 것**
- **출처 1~2개일 때의 칩(`SourceChip`)에는 `min-h` 가 없다.** `py-2` + 11px 글자라 높이가 대략 30px 안팎으로 보인다 — 터치 목표 44px 보다 작을 가능성. 실측의 첫 질문이 되어야 한다(검토안은 접힌 버튼·시트만 본다).
- 칩 제목은 `max-w-[150px]` 로 자른다 — 긴 한국어·영문 제목에서 몇 글자가 남는지가 실측 항목.
- 출처 성격 태그(`KindTag`, 공식·언론·기타)가 칩 폭을 늘린다 — 태그 유무 두 경우를 같이 잰다.

**확인하지 못한 것**
- `enesozturk/dimensional-drawing` 저장소의 내용·라이선스·HEAD 는 이 검토에서 직접 열어 보지 않았다 — 검토안의 기술을 그대로 옮겼을 뿐이다. 설치 전에 원문·라이선스·실행되는 스크립트를 읽는다.

## 2. AnatomyCard 를 보류하는 이유

- 11-03 [DEV_261103 §1](../logs/2026/11/DEV_261103.md) 에서 외부 Anatomy 통합 기획을 검토해 **새 의도 없이 `json:diagram` 고도화**로 방향을 바꿨다. 그때 문제: 걸리는 질문이 적다(공수 대비), 비전 bounding box 정확도 미측정, 새 의도·경계 세트가 필요, `physics`·`DiagramRenderer` 와 겹침.
- 이번 검토안의 AnatomyCard 는 "UI·제품의 구조와 치수 설명" 으로 대상을 바꿨지만, **사용자가 채팅에서 UI 치수를 물을 일이 얼마나 되는가**라는 수요 문제는 그대로다.
- 검토안이 더한 `evidence`(measured / documented / derived / estimated / unknown) 구분과 `schemaVersion` 은 좋은 계약이다 — 다시 꺼낼 때를 위해 여기 적어 둔다. 11-03 의 `observed | inferred | unknown` 과 같은 생각이다.
- 다시 볼 조건: 사용자 질문 로그(내용 열람은 승인 필요)에서 제품·기기 구조 설명 요청이 의미 있게 나올 때.

## 3. P0 — SourceBar 실측 계획

**방식** — 앱을 띄워 실제 브라우저로 잰다. 기존 dev 전용 미리보기 페이지 패턴(`app/dev/drug-preview` — 프로덕션 빌드에서 404)을 그대로 쓴다.

| 단계 | 내용 |
|---|---|
| 1 | `app/dev/source-bar-preview` — 고정 출처 데이터로 SourceBar 를 그린다(1·2·3·10개, 긴 한국어/영문 제목, 긴 도메인, 성격 태그 유무). 프로덕션 404 |
| 2 | `tests/manual/measure-source-bar.mts` — Playwright 로 375·390·430·1280px × 라이트·다크, 접힘/펼침 상태에서 `getBoundingClientRect()`·`getComputedStyle()` 수집 → JSON |
| 3 | 판정 — 터치 목표 ≥ 44px, 가로 넘침 없음(`scrollWidth ≤ clientWidth`), 시트 높이 ≤ 85dvh, 닫기 버튼 44×44, 제목 잘림 위치 |
| 4 | 도면 — 2의 JSON 으로 단일 HTML/SVG(치수선·변수표). 값마다 출처 표시: 실측 / 코드 선언 / 미확정 `[TBD]` |

**도구 상태(11-15)** — Playwright 브라우저(chromium)는 로컬 캐시에 있으나 **패키지는 레포에 없다**. 수동 진단 도구라 `tests/manual/` 에서만 쓰고, devDependency 로 넣을지 `npx` 로 부를지 정해야 한다(설치는 승인 뒤).

**산출물**
- 실측 JSON + 판정 결과(통과/실패 목록)
- HTML/SVG 도면 1장(스크래치 또는 `docs/` — 저장 위치는 결과를 보고)
- 찾은 문제(예: 칩 터치 목표 미달)는 **이 계획에서 고치지 않는다** — 목록만 내고 수정은 별도 요청으로

**하지 않는 것** — SourceBar 기능·디자인 변경, Skill 설치, 외부 스크립트 실행(읽기 전), 커밋·배포.

## 4. 판단이 필요한 것

1. Playwright 를 devDependency 로 넣을지(다른 UI 실측에도 재사용) / 일회성 `npx` 로 둘지.
2. 실측 판정(§3 단계 3)을 `tests/` 자동 하니스로 승격할지 — 브라우저가 필요해 `npm test`(네트워크·시크릿 없이 도는 하니스) 규칙에 안 맞는다. 승격한다면 CI 에 브라우저 설치가 붙는다.
3. dimensional-drawing Skill 을 실제로 쓸지 — 실측 스크립트와 도면 출력은 Skill 없이도 만들 수 있다. Skill 의 가치는 "도면 형식·작성 절차" 이므로, 원문을 읽고 형식만 참고하는 것도 방법이다.

## 6. 칩 높이 44px 반영(11-15)

미리보기에 현재/변경안을 나란히 그려 비교한 뒤 세 안을 검토했다.

| 안 | 휴대폰 | 데스크톱(마우스) | 태블릿 가로 | 판단 |
|---|---|---|---|---|
| **A. 항상 44px** | 44 | 44 | 44 | ✅ 채택 — 칩·접힌 바·닫기 버튼이 기기와 무관하게 같은 규칙. 출처 2개↔3개 답변의 출처 줄 높이가 같아진다 |
| B. 좁은 화면만 | 44 | 34.5 | 34.5 | ❌ 화면 폭은 입력 방식이 아니다 — 가로 태블릿(터치)은 작고, 좁힌 데스크톱 창(마우스)은 커진다 |
| C. 터치 입력만(`pointer: coarse`) | 44 | 34.5 | 44 | 데스크톱의 촘촘한 모습을 꼭 지켜야 할 때의 대안. 데스크톱에서 칩↔바 높이 어긋남은 남는다 |

- 근거: 터치 목표 44px(Apple 44pt, WCAG 2.5.5 AAA 44×44). 지금 34.5px 도 WCAG 2.5.8 AA(24×24)는 통과 — 결함이 아니라 기준 정렬.
- 변경: [SourceBar.tsx](../../components/SourceBar.tsx) `SourceChip` 에 `min-h-[44px]` 한 줄. 폭은 그대로.
- 재실측(375·1280px): 칩 8종 모두 44.0px, 성격 태그 칩도 44.0px, 가로 넘침 없음. 미리보기는 비교 열을 걷고 한 열로(이제 현재 = 변경안).
- 하니스 48개·tsc·knip·build 통과, eslint 오류 0(경고는 기존 `<img>`·ref 정리 4건).
