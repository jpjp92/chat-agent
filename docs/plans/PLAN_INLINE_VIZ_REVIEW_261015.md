# 인라인 시각화 엔진 기획안 검토

> 작성: 2026-10-15 · 상태: **검토만 — 착수 전**
> 대상: 외부(GPT) 기획안 "Chat Agent — 인라인 시각화 엔진 도입 기획서"(기준 2026-10-13, dev `e34ddf4`)
> 관련: [PLAN_CHATMESSAGE_REFACTOR_260801](PLAN_CHATMESSAGE_REFACTOR_260801.md) · [REF_Architecture § Client Rendering Pipeline](../guide/REF_Architecture.md#client-rendering-pipeline) · [REF_Chart](../guide/REF_Chart.md)

## 1. 결론

- **방향(기존 카드 유지 + 파서 분리 → 공통 레지스트리 → 신규 블록)은 동의한다.** 제외 범위(모델이 만든 HTML/JS 실행 금지, 강제 시각화 금지, 별도 시각화 라우터 보류)도 맞다.
- 다만 기획안이 **"새로 만든다"고 한 것 중 상당수가 이미 있다** — 본문 중간 렌더링, general 턴 자동 차트, 스트리밍 플레이스홀더, 미완성 블록 폴백. 그래서 실제 작업은 "엔진 도입"이 아니라 **기존 파이프라인 정리 + 신규 블록 몇 종**이다.
- Phase 1(파서 분리)은 이미 설계된 [PLAN_CHATMESSAGE_REFACTOR_260801](PLAN_CHATMESSAGE_REFACTOR_260801.md)과 같은 일이다. 새 계획을 세우지 말고 **그 계획을 실행**한다.
- 신규 블록은 렌더러보다 **프롬프트·데이터 근거**가 어렵다. general 턴에 스펙을 더 얹으면 문맥 오염(DEV_260731)과 근거 없는 수치 차트가 생긴다 — 측정 후 하나씩 넣는다.

## 2. 기획안 전제 vs 현재 코드

| 기획안 주장 | 현재 코드 | 판정 |

| 미완성 JSON 감지 → 플레이스홀더 | 스트리밍 중 미완성 블록이면 앞 텍스트만 보이고 `chart_loading` 표시(640~674) | 이미 있음 |

## 3. 기획안이 맞게 짚은 문제 — 레지스트리가 필요한 근거

- 블록 종류 목록이 `ChatMessage.tsx` 에만 3벌이고 **이미 어긋나 있다**: 563행 파서 목록에는 `paper` 가 있는데 641·647행 미완성 감지 목록에는 없다. 논문 카드는 서버가 통째로 보내 지금은 증상이 안 보일 수 있지만, 스트리밍 중 일부만 온 `json:paper` 는 플레이스홀더 없이 원문이 비칠 수 있다(확인 필요).
- 렌더러 하나를 추가하면 한 파일에서 여러 곳을 건드려야 한다 — 08-01 리팩터링 계획이 지적한 "렌더러 추가 시 8곳" 과 같은 문제.
- 회귀 하니스가 `ChatMessage.tsx` 의 전처리를 import 할 수 없어 손으로 흉내 낸다(같은 계획 §근거).

→ **블록 종류를 한 곳(레지스트리)에서 선언**하고 파서·미완성 감지·렌더 분기·TTS 정리가 모두 거기서 읽게 하는 것이 첫 단위로 맞다.

## 4. 기획안이 놓친 위험

1. **general 턴 프롬프트 오염** — 렌더러 스펙이 base 에 상주하던 시절, 날씨 표 규칙이 무관한 general 턴까지 새어 후속 대화에 표가 재출력됐다(DEV_260731 §3-3). 그래서 지금은 의도별로만 주입한다. KPI·다이어그램·테이블·위젯 스펙을 general 에 얹으면 같은 문제가 다시 생긴다. 스펙이 늘수록 프롬프트도 길어진다(프롬프트 캐시 이슈와 겹침 — [PLAN_OPENAI_COST_REVIEW_261014 §4-2](PLAN_OPENAI_COST_REVIEW_261014.md)).
2. **근거 없는 수치 시각화** — "2020~2025년 인구 변화" 를 검색·문서 없이 모델 기억으로 차트화하면 그럴듯한 가짜 데이터가 된다. 차트는 텍스트보다 신뢰감을 더 준다. 기획안의 "근거 데이터 존재" 조건을 **실제 규칙**(검색 결과·첨부 문서·사용자 제공 데이터가 있을 때만 수치 차트)으로 내려야 한다.
3. **위젯의 가정값** — 시연의 "가격탄력성 -1.3" 은 모델이 정한 가정이다. 계산은 검증된 컴포넌트가 해도 입력이 근거 없으면 결과도 근거 없다. 위젯은 가정 파라미터를 화면에 "가정"으로 드러내고 사용자가 바꿀 수 있어야 한다.
4. **번들 크기** — Mermaid 는 무겁다. 현재 JS 365KB gzip·Lighthouse 91 이라 반드시 지연 로딩, 도입 전 번들 측정.
5. **"서버 측 유효성 검증(validation.ts)"** — 블록은 모델 스트림 그대로 클라이언트로 간다. 서버 검증을 끼우려면 스트림을 버퍼링해야 해 TTFT 가 늘어난다. 검증은 클라이언트 레지스트리에서 하는 게 현 구조에 맞다(서버는 카드 도구 출력처럼 서버가 만드는 블록만).
6. **모델별 차이** — Gemini·GPT 가 같은 JSON 스키마를 같은 빈도로 지키지 않는다. 신규 블록은 두 공급자 각각의 생성 성공률을 재야 한다(기획안 Phase 4 를 앞당긴다).

|---|---|---|

| 1 | [PLAN_CHATMESSAGE_REFACTOR_260801](PLAN_CHATMESSAGE_REFACTOR_260801.md) 실행 + **블록 종류 단일 레지스트리**(파서·미완성 감지·렌더·TTS 정리) | 기존 14종 동작 동일, 하니스가 실제 파서를 import |
| 2 | 미완성 블록 처리 정리 — `paper` 누락 같은 목록 불일치 해소, 스트림 종료 후 깨진 블록을 조용히 버리지 말고 "표시할 수 없음" 한 줄로 | 깨진 블록 회귀 하니스 |
| 3 | 신규 블록 **하나씩** — 1순위 KPI(가장 단순, 근거 수치가 있는 턴만) → 다이어그램(Mermaid 는 번들 측정 후) → 테이블 | 공급자별 생성 성공률, general 턴 지연 변화 없음 |
| 보류 | 위젯(가정값 노출 설계 먼저), 지도, Artifact 런타임 | — |

## 6. 열린 질문

- 신규 블록 스펙을 general 에 둘지, 별도 의도(`data_viz` 확장)로 둘지 — 오염 위험 때문에 후자가 안전하나 라우터 분류에 의존하게 된다.
- 수치 차트의 "근거 있음" 판정을 어디서 하나 — search-gate 의 신호(검색 on·URL·문서)를 재사용할 수 있다.
- 08-01 리팩터링 계획의 선행 조건(인증 프로덕션 컷오버)이 아직 유효한가 — 상태 재확인 필요.
