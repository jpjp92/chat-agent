## 1. 문제

인증 MVP는 **게스트 승계**(guest → Google → 같은 uuid)를 풀었다. 그런데 실제로 써보니 **로그인 자체**가 세 군데서 막힌다.

| # | 증상 | 원인 |
|---|---|---|
| **P1** | 브라우저에 로그인된 Google 계정이 **묻지도 않고** 선택된다. 계정이 여러 개면 원하는 걸 못 고른다. | `linkIdentity` / `signInWithOAuth` 에 `prompt` 파라미터가 없다 ([useAuthSession.ts:127](../../src/hooks/useAuthSession.ts#L127)) |
| **P2** | 이미 계정이 있는 사용자가 로그인하려면 **실패를 한 번 거쳐야** 한다. Google 왕복 → `identity_already_exists` → 그제서야 "기존 계정으로 로그인" 버튼이 뜬다. | 모달에 **연결(link)만 있고 로그인(sign-in)이 없다.** 게스트의 대화가 0개여도 무조건 `linkIdentity` 를 부른다 |
| **P3** | 로그인한 상태에서 **다른 계정으로 바꿀 방법이 없다.** | 설정에 로그아웃뿐 |

P2가 특히 아픈 이유: **캐시를 지운 사용자가 정확히 이 경우다.** 세션이 사라져 새 게스트가 되고, 대화는 0개고, 하려는 건 "원래 내 계정으로 로그인"인데, 앱은 "이 게스트를 계정에 연결"을 시도했다가 충돌로 실패한다.

## 2. 설계

### 2-1. 계정 선택창 강제 (P1)

`linkIdentity` · `signInWithOAuth` 양쪽 옵션에 추가한다.

```ts
options: {
  redirectTo: window.location.origin,
  queryParams: { prompt: 'select_account' },
}
```

계정이 하나인 사용자에겐 클릭이 한 번 늘지만, 여러 개인 사용자는 **이게 없으면 아예 원하는 계정을 못 고른다.** 비대칭이 명확하다.

### 2-2. 게스트의 대화 유무로 호출을 가른다 (P2)

```
대화 > 0  →  linkIdentity        이어가기 — 같은 uuid 에 신원을 붙인다
                                 └ 충돌 시 기존 "기존 계정으로 로그인" 분기 (변경 없음)

대화 = 0  →  signInWithOAuth     그냥 로그인 — 고아가 될 데이터가 없다
```

**판단 주체는 `App.tsx`다.** 훅은 시키는 걸 하고, "이 게스트가 잃을 게 있나"는 화면이 이미 아는 사실(`sessionCount`)이다. 훅 안에서 세션 개수를 다시 세면 같은 사실의 출처가 둘이 된다.

모달 UI는 **바뀌지 않는다.** 버튼은 계속 한 개고, 문구도 그대로다. 사용자가 고를 게 없다 — 앱이 알아서 옳은 호출을 고른다.

### 2-3. 설정 › 계정에 "다른 계정으로 로그인" (P3)

`signInWithOAuth({ prompt: 'select_account' })` 한 번. **로그아웃을 먼저 할 필요가 없다** — 돌아오면 세션이 새 계정으로 교체되고, 원래 계정의 대화는 그 uuid 에 그대로 남아 다시 로그인하면 복구된다.

여기서 **이미 만들어둔 안전장치가 값을 한다.** 계정이 바뀌면 `useChatSessions` 의 **ownerId 불일치 가드**가 발화해 이전 계정의 대화 제목 캐시를 폐기한다([DEV_260714](../logs/2026/07/DEV_260714.md) §4-c 에서 프라이버시 버그를 고치며 넣은 코드). 계정 전환에도 그대로 맞는다 — **추가 작업이 없다.**

## 3. 🔴 철칙을 정확하게 다시 쓴다

MVP 내내 지켜온 규칙:

> ~~"활성 세션이 있으면 절대 `signInWithOAuth` 금지"~~

이 문장은 **목적을 잘못 일반화**했다. 원래 막으려던 건 **게스트의 대화가 고아가 되는 것**이다. 정확히는:

> **"승계할 게스트 데이터가 있을 때 `signInWithOAuth` 금지"**

대화 0개 게스트나 이미 정식인 사용자에겐 고아가 될 데이터가 없다. 그들에겐 `signInWithOAuth` 가 **금지가 아니라 정답이다.**

이 구분을 `useAuthSession.ts` 주석에 못 박는다. 안 그러면 다음 사람이 옛 규칙만 보고 §2-2·§2-3 을 **버그로 오해해 되돌린다.** (실제로 이 규칙은 프로젝트 전체에서 가장 자주 인용된 문장이다.)

## 5. 검증

**자동** — 회귀만. 인증 서버 경로가 안 바뀌므로 40건(RLS 18 · identity 10 · limit 6 · routes 6)이 그대로 통과해야 한다. `tsc --noEmit` 0.

**수동 3건** — 이 변경은 전부 실제 OAuth 리다이렉트에서만 드러난다. [DEV_260714](../logs/2026/07/DEV_260714.md) §4 의 교훈(자동 40건이 초록불인 채로 버그 3개가 나왔다)이 여기 그대로 적용된다.

| # | 시나리오 | 기대 |
|---|---|---|
| **a** | 대화 **있는** 게스트 → Google | 계정 선택창 뜸 → 링크 → **uuid·대화·이름·아바타 승계** (MVP 회귀) |
| **b** | 대화 **0개** 게스트(= 캐시 지운 사용자) → Google → 기존 계정 선택 | **충돌 화면 없이** 바로 로그인 → 그 계정의 대화가 사이드바에 나타남 |
| **c** | 로그인 상태 → 설정 › **다른 계정으로 로그인** → 다른 계정 선택 | 세션 교체 → 사이드바가 새 계정 것으로 **완전 교체**(이전 계정 제목 잔존 0) → 원래 계정으로 다시 로그인하면 **대화 복구** |

c 의 "잔존 0" 은 ownerId 가드가 실제로 발화하는지 보는 것이다. 여기가 뚫리면 §4-c 프라이버시 버그의 재발이다.

## 6. 리스크

- **`prompt=select_account` 가 `linkIdentity` 에서도 먹히는가** — `linkIdentity` 는 `signInWithOAuth` 와 같은 옵션 타입을 받으므로 `queryParams` 가 그대로 전달될 것으로 본다. 다만 **가정이다.** 검증 a 에서 선택창이 안 뜨면 여기가 원인이다.
- **버려지는 익명 유저** — 대화 0개 게스트가 `signInWithOAuth` 로 넘어가면 그 익명 행은 `auth.users` 에 고아로 남는다. 다만 **끝내 전환하지 않는 게스트도 똑같이 남으므로 새로 생긴 문제가 아니다.** 정리는 별도 스케줄 잡 과제.

## 7. 이 플랜이 하지 않는 것

- **카카오 로그인** — 별도 후속. 붙이는 순간 provider 파라미터화(`linkProvider(p)`), 리다이렉트 복귀 시 provider 복원(URL 에 provider 가 안 실려온다), 카카오 `identity_data` 필드명 실측, 이메일 미제공(비즈앱 심사) 대응이 전부 따라온다. **그 비용은 전부 "provider 가 둘이라서" 생긴다** — 이 플랜과 섞으면 위 세 문제의 수정이 그 안에 파묻힌다.
  - 사전 확인 사항: 카카오 `카카오계정(이메일)` 동의항목은 **비즈니스 앱 전환 대상**(사업자등록번호 필요). 이메일이 없으면 Supabase Automatic Linking(이메일 매칭)이 원리적으로 불가 → **Google 계정과 카카오 계정은 영원히 별개**가 된다. 이 분기는 에러 없이 조용히 일어난다.
  - 최대 미지수: 이메일 없는 신원을 gotrue 가 링크해주는가. `test-auth-link-preflight.ts` 에 kakao 를 추가하면 **브라우저 없이 30초**에 판정된다. 카카오 착수 시 이것부터 돌린다.
- 다중 신원 연결(한 계정에 Google + 카카오), 이메일 매칭 자동 연결, 프로바이더 분기 경고문.
