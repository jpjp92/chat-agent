> 선행: 프롬프트 침묵화(아래 §1)는 이 계획과 분리해 **먼저** 처리한다

## 문제

검색이 꺼진 턴에서 모델이 답변 **맨 앞에** `"현재 실시간 검색 없이 학습된 지식 기준으로 답해 드립니다"`를 붙였다.
`인공타액제 알려줘` — 검색을 요청한 적도, 실시간 데이터를 물은 적도 없는 질문이다.

두 갈래 문제다.

| | 내용 |
|---|---|
| **문구가 샌다** | [prompt.ts:310](../../server/agent/prompt.ts#L310)·[342](../../server/agent/prompt.ts#L342)의 조건("명시 요청했을 때"·"실시간 데이터일 때")을 무시하고 문구만 가져다 쓴다. **"평소엔 말하지 마라"는 기본값이 없다** — 예외만 있다 |
| **복구 경로가 없다** | 라우터 LLM이 `needs_search=false`를 내면 그걸로 끝이다. 사용자가 "검색이 안 됐네"를 알 방법이 저 문구밖에 없고, 문구를 없애면 그마저 사라진다 |

즉 문구를 지우는 것만으로는 두 번째가 남는다. **어색한 고백을 없애되, 복구는 UI로 옮긴다.**

---

## 1. 선행 조치 — 프롬프트 침묵화 (이 계획과 분리, 먼저 처리)

기본값을 침묵으로 만들고 예외를 명시한다. 두 곳에 흩어진 중복 예시 문장도 하나로 줄인다
(같은 문구가 두 번 나오는 것 자체가 새는 원인이다).

- 기본: 검색이 없었다는 사실을 **알리지도 사과하지도 설명하지도 않는다.** 그냥 답한다.
- 예외: ⓐ 사용자가 검색·검증을 명시 요청 ⓑ 질문이 실시간 데이터(시세·날씨·스코어·뉴스·"최신/오늘/현재")를 요구
  → 이때만 답변 **맨 끝에** 한 문장.

> 환각 방지력은 유지된다. 출처 날조를 막는 것은 [L308~309](../../server/agent/prompt.ts#L308)
> (인용 표기·출처 목록·"검색 결과" 류 표현 **전면 금지**)이고, L310의 고백 문구는 거기 얹힌 부가물이다.
> 금지 규칙은 그대로 두고 고백만 조건부로 되돌린다.

## 2. 본 계획 — 추천 칩

검색이 꺼진 턴의 답변 하단에 칩을 붙인다. 누르면 검색을 강제하는 후속 질문이 입력창에 채워진다.

```
[답변 본문 — 검색 언급 없음]

  🔍 웹에서 최신 정보 확인
```

### 2-1. 왜 판정 로직을 새로 안 만들어도 되나

칩 문구를 `"검색해서 확인해줘"` 계열로 두면 [`detectExplicitSearchRequest`](../../server/agent/intentRules.ts)에 걸려
**tier 300(USER_EXPLICIT)** 이 된다. 라우터 LLM이 뭐라 하든, 멀티턴 가드가 뭐라 하든 검색이 켜진다.
Step 2~4에서 만들고 16/16·23/23으로 검증한 경로를 그대로 쓴다.

### 2-2. 칩은 서버가 결정론으로 붙인다 🔴

**모델이 칩을 만들게 하면 안 된다.** 지금 문구가 새는 것과 정확히 같은 종류의 실패가 반복된다.

붙일 근거는 이미 있다 — `decideSearch()`의 **`winner.source`**:

| winner | 의미 | 칩 |
|---|---|:---:|
| `router-llm(100)` · `default(0)` | 판단 결과 검색 불필요 | ✅ **붙인다** |
| `multimodal(400)` · `history-image(400)` | API가 물리적으로 거부 | ❌ 눌러도 안 켜진다 |
| `url-content` · `doc-content`(200) | 답변 근거가 이미 있음 | ❌ 소음 |
| `video-content` · `renderer`(200) | 동상 | ❌ |
| `followup-guard(100)` | 직전 검색 결과를 가공 중 | ❌ |
| `rule(100, off)` | 코드·번역·창작·계산 | ❌ 검색이 무의미 |

> **tier 재설계의 부수 소득이다.** `useGoogleSearch`가 boolean이던 시절에는 "왜 껐는지"가 없어서
> 이 구분 자체가 불가능했다. 로그용으로 만든 `winner.source`가 그대로 UI 노출 조건이 된다.

추가 조건: `intent === 'general'` 일 때만. 카드 계열(날씨·영화·약국…)은 도구가 답을 만들었으므로 대상이 아니다.

### 2-3. 배선

`sources` 이벤트와 같은 경로다. 새 개념이 없다.

```
search-gate  decideSearch() → winner
  → generator  suggestSearch: boolean (state)
  → route.ts   sendEvent({ suggest: 'search' })
  → geminiService  onSuggest 콜백
  → useChatStream  Message.suggest 필드
  → ChatMessage  하단 칩 렌더 → onSelect → 입력창 prefill (전송은 사용자가)
```

### 2-4. 기존 `SuggestChips`는 재사용 못 한다

[components/SuggestChips.tsx](../../components/SuggestChips.tsx)는 **웰컴 화면 전용**이다:

- `hidden sm:grid grid-cols-4` — **모바일에서 아예 안 보이고**, 4개 고정 그리드다
- 칩 목록이 하드코딩 상수 — 메시지별 동적 칩을 못 받는다
- 사용처가 [App.tsx:355](../../App.tsx#L355) 한 곳뿐

메시지 하단 칩은 **모바일에서 보이는 게 핵심**이라(원래 결함을 발견한 것도 모바일 스크린샷이다) 별도 컴포넌트가 맞다.
공통화는 두 개가 다 생긴 뒤에 판단한다 — 지금 추상화하면 요구가 다른 둘을 억지로 묶게 된다.

### 2-5. 노출 규칙 (소음 방지)

- 검색 OFF + `general` + winner가 §2-2의 ✅ 목록일 때만
- **답변당 1개.** 여러 칩 금지
- 같은 대화에서 연속 노출 제한 검토 (매 턴 뜨면 배너가 된다)
- i18n 4개 언어 (ko/en/es/fr) — 프로젝트 기존 기준

## 3. 범위 밖

- 모델이 문맥에 맞춰 칩 문구를 생성하는 것 — §2-2 이유로 기각
- 추천 질문 카드 일반화(후속 질문 3개 제안 등) — 별건. 이 계획은 **검색 복구** 하나만
- 클릭 즉시 전송 — 기존 `SuggestChips`가 prefill만 하고 전송은 사용자에게 맡긴다. 그 규칙을 따른다
