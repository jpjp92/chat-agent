# DEV_260512.md

## 1. 모델 레지스트리 중앙화 계획

### 목적

- 현재 모델 문자열이 프론트/백엔드 여러 파일에 하드코딩되어 있어 모델 교체·추가 시 누락 위험이 큼.
- 우선 Gemini 모델 문자열을 단일 레지스트리로 모아 관리하고, OpenAI 등 멀티 프로바이더 확장은 별도 단계로 분리한다.
- 이번 작업의 목표는 **동작 변경 없는 중앙화**다. Provider 추상화나 OpenAI SDK 도입은 포함하지 않는다.

### 현재 하드코딩 위치

- **프론트엔드**
  - `App.tsx` — `selectedModel` 타입, localStorage 기본값
  - `components/Header.tsx` — 모델 선택 메뉴, 표시명, 선택 체크
  - `src/hooks/useChatStream.ts` — `selectedModel` 타입
- **백엔드**
  - `api/chat.ts` — 기본 채팅 모델 fallback
  - `api/_lib/agent/state.ts` — GraphState `model` 기본값
  - `api/_lib/agent/nodes/generator.ts` — generator fallback 모델
  - `api/_lib/agent/nodes/router.ts` — router lite 모델
  - `api/_lib/agent/nodes/vision.ts` — vision 분석 모델
  - `api/_lib/agent/drug-info-tool.ts` — 약품 정보 보강 모델
  - `api/speech.ts` — TTS 모델
  - `api/summarize-title.ts` — 세션 제목 생성 fallback 모델 배열

## 3. 명시적으로 제외할 범위

### Provider 추상화 제외

OpenAI / Gemini 멀티 프로바이더 전환은 이번 범위에서 제외한다.

이유:
- `generator.ts`는 Gemini SDK의 `fileData`, `inlineData`, Google Search grounding, grounding metadata 처리에 강하게 결합되어 있음.
- OpenAI는 YouTube `fileData`와 Google Search native grounding을 그대로 지원하지 않으므로 공통 메시지 포맷·fallback 정책·tool binding 정책이 별도로 필요함.
- 단순 상수화와 함께 진행하면 변경 범위가 커지고 회귀 위험이 높음.

### 모델 추가 제외

- `gemini-3.x`, OpenAI 모델, Imagen 등 신규 모델은 이번 작업에 추가하지 않는다.
- 현재 운영 중인 모델 문자열만 중앙화한다.

## 11. 모바일 초기 세션 공백 이슈 검토

### 사용자 증상

- 모바일에서 앱 시작 직후 사용자가 쿼리를 입력했는데 세션 화면에 아무 메시지도 나타나지 않는 경우가 있음.
- 입력창은 비워졌지만 현재 세션에는 사용자 메시지와 assistant 응답이 모두 붙지 않는 형태.
- 사용자가 보기에는 "세션이 종료됨" 또는 "빈 세션으로 이동함"처럼 보임.
- 추가 확인: 사용자가 채팅창에 입력/전송한 직후 전체 화면이 하얗게 바뀌며 멈춘 것처럼 보이는 케이스가 있음.
- 이 경우는 단순 빈 세션보다 강한 증상으로, React 렌더 트리의 uncaught runtime error 또는 lazy chunk 로드 실패 가능성을 우선 검토해야 함.
- 새로고침 후 다시 입력하면 정상 진행되는 경우가 있어, 영구 데이터 손상보다는 초기 로드/모바일 복귀/asset cache/chunk 로드 타이밍성 문제가 유력함.
- 새로고침 후 사이드바를 열면 assistant 응답은 DB에 저장되어 있으나 제목은 생성되지 않은 경우가 있음.
- 제목 생성은 `useChatStream.ts`에서 `streamChatResponse(...)`가 완료된 뒤 `summarizeConversation(...)` + `updateSessionTitle(...)`로 실행되므로, 이 패턴은 서버 응답 저장은 완료됐지만 프론트의 스트림 완료 후처리까지 도달하지 못했음을 시사함.

### 원인 후보

#### S0 — 첫 메시지 렌더 시 `ChatMessage` lazy chunk 실패 또는 렌더 예외

- **파일**: `components/ChatArea.tsx`, `components/ChatMessage.tsx`, `App.tsx`
- **문제**:
  - `ChatArea.tsx`는 첫 메시지가 생기는 순간 `React.lazy(() => import('./ChatMessage'))`로 메시지 렌더러 chunk를 로드.
  - 모바일 네트워크/캐시/백그라운드 복귀 상태에서 이 chunk 로드가 실패하거나, `ChatMessage` 하위 렌더러에서 예외가 발생하면 현재 앱에는 Error Boundary가 없어 React 루트 전체가 흰 화면이 될 수 있음.
- **왜 모바일에서 두드러지는지**:
  - 모바일은 첫 입력 직후 키보드/viewport 변화와 네트워크 재개가 동시에 발생.
  - 백그라운드 탭 복귀 후 stale asset cache 또는 일시적 네트워크 실패로 dynamic import 실패 가능성이 데스크톱보다 높음.
  - 데스크톱은 chunk preload가 먼저 끝날 확률이 높지만, 모바일은 사용자가 앱 로드 직후 바로 입력하면 첫 메시지 렌더 시점에 chunk 로드가 아직 완료되지 않았을 수 있음.
  - 새로고침 뒤 정상화되는 패턴은 실패한 dynamic import/cache 상태가 새 페이지 로드에서 해소되는 양상과 맞음.
- **수정 방향**:
  - 앱 루트에 Error Boundary 추가.
  - lazy import 실패 시 재시도 또는 fallback UI 제공.
  - `window.onerror` / `unhandledrejection` 최소 로깅을 추가해 모바일 실제 에러 메시지 수집.
  - 가능하면 `ChatMessage` chunk preload 실패를 잡아 toast/error 상태로 전환.

#### S0-2 — 모바일 스트림 연결 종료/프론트 후처리 중단

- **파일**: `src/hooks/useChatStream.ts`, `services/geminiService.ts`, `api/chat.ts`
- **문제**:
  - `api/chat.ts`가 user/assistant 메시지를 DB에 저장한 뒤에도, 프론트 `streamChatResponse(...)`가 정상 완료되지 않으면 `useChatStream.ts`의 제목 생성 단계로 가지 못함.
  - 모바일에서 탭 정지, 네트워크 전환, fetch reader 중단, dynamic import 실패가 겹치면 서버는 응답을 저장했지만 클라이언트는 완료 이벤트를 처리하지 못할 수 있음.
- **관찰과 맞는 점**:
  - 새로고침 후 응답이 보임 → 서버 저장은 성공.
  - 제목이 없음 → `summarizeConversation(...)` / `updateSessionTitle(...)` 후처리는 미실행 또는 실패.
- **수정 방향**:
  - 스트림 완료 후처리와 렌더 안정성을 분리.
  - 새 세션 첫 응답 저장 후 제목이 비어 있으면 세션 목록 로드/메시지 로드 시 제목 생성 보정 가능성 검토.
  - `streamChatResponse`가 done 이벤트를 못 받아도 서버 저장된 응답을 기준으로 복구할 수 있는 경로 검토.
  - 모바일 fetch 중단/reader error 로그를 남겨 실제 실패 지점을 확인.

#### S1 — `ChatInput` 전송 fire-and-forget

- **파일**: `components/ChatInput.tsx`
- **문제**: `onSend(...)`를 기다리지 않고 즉시 `input`과 첨부 상태를 비움.
- **영향**: `handleSendMessage`가 `currentUser` 없음, 세션 생성 실패, 네트워크 실패 등으로 조기 return하면 사용자가 입력한 쿼리가 UI에서 사라지고 세션에도 남지 않음.
- **수정 방향**:
  - `onSend`를 `Promise<boolean>` 또는 `Promise<void>`로 다루도록 타입 정리.
  - 최소한 전송 함수가 메시지를 세션에 수락한 뒤 입력창을 비우도록 변경.
  - 실패 시 입력값을 유지하거나 toast/error 상태로 사용자에게 알림.

#### S2 — 세션 목록 로드 후 현재 세션 미선택

- **파일**: `src/hooks/useChatSessions.ts`
- **문제**: DB에서 기존 세션 목록을 불러온 뒤 `setSessions(mappedSessions)`만 하고 `currentSessionId`를 설정하지 않음.
- **영향**: 세션 목록은 존재하지만 `currentSession`은 `undefined`가 되어 `App.tsx`가 `messages=[]`를 렌더링. 모바일에서는 사이드바가 숨겨져 있어 빈 화면처럼 보일 수 있음.
- **수정 방향**:
  - 세션 목록 로드 성공 시 기존 `currentSessionId`가 유효하면 유지.
  - 유효한 현재 세션이 없으면 첫 번째 세션을 `currentSessionId`로 설정.
  - 필요하면 첫 번째 세션의 메시지도 함께 lazy load 또는 즉시 load.

#### S3 — `userId` 일시 null에서 현재 세션 해제

- **파일**: `src/hooks/useChatSessions.ts`
- **문제**: `userId`가 없을 때 `setCurrentSessionId(null)`을 호출.
- **영향**: 모바일 브라우저 재개/초기 hydrate 중 `currentUser`가 잠깐 비면 현재 세션 선택이 해제될 수 있음.
- **수정 방향**:
  - 명시적 로그아웃/초기화가 아닌 transient `!userId`에서는 현재 세션 선택을 보존.
  - auth loading 또는 session bootstrap 상태를 별도 플래그로 분리.

#### S4 — 새 세션 생성 직후 stale `sessions` 참조

- **파일**: `src/hooks/useChatStream.ts`
- **문제**: 새 세션을 만든 직후 `setSessions(...)`를 호출하지만, 같은 함수 안의 `sessions.find(...)`는 이전 렌더의 stale 배열을 참조.
- **영향**: 첫 요청의 `activeSession` 기반 history/doc context가 비거나, 이후 스트림 업데이트가 예상 세션을 찾지 못하는 레이스가 생길 수 있음.
- **수정 방향**:
  - 새 세션 생성 시 로컬 `activeSession` 객체를 직접 구성.
  - 스트림 업데이트는 `activeSessionId`가 `prev` 안에 없을 때도 fallback insert가 가능하게 방어.

### 우선 수정 순서

1. 앱 루트 Error Boundary 추가로 흰 화면 대신 복구 가능한 에러 UI 표시.
2. 모바일에서 uncaught error / unhandled rejection 로그 수집 경로 추가.
3. 스트림 완료 후처리 미도달 시 제목 생성이 누락되는 경로 보정.
4. `ChatInput` 입력값 clear 시점을 `handleSendMessage` 수락 이후로 이동.
5. `loadUserSessions` 성공 시 현재 세션 자동 선택 보정.
6. transient `!userId`에서 `currentSessionId`를 즉시 null로 만들지 않도록 조정.
7. `useChatStream` 새 세션 생성 직후 stale `sessions` 참조 제거.

### 검증 항목

- 모바일 첫 입력 직후 화면 전체가 흰 화면으로 바뀌지 않는지.
- `ChatMessage` lazy chunk 로드 실패 시 앱 루트가 유지되고 에러 UI 또는 재시도 UI가 표시되는지.
- 모바일 흰 화면 후 새로고침했을 때 응답이 저장되어 있다면 제목 생성 보정이 수행되는지.
- 모바일 새로고침 직후 첫 쿼리 입력 시 사용자 메시지가 즉시 표시되는지.
- 기존 세션이 있는 사용자로 진입했을 때 빈 화면 대신 첫 세션 또는 마지막 세션이 선택되는지.
- `currentUser` 준비 전 전송 버튼이 눌리지 않거나, 눌리더라도 입력값이 유실되지 않는지.
- 세션 생성 실패 시 입력값 보존 + toast/error 표시가 되는지.
- 데스크톱 기존 세션 선택/새 채팅 흐름이 유지되는지.

## 12. 날씨 응답 언어 혼합 수정

### 문제

- UI 언어를 영어/스페인어/프랑스어로 바꾼 뒤 날씨를 물으면 표의 날씨 상태에 `맑음`, `흐림`, `비` 같은 한국어가 섞이는 경우가 있음.
- 날씨는 별도 renderer/tool 없이 Google Search grounding + `api/_lib/agent/prompt.ts`의 `[WEATHER FORMATTING]` 지시로 마크다운 표를 생성하는 구조.

### 원인

- `getSystemInstruction(langName)` 상단에서는 전체 응답 언어를 `langName`으로 강제하지만, `[WEATHER FORMATTING]` 예시와 이모지 가이드가 한국어로 고정되어 있었음.
- 모델이 "응답은 English/French/Spanish"와 "날씨 셀은 `🌞 맑음` 예시 사용" 지시를 동시에 받아 condition label만 한국어로 섞일 수 있었음.

### 수정

- `WEATHER_FORMATTING` 언어별 맵 추가.
  - Korean: 기존 한국어 표/가이드 유지
  - English: `Date | Weather | Low | High | Rain chance`, `🌞 Sunny`
  - Spanish: `Fecha | Tiempo | Mín. | Máx. | Prob. de lluvia`, `🌞 Soleado`
  - French: `Date | Météo | Min. | Max. | Risque de pluie`, `🌞 Ensoleillé`
- 비한국어 날씨 포맷에는 `맑음`, `흐림`, `비` 같은 한국어 condition label을 출력하지 말라는 명시 지시 추가.

### 검증

- `npx tsc --noEmit` 성공.

## 13. 프롬프트 점검 및 정리 계획

### 점검 범위

- `api/_lib/agent/prompt.ts`
  - base system instruction
  - weather formatting
  - URL summary formatting
  - YouTube analysis directive
  - renderer JSON schema examples
  - `getPillWarnFallback`
  - `INTENT_FOCUS_HINTS`
- `api/_lib/agent/nodes/router.ts`
  - intent classification prompt
  - fallback heuristic와 설명 문구 불일치
- `api/_lib/agent/nodes/generator.ts`
  - system instruction 조립 순서
  - current time / source text / intent hint 주입 위치

### 발견한 문제

#### P1 — URL 요약 예시 문구 한국어 고정

- **파일**: `api/_lib/agent/prompt.ts`
- **문제**: URL 요약 라벨(`One-Line Summary`, `Key Content`, `Key Points`)은 언어별 맵으로 분리되어 있지만, 각 섹션의 설명 placeholder가 한국어로 고정.
  - `> (핵심 메시지를 1문장으로)`
  - `(본문의 주요 섹션을...)`
  - `- (이 글에서 가장 중요한 takeaway...)`
- **영향**: 영어/스페인어/프랑스어 모드에서 URL 요약 응답에 한국어 placeholder 스타일이 섞일 수 있음.
- **계획**: `URL_SUMMARY_LABELS`를 `URL_SUMMARY_FORMATTING` 수준으로 확장해 label + placeholder 문구를 언어별로 분리.

#### P2 — YouTube fallback 문장 한국어 고정

- **파일**: `api/_lib/agent/prompt.ts`
- **문제**: 자막/영상 직접 분석 데이터가 없는 경우 안내 문장이 한국어로 하드코딩.
- **영향**: 비한국어 모드에서 YouTube 요약 fallback이 한국어로 섞일 수 있음.
- **계획**: `YOUTUBE_FALLBACK_MESSAGE` 언어별 맵 추가 후 directive 안에 `${youtubeFallbackMessage}` 주입.

#### P3 — 알약 DB 실패 fallback 한국어 고정

- **파일**: `api/_lib/agent/prompt.ts`
- **문제**: `getPillWarnFallback()`이 한국어만 반환.
- **영향**: 언어 설정이 영어/스페인어/프랑스어여도 알약 DB 조회 실패 시 한국어 안내가 출력될 수 있음.
- **계획**: `getPillWarnFallback(langName)` 또는 language code 기반 다국어 fallback으로 변경.

#### P4 — 전역 renderer schema의 한국어 예시

- **파일**: `api/_lib/agent/prompt.ts`
- **문제**: physics/drug/constellation 등 renderer JSON 예시의 `title`, `label`, `category`, `dosage`, `efficacy.label`에 한국어가 포함되어 있고, 이 schema가 모든 요청에 전역 주입됨.
- **영향**:
  - 비한국어 모드에서 카드/다이어그램 label이 한국어로 섞일 수 있음.
  - 관련 없는 요청에도 모든 renderer 지시가 들어가 토큰 낭비와 오분기 위험 증가.
- **계획**:
  - 단기: 예시 label은 영어 또는 `Use the selected response language` 지시를 각 schema에 추가.
  - 중기: base prompt에서 모든 renderer schema를 제거하고, `intent`별 schema만 `getIntentFocusHint` 또는 별도 `getIntentPromptSections(intent, langName)`에서 주입.

#### P5 — router intent 설명과 현재 도구 범위 불일치

- **파일**: `api/_lib/agent/nodes/router.ts`
- **문제**:
  - 주석은 9 categories라고 되어 있으나 실제 prompt는 12개 intent를 설명.
  - `pharmacy_search`, `hospital_search` 설명에 `(in Seoul)`이 남아 있음.
- **영향**: 전국 검색으로 확장된 현재 도구 범위와 라우터 설명이 맞지 않아 지역 질의 분류 품질에 영향을 줄 수 있음.
- **계획**:
  - 주석을 실제 intent 수와 맞춤.
  - pharmacy/hospital 설명에서 `(in Seoul)` 제거.
  - 필요하면 "Korea-wide public data search" 수준으로 설명 보정.

#### P6 — current time 포맷 한국어 고정

- **파일**: `api/_lib/agent/nodes/generator.ts`
- **문제**: `Intl.DateTimeFormat('ko-KR', ...)`로 current time을 항상 한국어 포맷으로 주입.
- **영향**: 모델이 현재 시간 문자열 자체를 사용자에게 노출하거나 참조할 때 비한국어 응답에 한국어 요일/날짜가 섞일 수 있음.
- **계획**:
  - 단기: 시스템 내부 컨텍스트이므로 우선순위는 낮게 둠.
  - 중기: `language` 또는 `langName`에 맞는 locale로 포맷하거나 ISO + timezone 포맷으로 중립화.

3. **P3 알약 DB 실패 fallback 다국어화**

5. **P6 current time 포맷 중립화**
