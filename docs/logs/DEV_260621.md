## 1. 목적

Gemini grounding은 실시간 스포츠 순위에 구조적으로 부적합(organic 웹페이지만 봄 → 조별 신선도 불균질, 소스 5~25 비결정적, 구글 스포츠 지식 패널 접근 불가 — DEV_260620 §5). 전용 sports API(football-data.org)를 LangGraph tool로 연동해 grounding을 우회.

## 2. 구현 내용

### 신규 파일
- **`lib/sports/football-data.ts`** — football-data.org v4 데이터 계층. `getStandings()`·`getScorers(limit)`·`getMatches({stage,status})`. fetch + 멀티그룹 파싱 + 인메모리 캐시(TTL: standings/scorers 300s, matches 600s, 에러/429 시 stale 폴백) + 마크다운 포맷. 요청 단계 대진이 전부 미정이면 `[NOT_DETERMINED]` 반환.
- **`server/agent/worldcup-tool.ts`** — LangChain `tool`. `resource`(standings/matches/scorers) 인자로 선택적 fetch, `[WORLDCUP_DATA]` + 지시문(데이터만 근거·팀명 한글화·미확정 안내) 반환.

### 수정 파일
- `server/agent/state.ts` — `IntentType`에 `"sports"` 추가.
- `server/agent/graph.ts` — `worldCupTool` import + ToolNode 바인딩.
- `server/agent/nodes/generator.ts` — `LANGCHAIN_INTENTS`에 `"sports"` 추가, `allTools` 분기에 `sports → [worldCupTool]` 바인딩, import 추가.
- `server/agent/nodes/router.ts` — LLM 프롬프트 intent 목록 + `validIntents` + **과거 대회(연도/지난·역대) → general 분기**(API는 현재 대회만, 과거는 학습지식).
- `server/agent/intentRules.ts` — `FALLBACK_RULES`에 sports 키워드 휴리스틱(월드컵/조별/16강/득점왕…).

### 🔴 플랜 갭 발견·수정
구현 계획(Task 3)은 `LANGCHAIN_INTENTS`·ToolNode 등록만 다뤘으나, **generator의 `allTools` 분기(line ~1070)에 sports 바인딩이 빠지면 tool이 LLM에 안 붙어 호출 불가**였음. 실행 중 발견해 `else if (state.intent === "sports") allTools = [worldCupTool];` 추가.

## 6. (별건) kordoc HWP 문서 파싱 연동 — P1~P3 구현

> 계획: `docs/plans/PLAN_KORDOC_INTEGRATION_260620.md` (P0 검증은 2026-06-20 완료)
> 업로드 타입 종합 가이드: `docs/guide/REF_Document.md`

### 목적
HWP 계열 문서를 **구조 보존 마크다운(진짜 표 포함)**으로 추출해 요약 정확도 향상. 기존 `.hwpx`는 JSZip `<hp:t>` 텍스트만 추출해 셀 경계 소실(표→평문 뭉개짐), `.hwp`/`.hwp3`/`.hwpml`은 미지원이었음.

### 사전 점검
- **npm audit**: 12건(7 mod·4 high)은 전부 기존 의존성(`ws`/`xlsx`/`uuid`/langgraph 등). **kordoc 의존성(cfb/xmldom/jszip 등)은 취약점 0건** → 보안 부채 추가 없음.
- **Supabase 리전**: `cf-ray ...-ICN`(서울 엣지)·gateway direct. ≤4MB 직행이라 영향 미미.

### 구현
- **신규 `app/api/parse-document/route.ts`** — kordoc 파싱 라우트. 입력 2종: ⓐ multipart raw(직행, raw≤4MB) ⓑ `{filePath}`(Storage download, 대용량). `SUPPORTED=['.hwp','.hwpx','.hwp3','.hwpml']`(PDF native/docx·xlsx 현행 유지), `runtime='nodejs'`, `preferredRegion='icn1'`, `maxDuration=60`. 응답 `{markdown,truncated,fileType,blockCount,tableCount,metadata}`(blocks[] 미반환, L5). 길이 상한 `MARKDOWN_MAX=100,000`자 초과 시 트렁케이트(L4).
- **`components/ChatInput.tsx`** — `parseViaKordoc(file)` 헬퍼(4MB 임계값 라우팅: 직행 multipart / create-signed-url→Storage PUT→`{filePath}`). HWP 분기를 `isHwpFile` 4종으로 교체(kordoc 우선 + `.hwpx` JSZip 폴백). accept·드롭 허용목록·아이콘 매핑 4종 반영.
- **`next.config.ts`** — `serverExternalPackages: ['kordoc']`.

### 🔴 빌드 갭 발견·수정
`npm run build`에서 webpack이 kordoc 번들링 중 내부 `pdfjs-dist/legacy/build/pdf.worker.mjs`(PDF 경로용·미설치) 정적 import를 해석하려다 실패. node 런타임 `import('kordoc')`는 정상(HWP 경로만 사용)이므로 `serverExternalPackages`로 번들 제외해 해결. → 빌드 성공(라우트 13→14).

### 🔴 보안 리뷰 대응 (IDOR — 자동 리뷰 지적)
`{filePath}` Storage 경로가 attacker-controlled인데 service-role로 다운로드+삭제 → chat-docs 내 임의 HWP 파일 **유출·파괴** 가능. 조사 결과 앱 전체에 인증 레이어가 없고(미들웨어 없음, upload/create-signed-url 모두 비인증) chat-docs는 유저별 prefix 없는 평면 네임스페이스라, 리뷰가 제안한 "세션 JWT + 유저별 prefix + RLS 유저 스코프"는 이 라우트 하나로 달성 불가(앱 전역 인증 도입은 별건). 무인증 환경의 비례적 조치 2종 적용:
1. **filePath 형식 엄격 검증** — `^\d+_[a-z0-9._-]+\.(hwp|hwpx|hwp3|hwpml)$`(create-signed-url 산출 형식). 슬래시·`..`·미지원 확장자 거부 → traversal/타 객체 접근 차단. (검증 8케이스 통과)
2. **route-side `remove()` 제거** — 소유권 검증 불가라 정리용 delete가 임의 삭제 벡터가 됨. 고아 정리는 버킷 TTL/스케줄로 위임.

### 검증 (dev E2E, localhost — 보안 수정 전 측정, 파싱 동작 동일)
- **직행 multipart**(데이터바우처 1.71MB hwp): 151블록·22표·11,626자, `<table>` 보존 ✅
- **Storage 경유**(signed-url→PUT→filePath): 동일 파싱 결과 ✅ (수정 후 정리는 route에서 안 함)
- **트렁케이트(L4)**(NIA 159K자): `truncated:true`, 100,055자에서 절단 + 안내 문구 ✅
- **미지원 포맷**(.docx): 415 ✅
- **filePath 검증 regex**: 정상 2 / traversal·슬래시·timestamp없음·미지원확장자 6 = 8케이스 전부 기대대로 ✅
- `npx tsc --noEmit` 0, `npm run build` 성공.

### 실사용 E2E (사용자 테스트, 2026-06-21)
- **직행**(데이터바우처 1.7MB hwp): `parse-document 854ms`, 표 수치(64.52%·56.6% 등) 보존된 구조화 요약 ✅
- **Storage 경유**(데이터바우처 10.6MB hwp): `create-signed-url 237ms → parse-document 1660ms` 자동 분기, 심사위원 수준 리뷰(참여율 0% 오타·일정표 누락·개인정보 검토·RTX3090/NAS120TB·체크리스트 표) ✅

### 잔여 백로그
- **chat-docs 고아 파일 정리** — route-side delete 제거에 따라 버킷 TTL 또는 스케줄 정리 필요(대용량 경로만 잔존).
- **앱 전역 인증 + 유저별 storage prefix** — IDOR 근본 해결. 현재는 형식 검증으로 blast radius만 제한.
- Supabase origin 리전 대시보드 최종 확인(ap-northeast-2 기대).

## 7. (연계) 첨부 문서 search-gate — grounding 기본 off

### 배경
kordoc 실사용 테스트 중 발견: 문서 요약/검토 요청인데 `intent=general, needsSearch=true → useGoogleSearch=true`로 그라운딩(two-track 2.5+search→3.5)이 발동해 응답 15~19초 + 불필요한 웹검색. 첨부 문서가 답변 근거인데 웹을 또 뒤지는 건 레이턴시·비용·환각 모두 손해.

### 우선순위 (사용자 정의)
1. 첨부 문서 있으면 grounding **off** 기본.
2. 단 사용자가 **문서 외 추가 검증**(검색/조사/최신/출처 등)을 명시 요청하면 **on**.

### 구현 ([server/agent/nodes/generator.ts](../../server/agent/nodes/generator.ts) renderer 게이트 직후)
- `hasDocContent` = `state.webContent`에 `[EXTRACTED_CONTENT:]`(현재 턴 첨부) / `[PREVIOUSLY_UPLOADED_DOCUMENT_CONTENT:]`(후속 턴, lastActiveDoc) 마커 존재.
- `hasDocContent && !explicitSearchRequested` → `useGoogleSearch=false`. 이미 false면 아래 general 게이트(`intent==='general' && useGoogleSearch`) 스킵 → 비활성 확정.
- `explicitSearchRequested`는 기존 정규식 재사용(`검색|찾아|조사|출처|근거|최신|최근|실시간|뉴스|latest|recent|search|source|cite`) — `검토`/`정리`/`요약`은 매치 안 됨.
- 기존 URL 게이트와 동일 철학(소스 있으면 off, 새 검색요구면 열어둠). PDF는 멀티모달이라 `[EXTRACTED_CONTENT:]` 미생성+`hasMultimodalContent`로 이미 off → 충돌 없음.

### 검증
- 게이트 결정 7케이스: 문서+검토/요약/정리 → OFF, 문서+최신/검색/출처 → 열림, 일반질의 → 기존. 전부 기대대로.
- **실사용**(10.6MB hwp + "문서 검토해줘"): `Doc content present ... suppressed` + `useGoogleSearch: false` + two-track 로그 소거 → 단일 패스 14.0s. 문서 근거만으로 상세 리뷰.
- `npx tsc --noEmit` 0.

## 9. (연계) PPTX 표 보존 — `<a:tbl>` 구조 파싱

### 배경
PPTX는 변환 라이브러리가 없어(mammoth=docx 전용, kordoc=pptx 미지원) `<a:tbl>`을 직접 파싱해야 함. 기존 코드는 슬라이드 XML의 `<a:t>`를 전부 평면 join → 표 구조 소실.

### 구조 파악 (`scripts/test-pptx-table.mjs`, fixture `reference/pptx_test/AgenQ_260513.pptx` 3.8MB·20슬라이드, 표는 슬라이드 20에 1개)
- 표 구조: `<a:tbl>`→`<a:tr>`(행)→`<a:tc>`(셀)→`<a:txBody>`의 `<a:p>`/`<a:t>`. 이 fixture는 3×5 clean grid(병합 셀 0).
- **🔴 추가 버그 발견**: 기존 `<a:t[^>]*>(.*?)</a:t>` 정규식의 `.`이 **개행 포함 런을 통째로 누락**(`<a:t>01\n데이터 규격화</a:t>` 같은 셀이 빈칸 → 표 R0/R1 헤더·설명행 전부 소실). 표뿐 아니라 일반 슬라이드 다줄 텍스트에도 영향. → `[\s\S]`로 교체해 동시 수정.

### 구현 (A안, 신규 의존성 0)
[components/ChatInput.tsx](../../components/ChatInput.tsx) pptx 분기: 슬라이드 XML을 `split(/(<a:tbl…<\/a:tbl>)/)`로 표/비표 분리 → 표는 `<a:tr>/<a:tc>` 파싱해 마크다운 표(ragged 행 패딩), 비표는 `[\s\S]` 런 텍스트. 읽기순서 유지, `[Slide N]` 헤더·빈 슬라이드 안내 유지.
- **병합 셀**(gridSpan/rowSpan/hMerge/vMerge): 마크다운 한계로 근사(빈 셀). self-closing `<a:tc/>`는 매칭 제외 → 병합 많은 표는 컬럼 밀림 가능(복잡 표는 PDF 권장).

### 검증
- A안 실측: 슬라이드 20 → 깔끔한 3×5 마크다운 표 + 제목/캡션 읽기순서. 현재 방식은 표 한 줄 뭉갬 + R0/R1 누락.
- 레이턴시(20슬라이드 전체 20회): flat 6.0ms → A안 8.56ms(**+2.5ms 무시 가능**).
- `npx tsc --noEmit` 0.
