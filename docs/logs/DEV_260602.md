## 2. Supabase MCP warning 검토

Codex 시작 시 발생한 Supabase MCP startup warning을 점검했다.

```txt
MCP client for `supabase` failed to start
OAuth token refresh failed: Failed to parse server response
```

확인 결과:

- `~/.codex/config.toml`의 MCP URL이 구 Supabase project ref를 가리킴.
- 현재 앱 env의 `SUPABASE_URL`은 신규 프로젝트 `gaomgqnpsjtabrvwnpad`를 사용.
- MCP warning은 앱 런타임 문제가 아니라 Codex MCP OAuth refresh 및 MCP 설정 불일치 문제로 판단.

권장 조치:

```bash
codex mcp logout supabase
# ~/.codex/config.toml project_ref를 신규 ref로 수정
codex mcp login supabase
```

이번 세션에서는 우선순위가 낮아 실제 MCP 설정 변경은 보류했다.

## 3. 사이드바 최근 기록 `New Chat` 순간 노출 수정

### 증상

웹에서 새 페이지로 진입할 때 사이드바의 가장 최근 기록이 잠깐 `New Chat`으로 보였다가, 이후 정상 제목으로 바뀌는 현상.

### 원인

사이드바는 초기 렌더링에서 DB fetch보다 먼저 `localStorage`의 `chat_sessions_cache_v1` 캐시를 사용한다.

문제 흐름:

1. 새 채팅 생성 시 DB 기본 제목은 `New Chat`.
2. AI 응답 완료 후 `summarizeConversation()` 결과로 세션 제목을 요약 제목으로 변경.
3. 화면 상태와 DB 제목은 갱신되지만, `localStorage` 세션 캐시는 갱신되지 않음.
4. 새 페이지 진입 시 오래된 캐시의 `New Chat`이 먼저 렌더링됨.
5. `/api/sessions` fetch 완료 후 DB 제목으로 덮여 정상화됨.

### 수정

수정 파일:

- `src/hooks/useChatSessions.ts`
- `src/hooks/useChatStream.ts`

변경 내용:

- `writeSessionsCache()`를 export해 스트리밍 훅에서도 캐시를 갱신할 수 있게 변경.
- 메시지 전송 중 새 세션 생성 시 `setSessions()`와 함께 `localStorage` 캐시도 즉시 갱신.
- 제목 요약 완료 후 세션 title 상태와 `localStorage` 캐시를 함께 갱신.
- 기존 캐시에 남아 있던 빈 `New Chat` placeholder는 초기 hydration에서 제외.

효과:

- 새 페이지 진입 시 오래된 `New Chat` 캐시가 먼저 노출되는 flicker 제거.
- DB fetch 전에도 로컬 캐시가 최신 제목을 유지.
- 이미 오염된 캐시의 빈 placeholder도 첫 로딩에서 숨김.

검증:

```bash
npx tsc --noEmit
```

결과: 통과.

### 품질 관찰

- `gpt-image-2-2026-04-21` 직접 접근 가능.
- `low + 1536x1024`에서도 영어/한국어 인포그래픽 텍스트가 대체로 읽힘.
- 한국어 normal은 서비스 기본값 후보로 충분.
- 한국어 dense는 가능하지만 카드 내부가 촘촘해져 기본값으로는 답답함.
- medium은 시각 균형은 더 좋으나 latency 60초대, output image tokens 1372로 크게 증가.
- medium에서도 일부 라벨이 한국어 지시를 무시하고 `Role / Pros / Watchout / Use case`로 출력됨.
- 생물/물리 주제는 카드형 prompt로 생성하면 도식이 아니라 요약 카드로 수렴함.
- `--layout diagram`을 추가하면 세포호흡은 플로우 도식으로 생성됨.
- `myelin sheath action potential`은 영어 canonical label 기반 textbook-style diagram이 가장 안정적.
- 논문/텍스트북 figure 스타일은 주요 과학 용어를 영어 원문으로 고정하는 것이 정확도 면에서 유리함.

### 이미지 생성 사용량 제한 초안

이미지 생성은 테스트 기준 `low`도 25~45초, `medium`은 60초대까지 걸렸고, 비용도 medium에서 크게 증가했다. 초기 서비스 적용 시 강한 리밋이 필요하다.

계획 문서에 아래 초안을 추가했다.

```txt
free user = 3 images/day, 1 image/min
premium user = 30 images/day, 3 images/min
per-user active job = 1
global concurrency = 2
global rate = 4 images/min
default quality = low
medium = premium/regenerate only
high = disabled until cost baseline confirmed
```

운영 구현 방향:

- queue 기반 처리 필요.
- 429/5xx는 Retry-After 우선, 없으면 30s -> 60s backoff.
- 자동 재시도는 1회로 제한.
- 생성 job에는 model, quality, size, layout_type, usage token, latency, estimated cost를 저장한다.
- `medium`은 low 대비 output image token이 크게 증가하므로 3~4 크레딧 차감 후보로 둔다.

### 이미지 텍스트 언어 라우팅 기준 정리

이미지 안 텍스트 언어는 사용자 채팅 언어만으로 정하지 않고, 이미지의 목적과 라벨 정확도 기준으로 라우팅하기로 정리했다.

기본 정책:

```txt
default = user language
override to English = academic diagram, engineering schematic, CS architecture, graph/circuit/reaction
mixed = Korean explanation + English canonical labels
minimal = photoreal/product/illustrative styles
```

권장 필드:

```json
{
  "image_text_language": "ko | en | mixed | minimal",
  "language_reason": "user_facing | canonical_terms | technical_standard | text_accuracy_risk | explicit_user_request",
  "term_policy": "translate | keep_english | bilingual_labels | minimal_text"
}
```

적용 기준:

- 일반 요약, UX 설명, comic, whiteboard, 마케팅 이미지는 사용자 언어를 기본으로 사용.
- 학술 diagram, textbook figure, 생물/의학, 물리 graph, 회로, 화학 반응, 컴공 architecture는 영어 또는 mixed를 우선.
- 국내 발표/교육자료는 한국어 제목 + 영어 canonical term 병기.
- photoreal/product scene은 visible text를 최소화.
- mixed는 핵심 용어 3~6개까지만 병기해 overflow를 피한다.

## 5. 3.5 Flash 검색 응답 지연 원인 분석 + Stage1 thinking 최적화 적용

### 배경

3.5 Flash에서 "서울 날씨" 같은 단순 검색 질의도 응답이 늦는 현상을 조사했다. 3.5+검색은 무조건 two-track(Stage1 2.5+grounding → Stage2 3.5 synthesis)으로 가는데, 어느 단계가 병목인지 테스트 스크립트로 실측했다.

상세 분석/검증 문서: [PLAN_THINKING_LATENCY_260602.md](../plans/PLAN_THINKING_LATENCY_260602.md)

### 근본 원인 (가설 정정 포함)

- 초기 가설 "Stage2(3.5 재정리)가 느리다"는 **오답** — Stage2는 이미 `thinkingLevel: minimal`로 1.4~2s에 불과.
- 실제 병목은 **Stage1(2.5+grounding)의 dynamic thinking**. production 시스템 프롬프트(~41KB)가 dynamic thinking을 폭증시켜(thoughts 147→879) Stage1이 **~8.5s**까지 늘어남.
- thinking budget을 제거하면 grounding 품질 저하 없이 Stage1이 ~4.5s로 단축됨을 확인.

### 사전 검증 (테스트 스크립트, 모두 gitignore 로컬 전용)
