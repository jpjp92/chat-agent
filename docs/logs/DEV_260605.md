## 1. Wikidocs Playwright fallback 실제 대화 플로우 검증

트리거:

- `/api/fetch-url` wikidocs Playwright fallback 적용 후 실제 UI 대화 흐름에서 동작 여부 확인.
- 테스트 URL: `https://wikidocs.net/blog/@jaehong/10121/`

공유 로그 요약:

```text
[fetch-url] Playwright fallback succeeded {
  url: 'https://wikidocs.net/blog/@jaehong/10121/',
  status: 200,
  selector: 'article',
  textChars: 4964
}
POST /api/fetch-url 200 in 3.7s

[LangGraph] URL content provided — Google Search disabled to use full article text
[LangGraph] Starting SDK stream | model: "gemini-3.5-flash" | useGoogleSearch: false
POST /api/chat 200 in 9.5s
```

확인 결과:

- `wikidocs.net` direct fetch 실패 이후 Playwright fallback이 정상 실행됨.
- 블로그형 페이지에서 `article` selector로 본문 4,964자를 추출함.
- `/api/fetch-url`는 200으로 종료했고 전체 소요 시간은 3.7초.
- 이후 `/api/chat`에서 `[URL_CONTENT]`가 제공된 것으로 판정되어 Google Search가 비활성화됨.
- Gemini 3.5 Flash는 검색 보강 없이 제공된 원문 기반으로 응답 생성 경로에 진입함.

판단:

- 의도한 전체 플로우가 실제 대화 경로에서도 정상 동작했다.
- 모델 선택과 무관하게 fetch 단계에서 본문이 주입되므로, Gemini 3.5 Flash에서도 동일하게 활용됨.
- 현재 남은 확인은 Vercel Preview/Production 환경에서 `@sparticuz/chromium` 실행, function size, cold start 로그를 보는 것이다.

성능 메모:

| 단계 | 결과 |
| --- | --- |
| `/api/fetch-url` | 200 / 3.7초 |
| Playwright 추출 | `article` / 4,964자 |
| `/api/chat` | 200 / 9.5초 |
| Google Search | 비활성화 |

## 2. Vercel 배포 런타임 누락 파일 수정

트리거:

- Vercel `/api/fetch-url` 호출 중 `playwright-core` external module 로딩 실패.

에러:

```text
Failed to load external module playwright-core-f386a448524c7e9d:
Error: Cannot find module '/var/task/node_modules/playwright-core/browsers.json'
Require stack:
- /var/task/node_modules/playwright-core/lib/coreBundle.js
```

원인:

- `playwright-core/lib/coreBundle.js`가 런타임에 `packageRoot/browsers.json`을 require한다.
- Next/Vercel output file tracing이 `coreBundle.js`는 포함했지만 `playwright-core/browsers.json`은 자동 포함하지 않았다.
- 따라서 Vercel 함수 번들에서만 external import 실패가 발생했다.

수정:

- `next.config.ts`의 `/api/fetch-url` 전용 `outputFileTracingIncludes`에 아래 파일 추가.

```ts
'./node_modules/playwright-core/browsers.json'
```

검증:

- `npm run build` 성공.
- `.next/server/app/api/fetch-url/route.js.nft.json` 재확인:
  - trace size: 약 `74.82MB`
  - files: `219`
  - `node_modules/playwright-core/browsers.json` 포함 확인
  - 기존 Chromium Brotli 파일 3종(`chromium.br`, `al2023.tar.br`, `fonts.tar.br`) 포함 유지

남은 확인:

- 수정 후 재배포에서 동일 에러가 사라지는지 확인.
- 다음 에러가 발생한다면 동일 방식으로 런타임 require 파일을 trace include에 추가할 수 있다.

후속 에러:

```text
[fetch-url] Playwright fallback error {
  url: 'https://wikidocs.net/blog/@jaehong/12473/',
  error: "ENOENT: no such file or directory, open '/var/task/node_modules/@sparticuz/chromium/bin/swiftshader.tar.br'"
}
```

판단:

- `chromiumBinary.setGraphicsMode = false`를 설정했지만, Vercel 런타임에서 `@sparticuz/chromium.executablePath()`가 여전히 `swiftshader.tar.br` 파일 접근을 시도했다.
- 서버리스 패키징 안정성을 위해 `swiftshader.tar.br`도 `/api/fetch-url` trace include에 되돌리는 것이 안전하다.

추가 수정:

```ts
'./node_modules/@sparticuz/chromium/bin/swiftshader.tar.br'
```

재검증:

- `npm run build` 성공.
- `.next/server/app/api/fetch-url/route.js.nft.json` 재확인:
  - trace size: 약 `78.23MB`
  - files: `220`
  - `swiftshader.tar.br` 포함 확인
  - `playwright-core/browsers.json` 포함 유지

## 3. Vercel Playwright 실행 후 wikidocs 403 진단

트리거:

- 패키징 누락 문제 해결 후 Playwright는 실행됐지만 wikidocs 본문 추출 실패.

Vercel 로그:

```text
[fetch-url] Playwright fallback failed {
  url: 'https://wikidocs.net/blog/@jaehong/12473/',
  status: 403,
  selector: 'body',
  textChars: 158
}
```

로컬 비교:

- 같은 URL을 `scripts/audit-sparticuz-playwright-comparison.mjs`로 테스트.
- `@sparticuz/chromium + playwright-core` 로컬 결과:
  - status: `200`
  - selector: `article`
  - textChars: `3925`
  - title: `중국, 메타의 AI 스타트업 마누스 인수를 막다: '싱가포르 세탁'의 종말 - 박재홍의 실리콘밸리`

판단:

- URL 자체나 selector 문제가 아니다.
- Vercel 함수 환경에서 Chromium은 실행되지만 wikidocs가 Vercel egress IP 또는 serverless/headless fingerprint를 403으로 차단하는 케이스다.
- 즉 패키징 단계 문제에서 런타임 접근 차단 문제로 넘어왔다.

추가 수정:

- Playwright context에 실제 브라우저에 가까운 header 추가:
  - `Accept`
  - `Accept-Language`
  - `Cache-Control`
  - `Pragma`
  - `Upgrade-Insecure-Requests`
- timezone을 `Asia/Seoul`로 지정.
- Chromium launch args에 `--disable-blink-features=AutomationControlled` 추가.
- 실패 로그에 `title`과 본문 `sample`을 추가해 다음 Vercel 로그에서 403 페이지 내용을 확인할 수 있게 함.

검증:

- `npm run build` 성공.
- 현재 로컬 dev server가 꺼져 있어 `/api/fetch-url` 직접 POST 재검증은 수행하지 못함.
- 별도 비교 스크립트 기준으로 같은 URL은 로컬 Sparticuz/Playwright에서 200 성공.

다음 판단 기준:

- Vercel 재배포 후 성공하면 header/fingerprint 보강으로 해결.
- 계속 403이면 Vercel IP 차단으로 판단하고, 다음 선택지는 별도 worker(Railway/Render/VPS) 또는 외부 브라우저/proxy/OpenAI web_search fallback이다.

후속 Vercel 로그:

```text
[fetch-url] Playwright fallback failed {
  url: 'https://wikidocs.net/blog/@jaehong/12473/',
  status: 403,
  title: 'Just a moment...',
  selector: 'body',
  textChars: 158,
  sample: 'wikidocs.net 보안 확인 수행 중 이 웹 사이트는 보안 서비스를 사용하여 악의적인 봇으로부터 보호합니다... Cloudflare의 성능 및 보안 개인 정보'
}
```

최종 판단:

- Vercel 함수 번들에서 `playwright-core`와 `@sparticuz/chromium`은 정상 로드된다.
- Playwright navigation도 실행되지만, wikidocs Cloudflare managed challenge 페이지를 받는다.
- `title: 'Just a moment...'`, 403, Ray ID 포함 sample은 패키징/selector 문제가 아니라 Vercel egress IP 또는 서버리스 headless browser fingerprint 차단을 의미한다.
- 로컬 Sparticuz/Playwright는 같은 URL에서 200/`article`/3,925자 성공했으므로 wikidocs 본문 구조 문제도 아니다.

결론:

- Vercel 내부 Playwright fallback만으로 wikidocs를 안정적으로 처리하기 어렵다.
- 더 많은 header 보강은 성공 가능성이 낮고 Cloudflare 정책 변화에 취약하다.
- 다음 현실적인 선택지는 wikidocs용 외부 render worker(Railway/Render/VPS), browserless/proxy 서비스, 또는 사용자가 허용할 경우 OpenAI web search fallback이다.

## 4. Wikidocs 외부 fetch API 비교: ScrapingBee vs Scrape.do

트리거:

- Vercel Playwright가 Cloudflare challenge에 막히는 상황에서 외부 scraping API가 wikidocs 본문을 가져올 수 있는지 검토.
- 사용자가 `scrape.do` 토큰과 `ScrapingBee` 키를 제공.
- 테스트 스크립트:
  - `scripts/audit-scrapingbee-url-fetch.mjs`
  - `scripts/audit-scrapedo-url-fetch.mjs`

인증 확인:

- ScrapingBee:
  - `https://example.com` 요청 성공
  - status `200`
  - `spb-cost: 1`
  - 본문 142자라 스크립트의 성공 기준 300자에는 미달했지만 인증/호출 자체는 정상.
- Scrape.do:
  - `https://example.com` 요청 성공
  - status `200`
  - 본문 142자라 스크립트 성공 기준에는 미달했지만 인증/호출 자체는 정상.

Wikidocs 테스트 URL:

- `https://wikidocs.net/blog/@jaehong/12473/`

ScrapingBee 결과:

| 조합 | 결과 | 메모 |
| --- | --- | --- |
| `classic_no_js` | 실패 | target initial status `403`, `spb-cost: 0` |
| `render_js=true + block_resources=false` | 실패 | Cloudflare 403, resolved URL에 `__cf_chl_rt_tk`, `spb-cost: 0` |
| `premium_proxy` 계열 | 보류/비추천 | 현재 무료 티어 기준 구독/고비용 옵션으로 판단 |

Scrape.do 결과:

| 조합 | 결과 | 메모 |
| --- | --- | --- |
| `classic` | 실패 | 45초 client timeout |
| `render=true + blockResources=false` | 성공 1회 | status `200`, selector `article`, 3,912자, 약 44.8초 |
| 같은 조합 재시도 | 실패 1회 | 58.2초 후 `ROTATION_FAILED`, 실패 요청은 미청구 메시지 |

판단:

- 무료/현재 계정 기준에서 wikidocs 본문 추출에 실제 성공한 외부 API는 Scrape.do `render=true` 경로뿐이다.
- ScrapingBee 무료 범위 조합은 wikidocs Cloudflare challenge를 넘지 못했다.
- Scrape.do는 성공 가능성이 있으나 latency와 rotation 안정성이 문제다.
- 따라서 기본 경로가 아니라 wikidocs 전용 최후 fallback 후보로만 검토한다.

## 5. Scrape.do 최적화 테스트

목표:

- Scrape.do 성공 조합의 44.8초 지연을 줄일 수 있는지 확인.
- URL 타입별 selector 차이를 확인해 범용 적용 가능성을 판단.

공식 문서상 조정 후보:

- `render=true`
- `blockResources`
- `customWait`
- `waitSelector`
- `waitUntil`
- `timeout`
- `retryTimeout`
- `disableRetry`

단일 블로그 URL 테스트:

테스트 URL: `https://wikidocs.net/blog/@jaehong/12473/`

| 조합 | 결과 | 시간 | 메모 |
| --- | --- | ---: | --- |
| `render=true + blockResources=false` | 성공 1회, 실패 1회 | 성공 시 44.8초 / 실패 시 58.2초 | 실패는 `ROTATION_FAILED` |
| `render=true + waitSelector=article` | 성공 | 35.4초 | 블로그형 selector에 적합 |
| `render=true + waitSelector=article + disableRetry=true` | 성공 2회 | 25.1초 / 25.0초 | 가장 빠르지만 범용 안정성은 별도 확인 필요 |

복수 URL 회귀:

테스트 URL:

- `https://wikidocs.net/blog/@jaehong/8007/`
- `https://wikidocs.net/31695`
- `https://wikidocs.net/288633`
- `https://wikidocs.net/blog/@jaehong/13700/`

`render=true + waitSelector=article + disableRetry=true` 결과:

| URL 타입 | URL | 결과 |
| --- | --- | --- |
| blog | `/blog/@jaehong/8007/` | 45초 timeout |
| book/page | `/31695` | 45초 timeout |
| book/page | `/288633` | 45초 timeout |
| blog | `/blog/@jaehong/13700/` | 32.7초 후 `ROTATION_FAILED` |

`render=true + disableRetry=true` 추가 확인:

| URL | 결과 | 시간 | 메모 |
| --- | --- | ---: | --- |
| `/31695` | 실패 | 43.2초 | `ROTATION_FAILED` |
| `/blog/@jaehong/13700/` | 성공 | 36.9초 | selector `article`, 8,483자 |

책형 페이지 selector 확인:

| 조합 | URL | 결과 | 시간 | selector |
| --- | --- | --- | ---: | --- |
| `render=true + waitSelector=#content` | `/31695` | 성공 | 55.6초 | `.page-content`, 3,550자 |

현재 판단:

- `disableRetry=true`는 빠른 성공 케이스가 있지만 wikidocs 범용 fallback으로 쓰기에는 위험하다.
- `waitSelector=article`은 블로그형 페이지에는 효과가 있으나 `/숫자` 책형 페이지에는 부적합하다.
- 책형 페이지는 `.page-content`가 실제 추출 selector였고, `#content` 대기에서도 성공은 했지만 55.6초로 느리다.
- URL 타입별 최적화가 필요하다:
  - 블로그형: `/blog/` 경로는 `waitSelector=article` 후보.
  - 책형/일반 숫자 경로: `.page-content` 또는 selector 없이 render 완료 후 extractor가 판단하는 방식 후보.
  - `disableRetry=true`는 기본 적용 대신 "빠른 1차 시도 후 실패 시 retry 허용 재시도" 구조로만 검토.

다음 테스트 후보:

- 블로그형:
  - `render=true + waitSelector=article + retryTimeout=5000`
  - `render=true + waitSelector=article + timeout=35000`
- 책형:
  - `render=true + waitSelector=.page-content`
  - `render=true + waitUntil=domcontentloaded + waitSelector=.page-content`
  - `render=true + retryTimeout=5000`
- 공통:
  - `output=markdown`이 응답량/파싱 안정성에 도움이 되는지 확인.

추가 타입별 테스트:

- `retryTimeout=5000`은 Scrape.do가 `render=true`와 함께 사용할 수 없다고 400을 반환했다.
  - 응답: `'RetryTimeout' parameter cannot be used with 'Render' parameter!`
  - 따라서 retry 시간 직접 조정은 render fallback 최적화 후보에서 제외.

블로그형 추가 결과:

| 조합 | URL | 결과 | 시간 | 품질 메모 |
| --- | --- | --- | ---: | --- |
| `render=true + waitSelector=article + timeout=35000` | `/blog/@jaehong/12473/` | 성공 | 13.7초 | selector `article`, 3,912자, 품질 좋음 |
| `render=true + waitSelector=article + output=markdown + timeout=35000` | `/blog/@jaehong/12473/` | 성공 | 18.3초 | 전체 markdown body 8,928자, meta/nav 잡음 섞임 |

책형 추가 결과:

| 조합 | URL | 결과 | 시간 | 품질 메모 |
| --- | --- | --- | ---: | --- |
| `render=true + waitSelector=.page-content + timeout=55000` | `/31695` | 실패 | 56.0초 | `ROTATION_FAILED` |
| `render=true + waitSelector=.page-content + output=markdown + timeout=55000` | `/31695` | 성공 | 12.9초 | body 32,192자, meta/nav 잡음 많음 |
| `render=true + waitSelector=.page-content + output=markdown + timeout=35000` | `/288633` | 성공 | 33.6초 | body 19,774자, meta/nav 잡음 많음 |

수정된 판단:

- 블로그형 `/blog/` URL은 raw HTML 응답 + `waitSelector=article` + API timeout 35초 조합이 현재 최선 후보다.
  - markdown보다 더 빠르고, extractor가 `article` 본문을 깔끔하게 잡는다.
- 책형 `/숫자` URL은 raw HTML render가 느리거나 rotation 실패가 잦다.
  - `output=markdown`은 성공률/속도 면에서 가능성이 있으나, 메타/네비게이션 잡음이 많아 후처리 없이는 모델 입력 품질이 낮다.
- 타입별 후보:
  - blog: `render=true&waitSelector=article&timeout=35000`
  - book/page: `render=true&waitSelector=.page-content&output=markdown&timeout=35000~55000`, 단 markdown cleaner 필요.
- `disableRetry=true`는 일부 블로그 URL에서 빠르지만 범용 실패율이 커 기본값 후보에서 제외.

## 6. Wikidocs markdown cleaner 검토

트리거:

- 책형 `/숫자` URL에서 Scrape.do `output=markdown`은 raw HTML render보다 빠르게 성공하는 경우가 있었지만, meta/nav/목차/댓글 쉘이 대량 포함됨.
- 모델에 그대로 주입하기엔 잡음이 많아 후처리 가능성을 검토.

추가 스크립트:

- `scripts/lib/wikidocs-markdown-cleaner.mjs`
- `scripts/audit-wikidocs-markdown-cleaner.mjs`
- `scripts/audit-scrapedo-url-fetch.mjs`
  - `--clean-wikidocs-markdown`
  - `--sample-chars`
  - `--save-dir`

Cleaner 전략:

- 전체 markdown이 한 줄로 반환되므로 먼저 whitespace normalize.
- 책형 페이지의 본문 시작점:
  - `# 현재 페이지 제목` 이후로 이동.
  - 이후 첫 광고 placeholder 2개(`광고가 출력될 위치입니다.`) 뒤를 본문 시작으로 사용.
- 본문 종료점:
  - `마지막 편집일시`
  - `[댓글`
  - `피드백`
  - `책갈피`
  - `이전글/다음글`

## 11. Vercel ScraperAPI timeout 조정

상황:

- Production 배포 후 `https://wikidocs.net/blog/@jaehong/12473/` 요청에서 `/api/fetch-url`이 502 반환.
- Vercel Runtime Log:
  - direct fetch: `wikidocs.net/...` → `403` in `28ms`
  - ScraperAPI: `api.scraperapi.com` → client timeout `40001ms`
  - function duration: `40066ms`
  - runtime: `nodejs24.x`, memory `289MB / 2048MB`

판단:

- Vercel/Chromium 문제가 아니라 ScraperAPI 응답이 오기 전에 내부 `AbortController` 40초 제한이 먼저 동작한 케이스.
- 기존 로컬 테스트는 18~26초 성공이었지만, 운영 경로에서는 ScraperAPI render가 40초를 넘길 수 있음.
- `/api/fetch-url`은 `maxDuration = 60`이므로 ScraperAPI timeout을 52초까지 늘려도 Vercel 함수 한도 안에 여유가 남는다.

변경:

- `app/api/fetch-url/route.ts`
  - `SCRAPER_API_TIMEOUT_MS = 52000` 상수 추가.
  - ScraperAPI fallback abort timeout `40000ms` → `52000ms`.
  - ScraperAPI error log에 `timeoutMs` 포함.
- `README.md`, `docs/guide/REF_Architecture.md`
  - ScraperAPI fallback timeout 문서 `40s` → `52s`.

추가 관찰 포인트:

- Vercel 로그에서 다음 실패가 `timeoutMs: 52000`으로 찍히면 ScraperAPI render 자체가 운영 경로에서 52초를 넘긴 것.
- 그 경우에는 wikidocs fallback을 비동기화하거나 캐시/재시도/사용자 안내 우선 정책을 별도로 검토해야 한다.

## 13. Notion DEV Records 자동 동기화 구축

목적:

  - `.env` / `.env.local`에서 `NOTION_TOKEN`, `NOTION_DEV_RECORDS_DB_ID` 자동 로드
  - 커밋 메시지 prefix(`feat:` / `fix:` / `refactor:` 등)로 카테고리 자동 분류
  - 커밋 메시지 키워드로 기술스택 자동 분류
  - 제목 앞에 `[chat-agent]` 프리픽스 자동 부여 (다른 레포 레코드와 구분)
  - `참고링크` 컬럼에 커밋 GitHub URL 삽입
  - Notion API rate limit 방지를 위해 350ms 딜레이 적용
- `.git/hooks/post-commit` — 커밋 시 자동 실행 hook
  - 백그라운드 실행으로 커밋 속도에 영향 없음 (`&`)
  - `--last 1`로 방금 커밋만 동기화

사용법:

```bash
# 오늘 커밋 전체
node docs/notion/sync-notion-dev-records.mjs

# 특정 날짜 이후 전체
node docs/notion/sync-notion-dev-records.mjs --after 2026-05-07
```

## 12. Failfast 테스트 스크립트 추가

목적:

- wikidocs처럼 direct fetch가 403으로 막히고 ScraperAPI가 오래 걸리는 URL을 대상으로, "기다리다가 실패"와 "빨리 handoff"를 비교한다.

추가 스크립트:

- `scripts/audit-wikidocs-failfast.mjs`

모드:

- `--policy failfast` — direct fetch 실패 시 바로 handoff
- `--policy direct-scraper` — direct fetch 후 짧은 ScraperAPI 시도
- `--policy compare` — 두 정책을 한 번에 비교

기본 timeout:

- direct fetch: 10초
- ScraperAPI render: 12초

이 스크립트는 운영 경로를 바꾸기 전에, 각 URL에 대해 "얼마나 빨리 포기하고 넘길지"를 정량 비교하는 용도다.

### 12-1. Failfast 비교 테스트

대상 URL:

- `https://wikidocs.net/blog/@jaehong/8007/`
- `https://wikidocs.net/blog/@jaehong/12473/`
- `https://wikidocs.net/blog/@jaehong/13700/`

명령:

```bash
node scripts/audit-wikidocs-failfast.mjs --policy compare --scraper-timeout-ms 12000 \
  https://wikidocs.net/blog/@jaehong/8007/ \
  https://wikidocs.net/blog/@jaehong/12473/ \
  https://wikidocs.net/blog/@jaehong/13700/
```

결과 요약:

| URL | direct fetch | direct-scraper | skip-direct-scraper | skip-direct-failfast |
|---|---:|---:|---:|---:|
| `/8007/` | 403 / 273ms | ScraperAPI abort 12.0s | ScraperAPI abort 12.0s | 즉시 handoff |
| `/12473/` | 403 / 49ms | ScraperAPI abort 12.0s | ScraperAPI abort 12.0s | 즉시 handoff |
| `/13700/` | 403 / 64ms | ScraperAPI abort 12.0s | ScraperAPI abort 12.0s | 즉시 handoff |

추가 확인:

```bash
node scripts/audit-wikidocs-failfast.mjs --policy skip-direct-failfast \
  https://wikidocs.net/blog/@jaehong/8007/ \
  https://wikidocs.net/blog/@jaehong/12473/ \
  https://wikidocs.net/blog/@jaehong/13700/
```

- 세 URL 모두 `totalElapsedMs: 0` 수준으로 즉시 handoff.

판단:

- direct fetch 생략으로 아끼는 시간은 수십~수백 ms라 핵심 병목은 아니다.
- ScraperAPI 동기 fallback은 12초 제한에서도 세 URL 모두 실패했고, 운영에서는 52초 제한에서도 실패 사례가 반복됐다.
- 따라서 현재 운영 안정성 기준으로는 `wikidocs.net` 도메인에서 ScraperAPI 동기 fallback을 시도하지 않고 즉시 handoff하는 정책이 가장 예측 가능하다.
