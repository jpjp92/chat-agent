## §2. Stage2 503/429 분리

### 진단 (날씨 검색 28.6s 로그)
- 날씨="검색" → 3.5+search → two-track. Stage2(3.5 종합)가 **503(모델 폭주)** 반환.
- 기존 catch가 `429 || 503`을 동일 취급 → **12개 키 전부 로테이션**(매번 503 확정, ~24s 낭비) 후에야 2.5 폴백.
- 503은 **모델 전체 현상**이라 어느 키든 같은 3.5 → 키 교체 무의미. 429(키별 레이트리밋)와 대응이 정반대여야 함.

### 수정
[generator.ts](../../server/agent/nodes/generator.ts) Stage2 catch를 원인별 3분기로 재작성:

| 분기 | 동작 |
|---|---|
| daily quota (RESOURCE_EXHAUSTED) | 즉시 2.5 폴백 (기존 유지) |
| **503** (모델 폭주) | 키 로테이션 **안 함** → 백오프(400·800ms) **최대 2회** 동일 키 재시도 → 그래도 503이면 즉시 2.5 폴백 |
| **429 / timeout** | 키 로테이션 최대 12회 (기존 유지) |

→ 관측 28.6s 케이스: 12키 헛돌기 제거, **≤1.2s 백오프 + 2.5 폴백 ≈ 6~7s** 예상. transient blip은 백오프로 구제. tsc 0.

**범위 한정**: Stage2만 수정. Stage1·단일패스·라우터의 503 거동은 재점검 대상(§아래·PLAN §10).

## §3. 지연 변동성 진단 — **3.5-flash 무료티어 선택적 붕괴** (재점검 교정)

초기엔 "Google 전역 503 폭주"로 봤으나, **재프로브(6/24 오후)로 진짜 정체가 드러남**:
같은 키·같은 질의("1+1?", minimal·100토큰)·같은 시간대에서 **2.5와 3.5의 건강이 정반대**.

| 모델 (plain, no search) | 무료키 12개 결과 |
|---|---|
| **2.5-flash** (budget0) | 9 OK **0.6~2.2s**, 3 키 429 — **건강** (Stage1 2.5+search도 3.4~4.2s 정상) |
| **3.5-flash** (minimal) | OK여도 **19~30s**, 나머지 429(quota)/503 — **사실상 사망** |

- 전역 폭주가 아니라 **3.5-flash 무료티어만** RPM 레이트리밋 + 서버측 큐잉. 2.5는 멀쩡.
- 429 정밀: 메트릭 `generate_content_free_tier_requests`, **retryDelay 7~18s = 분당 RPM**(일일 소진 아님, 일일이면 수 시간). **단, OK여도 20~30s**라 진짜 병목은 quota가 아니라 **throughput(느린 추론)** — 기다려도 리셋 안 됨.
- **치명점: 19~30s 케이스는 에러가 아니라 200 OK** → Stage2식 "에러 시 폴백"으로 못 잡음(사용자가 30s 대기). 타임아웃 레이스만 구제 가능.
- blast radius: `DEFAULT_CHAT_MODEL=3.5`([server/models.ts:13](../../server/models.ts)) → general 대화 + drug-info([drug-info-tool.ts:23](../../server/agent/drug-info-tool.ts)) 직격. `SUMMARY_MODELS`는 [lite,2.5]라 제목 생성은 무관(이전 12.1s는 오염).
- 사용자가 보고한 **"모바일 갑자기 느림/빠름"의 핵심 변동원 = 3.5 무료티어 건강 변동**(회복 시 ~3s ↔ 붕괴 시 20~30s).
- **재프로브 도구**: [scripts/test-free-tier-health.mjs](../../scripts/test-free-tier-health.mjs) (`node scripts/test-free-tier-health.mjs`).

### 결정 (6/24): **현행 3.5 유지 + 재확인 대기**
3.5 무료티어가 transient일 가능성에 걸고 코드 변경 보류. 회복 안 되면 `DEFAULT_CHAT_MODEL` 2.5 복귀 재검토(한 줄).
minimal 본래 효과(~4.5s)·Stage2 fix 효과(28s→6s)는 **3.5 회복 후** 재측정해야 정확.

## §4. 3.5-flash 파라미터 최적화 측정 (Tier1) — "튜닝 여지 없음 + 무료티어 확정"

§3에서 무료티어 3.5가 throughput 붕괴라 했으나, **혹시 sampling/token 파라미터로 짜낼 여지가 있는지** Tier1(유료, 스로틀링 없음)에서 순수 파라미터 효과만 측정.

- 도구: [scripts/test-35flash-param-opt.ts](../../scripts/test-35flash-param-opt.ts) (`npx tsx --import ./scripts/_loader-server-only-shim.mjs ...`).
- baseline = **현재 출시 설정**(generator.ts:453 — 3.5는 temp/topP/topK **미설정**, maxTokens 32768, thinkingLevel minimal).
- 6 config × 4쿼리(작문·코드·수학·지식) × 2런 = 48 유료콜. prod 시스템 프롬프트 적용, 전 케이스 `finish=STOP`(잘림 0).

### 쿼리별 지연 (평균 ms)

| config | 작문 | 코드 | 수학 | 지식 | **4쿼리 평균** | thinking |
|---|---|---|---|---|---|---|
| **CURRENT** (기본sampling+minimal) | 6924 | 5165 | 4609 | 3761 | **5115** | 0 |
| NARROW (topP0.5/topK20) | 7014 | 5463 | 3736 | 4290 | 5126 (+0.2%) | 0 |
| DETERMIN (temp0) | 7314 | 4803 | 4287 | 4202 | 5152 (+0.7%) | 0 |
| EXPLICIT (0.2/0.8/40) | 7431 | 4617 | 5188 | 4124 | 5340 (+4.4%) | 0 |
| TOK_TIGHT (maxTokens 8192) | 7886 | 5123 | 3691 | 4680 | 5345 (+4.5%) | 0 |
| **THINK_LOW** (thinkingLevel low) | 9272 | 4520 | 4607 | 4535 | **5734 (+12%)** | **133~403** |

품질: 전 config·전 쿼리 정답·완결. (스크립트의 수학 ❌는 출력 "2,800" 콤마로 인한 정규식 오작동 — 모델은 2,800원/44% **정답**.)

### 결론 3줄
1. **sampling(temp/topP/topK)은 지연·품질 둘 다 무의미** — CURRENT/NARROW/DETERMIN/EXPLICIT 전부 노이즈(±5%). → **3.5에 sampling을 안 넘기는 현행 설계가 옳음**(넘겨도 이득 0).
2. **maxTokens 32768 cap 무해** — TOK_TIGHT(8192)가 오히려 약간 느림(노이즈). 짧은 답은 EOS로 멈춰 cap이 지연에 영향 0 → 큰 cap 유지로 코드·문서 잘림 방지하면서 속도 손해 없음.
3. **minimal이 low보다 12% 빠르고 품질 동일** — low는 thinking 토큰(133~403) 소비분만큼 느림. Tier1(깨끗한 환경)에서도 low→minimal 결정 재확인.

### ⇒ 무료티어 문제 확정
**Tier1에서 3.5는 어떤 파라미터든 3.7~9.3s로 정상 동작.** 즉 파라미터 튜닝으로 얻을 게 없고, 현 설정이 이미 최적. **체감 지연(20~30s)의 원인은 100% 무료티어 3.5 throughput**([§3](#3-지연-변동성-진단--35-flash-무료티어-선택적-붕괴-재점검-교정))이며, 코드·파라미터로는 해결 불가(모델/티어 선택 문제). 실효 대책은 ① 3.5 회복 대기 ② `DEFAULT_CHAT_MODEL` 2.5 복귀 ③ Tier1 유료 — 셋 중 하나.

### §4-1. 무료 vs Tier1 head-to-head (동일 쿼리·동일 CURRENT 설정)

`scripts/test-35flash-param-opt.ts` CURRENT 쿼리 4종을 **같은 시각 무료키 로테이션 vs Tier1**로 직접 대조(무료는 첫 성공 키 기록):

| 쿼리 | Tier1 | 무료(성공) | 배수 | 무료 시도경로 |
|---|---|---|---|---|
| 작문 | 8215ms | 18441ms | **2.2x** | OK(1차 키) |
| 코드 | 4595ms | 6159ms | 1.3x | OK(1차 키) |
| 수학 | 4692ms | 5026ms | 1.1x | OK(1차 키) |
| 지식 | 5109ms | 4994ms | **1.0x** | OK(1차 키) |

**핵심: 속도 차이는 "고정 배수"가 아니라 "변동성"이다.**
- 이 측정 시점엔 무료가 회복돼 코드/수학/지식은 Tier1과 거의 동급(1.0~1.3x), 작문만 2.2x 스파이크.
- 그러나 **불과 1시간 전 같은 무료키로 "1+1?"이 19~30s**(§3) — 즉 무료티어는 분 단위로 출렁임.

| | Tier1(유료) | 무료티어 |
|---|---|---|
| 좋을 때 | 4~9s 안정 | 5~6s (거의 동급) |
| 나쁠 때 | 4~9s 그대로 | **18~30s 또는 429/503 실패** |
| 본질 | 낮은 변동성 | **높은 변동성** |

⇒ **Tier1의 가치 = "빠름"이 아니라 "일정함".** 무료는 한가하면 Tier1과 맞먹지만 RPM/큐잉 순간 3~6배로 튀거나 실패. 이 들쑥날쑥이 사용자가 보고한 **"모바일 갑자기 느림/빠름"의 실체.** 한 줄: *무료 = Tier1급이었다가 수시로 3~6배 느려지거나 실패 / Tier1 = 부하 무관 4~9s 고정.*

## §5. 검색 누락 진단 — "gpt 5.5 설명"을 검색 없이 "없다" 단정

**증상**: "gpt 5.5 설명/설명해줘" → 검색 없이 stale 지식으로 *"그런 모델 없음"* 단정(2.5·3.5 둘 다). "검색해서 찾아줘"라고 명시하면 찾음. 사용자 가설: thinking 낮춤 탓.

### 두 갈래 원인
1. **룰 OFF 경로** — [intentRules.ts:99](../../server/agent/intentRules.ts) `SEARCH_OFF_PATTERNS`가 `설명해/차이…설명/원리/개념/어떻게 작동`을 **강한 OFF로 단정** → 라우터 LLM의 needs_search를 **덮어써** false. ("gpt 5.5 **설명해줘**"가 여기 — thinking·모델 무관.)
2. **gray LLM 경로** — bare "설명" 등은 gray → 라우터 LLM(flash-lite, thinkingBudget0)이 "concept explanation→false"로 분류. 기존 프롬프트에 **"최근/불확실 엔티티는 검증" 가이드 부재**가 원인.

### 핵심 발견: 원인은 **프롬프트**, 모델/thinking 아님
라우터 프롬프트 true 절에 *"최근이거나 존재 불확실한 named product/model/version/person이면 검색(없다고 단정 전 검증)"* 한 절 추가 시:
- 4 config(lite/2.5 × thinking off/on) **전부 8/8**. **lite@0(현재 라우터)도 정답** → 2.5 격상·thinking 상향 **불필요(지연 0)**.
- 과검색 점검(GPT-4·아이폰·파이썬·트랜스포머·챗지피티·BTS 등 잘 알려진 엔티티) **전부 false** (과검색 없음).
- 라우터 LLM은 intent+needs_search **한 번에** 호출 → 룰 완화해도 추가 호출 없음. gray 폴백 `?? true`라 최악도 과검색 방향(안전).

## §6. grounding 병목 분해 측정 (Tier1) + KaTeX 수정

### grounding 병목 (Tier1, [scripts/test-grounding-bottleneck.ts](../../scripts/test-grounding-bottleneck.ts))
3.5=two-track(Stage1 2.5+search → Stage2 3.5합성), 2.5=single-pass. 단일런:

| 쿼리 | A.2.5 single | B.3.5 two-track | Stage1 / Stage2 | C.SLIM Stage1 | 총 단축 |
|---|---|---|---|---|---|
| 날씨 | **4592** | 6776 | 3982(out291) / 2794 | 5804 | −972 (14%) |
| 삼성주가 | **4503** | 9833 | 6038(out666) / 3795 | 7060 | −2773 (28%) |
| AI동향 | **8515** | 14314 | 8586(out1274) / 5728 | 13064 | −1250 (9%) |

**발견**:
1. **Stage1이 two-track의 55~60%**, **출력 토큰에 시간 비례**(291→3982ms, 666→6038ms, 1274→8586ms) → **Stage1 과생산이 병목 확정**(기존 8000자 truncation 증거와 일치).
2. **Stage1 슬림화**(lean notes 지시 + 2048cap): −9~28%, 중간길이 쿼리 최대.
3. **구조적: 2.5 single-pass가 3.5 two-track보다 30~45% 빠름** — two-track은 호출 2번, Stage2(3.5 재합성)가 restyling 위해 2.8~5.7s 추가.

**레버**: 소=Stage1 슬림(~17%, Stage2 유지) / 대=Stage2 스킵·검색은 2.5 single-pass(~40%).

**결정·적용: 대안(2.5 single-pass, Stage2 제거)** — ~40% 빠름 + production의 throttled 3.5(§3) 회피 + 품질 동등(아래 검증).
- 품질 AB(Tier1, 삼성주가·날씨): 2.5 single과 3.5 two-track 모두 정확·정상 포맷. 3.5가 3섹션 구조로 약간 더 정형적일 뿐, 2.5는 자연스러운 표/정리(weather 표는 base 프롬프트가 담당). 멀티턴 "구조 강제 안 함" 철학과도 일치.
- 적용 [generator.ts](../../server/agent/nodes/generator.ts): `useGoogleSearch && needsSearchFallback` 분기에서 Stage2(3.5 재합성)·synthesisInstruction·503/429 재시도·8000자 truncation 전부 제거(−161줄), `responseText = stage1Text`. Stage1(2.5+search, finalInstruction)이 최종 답. tsc 0.
- 잃은 것: generic 3섹션 구조(드물고 자연스러운 답이 더 나음). 유지: weather 표(base), grounding sources, Stage1 빈응답 1회 재시도.

## §7. RPD 소진 발견 · 제목 모델 검토 · 에러 처리 검증

### RPD(일일 요청한도) 소진 — 새 천장
grounding fix 후 날씨 테스트(6.9s, 표 정상)에서 로그상 **12개 무료키 거의 전부 `daily quota exhausted (RPD). Disabled for 24h`** → `All API keys rate-limited. Returning null` 반복.
- §3는 RPM/큐잉(분 단위 회복)이었으나 이건 **RPD = 하루치 요청 자체 소진**, 24h 비활성화 → 다음날까지 회복 불가. **무료티어의 더 단단한 천장.**
- 완화: 이번 **grounding Stage2 제거가 검색 1턴당 호출을 1개 줄여** RPD 수명 연장(우연한 이득). 근본은 호출 수 절감(라우터/제목) 또는 Tier1.
- 관련 메모리: [[35-flash-free-tier-throughput]].

### 제목 생성 모델 — Gemma 검토 후 보류
사용자 제안(Gemma는 별도 RPD 풀 1.5K/일 → gemini 쿼터 보존). 테스트 [scripts/test-gemma-title.ts](../../scripts/test-gemma-title.ts):
- 가용 ID: `gemma-4-26b-a4b-it`(MoE), `gemma-4-31b-it`. **품질 우수**("파이썬 OrderedDict를 활용한 LRU 캐시 구현 코드 및 상세 설명").
- **그러나 13~33s** — Gemma4는 thinking 모델(thoughtsToken 366~952)인데 `thinkingConfig`로 끄려면 400(미지원) → thinking 강제 + 무료티어 throttling. 500 에러 1건.
- **결론: 보류.** 별도 RPD 풀 매력 < 13~33s 지연·불안정. 제목은 빠르고 가벼워야 함(현 lite/2.5는 ~1~2.5s).

### 제목 폴백 — 도입했다 사용자 요청으로 제거
"키 소진 시 첫 사용자 메시지 앞부분으로 제목" 폴백을 서버/클라 양쪽에 넣었다가, **사용자 결정으로 원복**. 제목은 **2.5-flash-lite → 2.5-flash만**, 둘 다 실패 시 **"New Chat"** 유지(세션 시작 전과 동일).

### 키 전소진 에러 처리 — 검증 완료(견고, 변경 없음)
키 0개 시 체인: generator `throw "No API key available"` → [route.ts:282](../../app/api/chat/route.ts) `isAllKeysDailyExhausted()`로 **dailyExhausted vs rateLimit 구분** → 로컬라이즈(4개국어) SSE error → client는 **재시도 안 함**(isRetryable=빈응답/네트워크만) → `onError → showToast`. 빈 말풍선·크래시 없음, user 메시지 유지(재요청 가능). **수정 불필요.**
