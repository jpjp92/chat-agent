## 6. Wikidocs URL fetch 실패 경로 감사

### 6-1. 배경

`wikidocs.net` 같은 일부 사이트는 `/api/fetch-url`의 서버사이드 직접 fetch와 Jina Reader fallback에서 반복적으로 실패한다. 기존 가설은 두 갈래였다.

- 직접 fetch가 데이터센터/서버 IP에서 403 또는 보안 검증 페이지를 받음.
- fetch 자체는 성공해도 본문 selector가 현재 정규식 기반 추출 패턴과 맞지 않음.

이번 감사에서는 `https://wikidocs.net/13`을 기준으로 직접 fetch, Jina, Gemini `urlContext`, OpenAI `web_search`, Cheerio, Playwright를 비교했다.

### 6-2. 테스트 스크립트

- `scripts/audit-wikidocs-url-fetch.mjs`
  - 직접 fetch
  - Jina Reader
  - Gemini `urlContext`
  - OpenAI Responses API `web_search`
- `scripts/audit-playwright-url-fetch.mjs`
  - Playwright Chromium으로 페이지 렌더링
  - title/status/body text/selector 후보 출력

Cheerio 테스트 스크립트도 일시적으로 작성했으나, wikidocs 케이스에서는 fetch 단계에서 이미 보안 페이지를 받는 문제가 확인되어 제거했다. `cheerio` 의존성도 제거함.

### 6-3. 결과

`https://wikidocs.net/13` 기준:

| 경로 | 결과 | 비고 |
| --- | --- | --- |
| 직접 fetch | 실패 | `403`, `Just a moment... Enable JavaScript and cookies to continue` |
| Jina Reader | 실질 실패 | `200`이지만 wikidocs 본문이 아니라 보안 검증/CAPTCHA 안내 페이지 |
| Cheerio | 불필요 | 보안 페이지를 파싱할 뿐 실제 본문을 얻지 못함 |
| Gemini `urlContext` | 실패 | 호출은 성공했지만 `URL_RETRIEVAL_STATUS_ERROR` |
| OpenAI `web_search` | 성공 | `open_page`로 `https://wikidocs.net/13` 열람, 같은 URL citation 반환 |
| Playwright Chromium | 성공 | `200`, 실제 렌더링 DOM에서 본문 추출 가능 |

Playwright 결과:

- status: `200`
- title: `02-2 문자열 자료형 - 점프 투 파이썬`
- body text: 약 `20,883` chars
- 본문 selector 후보:
  - `.page-content`: 약 `19,804` chars — 실제 본문 중심, 최우선 후보
  - `.content`: 약 `20,883` chars — 사이드바/목차 포함
  - `pre`: 96개, `code`: 205개
- 보안 검증 페이지가 아니라 실제 문서 DOM까지 도달함.

### 6-4. 판단

- wikidocs는 현재 기준으로 "파서가 약해서 실패"가 아니라 "일반 fetch/Jina/Gemini urlContext가 본문 HTML을 가져오지 못해서 실패"하는 케이스다.
- Cheerio는 정상 HTML을 받은 뒤 selector/본문 추출 품질을 높이는 도구이므로, wikidocs 해결용으로는 우선순위가 낮다.
- OpenAI `web_search`는 정확 URL 열람에 성공했으나 외부 모델 호출 비용/지연시간이 있다.
- Playwright는 로컬 테스트에서 정확 URL 렌더링과 본문 추출에 성공했다. 서버 fetch 실패 시 자체 fallback으로 가장 직접적인 대안이 될 수 있다.

### 6-5. Playwright fallback 최적화 검토

운영 적용 시 고려사항:

- **콜드스타트 비용**: Chromium 실행/로드가 무겁다. 로컬 테스트에서 wikidocs는 약 6~10초 소요.
- **서버리스 호환성**: Vercel 배포 환경에서는 Playwright 브라우저 바이너리, 함수 크기, 메모리, 실행 시간 제한을 별도 검증해야 한다.
- **브라우저 재사용**: Node runtime에서 가능하면 `browser` 인스턴스를 모듈 스코프에 캐시해 warm invocation 재사용을 검토. 단, 동시성/종료 처리 필요.
- **도메인 제한**: 모든 URL에 Playwright를 쓰면 비용이 크다. 직접 fetch/Jina 실패 후, 허용된 공개 웹 URL에만 fallback 적용.
- **타임아웃**: `domcontentloaded` 기준 15~30초 내 제한. 렌더 후 3~5초 추가 대기 정도만 허용.
- **selector 우선순위**: wikidocs는 `.page-content`가 가장 좋음. 일반화 시 `article`, `main`, `.page-content`, `.post-content`, `.entry-content`, `.content` 순으로 가장 긴 유효 텍스트를 선택하되, `.content`는 목차/사이드바 노이즈 가능성을 감안.
- **보안 검증 감지**: title/body text 기준으로 `Just a moment`, `security verification`, `captcha`, `please enable cookies` 등을 감지하면 실패 처리. HTML 전체 검사 시 정상 페이지 내부 스크립트 문구로 오탐 가능.
- **OpenAI fallback 위치**: Playwright가 실패하거나 배포 환경에서 비활성인 경우 OpenAI `web_search`를 최종 fallback으로 둘 수 있다.

권장 흐름:

1. `/api/fetch-url` 직접 fetch + 기존 Jina fallback 유지.
2. 실패 또는 보안 검증 감지 시 Playwright fallback 시도.
3. Playwright도 실패하면 OpenAI `web_search` fallback 검토.
4. 최종 실패 시 사용자에게 본문 붙여넣기 또는 접근 가능한 URL 제공 요청.

### 6-6. Playwright fallback 최적화 테스트

추가 스크립트:

- `scripts/audit-playwright-fallback-optimization.mjs`

테스트 방식:

- 대상 URL: `https://wikidocs.net/13`
- 동일 Chromium browser 인스턴스 재사용, variant별 새 context/page 생성.
- 추출 성공 조건:
  - HTTP 200
  - title/body text에서 보안 검증 문구 미감지
  - target selector 텍스트 300자 이상
- selector 우선순위:
  - `.page-content` → `article` → `main` → `#book_content` → `#content` → `.content` → `body`

비교 결과:

| 전략 | 결과 | 시간 | 비고 |
| --- | --- | ---: | --- |
| `commit + .page-content 대기 + image/media/font 차단` | 성공 | 624~776ms | 가장 빠름. 순서 변경 후에도 1위 유지 |
| `domcontentloaded + .page-content 대기` | 성공 | 1.1~1.2s | 차단 없이도 충분히 빠름 |
| `domcontentloaded + media/font 차단` | 성공 | 1.3~1.4s | 큰 이득 없음 |
| `domcontentloaded + media/font/stylesheet 차단` | 성공 | 1.3~1.4s | 텍스트에 `Copy` 같은 UI 문자열이 더 섞임 |
| `load + media/font 차단` | 성공 | 2.6~2.9s | 불필요하게 느림 |
| 기존 `domcontentloaded + 5s 고정 대기` | 성공 | 6.0~6.3s | 제거 대상 |

추가 관찰:

- 브라우저 launch 시간은 68~333ms로 로컬 warm 상태에서는 작았다. 배포 cold start는 별도 검증 필요.
- `.page-content`가 wikidocs 본문만 잘 잡는다. `.content`는 사이드바/목차까지 포함해 노이즈가 많다.
- stylesheet까지 차단하면 본문은 얻지만 code block의 숨김 UI 텍스트(`Copy`)가 섞일 수 있어 권장하지 않는다.
- Google analytics/ads 요청 실패는 본문 추출에 영향이 없으므로, media/font 차단 또는 request error 무시 정책으로 충분하다.

현재 권장 구현 형태:

- `page.goto(url, { waitUntil: 'commit', timeout: 30000 })`
- 이미지/미디어/폰트만 차단, stylesheet/script는 유지.
- `.page-content` 포함 selector 후보 중 300자 이상 텍스트가 처음 준비되는 즉시 추출.
- 성공 시 15,000~17,000자 범위로 잘라 기존 `/api/fetch-url` 응답 포맷과 동일하게 반환.
- 보안 검증 문구가 title/body text에 있으면 실패 처리하고 OpenAI fallback 또는 사용자 안내로 넘김.

wikidocs 전용 권장 흐름:

1. direct fetch 시도.
2. `403` 또는 `Just a moment`/보안 검증 문구 감지.
3. Jina를 건너뛰고 Playwright optimized fallback 실행.
4. Playwright 실패 시 OpenAI `web_search` 또는 사용자 안내.

일반 URL 흐름은 아직 별도 판단 필요. Jina가 다른 사이트에서 유효할 수 있으므로, 전체 도메인에 대해 Jina를 즉시 제거하기보다는 `wikidocs.net` 도메인 특화 fast-path로 시작하는 것이 안전하다.

## 7. CI(auto-PR dev→main) 검토 + main 브랜치 보호 적용

> 트리거: "dev 푸시 시 auto PR 생성 방식이 일반적인지 / GitHub 웹의 main 보호 권고 문구는 왜 나오는지" — 검토 후 최소 보호 규칙 적용.

### 7-1. 현재 구조

- `.github/workflows/auto-pr.yml` — `dev` push 시 동작. 열린 dev→main PR이 있으면 skip(멱등), 없으면 `git log origin/main..HEAD` 요약을 body로 PR 생성. 제목 `dev -> main: YYYY-MM-DD`.
- 권한 최소화(`contents:read`, `pull-requests:write`) + `GITHUB_TOKEN`(PAT 없음).
- PR에 **Vercel 체크 3종**(`chat-agent`, `chat-agent-dev`, Preview Comments) 부착, 실제 pass 확인.
- 실데이터: PR #18~22 모두 생성 후 **수 분 내 self-merge**(솔로 승격 흐름).

### 7-2. 평가 — 합리적이고 비표준 아님

- **경량 "dev→main 승격 자동화"** 패턴. Vercel 솔로/소규모 프로젝트에서 흔함(release-please의 release PR, GitHub Flow의 단순화 버전).
- `next.config.ts`가 `typescript.ignoreBuildErrors`/`eslint.ignoreDuringBuilds`를 **끄지 않음** → Vercel `next build`가 **타입체크 + ESLint를 실제 수행**. 즉 빌드 실패 = 타입/린트 에러 캐치 → **Vercel 체크가 진짜 품질 게이트** 역할.

### 7-3. 갭 (심각도 순)

1. **✅ main 브랜치 미보호 → 2026-06-04 보호 적용으로 해소** (7-5 참조). 적용 전: `protection` 404, Vercel 체크가 빨간색이어도 머지·직접 push 가능(advisory)이라 가장 큰 비표준 지점이었음.
2. **🟡 PR = 리뷰 게이트 아닌 배포 기록/형식**(동일인 self-merge). 솔로면 정상.
3. **🟡 PR body가 생성 시점 고정** — 이후 push는 skip 경로라 `## Changes` 미갱신(commits 탭은 정확, 빠른 머지라 실문제 적음).
4. **🟢 Actions에 독립 코드체크 없음** — `tsc/lint/test`가 GitHub에 없고 Vercel build에만 의존. 문서-only 변경엔 게이트 의미 0.

### 7-4. GitHub 웹의 "main 보호" 권고 문구

- 에러 아님 = **기본 브랜치에 보호 규칙이 0이면 GitHub이 모든 리포에 띄우는 일반 권고**. 특정 잘못 때문 아님, 무시해도 동작 정상.
- 의미는 7-3의 #1과 동일 → 아래 7-5로 해소.

### 7-5. main 브랜치 보호 적용 (2026-06-04 완료)

`gh api -X PUT repos/jpjp92/chat-agent/branches/main/protection`로 최소 보호 규칙 적용. 적용 결과(재조회 확인):

| 설정 | 값 | 효과 |
|---|---|---|
| Require PR before merging | ✅ (승인 **0**) | PR 필수, self-merge 흐름 그대로 유지 |
| Required status checks | `Vercel – chat-agent` (프로덕션 프로젝트) | 빌드(타입체크+린트+빌드) 통과 안 하면 머지 불가 |
| strict (branch up-to-date) | `false` | 불필요한 branch 갱신 마찰 제거 |
| Block force pushes | ✅ | main force-push 차단 |
| Block deletions | ✅ | main 삭제 차단 |
| enforce_admins | `false` | 체크가 멈춰도 관리자(본인) 긴급 머지 가능 — 락아웃 방지 |

구현 노트:

- required check 컨텍스트는 **dev 최신 커밋의 legacy commit status에서 실제 보고값을 조회**해 정확히 일치시킴. 구분자는 일반 하이픈이 아니라 **en-dash(`–`)** — 불일치 시 "영영 안 끝나는 체크"로 머지가 막히므로 주의.
- required 체크는 **프로덕션 프로젝트 `Vercel – chat-agent` 1개**로 지정. `chat-agent-dev`는 dev 브랜치를 같은 소스·동일 환경변수로 빌드하는 중복이라 게이트에서 제외(머지=프로덕션 배포 주체인 `chat-agent`만 보장하면 충분). 단순 코멘트봇(`Vercel Preview Comments`)·auto-pr 액션(`create-pr`)도 제외.
- `Require approvals ≥1`은 의도적으로 미적용 — 솔로면 self-approve 불가라 머지가 막힘.

남은 선택지(미적용, 후순위):

- Actions 경량 CI job(`tsc --noEmit` + `next lint`) — 테스트 도입 시 함께. 현재는 Vercel build와 중복이라 불필요.
- `concurrency` 그룹, PR body 자동 갱신 — 빠른 self-merge 흐름이라 실문제 적음.
