## 1. 현상

이미지를 첨부하면 약품과 무관한 경우에도 약품 식별(Vision Node → 약학정보원 DB 조회)로 처리되는 문제.

- "이 사진 분석해줘", "이거 뭐야?", 캡션 없는 이미지(고양이·풍경·문서 등) → 모두 `drug_id` 분류 후 Vision Node 진입
- 2.5 Flash / 3.5 Flash 모델 모두 동일하게 발생
- 약품 관련 키워드가 없는 이미지가 약학정보원 DB를 거쳐 엉뚱한 "약품 식별 불가" 응답 반환

## 2. 원인 분석

### 루트 원인 — `router.ts` + `intentRules.ts`

`server/agent/nodes/router.ts`에서 이미지를 강제로 `drug_id`로 보내는 두 경로가 과도하게 넓게 설정되어 있었음.

#### 경로 1 — Fast-path (L59)

```typescript
if (hasImage && isAmbiguousImageIdentificationRequest(textContent)) {
    return { nextNode: "vision", intent: "drug_id" };
}
```

#### 경로 2 — LLM 후처리 오버라이드 (L94)

```typescript
if (intent === "general" && hasImage && isAmbiguousImageIdentificationRequest(textContent)) {
    intent = "drug_id";
}
```

두 경로 모두 `isAmbiguousImageIdentificationRequest(text)` 술어를 사용했고, 이 함수가 문제의 원인:

```typescript
// intentRules.ts
export const isAmbiguousImageIdentificationRequest = (text: string): boolean => {
    const normalized = text.trim();
    if (!normalized) return true;               // ← 빈 캡션 = 항상 true
    if (hasMedicalIntentKeyword(normalized)) return true;
    return normalized.length <= 40 && AMBIGUOUS_IMAGE_IDENTIFICATION_PATTERN.test(normalized);
};

const AMBIGUOUS_IMAGE_IDENTIFICATION_PATTERN =
    /(이거|이것|사진|이미지|분석|확인|식별|뭔지|무엇|뭐야|알려|봐줘|판독|
      identify|analy[sz]e|what is this|check this|read this|image|photo|
      imagen|foto|identificar|analizar|qué es|...)/i;
```

**결과**:
- 빈 캡션 → `!normalized` → `return true` → 약품 식별 강제
- `"이거 뭐야?"`, `"이 사진 분석해줘"`, `"what is this?"`, `"analyze this image"` → 패턴 매칭 → `return true`
- 이미지를 포함하는 모든 일반 요청이 전부 Vision Node → 약품 DB 조회로 빨려 들어감

한편 결정론적 폴백인 `classifyIntentByRules()`는 **이미 올바르게** 동작 중이었음:
- 실제 약품 키워드(`알약`, `약품`, `약`, `pill`, `tablet` 등)가 있을 때만 `drug_id` 반환
- 버그는 오직 router의 `isAmbiguousImageIdentificationRequest` 술어

커밋 `2240f21`(2026-05-26, 약품 식별 기능 도입) 시 "Router LLM은 텍스트만 보기 때문에 약 이미지 + 짧은 캡션을 놓칠 수 있다"는 이유로 추가된 휴리스틱이 과도하게 설정되었던 것.

## 3. 수정

### 수정 방향

이미지 → drug_id 강제 조건을 **실제 약품/의료 키워드(`hasMedicalIntentKeyword`)가 있을 때**로만 한정.

`hasMedicalIntentKeyword`는 이미 `routerNode` L47에서 계산되어 있으므로, 새 LLM 호출 없이 재사용.

### 수정 1 — `server/agent/nodes/router.ts`

**Fast-path 수정:**

```typescript
// 변경 전
if (hasImage && isAmbiguousImageIdentificationRequest(textContent)) {
    console.log('[LangGraph] Router fast-path: image identification request → drug_id vision');
    return { nextNode: "vision", intent: "drug_id" };
}

// 변경 후
if (hasImage && hasMedicalKeyword) {
    console.log('[LangGraph] Router fast-path: image + drug keyword → drug_id vision');
    return { nextNode: "vision", intent: "drug_id" };
}
```

**LLM 후처리 오버라이드 수정:**

```typescript
// 변경 전
if (intent === "general" && hasImage && isAmbiguousImageIdentificationRequest(textContent)) {
    intent = "drug_id";
}

// 변경 후
if (intent === "general" && hasImage && hasMedicalKeyword) {
    intent = "drug_id";
}
```

**import 정리:**

```typescript
// 변경 전
import { classifyIntentByRules, hasMedicalIntentKeyword, isAmbiguousImageIdentificationRequest } from "../intentRules";

// 변경 후
import { classifyIntentByRules, hasMedicalIntentKeyword } from "../intentRules";
```

### 수정 2 — `server/agent/intentRules.ts`

사용처가 없어진 `isAmbiguousImageIdentificationRequest` 함수와 `AMBIGUOUS_IMAGE_IDENTIFICATION_PATTERN` 상수 제거.

## 4. 동작 변화

| 케이스 | 수정 전 | 수정 후 |
|--------|---------|---------|
| "이 알약 뭐야?" + 이미지 | drug_id → Vision Node ✓ | drug_id → Vision Node ✓ |
| "이 약 식별해줘" + 이미지 | drug_id → Vision Node ✓ | drug_id → Vision Node ✓ |
| "이거 뭐야?" + 이미지 | drug_id → Vision Node ✗ | general → Generator (이미지 직접 설명) ✓ |
| "이 사진 분석해줘" + 이미지 | drug_id → Vision Node ✗ | general → Generator ✓ |
| 캡션 없는 이미지 | drug_id → Vision Node ✗ | general → Generator ✓ |
| "identify this" + 이미지 | drug_id → Vision Node ✗ | general → Generator ✓ |

> 약품 사진 + 약 관련 단어 없이 "이거 뭐야?"만 쓰면 이제는 약학정보원 DB 조회 대신 일반 이미지 설명.
> 사용자가 "이 약 검색해줘", "알약 식별" 등 약 관련 단어를 포함하면 기존대로 약품 DB 조회 경로 동작.

## 7. 약품 식별 DB 조회 개선 (pharm.or.kr)

### 7-1. 발단

일반 이미지 분류 수정 후, 실제 약품 이미지(`마그네스정` — 노랑 장방형, 각인 `dP`)를 테스트. 약품 식별은 되는데 정확한 약품을 찾지 못하는 문제 확인.

### 7-2. ToolMessage 반환 타입 버그 (`generator.ts`)

`identifyPillTool.invoke()`가 LangChain 버전에 따라 raw string 대신 ToolMessage 객체를 반환할 때 `String(toolMessage)` → `"[object Object]"` 변환됨. fast-pass 검사 문자열 매칭 실패 → LLM이 직접 호출되어 "식약처(MFDS) 데이터베이스" 같은 자체 생성 응답 출력.

```typescript
// 수정 전
const pillLookupText = typeof pillLookupResult === 'string'
    ? pillLookupResult : String(pillLookupResult ?? '');

// 수정 후
const pillLookupText = (() => {
    if (typeof pillLookupResult === 'string') return pillLookupResult;
    const c = (pillLookupResult as any)?.content;
    if (typeof c === 'string') return c;
    if (Array.isArray(c)) return c.map((p: any) => (typeof p === 'string' ? p : (p?.text ?? ''))).join('');
    return String(pillLookupResult ?? '');
})();
```

tool 경로 fast-pass(`lastMsg.content` 추출)도 동일하게 수정.

### 7-3. Vision 프롬프트 편향 수정 (`vision.ts`)

프롬프트 예시에 `"dHP"`가 포함되어 있어 `"dP"` 로고를 볼 때 `"dHP"`로 오독하는 경향 발생. `"dHP"` 예시 제거, 알약의 물리적 홈(score line)을 하이픈으로 오인하지 않도록 명시 추가.

### 7-4. `filterResults` 개선 (`pill-logic.ts`)

| 항목 | 내용 |
|---|---|
| 1단계-b 추가 | 각인 완전 일치(색상/모양 불일치 허용) → 색상이 달라도 같은 각인 약품을 `imprint_only` 후보로 우선 노출 |
| 2단계 임계값 | `>= 2` 시도했다가 "DP" 2자가 "DP24", "DPCRA" 등을 오탐 → `>= 3`으로 원복 |
| 2단계-b 변형 매칭 | `normTarget.length === 2` 전용으로 제한 (3자 이상은 DAHP 같은 false positive 발생) |

### 7-5. 검색 쿼리 대소문자 보존 (`pill-logic.ts`)

pharm.or.kr이 대소문자 구분 검색을 하는 경우, `"d-P"` → normalize → `"DP"` (대문자)만 전송하면 `"dP"` 로 저장된 약품을 누락. `fetchPage` 내부 `.toUpperCase()` 제거, `searchPill`에서 대문자 정규화 버전(`"DP"`) + 원본 케이스 보존 버전(`"dP"`)을 모두 primaryQueries에 포함.

3자 imprint 역방향 검색 추가: Vision이 `"dP"`를 `"dHP"`로 오독한 경우, 중간 문자 제거 → `"dP"` 재검색.

## 10. 다음 단계 계획 — MFDS 전체 데이터 Supabase 저장

### 설계

- 테이블: `mfds_pills` (기존 테이블과 독립)
- `mark_codes TEXT[]`: 앞/뒷면 각인 변형 전부 정규화해서 배열로 저장
- GIN 인덱스 → `mark_codes @> ARRAY['DP']` 쿼리로 즉시 검색

```sql
CREATE TABLE IF NOT EXISTS mfds_pills (
  item_seq             TEXT PRIMARY KEY,
  item_name            TEXT,
  entp_name            TEXT,
  chart                TEXT,
  drug_shape           TEXT,
  color_class1         TEXT,
  color_class2         TEXT,
  form_code_name       TEXT,
  mark_code_front_anal TEXT,
  mark_code_back_anal  TEXT,
  mark_codes           TEXT[],   -- 정규화 각인 배열 (GIN 인덱스)
  item_image           TEXT,
  mark_code_front_img  TEXT,
  mark_code_back_img   TEXT,
  class_name           TEXT,
  etc_otc_name         TEXT,
  leng_long TEXT, leng_short TEXT, thick TEXT,
  synced_at            TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_mfds_pills_mark_codes ON mfds_pills USING GIN (mark_codes);
CREATE INDEX idx_mfds_pills_color      ON mfds_pills (color_class1);
CREATE INDEX idx_mfds_pills_shape      ON mfds_pills (drug_shape);
```

### 동기화 스크립트

`scripts/sync-mfds-pills.mjs` 작성 완료. 사용법:

```bash
node scripts/sync-mfds-pills.mjs --dry-run  # 파싱 테스트
node scripts/sync-mfds-pills.mjs            # 전체 동기화 (~256페이지, 2~3분)
```

실행 전 Supabase Dashboard에서 DDL 먼저 실행 필요.

### 검색 예시 (동기화 후)

```typescript
// Vision: imprint_front="dP", color="노랑", shape="장방형"
const { data } = await supabase
    .from('mfds_pills')
    .select('item_name, entp_name, mark_codes, color_class1, drug_shape, item_image')

// → 마그네스정 (대화제약) 직접 반환 예상
```

## 11. `mfds-logic.ts` 구현 — Supabase 기반 약품 검색

`server/mfds-logic.ts` 신규 작성. pharm.or.kr 스크래핑을 대체하는 Supabase 쿼리 기반 검색.

### 검색 전략 (3단계)

| 단계 | 조건 | match_type |
|---|---|---|
| 1단계 | 각인 + 색상 + 모양 일치, **결과 1건** | `exact` |
| 1단계 | 각인 + 색상 + 모양 일치, **결과 2건+** | `imprint_only` (후보 테이블) |
| 2단계 | 각인만 일치 (색상/모양 무관) | `imprint_only` |
| 3단계 | 색상 + 모양만 일치 (각인 없는 약품 대응) | `similar` |

`exact` 조건을 결과 1건으로 제한한 이유: 동일 기업 로고(`dP`)를 가진 약품이 여러 개일 때 첫 번째를 단일 drug 카드로 오확정하는 문제 방지.

### 각인 검색 코드 생성

Vision 추출값 → 정규화 + 변형 후보 집합 생성:

```typescript
// "d-P" → ["DP", "dP", "DHP", "DAP", "DMP", "DPP"]
// "dHP" → ["DHP", "DP"]  (중간 문자 제거 역방향)
```

### MFDS 상세 URL

`item_seq`로 공식 상세 페이지 URL 자동 생성:
```
https://nedrug.mfds.go.kr/pbp/CCBBB01/getItemDetail?itemSeq={item_seq}
```
`DrugRenderer`의 기존 `mfds_url` 필드와 호환.

## 13. 약품 식별 결과 UX 개선 (`generator.ts`, `mfds-logic.ts`)

### 문제

- `exact` match 8건 → LLM이 첫 번째 약품(마르나에프정)만 단일 drug 카드로 렌더링
- Vision 이미지 기반 식별은 단일 확정이 불가능한 경우가 대부분
- "약학정보원 DB" 표기 잔존

### 수정

**`mfds-logic.ts`**: 결과 2건 이상 → `exact` 대신 `imprint_only` 반환
→ generator fast-pass `pillCandidateTableMessage` 경로 진입

**`generator.ts` `pillCandidateTableMessage`**: 안내 문구 개선
```
이전: "...완전히 일치하는 약품은 찾지 못했습니다. ... 약학정보원 DB에서 확인된 ..."
수정: "이미지에서 추출한 특징(...)과 일치 가능한 후보 약품입니다. ... MFDS 식약처 DB 기준 ..."
```

```
사용자: 알약 이미지 + "이 약이 뭐야?"

mfds_pills 쿼리 (mark_codes @> ['DP'] + 노랑 + 장방형) → 8건
  ↓ (2건 이상 → imprint_only)

## 16. 3.5 Flash 멀티턴 타임아웃 수정

### 현상
3.5 Flash 사용 시 1분 초과 타임아웃이 간헐적으로 발생.

### 원인
`app/api/chat/route.ts`에 `maxDuration = 60`(60초 Vercel 제한)이 설정된 상태에서, 멀티턴 3.5 Flash 요청에 `thinkingLevel: "medium"`이 적용되어 복잡한 쿼리에서 thinking 시간만 30~60초를 소비.

### 수정 (`server/agent/nodes/generator.ts`)

```typescript
// 수정 전
const thinkingConfig = is3xModel
    ? ((isYoutubeRequest && hasVideoData) || rendererIntentSet.has(state.intent))
        ? { thinkingLevel: "minimal" }
        : isMultiTurn
        ? { thinkingLevel: "medium" }   // 멀티턴에서 60s 초과
        : { thinkingLevel: "low" }

const thinkingConfig = is3xModel

        ? { thinkingLevel: "minimal" }
        : { thinkingLevel: "low" }      // 멀티턴/단일턴 구분 없이 "low"

## 17. Treemap 차트 JSON raw 출력 수정

### 현상

이미지 분석 요청에서 treemap 차트 응답이 렌더링되지 않고 `` ```json:treemap `` 코드블록 raw JSON이 그대로 출력됨.

### 원인

`server/agent/prompt.ts`의 차트 스키마 예시에서 `"type"` 필드 값 목록에 `"treemap"`이 포함되어 있어, AI가 `` ```json:chart `` 블록 내 `"type": "treemap"`으로 출력해야 함에도 `` ```json:treemap `` 이라는 별도 블록 타입을 할당함.

`ChatMessage.tsx`의 `blockRegex`는 `chart|smiles|bio|...` 타입만 인식하므로 `treemap` 블록은 매칭되지 않아 일반 코드블록으로 렌더링됨.

### 수정

#### 1. `server/agent/prompt.ts` — 프롬프트 명시적 경고 추가
```
IMPORTANT: Always use ```json:chart``` as the block type — NEVER write ```json:treemap```,
```json:bar```, or any other variant. The chart type is specified via the "type" field inside the JSON.
```

#### 2. `components/ChatMessage.tsx` — blockRegex + 로직 3곳 수정

| 수정 위치 | 수정 내용 |
|---|---|
| `blockRegex` | `chart\|treemap\|smiles\|...` — `treemap` 타입 인식 추가 |
| `blockType` 분기 | `blockType === 'chart' \|\| blockType === 'treemap'` → `chart` 타입으로 매핑 |
| 스트리밍 미완성 감지 | `hasIncompleteViz` 정규식 및 `split` 기준에 `treemap` 추가 |

`ChartRenderer`는 이미 `"type": "treemap"`을 지원하므로 렌더러 수정 불필요.
