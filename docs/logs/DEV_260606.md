# DEV_260606

## 1. 배경 — wikidocs fetch가 운영에서 53초 후 502

Vercel 운영 런타임 로그(production, `chat-gem.vercel.app`):

```text
POST /api/fetch-url → 502   Duration: 53288ms   Region: icn1 (function: iad1)
External APIs:
  GET wikidocs.net/blog/@jaehong/8007/ → 403 60ms
  GET api.scraperapi.com/ → timeout 52002ms
Function Duration: 52177ms → 502
```

유저가 53초를 기다린 끝에 502를 받는 최악의 UX. 직전 커밋에서 Playwright → ScraperAPI 전환 + timeout 조정을 했지만, wikidocs 계열은 여전히 불안정.

이날의 목적: **"wikidocs는 direct fetch로 시간낭비하니 바로 처리하자"** 라는 가설(failfast / 12초 cap)이 맞는지 `scripts/audit-wikidocs-failfast.mjs`로 정량 검증하고, 무료 티어 제약 안에서 최적화 방법을 찾는 것.

## 2. 전제 검증 — direct fetch는 "시간낭비"가 아니다

wikidocs direct fetch 실측:

```text
https://wikidocs.net/31695   → 403  0.187s  5674b
https://wikidocs.net/288633  → 403  0.067s  5677b
https://wikidocs.net/blog/@jaehong/13700/ → 403 0.113s
```

- direct fetch는 **0.06~0.2초**만에 403을 즉시 반환한다. 10초 타임아웃까지 매달리지 않는다.
- `route.ts`의 `directFetchBlocked` 판정이 이미 0.1초만에 끝나고 fallback으로 넘어감.
- 예외: `blog/@jaehong/12473/`는 direct가 10초 타임아웃까지 행한 케이스가 1회 관측됨(드묾).

**결론: "direct fetch 시간낭비" 전제는 거의 거짓.** 진짜 병목은 그 다음 단계인 ScraperAPI render.

## 3. 차단 정체 — 도메인 전체가 Cloudflare 챌린지

```text
<title>Just a moment...</title>
cloudflare / cf-ray ...
```

- wikidocs.net 전체가 Cloudflare "Just a moment" JS 챌린지로 덮여 있음.
- 대체 경로 프로브 — 전부 403 (5.5KB 챌린지 페이지):
  - `wikidocs.net/api/v1/page/31695` → 403
  - `wikidocs.net/31695.md` → 403
  - `wikidocs.net/feed` → 403
  - `wikidocs.net/book/31695` → 403
- 무료 우회 후보 `r.jina.ai` 도 동일하게 `Just a moment... 403`으로 막힘.

**결론: 무료 우회 경로(jina, alt path)는 전부 사망. JS 챌린지를 푸는 헤드리스 브라우저(ScraperAPI `render=true`)만 유효.**

## 5. 파라미터 튜닝은 프리티어에서 막힘

`--ultra-premium` / `--premium` 응답 본문:

```text
Your current plan does not allow you to use our premium proxies.
Please upgrade your plan to gain access to our Premium and Ultra Premium pools.
```

- Cloudflare 신뢰도를 올릴 유일한 ScraperAPI 옵션(ultra_premium)이 **유료 업그레이드 필요** → 프리티어 차단.
- 프리미엄 구독은 안 함(프리티어 유지). **파라미터로 더 안정적으로 만들 길 없음.**
- 쓸 수 있는 건 기본 `render=true`뿐 = 24~44s / 비결정적 그 경로.

## 6. 성공률 배치 측정 + 시간 상관성 발견

cap 50s, 단일 시도, 10회 배치:

```text
성공 9/10 (90%), 성공 시간 24~34초, 실패 1건은 풀 타임아웃
```

cap 45s, **parallel=3** (한 요청에 3개 동시, first-success 채택):

```text
단일 URL(31695) 단독 실행: 3/3 전부 성공 (26.6 / 28.5 / 32.5s), 크레딧 60
직전 5-URL 배치:           0/5 전멸 (전부 45s 타임아웃)
```

→ 동시성 한도 문제가 아님(3 concurrent는 명백히 허용). **실패가 시간적으로 상관됨(correlated)**:
"한동안 전부 실패하는 bad window"와 "대부분 성공하는 good window"가 존재.

**함의:**

- 재시도 성공 확률에 독립 가정 `1−(1−p)^k`를 그대로 못 쓴다. bad window에 걸리면 짧은 간격 연속 재시도는 동반 실패 위험.
- **재시도는 간격을 둬야** 효과적(다른 window로 넘어가도록).
- **병렬은 프리티어에서 비효율**: good window선 latency 이득 미미(27 vs 28.5s), bad window선 무의미. → 채택 안 함.

### 6-1. 순차-간격 vs 버스트 A/B (단서: 0/5 전멸이 throttle인가 window인가)

같은 URL(31695), cap 45s:

| 조건 | 성공률 | first/avg | 크레딧 |
|------|--------|-----------|--------|
| 버스트 (parallel=5 동시) | **5/5 (100%)** | first 25.5s | **100** (5건 전부 과금) |
| 순차-간격 (single×5, 20s gap) | **4/5 (80%)** | avg 31.1s | **80** (성공당 1건) |

판정:

- **버스트 parallel=5가 5/5 성공** → 동시 5개 몰아쳐도 throttle로 죽지 않음. **프리티어 동시성 허용 확정.**
- 따라서 §6의 이전 0/5 전멸은 **버스트 throttle이 아니라 bad window**. "하나씩"이 throttle 회피용 *필수*는 아님.
- 실패는 **두 층위**: ① window 상관(한동안 전부 실패) ② 개별 랜덤(good window 안 r5만 단독 실패).
- **병렬 기각 사유는 throttle이 아니라 비용**: good window선 parallel=5가 5건 전부 과금(100크레딧/페이지). 단일 순차는 성공당 정확히 20. **단일이 크레딧 효율 압도.**
- **크레딧이 진짜 제약**: 프리티어 ~월 1000크레딧 ÷ 20 = **월 ~50회 성공 fetch** 한계 → 캐시는 UX뿐 아니라 크레딧 생존용 필수.

## 7. Codex 가설(failfast / 12초 cap) 최종 평가 — 데이터로 반박

- **12초 cap → handoff**: 성공이 24초 이전에 전무하므로 성공률 0% 보장. ❌
- **direct-skip**: direct는 0.1초라 아껴봐야 무의미. ⚠️ 무해하나 이득 없음.
- **failfast(즉시 포기)**: "빠른 성공" 경로 자체가 없어 사실상 wikidocs 콘텐츠 포기와 동의어. ❌

## 8. 결론 & 권고 설계 (확정)

> ⚠️ **업데이트(§11 공급자 재비교 후):** 아래 8-0의 "ScraperAPI 유일 카드"는 **browserless `/unblock`+residential 발견으로 뒤집힘.** 최신 권고는 §11 참조. 8-1~8-3은 ScraperAPI를 쓸 경우의 튜닝으로 여전히 유효(폴백용).

### 8-0. (구) 공급자 선택 — ScraperAPI가 유일 카드 ❌ 뒤집힘

- 다른 무료 공급자 1차 테스트(잘못된 설정)에선 거의 성공 안 됨으로 판단 → ScraperAPI 유일 결론.
- **그러나 §11에서 browserless를 올바른 엔드포인트(`/unblock`+residential)로 재테스트하니 9/9 100%.** 이 절은 무효.

### 8-1. 확정 구성

무료 티어 제약(프리미엄 프록시 X, render만 가능, 비결정적 + 시간상관 실패, 월 ~1000크레딧) 하에서:

| 항목 | 값 | 근거 |
|------|-----|------|
| 공급자 | ScraperAPI `render=true` | 유일 작동 (§3, §8-0) |
| direct fetch | 유지 | 0.1초 공짜 403 감지기 (§2) |
| 타임아웃 cap | **52s → 45s** | 성공 늦어도 ~44s, 실패 7s 빨리 포기, maxDuration=60 여유 (§4) |
| 동기 콜드미스 | **단일 1회** (parallel off) | throttle 아닌 비용 때문에 병렬 기각 (§6-1) |
| 캐시 | Supabase `url_cache` (url_key, content, status, fetched_at), TTL 7~30일 | 1회 성공=영구·무료·크레딧 생존 (§6-1) |
| 실패 시 | "가져오는 중" 안내 + `after()` background 재시도 2~3회, **15~20s 간격** | 시간상관 실패라 간격 필수 (§6) |
| negative cache | 5분 | background 폭주 방지 |

### 8-2. parallel=2 = 선택적 다이얼 (기본 OFF)

- 신뢰도 장치 아님 — **"첫 방문자가 그 자리에서 콘텐츠 보는 확률"만** 올림 (p=0.7 기준 70→91%).
- 대가: 성공 시 크레딧 2배(40). 같은 40크레딧이면 다른 페이지 2개를 캐시에 채우는 게 월 ~50회 천장에서 더 남음.
- 환경변수 스위치(예: `WIKIDOCS_PARALLEL`)로 꺼둔 채 넣고, 예산·UX 필요 시에만 켠다.

### 8-3. 기각 목록

- **병렬 기본 사용** — 비용(good window선 페이지당 N×20크레딧).
- **ultra_premium / premium** — 프리티어 차단.
- **failfast / 12s cap (Codex 안)** — 성공이 24초 이전에 전무 → 성공률 0%.
- **direct-skip** — direct는 0.1초라 이득 없음.

핵심 한 줄: **"빨리 포기 vs 늦게 포기"가 아니라, 비결정적 성공을 캐시로 1회만 확보하고 background 재시도(간격 둔)로 흡수하는 것이 본질. 크레딧 천장 때문에 캐시는 선택이 아니라 필수.**

## 11. 공급자 재비교 — browserless 발견 (결론 갱신)

통합 비교 스크립트 `scripts/audit-provider-compare.mjs` 신규 작성:
동일 URL에 4개 공급자(scraperapi/scrapedo/scrapingbee/browserless)를 각자의 Cloudflare 최강 설정으로 순차 실행, `--repeat`로 성공률 집계.

### 11-1. 결과 (wikidocs 5개 URL)

| 공급자 | 설정 | 성공률 | 속도 | 본문 | 비고 |
|--------|------|--------|------|------|------|
| **browserless** | `/unblock` + `proxy=residential` | **9/9 (100%)** | 18~24s | 3585~8483자 | Cloudflare 전용 엔드포인트 |
| scraperapi | base `render=true` | 0~90% (비결정적; 한 window 0/6) | 27~44s | ~3568자 | |
| scraperapi | `ultra_premium=true` | — | 즉시 403 | — | 프리티어 차단 |
| scrapedo | `render=true&super=true` | 0% | 50s 타임아웃 | — | super 미작동/느림 |
| scrapingbee | `render_js=true&premium_proxy=true` | 0% | 28~44s | — | HTTP 500 "check your request" |

### 11-2. 핵심

- **browserless `/unblock` + residential 이 압도적 1위**: 100% 성공, ScraperAPI보다 빠르고(18~24 vs 27~44s) 본문도 많음.
- 1차 "다른 공급자 별로" 판단은 **browserless를 `/unblock`+residential로 안 돌렸기 때문**. 이 조합이 핵심(=browserless의 Cloudflare 전용 경로).
- 구현 주의: browserless `/unblock` 응답은 JSON이고, `cf_clearance` 쿠키/메타에 `cloudflare`/`cf-ray` 문자열이 들어가므로 **security-block 판정은 raw JSON이 아니라 추출된 본문 텍스트에만** 적용해야 함(스크립트에서 오탐 1건 → 수정 반영).

### 11-3. browserless 최적화 — residential 불필요 (datacenter가 더 빠르고 쌈)

`/unblock`을 residential 유/무로 비교:

| 설정 | 성공률 | 속도 | 비용 |
|------|--------|------|------|
| **/unblock datacenter (residential X)** | ~100% (누적 11/12) | **10~16s** | 저렴 (proxy 대역폭 없음) |
| /unblock + residential | 100% (9/9) | 18~24s | 비쌈 (residential 대역폭 과금) |

- **residential은 불필요하고 오히려 느리다.** datacenter가 더 빠르고(평균 ~12s) 싸고 동일하게 안정적.
- datacenter 실패 1건(13700 HTTP 500 "[object Object]")은 **일시적** — 즉시 재시도 3/3 성공(8483자). 캐시+1회 재시도로 흡수 가능.
- 따라서 **browserless 최적 설정 = `/unblock` + content:true, residential 미사용, cap ~25~30s.**

### 11-4. 갱신된 권고 (최종)

1. **wikidocs(Cloudflare) 1차 경로 = browserless `/unblock` (datacenter, residential X).** ScraperAPI render는 폴백.
2. cap **25~30s** (성공이 10~16s, 일시 지연 여유 포함).
3. 일시적 500/실패 대비 **1회 즉시 재시도** + `url_cache` 캐시 + background 재시도.
4. browserless 100%에 가까우니 **재시도/병렬 의존도 대폭 감소** — 캐시는 여전히 크레딧·속도용으로 유지.
5. **유일 미확인 변수: browserless 프리티어 unit 한도.** datacenter는 residential 대역폭 과금이 없어 unit 소모가 더 유리. 대시보드에서 월 한도 확인 필요(성능은 이미 압도적).

### 11-5. browserless 프리티어 unit 비용 측정 (확정)

대시보드 직접 측정 (Cloud Subscription, 1000 units/월, 동시성 2, 리셋 7/5):

```text
370 → 378 = 4회 호출에 8 units = 회당 평균 ~2 units
(4회 = 헤더확인 1 + 500 + 500 + 200, datacenter /unblock)
```

- **datacenter /unblock = 회당 ~2 units** (매우 저렴). 응답 헤더엔 usage 정보 없음 → 대시보드 델타로만 측정 가능.
- 500 과금 여부는 단정 불가(시나리오 A: 회당 2 flat / B: 성공 4·실패 0, 둘 다 8과 일치)이나 per-call ~2로 보면 안전.
- **일시적 500이 datacenter에서 잦음**(측정 burst 5회 중 3회 500). residential은 9/9 무결이었음 → datacenter는 "빠르고 싸지만 재시도 필요", residential은 "느리고 비싸지만 견고"의 트레이드오프.

월 capacity (datacenter, ~2 units/call, 일시 500 감안 성공당 ~2.5 units):

| | 캐시 없음 | **캐시 있음** |
|---|---|---|
| 월 처리량 | ~400~500 fetch | **고유 URL ~400개/월 + 반복읽기 무한** |

→ ScraperAPI(20크레딧·~50회·불안정) 대비 **~8배 효율**. 동시성 2이므로 병렬은 ≤2(단일 사용이라 무관).

### 11-6. 신규 파일

| 항목 | 값 |
