### 2-1. OCR 토큰 누출 — 텍스트 질문 답변 앞에 "JPW" 등 노출

[chat/route.ts](../../app/api/chat/route.ts)의 `on_chat_model_stream` 포워딩이 **denylist(`langgraph_node === 'vision'`만 차단)** 라 `tools` 노드의 중첩 OCR 토큰("JP"/"W")이 부모 SSE로 누출. 진단 로그 실증: `node="tools"`→"JP"/"W", `node="generator"`→json:drug. 실각인 약품(타이레놀 TYLENOL·엔테론정 E50)은 `needsVision=false` → 누출 없음(증상 비발생이 원인 입증).
- **수정**: chat 라우트 스트림 게이트를 **allowlist**로 전환 — `if (langGraphNode !== 'generator') continue;`. 사용자 prose는 최종 generator 노드 토큰만 전달, vision·tools중첩·router LLM 전부 배제. 안전망: `on_chain_end==='generator'` 폴백 존재.
- **검증**: 파모티딘 재현 → 스트림이 곧바로 `\`\`\`json:drug`로 시작(누출 소멸), 타이레놀 회귀 정상, tsc 0.

### 2-2. 각인 OCR 로고 오판 — 애매하면 "마크" 유지
- **문제**: placeholder "마크"(로고형) 약품을 `extractImprintViaVision`가 OCR할 때 프롬프트가 *"로고도 가장 유사한 알파벳으로 표현하라"*고 강제 → 곡선 로고를 "M"/"W"/"JP"로 **자신 있게 오판**(M/W는 180° 뒤집힌 동형이라 특히 취약), temp 0.1이라 실행마다 흔들림. 약품 식별 맥락에서 "틀린 각인 단정"은 위험.
- **수정** (사용자 설계): ① 프롬프트를 "명확한 숫자·알파벳만 그대로, 로고·애매한 기호·방향따라 달라보이는 건 `마크` 출력"으로 전환(억지 추측 제거) ② Vision이 `마크`/`없음` 반환 시 override 안 함(DB placeholder 유지) ③ temp 0.1→0(결정성).
- **검증**: 위더스파모티딘정(곡선 로고) → Vision raw `"마크"` → 카드 `imprint_front: "마크"`, 뒷면 명확한 숫자 `"2"` 그대로. 다른 후보의 실제 "JP" 각인은 정상 override. tsc 0.

## 4. 위키독스 URL fetch 재차단 수정 — browserless /unblock → ScrapingBee 전환

`https://wikidocs.net/blog/@jaehong/8007` 요약 시 "원문을 가져오지 못했습니다(보안 확인/CAPTCHA/접근 제한)" 502.

- **진단 (재현·직접 호출로 실증)**: [fetch-url/route.ts](../../app/api/fetch-url/route.ts)의 위키독스 전용 경로(`isWikidocsHost`)는 **browserless `/unblock`(datacenter) 단일 의존**이었음(ScraperAPI 폴백은 `SCRAPER_KEY` 부재로 스킵). browserless `/unblock`을 직접 호출하니 **Cloudflare "Just a moment..." 챌린지 페이지를 그대로 반환**(미우회) — `waitForTimeout 9s`도 무효, `waitForSelector article`은 408. residential 프록시는 이 플랜에서 500. 즉 DEV_260606(§11) 당시 datacenter `/unblock`으로 100% 뚫리던 게 **CF 강화로 더는 안 통함**(provider-capability 회귀).
- **해결**: env에 이미 있던(라우트 미사용) **`SCRAPINGBEE_KEY`로 ScrapingBee(`render_js=true` + `premium_proxy=true` + `country_code=kr`) 직접 호출이 CF 우회 성공** — HTTP 200, 실제 본문 65k자, ~4.6s 확인. → `scrapingBeeFetch()` 추가하고 `cloudflareUnblock` 체인을 **ScrapingBee 1차 → browserless 폴백 → ScraperAPI 폴백**으로 재정렬(실패하는 browserless ×2 재시도가 ~9s 낭비였음). 성공분은 `url_cache`(14일 TTL) 저장.
- **검증**: tsc 0. 로컬 라우트 재현 — 1차 ScrapingBee 6.1s(본문 4,178자 "ACE-Step 1.5…") → 2차 **캐시 HIT 0.089s**. 실패는 캐시 안 하므로 negative cache 없음.
- **비용 주의**: ScrapingBee `render_js`+`premium_proxy`는 크레딧 소모가 큼(요청당 ~25 credits급). 14일 캐시로 고유 URL만 과금되게 흡수 — 반복 읽기는 0. 무료 크레딧 소진 시 후속 대안(ScraperAPI 키 복구 등) 필요.
- **후속**: 프로덕션엔 `SCRAPINGBEE_KEY`가 Vercel env에 등록돼 있어야 동작(로컬은 `.env.local` 확인됨). browserless는 다른 CF 사이트용으로 폴백 잔류.

## 5. "영화 정보" 라우팅 변동성 수정 — LLM general 오분류 deterministic 구제

모바일 프로덕션에서 "영화 정보"가 **간헐적으로** movie_search 카드(지역 질의)가 아니라 general+검색(현재 상영작 마크다운 요약)으로 답하는 회귀. 같은 입력이 어떤 땐 카드, 어떤 땐 요약.

- **원인**: 라우터는 LLM 분류(1차) → 실패 시 휴리스틱 regex(폴백) 구조. "영화 정보"는 [intentRules.ts:19](../../server/agent/intentRules.ts#L19) movie regex(`영화\s*정보` 포함)가 movie_search로 잡지만, **LLM이 성공하면 이 phrase를 general(+needs_search)로 분류**하는 변동성이 있어 SDK+Google Search 경로로 빠짐. 503으로 LLM이 실패할 때만 휴리스틱이 돌아 movie_search가 됐기에(로그상 503→heuristic→movie_search 정상) **결과가 LLM 성패에 따라 갈림**.
- **수정** [router.ts](../../server/agent/nodes/router.ts): LLM/휴리스틱 분류 직후, `intent==='general' && !movieContext && classifyIntentByRules()==='movie_search'`이면 movie_search로 교정. 활성 카드 세션(movieContext)은 기존 후속 가드가 처리하므로 제외.
- **검증**: tsc 0. movie regex 샘플 — "영화 정보"·"영화정보"·"무슨 영화 하는지"·"강남 영화 상영시간표"→movie_search 교정, "영화 추천해줘"·"토이스토리 줄거리"·"영화 산업 동향"·"오늘 날씨"→general 유지(오발 0).
- **메모**: 같은 LLM 변동성이 다른 도구 인텐트(pharmacy 등)에도 잠재하나, 일반 키워드 오발 위험이 있어 이번엔 보고된 movie로 한정. 필요 시 동일 패턴 확장.

## 6. Vercel 함수 리전 전역 icn1 전환 (인프라, 코드 변경 0)

## 7. YouTube SDK 경로 2.5-flash 고정 — 60s 천장 마진 확보 (③ 모델 정책 확장)

배포 실측에서 YouTube 요약이 **59.20s/60s**(성공이지만 천장에서 0.8s)로 측정 — 다음에 조금만 무거우면 무응답 위험. ③에서 LangChain 도구를 2.5로 내린 것과 동일 논리를 SDK 경로의 YouTube에 적용.

- **원인**: YouTube는 SDK 경로(generator.ts)라 `resolvedModel = state.model || DEFAULT_CHAT_MODEL`을 따름. `DEFAULT_CHAT_MODEL`이 5/30부터 3.5라 영상 토큰이 큰 generateContent가 3.5로 돌며 단일 호출만으로 수십 초. 사실 [generator.ts:625](../../server/agent/nodes/generator.ts#L625) YouTube 폴백 블록 주석이 "primary 2.5 → fallback 3.5"를 전제 — **5/30 이전 원래 설계가 YouTube=2.5였고**, 기본 모델 전환으로 primary가 3.5가 되며 그 폴백이 죽어 있었음.
- **수정** [generator.ts:81](../../server/agent/nodes/generator.ts#L81): **영상을 실제 읽는 턴(`isYoutubeRequest && hasVideoData`)** 에만 `resolvedModel`을 `SERVER_MODELS.FLASH`(2.5)로 고정. `hasVideoData`(fileData 전송 여부)를 resolvedModel 위로 hoist. 나머지는 기존 인프라가 자동 정합 — thinking은 [generation-config.ts:57](../../server/agent/nodes/generation-config.ts#L57)의 `2.5+YouTube → {thinkingBudget:0}` 분기, `needsSearchFallback=false`(2.5 grounding 직접 지원)로 2.5↔3.5 왕복 제거, 2.5 키 전부 실패 시 ~625줄 폴백(`isYoutubeRequest && hasVideoData`)이 3.5 재시도(이제 정상 동작). 외부 콘텐츠 처리=2.5 정책과도 일치. 영상 핀 작동 시 실제 모델 명시 로그 추가(L23 `state.model` 로그 오해 해소).
- **멀티턴 처리**: YouTube 후속 질문은 URL이 history에만 있고 영상 미재전송(`isYoutubeFromPrompt=false` → `hasVideoData=false`)이라 영상 토큰이 없음 → **영상 턴만 2.5, 후속 텍스트 Q&A는 일반 대화 정책(3.5)으로 복귀**. (`isYoutubeRequest` 단독 핀은 history 매치로 대화 전체가 2.5에 묶이는 문제가 있어 `&& hasVideoData`로 좁힘.)
- **검증**: tsc 0. dev 실측 — YouTube 영상 턴 **16.4s**(이전 59.20s, 로그 `Starting SDK stream | model: gemini-2.5-flash`·핀 로그 확인). 후속 텍스트 턴은 3.5.

## 8. LangChain 도구 인텐트 멀티턴 처리 분석 (약국/병원/법령/약품/축구 — 코드 변경 0)

YouTube/영화 멀티턴을 정리한 김에 나머지 LangChain 경로 인텐트(pharmacy/hospital/vet/law_search/drug_info/drug_id/sports)의 멀티턴 동작을 코드로 점검. **버그 아님 — 현재 동작 문서화 + 잠재 비대칭 기록.**

- **공통 구조**: 이들은 영화(`movieContext`) 같은 **전용 후속-상태가 없다**. 멀티턴은 두 메커니즘에만 의존 — ① **매 턴 라우터 재분류**([router.ts](../../server/agent/nodes/router.ts), LLM+휴리스틱), 직전 어시스턴트 응답 **앞 300자**를 `prevContext`로 주입([router.ts:42](../../server/agent/nodes/router.ts#L42)) ② **전체 history 적재** — 카드 JSON 블록이 DB에 저장됨([route.ts:230-235](../../app/api/chat/route.ts#L230-L235): fast-pass라도 `on_tool_end`에서 ` ```json:<type> ``` `를 `fullAiResponse`에 붙여 persist), 다음 턴엔 last-10 메시지가 `AIMessage(전체 content)`로 들어가([route.ts:56](../../app/api/chat/route.ts#L56)) 카드 데이터 전문이 대화 맥락에 존재.
- **후속 질문 두 갈래**: ① **새 조회성**("다른 약국도"·"강남으로") → 라우터가 같은 tool intent 재분류 → 새 API 호출·새 카드(**2.5**) ② **기존 카드 질문성**("거기 영업시간은?"·"그 약 부작용은?") → 라우터가 `general`로 분류(line 107 "이미 논의된 것 처리") → SDK가 history의 카드 데이터 읽고 산문 답(**3.5**). 모델 정책(도구=2.5/general=3.5)과 일관.
- **주목할 비대칭 ⚠️**: **영화에만** 전용 후속 가드(`movieContext`, [router.ts:178](../../server/agent/nodes/router.ts#L178))가 있어 질문성 후속을 표시된 상영표로 답하게 강제. 나머지는 이 가드가 없어 **순전히 라우터 재분류 변동성에 노출** — §5 "영화 정보" 흔들림과 동종 잠재 이슈(같은 후속이 general↔도구로 갈릴 수 있음). 또 fast-pass(약국/병원/법령)는 저장 콘텐츠가 **카드 JSON뿐**(산문 없음)이라 general 후속 시 SDK가 raw JSON 파싱해 답해야 함 — 동작은 하나 합성형(drug_info/sports, 산문+카드 저장)보다 맥락 빈약.
- **결론**: 현재 버그 아님. 특정 인텐트(예: 약품 후속)에서 흔들림 보고 시 movie식 후속 가드 확장이 다음 후보. [TODO](../TODO.md) 보류 항목으로 기록.

## 9. 라우터 레이턴시 요소 전반 검토 (분석 — 실행 항목은 TODO화)

라우터는 그래프상 `START → router → generator`로 **모든 비-fast-path 요청에서 serial-blocking**([graph.ts:51-52](../../server/agent/graph.ts#L51-L52)) — 생성 시작 전 반드시 1회 LLM 분류 round-trip을 치름. [router.ts](../../server/agent/nodes/router.ts) 전반을 훑어 비용 요소를 분류.

**🟢 이미 잘 된 부분**
- **fast-path 2종**으로 가장 싼 우회 확보: YouTube URL→general([router.ts:67](../../server/agent/nodes/router.ts#L67)), image+약품 키워드→vision([router.ts:77](../../server/agent/nodes/router.ts#L77)) — LLM 호출 스킵.
- 모델은 이미 최경량 `gemini-2.5-flash-lite`(ROUTER_MODEL). 휴리스틱(classifyIntentByRules·classifySearchNeed)은 regex라 CPU 무시 가능. `temperature:0`+JSON 강제로 출력 결정성 확보.

**🔴 개선 후보 (레이턴시 영향순)**
1. **[A] 라우터 LLM에 `thinkingConfig:{thinkingBudget:0}` 미설정** → **적용 완료**. [router.ts:112](../../server/agent/nodes/router.ts#L112)는 `config:{temperature:0, responseMimeType:"application/json"}`뿐이었음. **같은 flash-lite를 쓰는 summarize-title은 `thinkingBudget:0`을 명시**([summarize-title/route.ts:44](../../app/api/summarize-title/route.ts#L44))하는데 라우터만 누락 — 순수 JSON 분류에 thinking 불필요하고 매 턴 serial-blocking이라 영향 직접적. flash-lite 기본 thinking이 off라도 명시 핀이 안전(API 기본값 변동 면역). **수정**: `config`에 `thinkingConfig:{thinkingBudget:0}` 추가(tsc 0). **분류 품질 영향 없음 예상** — 인텐트 분류(15개 택1+boolean)는 얕은 패턴 작업이라 thinking 불요, flash-lite 기본 off라 사실상 현 동작 명시화, `temperature:0`+JSON 강제 유지.
2. **[B] 고신뢰 인텐트 휴리스틱 단축(short-circuit)** — 현재 LLM-first(정확도 우선). `classifyIntentByRules`는 movie 구제([router.ts:162](../../server/agent/nodes/router.ts#L162))에서 이미 돌고 있음. 명백·고정밀 패턴(예: "CGV 상영시간표", "약국 찾아줘")은 LLM 호출 자체를 스킵해 round-trip 1회 통째 제거 가능 → **가장 큰 레이턴시 절감**. 단 regex 오발 시 오라우팅 위험 → 고정밀 소수 패턴만 opt-in 필요. **중위험·중효과**.
3. **[C] 실패 재시도 꼬리 레이턴시** — 503/429 시 키 로테이션 2회 시도([router.ts:85](../../server/agent/nodes/router.ts#L85), backoff 없음). 혼잡 시 라우터 단독으로 LLM round-trip 2회 → 라우터 지연 2배 가능. 정확도/안정성 위해 **현행 유지 권장**(꼬리 지연 수용).
4. **[D] 전체 카테고리 프롬프트 매 호출 전송**(~1.5KB 입력) — flash-lite엔 부담 작음. 트리밍 가치 낮음, 보류.
