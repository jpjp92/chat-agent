## 2. 버그픽스 — drug_info OCR 토큰 누출 + 각인 로고 오판 (pre-existing, 3-A E2E 중 발견)

### 2-1. OCR 토큰 누출 — 텍스트 질문 답변 앞에 "JPW" 등 노출
- **증상**: 이미지 없이 텍스트로 약품 설명만 요청("파모티딘 설명해줘")했는데 답변 맨 앞에 `JPW` 같은 무관한 토큰이 붙음.
- **근본 원인** (systematic, 진단 로그로 실증): [drug-info-tool.ts](../../server/agent/drug-info-tool.ts) `extractImprintViaVision`가 MFDS DB 각인이 placeholder `"마크"`인 약품의 알약 이미지를 **LangChain `ChatGoogleGenerativeAI.invoke()`** 로 OCR — 이 중첩 LLM이 `tools` 노드에서 실행됨. [chat/route.ts](../../app/api/chat/route.ts)의 `on_chat_model_stream` 포워딩이 **denylist(`langgraph_node === 'vision'`만 차단)** 라 `tools` 노드의 중첩 OCR 토큰("JP"/"W")이 부모 SSE로 누출. 진단 로그 실증: `node="tools"`→"JP"/"W", `node="generator"`→json:drug. 실각인 약품(타이레놀 TYLENOL·엔테론정 E50)은 `needsVision=false` → 누출 없음(증상 비발생이 원인 입증).
- **수정**: chat 라우트 스트림 게이트를 **allowlist**로 전환 — `if (langGraphNode !== 'generator') continue;`. 사용자 prose는 최종 generator 노드 토큰만 전달, vision·tools중첩·router LLM 전부 배제. 안전망: `on_chain_end==='generator'` 폴백 존재.
- **검증**: 파모티딘 재현 → 스트림이 곧바로 `\`\`\`json:drug`로 시작(누출 소멸), 타이레놀 회귀 정상, tsc 0.

### 2-2. 각인 OCR 로고 오판 — 애매하면 "마크" 유지
- **문제**: placeholder "마크"(로고형) 약품을 `extractImprintViaVision`가 OCR할 때 프롬프트가 *"로고도 가장 유사한 알파벳으로 표현하라"*고 강제 → 곡선 로고를 "M"/"W"/"JP"로 **자신 있게 오판**(M/W는 180° 뒤집힌 동형이라 특히 취약), temp 0.1이라 실행마다 흔들림. 약품 식별 맥락에서 "틀린 각인 단정"은 위험.
- **수정** (사용자 설계): ① 프롬프트를 "명확한 숫자·알파벳만 그대로, 로고·애매한 기호·방향따라 달라보이는 건 `마크` 출력"으로 전환(억지 추측 제거) ② Vision이 `마크`/`없음` 반환 시 override 안 함(DB placeholder 유지) ③ temp 0.1→0(결정성).
- **검증**: 위더스파모티딘정(곡선 로고) → Vision raw `"마크"` → 카드 `imprint_front: "마크"`, 뒷면 명확한 숫자 `"2"` 그대로. 다른 후보의 실제 "JP" 각인은 정상 override. tsc 0.

## 3. 도구 응답 성능 회귀 수정 — 모델 정책 정리(도구=2.5 / 일반=3.5) + sports 비스트리밍

### 3-1. 회귀 원인 특정 — 5/30 기본 모델 전환
- `extractImprintViaVision`의 후보별 Vision OCR fan-out(MFDS `numOfRows=5` × 앞뒤 2면 = **최대 10콜**)은 작년부터(`2240f21`) 동일한 구조. 바뀐 건 **모델** — 커밋 `1cd48c2`(2026-05-30 "기본 모델을 3.5 Flash로 변경")가 `DEFAULT_CHAT_MODEL`을 2.5→3.5-flash로 전환. Vision OCR과 LangChain 도구 경로 invoke가 모두 `DEFAULT_CHAT_MODEL`을 쓰므로, 같은 작업이 **무거운(기본 thinking 큰) 3.5-flash로 돌며** 지연 급증 → Vision fan-out은 Vercel 60s 초과(무응답), 다른 도구 인텐트는 체감 저하. 5/30 이전엔 전부 빠른 2.5-flash였던 게 "예전엔 빨랐다"의 정체.
- **제약**: Vercel **무료티어 → maxDuration 60s가 절대 천장**(상향 불가). 해결은 예산 확대가 아니라 호출 지연 축소만 가능. → [[chat-agent-vercel-60s-cap]]

### 3-2. 모델 선택 정책 — 외부 API 도구는 2.5, 일반 대화만 3.5
LangChain 경로 인텐트는 전부 외부 API 도구 기반(MFDS·약국·병원·동물병원·법령·영화·football-data)이라 핵심은 API 데이터지 모델 추론이 아님 → 빠른 2.5-flash로 충분. 일반 대화(SDK 경로)만 3.5 품질 업그레이드 유지. 5/30 이전 도구 경로 속도를 복원.

## 4. 위키독스 URL fetch 재차단 수정 — browserless /unblock → ScrapingBee 전환

`https://wikidocs.net/blog/@jaehong/8007` 요약 시 "원문을 가져오지 못했습니다(보안 확인/CAPTCHA/접근 제한)" 502.

- **진단 (재현·직접 호출로 실증)**: [fetch-url/route.ts](../../app/api/fetch-url/route.ts)의 위키독스 전용 경로(`isWikidocsHost`)는 **browserless `/unblock`(datacenter) 단일 의존**이었음(ScraperAPI 폴백은 `SCRAPER_KEY` 부재로 스킵). browserless `/unblock`을 직접 호출하니 **Cloudflare "Just a moment..." 챌린지 페이지를 그대로 반환**(미우회) — `waitForTimeout 9s`도 무효, `waitForSelector article`은 408. residential 프록시는 이 플랜에서 500. 즉 DEV_260606(§11) 당시 datacenter `/unblock`으로 100% 뚫리던 게 **CF 강화로 더는 안 통함**(provider-capability 회귀).
- **해결**: env에 이미 있던(라우트 미사용) **`SCRAPINGBEE_KEY`로 ScrapingBee(`render_js=true` + `premium_proxy=true` + `country_code=kr`) 직접 호출이 CF 우회 성공** — HTTP 200, 실제 본문 65k자, ~4.6s 확인. → `scrapingBeeFetch()` 추가하고 `cloudflareUnblock` 체인을 **ScrapingBee 1차 → browserless 폴백 → ScraperAPI 폴백**으로 재정렬(실패하는 browserless ×2 재시도가 ~9s 낭비였음). 성공분은 `url_cache`(14일 TTL) 저장.
- **검증**: tsc 0. 로컬 라우트 재현 — 1차 ScrapingBee 6.1s(본문 4,178자 "ACE-Step 1.5…") → 2차 **캐시 HIT 0.089s**. 실패는 캐시 안 하므로 negative cache 없음.
- **비용 주의**: ScrapingBee `render_js`+`premium_proxy`는 크레딧 소모가 큼(요청당 ~25 credits급). 14일 캐시로 고유 URL만 과금되게 흡수 — 반복 읽기는 0. 무료 크레딧 소진 시 후속 대안(ScraperAPI 키 복구 등) 필요.
- **후속**: 프로덕션엔 `SCRAPINGBEE_KEY`가 Vercel env에 등록돼 있어야 동작(로컬은 `.env.local` 확인됨). browserless는 다른 CF 사이트용으로 폴백 잔류.
