## 3. 신규 하니스 — `tests/test-doc-index.mts`

누락 6건의 공통점이 **링크 검사기가 잡을 수 없는 종류**였다. [test-doc-links](../../../../tests/test-doc-links.mts) 는 *있는 링크가 깨졌는가* 를 보는데, 이건 *있어야 할 링크가 없는가* 다. 기록 규칙이 이미 "새 날짜 로그는 `DEV_HISTORY.md` 와 해당 월 `README.md` 에 링크한다" 고 정해 뒀는데도 사흘이 빠진 것이 핵심이다 — **규칙이 있어도 사람이 거르면 아무 신호가 없었다.**

검사 6종: 날짜 로그 → 월 인덱스·`DEV_HISTORY` · 계획서 → `PLAN_INDEX` · `REF_*` → `guide/README` · `.sql` → `guide/db/README` · 하니스 → `tests/README`.

판정을 가른 기준:

- 부록형 로그(`DEV_YYMMDD_SUFFIX.md`)는 `DEV_HISTORY` 를 **경고**로만 본다. 실측하니 부록 4개 중 `DEPLOY_CHECK`·`DEADCODE`·`DEPS` 셋은 등록돼 있고 `COMMENT_ARCHIVE` 만 없다 — 주석 원문 보관이라 본문 로그가 대리하는 게 맞다. 빈 규칙을 세우는 대신 규칙을 현실에 맞췄다([09-04 감사 §4](../09/DEV_260904.md) 와 같은 판단).
- 월 `README.md` 가 없는 달은 건너뛴다(2026/04~07 은 `DEV_HISTORY` 로 갈음한다는 명시 규칙).
- 링크 문법이 아니라 **이름이 등장하는지**만 본다. 형식까지 강제하면 10-20 행처럼 날짜 로그 없이 계획서만 적는 정당한 변형이 거짓 실패가 된다.

작성 중 실패 25건이 떴는데 전부 거짓이었다 — `git ls-files` 의 pathspec 은 `*` 가 **디렉터리 경계를 넘어** `tests/*.mts` 가 `tests/manual/` 까지 잡았다. `run-all.mts` 는 자기 디렉터리만 훑으므로(하위는 의도적 제외) 깊이를 고정했다.

`run-all.mts` 가 `tests/*.mts` 를 자동 수집하므로 `npm test` → `npm run verify` → CI 에 바로 편입된다. 결과: 대상 245건, 실패 0 · 경고 1(위 `COMMENT_ARCHIVE`). 하니스 **38종**.
