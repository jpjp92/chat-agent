# Gemini 3.8 도입 전 스크립트와 1차 호환성 확인

> 날짜: 2026-09-06 · 상태: 테스트 스크립트 추가, 프로덕션 코드·모델 등록·배포 변경 없음.
> [계획](../../../plans/PLAN_MODEL_3_8_MIGRATION_260906.md) · [실행 방법](../../../../tests/manual/gemini-3-8/README.md)

## 1. 판정

**유료용 키의 제한된 직접 호출은 통과했지만, 앱에 바로 적용할 준비는 안 됐다.**
서버·클라이언트 허용목록과 capability/thinking 등록이 없고, 기존 Gemini tool intent는 2.5를 사용한다.
직접 호출 성공을 실제 앱 전체의 3.8 검증으로 해석하지 않는다.

## 2. 실행 결과

Node v24.15.0, 현재 설치 SDK·LangChain 사용. 각 사례/키 선택당 1회이며 반복 통계가 아니다.
`paid`는 `API_KEY_TIER1`, `free`는 기본 키 풀의 이름순 첫 유효 키다. 실제 프로젝트 결제 상태는 조회하지 않았다.
키 회전·재시도 없이 유료용 9회, 기본 키 7회 요청. 기본 키는 429에서 즉시 중단했다.

|---|---|---|

성공한 SDK 응답의 `modelVersion`은 `gemini-3.8-flash`였다.
LangChain은 모델명을 반환하지 않아 null로 기록했다. 명시한 3.8 모델로 직접 호출했으며 앱의 자동 강등은 실행하지 않았다.
기본 키의 429는 쿼터 오류로 분류했으며 RPM/TPM/RPD 중 어느 한도인지는 이번 기록으로 확정하지 않는다.
최초 샌드박스 실행은 통신 오류로 중단됐고, 네트워크 허용 후 위 결과를 얻었다. 이를 모델 오류로 집계하지 않았다.

## 3. 확인한 문제와 주의점

- **thinking 미등록의 영향:** 현재 `resolveThinkingConfig`는 3.8 일반/렌더러에 undefined를 반환한다.
  같은 산술 입력에서 명시적 low는 사고 토큰이 보고되지 않았고, 설정 생략은 유료용 87·기본 키 134 사고 토큰을 보고했다.
  유료용 단발 지연은 1.962s 대 7.339s. 일관된 속도 우위의 증명은 아니지만 기본 설정 방치의 차이는 관찰됐다.
- **minimal 금지:** 양쪽 키 모두 예상된 400 거부. 최소 레벨·복구 목표를 모델 표에 명시해야 한다.
- **budget 0:** 양쪽 키에서 수용됐다. 단발 산술 성공만으로 모든 미디어/긴 입력 경로의 budget 호환성을 주장하지 않는다.
- **무료 경로 미완주:** 차트 요청에서 429. 그 이후 긴 히스토리·LangChain은 기본 키로 미실행이다.
- **앱 연결 검사:** 9개 항목 중 기본값 서버/UI 일치만 통과, 나머지 8개는 미등록 관련 차단이다.
  `noMinimal: false`도 현재 minimal을 주입한다는 뜻이 아니라 지원 표가 없어 정책을 확인할 수 없다는 뜻이다.
- **검증 범위:** 차트 한 종류의 JSON·수치 보존, 약 1만 입력 토큰의 12턴 합성 히스토리 회수,
  합성 add 함수 인자 생성, 단독 LangChain 텍스트 호출까지만 검증했다.
  실제 카드·검색 grounding·미디어·전체 그래프/SSE/UI·재시도/fallback·반복 품질/비용은 미검증이다.

## 4. 다음 단계

1. 기본 키 429의 프로젝트 한도 상태를 확인한 뒤 중단된 사례를 재검증한다. 키 회전으로 실패를 숨기지 않는다.
2. 3.8 후보 등록 시 실제 thinking 함수·서버 허용목록·UI·capability를 함께 연결한다.
3. 3.6/3.7 비교, 반복 표본, 미디어·검색·실제 카드 경로를 검증한 뒤 선택 옵션 공개를 판단한다.
   하드닝 1·2 선행과 기본 승격 분리 원칙은 유지한다.

## 5. 검증 산출물

- `check-integration.mts`: 오프라인 실제 정책 import. 현재 종료 2(도입 미준비).
- `live-compat.mts`: 기본 dry-run, 명시적 live, 요청/토큰/시간 제한, 키 회전 없음, JSON 보고서.
- 스크립트 타입 검사와 dry-run 통과. 문서 링크·diff 확인.
- 실행 JSON은 로컬 `/tmp/gemini-3-8-{paid,free}-extended.json`과 `/tmp/gemini-3-8-integration.json`.
  `/tmp` 파일은 영구 보관되지 않으므로 핵심 판정과 수치를 이 로그에 기록했다.


## 6. 후속 — 여러 인텐트와 실제 멀티턴 그래프

`live-intents-multiturn.mts`·`scenarios.mts`를 추가했다. 3.8을 프로덕션에 등록하지 않고
실제 router·그래프·히스토리 변환·스트림 dispatcher를 실행한다. HTTP 인증/모델 허용목록은 우회하는 수동 프로브다.
앱 설정은 유지하되 프로브 전송 경계에서 출력 4096토큰 상한을 적용한다.
검색/외부 도구 네트워크는 막고, 요청·응답 모델을 추적한다.

### 6-3. 처음 실패로 보였던 세 건은 테스트 기대값 문제였다

1. 보관 코드: 출력의 밑줄은 제거하면서 기대값의 밑줄은 남겨 ALPHA_731을 오답으로 판정했다.
   판정기를 고쳤고 중단됐던 후속 대화를 포함해 기억 시나리오 3턴을 다시 실행했다.
2. 분자식: `\text{C}_2\text{H}_6\text{O}`를 C2H6O와 다르게 보던 오류.
   LaTeX/유니코드 표현을 정규화한 뒤 저장된 실제 출력을 **오프라인으로 재검사**했다. 모델 재실행은 하지 않았다.
3. 월드컵: 연도 포함 질의는 `router.ts`의 기존 후처리상 general로 내려간다.
   기존 결과를 해당 정책 기준으로 재검사하고, 연도 없는 현재 대회 sports와 명확한 medical_qa 사례를 추가 호출했다.

따라서 최초 graph 보고서는 10턴 중 2건 FAIL·2턴 미실행, 후보 routing 보고서는 24건 중 1건 FAIL이었다.
원본을 덮어쓰지 않고 `review-results.mts`로 출처·원래 판정을 보존해 재평가했다.
기억 대화 재실행과 추가 라우팅까지 합친 고유 사례가 위 12턴/26건이다.
판정기에는 올바른 표현뿐 아니라 다른 코드·다른 분자식·수정되지 않은 차트·JSON 파손을 거부하는 10개 대조 검사를 넣었다.

### 6-4. 남은 범위

- 검색 grounding, 실제 외부 도구 조회·카드 생성과 그 뒤 멀티턴은 미실행이다.
- paper/약국/병원/법률 등은 이번에 라우팅만 확인했다. 도구 intent의 현재 2.5 고정을 해제한 결과가 아니다.
- 무료 기본 키 반복 안정성, 3.6/3.7과 같은 조건의 비교, HTTP/SSE 전체 응답 계약·브라우저 화면은 후속이다.
- 생산 코드 등록과 thinking 표 연결이 여전히 필요하다. 이번 그래프는 미등록으로 생긴 기본 thinking도 그대로 사용했다.

후속 검증의 Gemini HTTP 요청은 최초 graph 20회 + 기억 재실행 6회 + 후보 router 23회 + 추가 router 2회 = 51회다.
1차 호환성 검증과 별도 집계이며, 실제 비용을 추정 단가로 확정하지 않았다.
스크립트 타입 검사·dry-run·판정기 10건·오프라인 재평가·문서 링크·diff 검사를 수행했다.

## 7. 3.7과 3.8 생성 성능 비교 — 현재 표본에서는 3.7 유지

`compare-models.mts`로 12개 사례를 모델당 3회씩 실행했다. 총 72회다.
두 모델에 같은 `API_KEY_TIER1`, 명시적 `LOW`, 출력 4096토큰, 요청별 45초 상한을 적용했다.
각 쌍의 시스템 프롬프트·질의·합성 히스토리는 SHA-256 해시가 같으며, 모델 실행 순서를 교차했다.
라우터·검색·외부 도구·미디어·브라우저를 제외해 생성 모델 자체를 비교했다.

| 지표 | Gemini 3.7 Flash | Gemini 3.8 Flash |
|---|---:|---:|
| 결정론적 구조·값 검사 | **36/36** | **36/36** |
| 전체 완료시간 중앙값 | **1.116s** | 1.731s |
| 첫 텍스트 시간 중앙값 | **0.979s** | 1.165s |
| 전체 완료시간 평균 | **1.798s** | 2.715s |
| 최댓값 | **4.574s** | 23.817s |
| 5초 초과 | **0/36** | 2/36 |
| 입력 토큰 합계 | 217,095 | 217,095 |
| 출력 토큰 합계 | **7,390** | 7,549 |
| 보고된 사고 토큰 | 0 | 0 |

36개의 같은 입력 쌍 중 3.8이 빠른 경우는 11개, 3.7이 빠른 경우는 25개였다.
쌍별 `3.8/3.7` 완료시간 비율 중앙값은 **1.125**로, 이 표본에서는 3.8이 약 12.5% 느렸다.
23.817초 이상값 한 건을 제외해도 비율 중앙값은 **1.114**다. 첫 텍스트 비율 중앙값도 1.133이었다.
출력 토큰은 3.8이 159개(약 2.2%) 많았으나, 이 차이를 청구 비용 차이로 단정하지 않는다.

사례별 완료시간 중앙값도 12개 중 10개에서 3.7이 빨랐다. 3.8이 앞선 것은
차트 뒤 새 주제 산술(0.972s 대 1.018s)과 천문 JSON(3.069s 대 3.161s)뿐이며 차이는 작았다.
3.8은 한 회차에서 `42`를 반환하기까지 23.817초가 걸렸다. 사고 토큰은 보고되지 않았고
첫 텍스트도 23.815초 뒤에 왔다. 원인은 확인하지 못했으므로 결과에서 제외하지 않았다.

**현재 결론:** 두 모델 모두 구조적 호환성은 통과했지만, 3.8의 품질 우위는 이 검사로 확인되지 않았고
지연과 출력 토큰은 3.7이 유리했다. 따라서 3.8을 기본 모델로 승격할 근거가 없다.
하드닝 후 선택 옵션으로 제한 공개하는 판단은 가능하지만, 기본값 후보는 3.6과의 비교 및
검색·실제 도구·미디어 품질 측정까지 마친 뒤 다시 정한다.

이 비교가 말하지 못하는 범위도 분명하다. 구조·값 보존 검사이지 자유서술의 사실성·설명 품질을
사람이나 독립 판정기로 비교한 것이 아니다. 각 사례 3회라 낮은 빈도의 실패율이나 통계적 우월성을
추정할 수 없다. 멀티턴은 두 모델의 sampled 답변이 다음 입력을 다르게 만드는 혼선을 피하려고
