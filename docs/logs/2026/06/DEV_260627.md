## §1. 업로드 영상이 분석 안 됨 — mp4가 image/jpeg로 둔갑

### 증상
웹에서 mp4 영상 업로드 후 "영상 분석" 요청 시, 모델이 분석 대신 **"어떤 영상을 분석해 드릴까요? URL을 알려주시거나 업로드해 주세요"**라고 되물음 — 영상 데이터가 모델에 안 닿은 상태.

### 원인 (mimeType 유실 2단)
1. **[chat/route.ts](../../../../app/api/chat/route.ts)**: 업로드 영상은 `att.mimeType='video/mp4'`로 보존된 채 스토리지 URL이 됨. 그런데 공개 URL 첨부 처리에서 **PDF가 아니면 `image_url`로 감싸며 mimeType을 안 넘김** → `video/mp4` 정보 유실. (현재 턴 + 히스토리 양쪽)
2. **[sdk-contents.ts:45-49](../../../../server/agent/nodes/sdk-contents.ts#L45)**: URL에서 mime 재추론하는데 `.png/.webp/.gif/.pdf`만 체크 → **`.mp4`는 모르므로 `image/jpeg`로 확정**.

→ 영상이 `image/jpeg` 라벨로 Gemini에 전송 → 모델이 영상으로 못 받음. (base64 인라인 영상은 `data:video/mp4;...`로 mime 보존돼 동작했음 → "작은 영상만 됐던" 이유)

### 수정 ([chat/route.ts](../../../../app/api/chat/route.ts), 현재 턴 + 히스토리 2곳)
```
if (att.mimeType.startsWith('image/')) → image_url
else → fileData { fileUri: url, mimeType: att.mimeType }   // pdf/video/audio: 실제 mimeType 보존
```

### 검증
- 한복 입은 아기 표범 10초 mp4 정상 분석(민트색 한복·한옥 배경·피아노 음악·표정 변화 정확). **Gemini가 Supabase 스토리지 영상 URL을 fileData로 처리함을 확인** → Files API 경로 불필요.
- tsc 0.

## §2. 영상 분석 출력 포맷 — URL 요약식으로 통일

### 문제
첫 동작 시 출력이 `[00:00]` 타임스탬프를 절마다 흩뿌리고(같은 값 중복), 헤딩 없는 평면 산문이라 어수선. 원인: [prompt.ts](../../../../server/agent/prompt.ts) 직접 영상 분석 지시가 "Use approximate timestamps (e.g., [01:00])"로 모호.

### 설계 판단 — YouTube 포맷 아님
업로드 영상은 YouTube와 본질이 다름:
- **클릭 타임스탬프 불가** (점프할 URL 없음) — YouTube 리치 포맷의 핵심 가치가 무용
- 보통 **짧은 클립** → "Introduction → 번호 섹션 → Conclusion" 무거운 구조 과함

→ **업로드 영상 = URL 요약식 간결 포맷**(`한 줄 요약 / 주요 내용 / 핵심 포인트`)이 적합. YouTube(URL 기반)는 기존 리치 포맷 + 클릭 타임스탬프 유지.

### 수정 ([prompt.ts](../../../../server/agent/prompt.ts) Video Analysis Fallback)
- 직접 영상(fileData, NO TRANSCRIPT) → `[URL_CONTENT]`와 **동일 포맷**(`${lbl.summary}` 1문장 → `${lbl.content}` 불릿 → `${lbl.points}` 2~4개)
- 타임스탬프는 **장면 전환 불릿 맨 앞에만** `[MM:SS]`, 문장 중간·중복 금지, 30초 이하 클립은 생략
- **도입 문장 금지** — `${lbl.summary}` 헤딩으로 바로 시작(`"이 영상은 …를 보여줍니다"` 류 군더더기 제거)

### 검증
- 재테스트: 한 줄 요약 → 주요 내용(장면별 `[00:00]/[00:01]/[00:04]` 불릿) → 핵심 포인트 구조로 깔끔 출력. 도입 문장 금지 규칙 추가 후 재확인.
- 프롬프트 변경이라 출력 확률적 — dev 재테스트 권장.

## §3. SDK/LangChain 호출 타임아웃 + 3.5 timeout→2.5 강등

### 증상
movie 질의(2.5 LangChain) 중 `[GoogleGenerativeAI Error]: ...gemini-2.5-flash:streamGenerateContent: fetch failed` 발생. **`POST /api/chat 200 in 5.1min`** — fetch 끊김(WSL2 네트워크 블립)인데 호출에 타임아웃이 없어 OS 소켓 타임아웃(~5분)까지 매달림. production(Vercel 60s 캡)이면 60s에 잘려 사용자에겐 에러만.

### 원인
- **SDK 경로([generator.ts](../../../../server/agent/nodes/generator.ts))**: `genai.models.generateContent` 호출에 `abortSignal` 없음 → 행.
- **LangChain 경로([langchain-path.ts](../../../../server/agent/nodes/langchain-path.ts))**: `llmWithTools.invoke(messages)`에 `signal` 없음 → 행.
- 기존 `unavailableDowngrade`(3.5→2.5)는 **503에서만** 발화. 느림/timeout은 강등 안 됨 — 무료티어 3.5가 혼잡으로 느릴 때 키 로테이션만 돌다 소진.

### 수정
1. **호출당 25s 데드라인**(`SDK_CALL_TIMEOUT_MS`/`LC_CALL_TIMEOUT_MS` = 25_000):
   - SDK: attempt마다 `AbortSignal.timeout(25s)` 1개 생성 → 그 attempt의 모든 서브콜(stage1/single-pass/retry 등) `config.abortSignal`에 주입. (`httpOptions.timeout`은 "자동 재시도" 경고가 있어 회피, 결정적 abort 채택)
   - LangChain: `.invoke(messages, { signal: AbortSignal.timeout(25s) })`.
2. **timeout→2.5 강등**: [generator.ts](../../../../server/agent/nodes/generator.ts) catch에서 강등 트리거를 `isUnavailable`→`(isUnavailable || isTimeout)`로 확장. **다른 키가 없어도** 방금 강등했으면 같은 키로 2.5 재시도(모델이 바뀌므로 의미 있음 → 단일 키 환경 대응).
3. [retry.ts](../../../../server/agent/nodes/retry.ts) `isTimeoutError`에 `AbortSignal.timeout` 발화(`TimeoutError`/`AbortError`)와 `fetch failed` 추가 → abort가 timeout으로 분류돼 강등/재시도 경로로.

### 왜 25s인가 (Vercel 60s 하드캡)
"1분 넘으면 2.5 재시도"는 불가 — 첫 시도가 60s를 다 쓰면 함수가 죽어 재시도 예산이 없다. **25s 컷이면 25s(3.5)→강등→25s(2.5) ≈ 50s < 60s**로 production 캡 안에서 폴백 완결. 건강한 무료티어 3.5는 보통 <15s라 정상 응답은 거의 안 잘림.

### 검증
- tsc 0. 로컬 5분 행 → 25s abort + 2.5 강등으로 단축(재현은 네트워크 블립 의존).
- 주의: movie 등 LangChain 인텐트는 floor가 2.5라 강등 없이 25s 빠른 실패 + 다음 키 재시도.

## §5. YouTube 요약 전부 타임아웃 — §3의 25s 컷이 영상 분석을 끊은 회귀

### 증상
며칠 전까지 정상이던 YouTube 요약이 **전부** 타임아웃(영구 "..."). Vercel 로그 `Execution Duration 1m/1m`, `gemini-2.5-flash:generateContent`, status 0.

### 원인 (§3 25s 일률 적용의 부작용)
§3에서 movie/grounding 케이스용으로 넣은 `SDK_CALL_TIMEOUT_MS=25s`를 **모든** SDK 호출에 일률 적용했는데, YouTube 영상 single-pass([generator.ts](../../../../server/agent/nodes/generator.ts) ~327)에도 걸렸다. YouTube 영상 분석은 프로파일이 정반대:
- 영상 토큰이 무거운 **단일 heavy 호출**이 60s 예산 대부분을 정당하게 소모(보통 ~30~40s) → 25s 컷이 정상 분석을 중단.
- abort가 `isTimeout`으로 분류 → 키 로테이션(또 25s) → 3.5 폴백(또 25s, **무료티어 영상은 2.5보다 더 느림**) → 누적 60s 천장 초과 → 함수 강제종료 → 전부 실패.
- 25s는 `25s(3.5)→25s(2.5)<60s`이고 2.5가 더 빠른 movie 케이스용. YouTube는 폴백이 더 느려 캐스케이드가 손해.
- **회귀 출처**: aa9d701(§3)이 abort를 추가한 유일한 generator 커밋. 그 전엔 per-call 타임아웃 없어 단일 호출이 자연 완료.

### 수정 ([generator.ts](../../../../server/agent/nodes/generator.ts))
- `YOUTUBE_CALL_TIMEOUT_MS=48_000` 신설. 영상 턴(`isYtVideoTurn = isYoutubeRequest && hasVideoData`)만 attemptSignal 데드라인을 48s로(그 외 25s 유지). 48s = 정상 영상 분석 커버 + DB write/return ~10s 여유(60s 캡 안).
- **timeout 캐스케이드 차단**: 영상 턴 timeout(`isYtVideoTurn && isTimeout`)이면 `ytPrimaryTimedOut=true` 후 즉시 break — 키 로테이션 안 함(이미 48s 소진, 또 48s는 캡 초과).
- **3.5 폴백 가드**: `!ytPrimaryTimedOut`일 때만 폴백(빠른 실패 429/500/빈응답에서만). timeout 후엔 LangChain 폴백이 LLM 호출 없이 즉시 "일시 불안정" 에러 반환([langchain-path.ts](../../../../server/agent/nodes/langchain-path.ts) ~55) → ~48s에 깔끔 종료.

### 검증
- tsc 0. 정상 영상은 단일 48s 안에 완료, 진짜 행은 48s + 즉시 에러로 ≤60s.
- 프로덕션 재테스트 권장(실 API·영상 의존). 일부 긴 영상이 여전히 잘리면 52s로 상향 여지.
