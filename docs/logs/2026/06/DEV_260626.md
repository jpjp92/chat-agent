## §1. URL fetch 폴백 최적화 — wikidocs 직접 fetch 스킵 + 비-wikidocs 2단계

### 증상 / 동기
- wikidocs는 Cloudflare가 **항상 403 "Just a moment" 챌린지**를 반환(직접 fetch 100% 무용). 그런데도 캐시 미스마다 10s 직접 fetch를 먼저 시도 → 순수 낭비.
- 비-wikidocs 폴백이 `render_js=true + premium_proxy`(40s) 단일이라, aitimes 같은 **SSR 뉴스/블로그도 불필요한 Chrome headless**를 돌림.

### 수정 ([app/api/fetch-url/route.ts](../../../../app/api/fetch-url/route.ts))
| # | 변경 | 효과 |
|---|---|---|
| 1 | **wikidocs 직접 fetch 스킵** | `useCloudflareUnblock`이면 `directFetchBlocked=true`로 시작 → 곧바로 CF 우회 체인. 캐시 미스 첫 호출 ~10s 단축 |
| 2 | **비-wikidocs 폴백 2단계** | `scrapingBeeStaticFetch`(render_js=false, 15s) 신설 → 실패 시 기존 render_js(40s). SSR 사이트는 static(~3-5s)에서 종결 |
| 3 | 캐시 provider 값 `scrapingbee-static` 추가, 로그 라벨 `ScrapingBee(static)`/`(render)` 구분 | — |

wikidocs 우회 체인(ScrapingBee render → browserless → ScraperAPI)은 변경 없음.

### 검증
- wikidocs.net/31695 직접 fetch: HTTP 403 + `<title>Just a moment...</title>` 확인 → 스킵 정당.
- tsc 0.

## §2. URL 요약 모델 정책 — 2.5-flash + thinking off 고정 (측정 기반)

### 동기
URL 본문 주입 턴(`[URL_CONTENT:`)은 Google Search OFF + **본문이 답을 결정하는 추출성 작업**. 기본 모델 3.5-flash는 무료티어 throughput 한계로 20~30s를 끌거나(메모리 `35-flash-free-tier-throughput`) 503 폭주 시 무응답. 외부 API 도구 인텐트와 같은 논리로 throughput 좋은 2.5 고정이 타당한지 **측정으로 검증**.

### 측정 (scripts/test-url-summary-*.ts)
**A. 4조합 (2.5/3.5 × thinking on/off), aitimes 1건:**
| 조합 | 지연 | 비고 |
|---|---|---|
| 3.5 thinking-ON | 64.0s | 60s 캡 초과 |
| 2.5 thinking-OFF | **5.6~6.1s** | 최적 |
| 2.5 thinking-ON | 8.7~10.1s | thinking 토큰만 추가, 품질 차이 미미 |

**B. 2.5 vs 3.5 (둘 다 OFF) × URL 3유형 (일반 위키피디아 / aitimes 뉴스 / wikidocs 기술):**
| URL | 3.5 OFF (무료) | 2.5 OFF (무료) |
|---|---|---|
| 일반 | 97.1s (4 retries) | **15.2s** |
| aitimes | 86.7s | **5.2s** |
| wikidocs | **ERROR** (12키 전멸 503) | **5.9s** |

품질(육안): 3유형 모두 2.5가 3.5와 **동등**(일반은 2.5가 더 망라적, 뉴스 호각, wikidocs는 2.5만 답 생성). "3.5가 품질 우위"는 어느 유형에서도 성립 안 함 — 요약 품질은 주입 본문이 결정.

**C. Tier1(유료) 키로 재측정 — 무료 503의 진짜 원인 규명:**
| URL | 3.5 OFF (Tier1) | 2.5 OFF (Tier1) |
|---|---|---|
| 일반 | 9.3s | 14.7s |
| aitimes | 6.2s | 4.8s |
| wikidocs | 6.4s | 7.3s |

→ **무료 86~97s/ERROR는 3.5 모델 탓이 아니라 무료티어 503 혼잡 탓**으로 확정. Tier1에선 3.5가 6~9s 정상 + 품질 미세 우위(간결·정제).

### 수정
- [generator.ts](../../../../server/agent/nodes/generator.ts): `hasUrlContentForModel = state.webContent.includes('[URL_CONTENT:')` → true면 `resolvedModel = 2.5`. YouTube 영상 턴 2.5 고정과 동일 분기.
- [generation-config.ts](../../../../server/agent/nodes/generation-config.ts): `resolveThinkingConfig`에 `hasUrlContent` 추가 → 2.5 경로에서 URL 콘텐츠면 `thinkingBudget:0`.

### 이미지·영상 미디어 턴 (동일 정책 확장)
이미지/업로드 영상도 멀티모달이라 무료 3.5에서 동일 타임아웃. 측정: 무료 3.5 이미지 분석 **56.4s**(60s 캡 직전) vs 2.5 **5.0s**, **Tier1 3.5는 3.5s**(2.5보다도 빠름) — URL과 동일하게 "56s는 모델이 아니라 무료티어 throughput 탓" 확정. 품질은 호각(차트 수치 정확, 알약은 3.5가 더 상세).
- [generator.ts](../../../../server/agent/nodes/generator.ts): `isMediaTurn = hasMultimodalContent && !hasDocumentContent`(이미지·영상, PDF/문서 제외) → `effectiveModel = 2.5`. YouTube 핀(`isYoutubeRequest`)이 못 잡는 **업로드 영상**까지 커버.
- [generation-config.ts](../../../../server/agent/nodes/generation-config.ts): 미디어 턴 → `thinkingBudget:0`.
- **PDF/문서(`hasDocumentContent`)는 제외** — 16384토큰 긴 출력 기대 경로라 별도 측정 후 결정(보류).

### 멀티턴 거동 (의도된 동작)
- **URL**: `webContext`는 매 턴 `''`로 초기화([useChatStream.ts:246](../../../../src/hooks/useChatStream.ts#L246)), 현재 메시지 URL만 `[URL_CONTENT:`로 채움 → URL 재전송 안 한 후속은 3.5 복귀(단 후속 3.5는 기사 전문 아닌 직전 요약본 컨텍스트).
- **이미지/영상**: chat route `isRecent = index >= array.length - 3`([route.ts:57](../../../../app/api/chat/route.ts#L57))로 **최근 3턴 미디어만 데이터 재전송**, 그 외는 `[Attached File]` 텍스트 강등. → 미디어 첨부 턴 + 윈도우 내 후속은 `hasMultimodalContent=true`라 **2.5 유지**(재전송되는 동안 방어), 윈도우 밖이면 텍스트 전용 → **3.5 복귀**. YouTube 영상 턴 패턴과 일치.

### 결정 / 후속
- **기본값 = 무료 2.5 OFF 유지.** 비용 $0, 5~15s, 60s 안전, 품질 동등.
- **하이브리드 Tier1 폴백은 백로그**([TODO.md](../../../TODO.md) "지연 단축 후속"): 무료 2.5 우선 → 503·전키 소진 시 Tier1 3.5 폴백. 전제: `config.ts`가 현재 `API_KEY_TIER1` 미배선.

## §3. SDK 경로 503 다운그레이드 (3.5 → 2.5)

### 증상
URL 요약(검색 OFF → effectiveModel=3.5) 턴에서 3.5 503 발생 시, [generator.ts](../../../../server/agent/nodes/generator.ts) SDK catch가 503도 키 로테이션 대상으로 처리 → **12개 키를 같은 혼잡 3.5에 던지고 전멸**(실측 26회 재시도/33~115s). 503은 키 문제가 아니라 모델 측 혼잡이라 다음 키도 동일 503.

### 수정
- 첫 503에서 `unavailableDowngrade=true` → 이후 attempt의 `effectiveModel`을 2.5로 강등(throughput 양호). `resolvedModel === FLASH_3_5`일 때만(이미 2.5거나 YouTube면 무의미).
- `Starting SDK stream` 로그를 `resolvedModel` → `effectiveModel`로 정정(강등 시 실제 모델 표시).
- DEV_260624 §"503 처리 확장 점검" 백로그의 SDK 경로분 해당(Stage2는 이미 수정됨).
