## 2. kordoc 한글문서 파싱 연동 — 검토·검증·계획

`.hwpx`만 JSZip `<hp:t>` 텍스트 추출(표·구조 소실), 구형 `.hwp`/`.hwp3`/`.hwpml`은 미지원인 현 상태를 [`kordoc`](https://www.npmjs.com/package/kordoc) v3.1.1 서버 라우트로 개선하는 방안. 레퍼런스(`reference/kordoc/`: 통합가이드·route.ts·kordoc-tester.html) 기반.

### 2-1. 스코프 확정
- **HWP 계열 4종(`.hwpx`/`.hwp`/`.hwp3`/`.hwpml`)만 kordoc 경유.**
- **`.pdf`는 현행 유지** — Gemini 네이티브 멀티모달 직접 전달 중이라 kordoc 경유 시 레이아웃·이미지 인식 손실(회귀). 라우트 `SUPPORTED`에서 `.pdf` 제외.
- `.docx`(mammoth)·`.xlsx`(XLSX)도 현행 충분 → 유지.

### 2-2. 검증 스크립트 3종 작성 + 실측 (정부 사업계획서 4종)

| 스크립트 | 목적 | 결과 |
|---|---|---|
| `scripts/test-kordoc.mjs` | 파싱 품질 | **4종 전부 success, 표 `<table>` 구조 완벽 보존**(colspan/rowspan). 32MB도 581ms |
| `scripts/test-kordoc-pipeline.mjs` | Storage 왕복 end-to-end | signed upload→download→parse→remove **전 단계 동작**. 32MB 왕복 4초 |
| `scripts/test-kordoc-latency.mjs` | 전송 아키텍처 레이턴시 | 직행 multipart가 Storage 경유 대비 **55~62% 단축** |
| `scripts/test-kordoc-compare.mjs` | 기존 vs kordoc | 문체부 hwpx: 기존 25,007자(평문) vs kordoc 31,173자(표 30개) |

검증 데이터: `reference/kordoc/` 문체부(3.64MB hwpx)·중기부(3.91MB)·데이터바우처(1.71MB)·NIA(32MB).

### 2-3. 핵심 발견
- **파싱 품질·속도 우수** — `.hwp` 바이너리·`.hwpx` 모두 표/제목/리스트 보존. 파싱은 전체 레이턴시의 <10%.
- **셀 경계 보존이 진짜 가치** — 기존 JSZip 방식은 표 셀이 공백으로 뭉개져 "용어=정의" 쌍 구분 불가. kordoc은 `<th>`/`<td>`로 명확 → 표 질의·요약 정확도 직결. 정부 문서는 대부분 표 양식이라 영향 큼.
- **🔴 전송 방식 재설계** — 4종 중 3종이 base64 변환 시 Vercel 4.5MB 본문 한도 초과. 레퍼런스의 인라인 base64 POST는 실제 문서 대다수에서 413 실패.

### 2-4. 설계 결론 — 4MB 임계값 라우팅
- **`raw ≤ 4MB` → 직행 multipart POST** (download hop 없음, 55~62% 빠름). base64 아닌 raw 바이너리라 +33% 부풀림 회피, 가용 범위 넓음.
- **`raw > 4MB` → Storage 경유** (`create-signed-url`→직접 PUT→`{filePath}`→서버 download→parse→remove). Vercel 한도 우회.
- 임계값 4MB = Vercel 4.5MB − multipart 오버헤드/마진 0.5MB.
- **첨부 시점 백그라운드 파싱** — docx/xlsx처럼 `processFile`에서 추출해 응답 critical path 밖으로(2~4초 체감 제거).
- `.hwpx` kordoc 실패 시 기존 JSZip `<hp:t>` 폴백 유지.

**레이턴시 레버 종합(계획 §3.5):** L1 백그라운드 파싱 · L2 4MB 직행 multipart · **L3 `preferredRegion='icn1'` 라우트 고정(필수 — 누락 시 기본 iad1로 태평양 횡단+Storage leg 악화)** · L4 마크다운 길이 상한(大문서 LLM 지연 절감) · L5 응답 페이로드 최소화. ⚠️ §1.5 레이턴시 벤치는 로컬→Supabase 측정이라 프로덕션(icn1→Supabase)과 절대값 상이 → **Supabase 리전 ap-northeast 여부 검증 필요**.

### 3-2. 수정 구현 완료

#### generator.ts — `dropImageForSearch` 가드 추가
- **조건**: `intent==='general'` && 현재 턴 이미지 없음(`!_currentTurnHasImage`) && history에 이미지 있음(`_historyHasImageForGuard`) && `_explicitSearchForGuard`.
- **동작**: `forceTextOnly = true`(SDK contents 조립 시 이미지 파트 제거) + `useGoogleSearch` 강제 허용(`!historyHasImage || dropImageForSearch` 조건으로 변경).

#### `_explicitSearchForGuard` — 라우터 `needsSearch` 우선, 키워드 정규식 보조
- **1순위**: `state.needsSearch === true` — 라우터 LLM이 문맥을 파악해 이미 판정한 값 직접 사용. 키워드가 없어도 의미상 검색 필요 케이스를 모두 커버.
- **2순위**: 키워드 정규식(`검색|팩트체크|웹에서|확인해|논문|verify|fact-check` 등) — 라우터가 놓친 엣지케이스 보조 안전망.
- **배경**: 초기 구현은 키워드 정규식만 사용했으나, "팩트체크를 위해 웹에서 해당 연구가 있는지 검토해보자"처럼 키워드 없이 의미상 검색을 요구하는 쿼리를 누락. 라우터 LLM이 `needsSearch=true`로 정확히 판정했음에도 제너레이터가 이를 무시하던 구조적 불일치를 해소.

#### prompt.ts — `[CRITICAL — ABSOLUTE RULE: NEVER FABRICATE SOURCES]` 최상단 삽입
- 모든 포맷 지시보다 우선하는 불변 규칙으로 `getSystemInstruction` 상단 배치.
- `google_search` 도구가 **실제 호출**된 경우에만 `[1]`·참고 자료·URL·"검색 결과" 표현 허용.
- 미호출 시 인용 마커·출처 섹션·검색 암시 표현 **일절 금지**. 검색 불가 시 `"실시간 검색 없이 학습된 지식 기준으로 답합니다"` 명시 요구.

사용자가 "전체 조별 순위 검색해서 정리" 요청 시 일부 조만, 조마다 신선도가 다르게 나옴. 체계적 디버깅으로 원인 추적:

|---|---|---|
| 출력 토큰 제한 | 로그 `maxTokens: 32768`, 응답 수백 토큰 | ❌ 무관 |
