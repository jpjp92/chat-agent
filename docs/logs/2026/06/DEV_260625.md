## §1. fotmob(SPA) URL 요약이 본문 대신 약관만 → 모델이 제목으로 추정

### 증상
모바일에서 fotmob 이적 기사 링크(`/embed/news/...`) 요약 요청 시, 모델이 "약관 안내 정보만 포함되어 있고 본문은 없다"고 **정확히 보고한 뒤**, 곧바로 "학습된 지식 기준으로 답합니다"라며 **제목 기반으로 기사 내용을 지어냄**(레알 마드리드 올리세, 바르셀로나 래시포드 등).

### 원인 (2단)
1. **fetch가 푸터/약관만 추출** — fotmob `/embed/news`는 React SPA라 정적 HTML의 `<article>`이 비어 있음(bodyText 0자). 직접 fetch는 200 OK지만 본문 없음 → 일반 URL 폴백인 **jina(`r.jina.ai`)는 JS 렌더를 안 해** 968바이트 푸터(`© Copyright`, `Terms of use`, "automatic services (robots, crawler) not permitted", "Follow us")만 반환. 이게 `length≥100` 통과 + `isJinaSecurityBlock` 미감지(CF/CAPTCHA 아닌 단순 푸터)라 **정상 `[URL_CONTENT]`로 수용**됨.
2. **숨은 함정** — `bodyText<300`이고 폴백 실패 시, 마지막 분기가 `extracted.content`(제목+desc만)가 비어있지 않아 **제목만 담긴 콘텐츠를 반환**하는 fall-through 경로 존재. jina가 실패했어도 추정 유발.

→ 클라이언트([useChatStream.ts:351](../../../../src/hooks/useChatStream.ts))는 `[FETCH_ERROR]`로 시작하지 않는 응답을 정상 `[URL_CONTENT]`로 주입 → LLM이 푸터를 본문으로 오인. (서버가 `[FETCH_ERROR]`를 줘야 클라가 `[URL_FETCH_FAILED]` 주입 → chat route가 LLM 호출 없이 깔끔한 "원문 못 가져옴" 메시지로 종료, 추정 원천 차단.)

### 수정 ([app/api/fetch-url/route.ts](../../../../app/api/fetch-url/route.ts))
| # | 변경 | 효과 |
|---|---|---|
| 1 | **jina(`r.jina.ai`) 제거** | JS 못 거는 jina가 SPA에서 푸터만 긁어와 추정 유발하던 경로 삭제 |
| 2 | **일반 URL 폴백 → ScrapingBee(`render_js`)** | `renderFallback()`: wikidocs는 기존 CF 우회 체인, 그 외는 ScrapingBee 단일 |
| 3 | **폴백 실패 분기 terminal화** | `bodyText<300` 시 제목만 반환하던 fall-through 제거 → 폴백 실패면 항상 `[FETCH_ERROR]` |
| 4 | **`isBoilerplateOnly` 게이트** | 푸터·약관·"robots/crawler not permitted"만 추출된 결과(1500자 미만)도 실패 처리 — ScrapingBee 수용 조건 + 직접 추출 분기에 적용 |

### 검증
- ScrapingBee render_js 실측: fotmob embed 본문 **4,630자 정상 추출**(Enzo Fernández·Chelsea·Real Madrid 등 실제 이적 루머), cost 25 크레딧. tsc 0.
- **재발 원인 = stale 캐시**: 첫 재테스트에서 `[fetch-url] cache hit`으로 이전 jina 푸터(968B)가 Supabase `url_cache`에 14일 캐시로 남아 새 코드 실행 전 반환됨. 오염 캐시 12개 삭제(fotmob 2 + deprecated jina 11). 이후 정상 본문 요약 확인.

### 트레이드오프 / 후속
- jina(무료)로 잡히던 일부 정적·차단 사이트도 이제 ScrapingBee 크레딧 소모(SPA당 25). 단 직접 fetch로 본문 ≥300자 잡히는 일반 사이트는 폴백 미진입이라 영향 없고 **SPA·차단 사이트만** 넘어감. 14일 캐시로 반복 흡수. SPA URL 급증 시 ScrapingBee 소모 모니터링 필요.
- 새 코드는 boilerplate를 `setCached` 전에 걸러 캐시 오염 재발 없음.
- (선택·미적용) Fix B 프롬프트 가드 — ScrapingBee가 thin하게(300자 초과) 일부만 추출하면 모델이 또 채울 여지. "본문에 요청 정보 없으면 추정 말고 알려라" 규칙으로 완전 방어 가능. 이번 케이스는 해결돼 필수 아님.

## §2. 본문 추출이 잘못된 `<article>`(폰트 위젯)을 잡던 버그 — 가장 긴 블록 선택으로 수정

### 증상
§1 직후 aitimes 기사(`articleView.html?idxno=...`) 요약이 "보안 확인/접근 제한으로 본문 못 읽음"(`[FETCH_FAILED]`)으로 실패. 기존엔 정상이었음.

### 원인
- aitimes는 200 OK·128KB 정상 응답인데, `extractReadableContent`의 `cleaned.match(/<article…>/i)`가 **첫 번째 `<article>`만** 잡음 → 그게 폰트크기 조절 위젯(`"가 가 기사의 본문 내용은 이 글자크기로…"`, 29자)이라 `bodyText 29 < 300` → renderFallback → ScrapingBee도 같은 추출 로직이라 실패 → `[FETCH_FAILED]`.
- 실제 본문은 9개 `<article>`/`<main>` 블록 중 **가장 긴 것(2,015자)**에 있음. **이전엔 jina가 자체 readability로 본문을 뽑아줘 이 추출 버그가 가려져 있었음** — §1에서 jina를 제거하자 드러남.

### 수정 ([app/api/fetch-url/route.ts](../../../../app/api/fetch-url/route.ts) `extractReadableContent`)
- `match(첫 블록)` → **모든 `<article>`/`<main>` 블록을 수집해 텍스트가 가장 긴 것 선택**. 가장 긴 블록도 300자 미만이면 `null`로 보고 기존 divMatch(content-class div) → body 순으로 폴백.
- 부수 효과: 대부분의 일반 뉴스 사이트가 **직접 fetch(무료)로 처리** → ScrapingBee는 진짜 SPA·차단 사이트만 진입(크레딧 절약). 예전 jina 시대엔 이런 사이트가 불필요하게 jina로 넘어갔음.

### 결론: jina 복원·per-site 예외 불필요
aitimes 회귀는 "jina 부재"가 아니라 추출 버그였고, 가장 긴 블록 선택으로 일반 fetch만으로 해결. 최종 구조 = **직접 fetch(개선 추출) → ScrapingBee render_js(SPA·차단) → FETCH_FAILED(추정 차단)**. jina를 되살리면 fotmob 푸터 false-positive(§1)만 재발하고 ScrapingBee가 jina보다 우수해 이득 없음.

### 검증
- aitimes 직접 fetch 실측: selector `main`, bodyText **2,015자**(≥300) → 폴백 미진입. tsc 0.
- dev E2E: `POST /api/fetch-url 200 in 598ms`(ScrapingBee 미진입), 본문 기반 정상 요약 확인.
