## 2. T2 — 루트 run 메타데이터 = [turn] 값 (완료)

- 방식: 계획 후보 1. 정리 Client 가 **루트 run 의 끝 전송만** 잡아 두고, route.ts `finally` 가 `[turn]` 값을 넘기면 합쳐 보낸다.

- 값의 출처는 한 곳이다. `turn-log.ts` `turnFields()` 가 `[turn]` 줄과 LangSmith 가 쓰는 같은 필드 객체를 만든다(GPT 제안). `logTurn` 이 그 객체를 돌려주므로 블록 파싱은 한 번만 한다. `tracing.ts` `turnMetaOf()` 는 그중 키·형태를 다시 고른다.
  - 키: `intent`·`intentFrom`·`provider`·`model`·`modelDowngraded`·`search`(불리언)·`searchBy`·`sources`·`sources_official|secondary|other`·`outcome`·`errCode`·`commit`(`VERCEL_GIT_COMMIT_SHA` 앞 7자, 로컬은 `local`).
  - 빼는 것: `ms`(LangSmith 가 이미 잰다), `blocks`·`chars`, `traceId`(run ID 와 같다).
- 동시 요청이 섞이지 않게 보류와 턴 값을 모두 `traceId` 키로 관리한다.
- 해제 경로:
  - 턴 값이 루트 끝보다 먼저 오든 나중에 오든 둘이 만나는 순간 보낸다.
  - 응답 뒤 `after(flushTraces(…, traceId))` 는 **그 요청의 trace 만** 기다리지 않고 보낸다. `finally` 가 턴 값을 못 넘긴 경우를 위한 것이다.
  - 다른 요청의 trace 는 다음 기준으로만 보낸다: 루트가 끝났으면 턴 값을 30초까지 기다린 뒤, 진행 중이면 10분 뒤 숨김으로.
  - `traceId` 는 `after` 에 넘기려고 POST 시작으로 옮겼다(요청당 1개라 값의 의미는 같다).
- **격리 범위**(GPT 검토): `traceId` 별 격리는 **보류 상태(어느 trace 를 언제 놓을지)** 까지다. 놓은 뒤의 네트워크 배치는 SDK 전역 큐라서, 한 요청의 flush(`awaitPendingTraceBatches`)가 다른 요청의 이미 놓인 run 을 같이 보낼 수 있다. 값이 섞이는 것은 아니다(run 마다 자기 ID·메타데이터).
- 합치기는 교체가 아니다: 루트 끝 전송의 기존 메타데이터(허용 목록 통과분) 위에 턴 값을 얹는다. 처음 만들 때 붙은 값(`ls_run_depth`·`LANGSMITH_*`)은 원래 끝 전송에 실리지 않는다(정리에서 빠짐). 그래서 이 값들이 유지되는지는 LangSmith 서버의 병합에 달려 있고, 배포 화면에서 확인한다.

## 3. K-EXAONE 2.5 라우터 비교 — 교체 보류

외부 기획(라우터를 K-EXAONE 으로 바꿀 수 있는지 A/B)을 검토했다. 새 평가 체계를 따로 만들지 않고, 기존 `probe-router-gpt` 방식(운영 `routerNode` 의 모델 호출만 갈아 끼움)과 `router-cases` 를 그대로 썼다.

- **요청 옵션**(`probe-exaone-options`, 짧은 합성 지시, 조합마다 1회). 호스팅 API 공식 문서를 못 찾아 실제 응답으로 확인했다.
  - `reasoning_effort` 는 `low` 가 최저다. `none`·`minimal` 은 400 으로 거부된다.
  - `chat_template_kwargs.enable_thinking: false` 는 받아들여진다. 그러나 이것만 주면 추론 문장이 본문으로 새어 JSON 이 깨진다.
  - 추론 끄기 + `json_schema`(strict) 만 짧은 지시에서 JSON 만, 0.74초, 21토큰이었다.
  - 추론을 켠 채 JSON 옵션을 주면 더 느려진다: `json_object` 2.4초, `json_schema` 6.4초.
  - 스트리밍은 본문 첫 조각 1.38초, 완료 1.64초라 라우터에는 이득이 없다.
  - 추론 토큰은 `usage.reasoning_tokens`(최상위)에 온다. `completion_tokens` 에 포함되고, `completion_tokens_details` 는 null 이다.
  - 무료 한도는 **초당 1회**다(429 "second limit(1)").
- **운영 라우터 비교**(`probe-router-exaone`, `base` 세트 19개 질의 × 1회, 운영 프롬프트·규칙·후처리 그대로, Gemini 는 유료 키):

| 라우터 모델 | 최종 정확도 | 모델이 낸 의도 정확도 | 깨진 JSON | API 지연 p50 / p90 |
|---|---|---|---|---|
| Gemini 2.5-flash(현행, 생각 끔) | 19/19 | 18/19 | 0 | 1.18 / 1.35초 |
| EXAONE `low` | 19/19 | 18/19 | 0 | **5.96 / 9.94초** |
| EXAONE 추론 끔 + `json_schema` | 16/19 | 6/19 | **12** | 0.31초(중단 응답) |
| EXAONE 추론 끔 + `json_object` | 16/19 | 8/19 | 7 | 0.94초 |

- 운영 프롬프트처럼 길면, 추론을 끈 설정에서 `finish_reason: abort` 와 본문 "We{" 가 잦다. 모델이 문장부터 쓰려다 생성이 중단되는 것으로 보인다. 깨진 JSON 은 규칙 폴백으로 넘어가 3건이 틀렸다(예: "약국 창업" → `pharmacy_search`).
- 함정: EXAONE 의 429 를 라우터에 그대로 넘기면 라우터가 **Gemini 키를 블랙리스트에 올려** 이후 전부 규칙으로 분류된다(첫 실행에서 실측). probe 는 429 를 안에서 재시도하고, 실패는 500 으로 넘긴다.
- **판단: 교체 보류.** 정확도가 같은 설정은 지연이 5배이고, 빠른 설정은 JSON 이 깨진다. 무료 한도(초당 1회)로는 운영도 불가능하다. 세트를 넓혀도 지연 결론은 바뀌지 않는다고 보고 여기서 멈췄다.
- 호출: Gemini 유료 약 76회(입력 약 23만 토큰, 약 $0.08), EXAONE 약 80회(무료, 합성 질의만).
