계획: [PLAN_GEMINI_25_SHUTDOWN_261122 §10-6](../../../plans/PLAN_GEMINI_25_SHUTDOWN_261122.md) · 앞: [DEV_261124 §7](DEV_261124.md)

## 1. 문제

DEV_261124 §7 ⑥(도구 안 허가사항 검색)을 넣자 drug_info 평균이 14.3 / 17.5s → 17.4 / 18.7s 로 늘었다(2.5 / 3.5 FL).
- 전문의약품(아모잘탄)은 검색 1회만큼 +~8s — 근거를 얻는 대가.
- **타이레놀은 필요 없는 검색**(+~6s): "e약은요에 없는 첫 후보"를 검색 대상으로 잡아, 1번 후보(타이레놀정500mg, 수록) 대신 2번 후보(우먼스타이레놀)를 검색했다.

## 2. 바꾼 것 (`server/agent/drug-info-tool.ts`)

- **검색 대상 = 질문과 맞는 후보 1건**(없으면 첫 후보). 그 후보가 e약은요에 있으면 검색하지 않는다.
- **순차 유지** — e약은요 실측 486~572ms(6회). 병렬로 줄어드는 건 ~0.5s 뿐이고, 일반의약품(대부분 수록) 조회마다 버려지는 검색 호출이 생긴다. 병렬로 바꿨다가 실측 뒤 되돌렸다.
- **품목기준코드별 캐시** — 인스턴스 메모리, 6시간, 200건.
- **이름 정규화 Strategy 4(구 → 신 표기)** — 측정 중 3.5 FL 이 "아모잘탄정5/50밀리그**람**"으로 넘겨 신 표기 품목("…밀리그**램**")을 놓치고 참조 검색 경로(18s)로 빠졌다. 기존 Strategy 3 은 신 → 구 방향뿐이었다(주석의 "DB 는 구 표기 기준"도 실제는 혼재라 정정).

## 3. 측정 (`probe-tool-intents.mts` drug_info 4문항 × 2회, 모델별 별도 프로세스)

캐시가 프로세스 안에서 공유돼, 두 모델을 한 번에 돌리면 뒤 모델이 앞 모델이 채운 캐시를 써 지연이 짧게 나온다 → `ONLY=` 로 모델별 실행.

| 문항 | 2.5 (1회 · 2회) | 3.5 FL (1회 · 2회) |
|---|---|---|
| 타이레놀(e약은요 수록) | 10.0 · 13.0s | **5.0 · 4.7s**(연동 이전 수준) |
| 아모잘탄(전문, 허가사항 검색) | 17.4 · 8.1s(캐시) | 15.3 · **4.7s**(캐시) |

- 남은 것: 허가사항 검색 1회 ≈ +10s(캐시 없을 때). 이 검색은 아직 `DRUG_SEARCH_MODEL`(2.5, 기본 thinking) — §9 에서 3.5 FL `minimal` 유료 검색으로(§8-1 검색 1.9s vs 4.2s).
- 성분 질문·액제 15~25s 는 기존 참조 검색 경로(Google grounding + DDG) 몫, 이번 변경과 무관.
- 하니스 판정 함정 두 번: 도구 결과에서 "e약은요"·"[PRODUCT_LABEL_SEARCH]" 를 찾으면 **지시문 본문에 있는 같은 단어**까지 잡아 오탐 → 실제 블록 줄(`용법(e약은요·식약처):`, 검색 결과 블록)로 판정.

## 4. §9 구현 — 2.5 Flash 역할을 3.5 Flash-Lite 로 (상세: [PLAN §11](../../../plans/PLAN_GEMINI_25_SHUTDOWN_261122.md))

- `SERVER_MODELS.FLASH`(2.5)는 사용자 선택 ID 라 그대로 두고 **`ROLE_MODEL`** 을 새로 뒀다. 라우터·법령 해석·약 검색·각인/알약 비전·도구 의도 11개·미디어/URL 핀·검색 강등·PDF/MALFORMED/tool_code 재시도·제목 요약 폴백이 이것을 쓴다.
- 직접 적던 `thinkingBudget: 0`·sampling 은 `roleGenConfig`(측정표 기반) 하나로. tool_code 재시도가 선택 모델(3.6)에도 budget 을 보내던 잠재 400 도 같이 사라졌다.
- 역할 호출 키는 `getRoleApiKey`(게스트 포함 유료 키부터). 역할 모델로 가는 생성기 시도도 그 시도만 유료 키로.
- 의학 질문이 역할 모델로 가면 `medium`. 저장된 2.5 선택값은 기본 모델로.
- 스모크(운영 코드, 유료 키): 라우터 19/19 · 중앙 857ms, 도구 의도 24문항 오류 0 · 도구·카드 24/24.

## 7. 날씨 카드에 3일 전 데이터 — fetch 캐시

**증상**(dev 실화면, GPT-6 luna): "오늘 서울 날씨" 카드 출처가 OpenWeather, 예보 요일이 "일·월·화·오늘·목", 문장은 "오늘 2~5°·0%" 인데 카드 오늘 칸은 -1/9°·49%.

**원인**
- 로그: `[weather] KMA 실패 → OpenWeather 폴백: 서울 The operation was aborted due to timeout` — KMA API Hub 가 간헐 지연(로컬 4회 중 3회 9.5~9.8s 시간 초과, 정상 1.7~2.8s). 출처가 OpenWeather 인 이유.
- 카드 원문: `updatedAt` 2026-11-25(서버가 카드 만든 시각)인데 `observedAt` **2026-11-22**, `daily` 도 11-22부터 — OWM 응답 자체가 3일 전 것.
- `fetch(url, { next: { revalidate: 600 } })` 는 만료 뒤 첫 요청에 **오래된 캐시를 그대로 주고** 뒤에서 갱신한다(stale-while-revalidate). Vercel 데이터 캐시는 배포를 넘어 유지된다. 서울은 평소 KMA 가 답해 OWM 캐시가 11-22 이후 안 갱신됐고, 이번 폴백 때 그게 나갔다. GPT 와 무관(어느 모델이든 같은 카드).
- KMA 는 요청 URL 에 발표 시각이 들어가 슬롯마다 캐시 키가 달라 같은 위험이 작다.

**고침**(`server/lib/weather/index.ts`)
- OWM 현재·예보는 `cache: 'no-store'`, 좌표 변환(geocode)만 하루 캐시.
- 관측 신선도 검사 `isStaleObservation` — 관측이 3시간보다 오래됐거나 읽을 수 없으면 카드로 내보내지 않는다(KMA 면 OWM 폴백, OWM 이면 오류 카드 `WEATHER_STALE`). 진입점의 세 반환이 모두 거친다.
- 하니스 `test-weather-freshness.mts` 10항목(실제 사고 값, 경계, 깨진 값, 캐시 옵션 소스 고정).
- 실호출: KMA 시간 초과 때 OWM 폴백이 오늘(11-25) 데이터.

**남김**: KMA 시간 초과 9s → 폴백까지 기다리는 시간. 4~5s 로 줄일지는 KMA 지연 분포를 며칠 본 뒤.
