# DEV_261113 — 떠돌이 rejection 근원 수정 · 메시지 저장 정리 · [turn] 계측 · 이전 모델 숨김 · 로그 원문 제거

계획: [PLAN_STABILITY_261112](../../../plans/PLAN_STABILITY_261112.md) §1

## 1. 근원 — SDK 가 만들고 LangChain 이 버린 Promise

- `@google/generative-ai`(0.24.1) `generateContentStream` 은 응답 스트림을 tee 해 `{ stream, response }` 를 준다. `response` 는 스트림을 끝까지 읽는 별도 Promise 다.
- `@langchain/google-genai`(2.2.0) 스트리밍 경로는 `const { stream } = …` 로 `response` 를 버린다. LangGraph `streamEvents` 아래에선 이 경로를 탄다.
- 스트림이 깨지거나(`Failed to parse stream`) 25s 타임아웃으로 끊기면 같은 오류가 두 곳으로 간다.
  - `stream` 쪽 → langchain-path catch → 다음 키로 재시도(정상).
  - `response` 쪽 → 받는 쪽 없음 → `unhandledRejection`.
- 가짜 fetch(잘린 마지막 청크)로 재현: 호출 1번에 caught 1 + 떠돌이 1.

## 2. 그동안의 증상

- [route.ts](../../../../app/api/chat/route.ts) 가 요청마다 `process.once('unhandledRejection')` 를 걸어 자기 스트림에 generic 오류를 보냈다(4월 K3, [DEV_260423](../04/DEV_260423.md)).
- `process` 는 동시 요청이 공유한다 → 떠돌이 1건에 **그 순간 열린 요청 전부**가 오류 문구를 받았다.
- 재시도가 성공한 턴에도 오류 문구가 먼저 나갈 수 있었다. TODO 의 "빈 답 + 출처만"(10-18, [DEV_261018 §6](../10/DEV_261018.md#6-실측-키--제목-생성-키-tier))도 같은 길이다 — 무료 키 소진 중 스트림 오류가 떠돌았다.

## 3. 수정

- [server/process-guard.ts](../../../../server/process-guard.ts) `installProcessGuard()` — route 모듈 로드 때 한 번.
  - `GenerativeModel.prototype.generateContentStream` 결과의 `response` 에 빈 catch 를 붙인다. 오류는 `stream` 으로도 오므로 잃는 것 없음.
  - 프로세스 리스너 1개(`globalThis` 표식으로 중복 방지) — `[process] unhandled rejection {name, code, status}` 로그만, 오류 문구·SSE 없음.
  - 리스너를 없애지 않은 이유: Node 15+ 는 처리 안 된 rejection 에 프로세스를 끝낸다.
- route 의 요청별 `process.once`/`process.off` 제거. 요청 오류는 기존 try/catch/finally 만.
- `@google/generative-ai` 를 직접 의존성으로 올림(이미 설치된 0.24.1 그대로, 직접 import 하므로).

## 4. 검증

- 하니스 [test-process-guard](../../../../tests/test-process-guard.mts) 7건 — 실제 `ChatGoogleGenerativeAI` 에 깨진 스트림, 동시 3개: 각 호출 catch 로 오류 전달 · 떠돌이 0건 · 리스너 1개 · 요약에 문구 없음. **패치를 빼면 2건 실패**(떠돌이 3건)로 하니스가 회귀를 잡는 것도 확인.

- 남은 확인(배포 후): `[process] unhandled rejection` 줄이 찍히는지 — 찍히면 다른 출처가 있다는 뜻이라 그 Promise 를 찾아 막는다.
- 패키지 갱신 주의: LangChain 이 `response` 를 처리하게 바뀌거나 SDK 구조가 바뀌면 패치는 무해한 덧칠이 된다. 하니스가 계속 지킨다.

## 5. 메시지 저장 — 순서·로그·종료 뒤 마무리

계획: [PLAN_STABILITY_261112](../../../plans/PLAN_STABILITY_261112.md) §2

- 문제 3가지(코드 확인, 유실 재현은 아님):
  1. 저장 실패 로그가 Postgres `message`·`hint` 를 남겼다 — 입력값(`invalid input syntax for type uuid: "…"`)이 섞여 `session_id` 가 로그에 갈 수 있다. URL 실패 경로는 오류 객체 통째.
  2. 빨리 끝나는 경로(URL 실패·생성 즉시 실패)는 저장이 끝나기 전에 스트림이 닫힌다 → 함수가 멈추면 유실 가능.
  3. user 저장은 안 기다리고 assistant 만 기다려 순서가 코드로 확정되지 않았다.
- 수정: [server/chat-message-save.ts](../../../../server/chat-message-save.ts) `createMessageSaver` — 턴마다 하나.
  - `save(role, row)`: 같은 턴 저장을 시작 순서대로 잇는다(assistant 는 user 뒤). 앞이 실패해도 뒤는 진행. `role`·`trace_id` 는 여기서 붙인다.
  - Promise 는 만드는 즉시 실패를 받아 항상 resolve — 저장 Promise 가 떠돌이 rejection(§1)이 되지 않게.
  - `settle()`: route 가 `after()` 로 부른다. **스트림이 닫힌 뒤** 남은 저장을 기다리므로 요청 완료 시간이 늘지 않는다(외부 검토의 "finally 대기가 종료를 늦춘다" 우려 해소). 상한 5s — 넘으면 로그만(DB 요청은 취소 안 됨).
  - 로그: `[save] {"event":"chat_message_save_failed","role","traceId","code"}`. code 는 SQLSTATE(5자)·`PGRSTnnn` 만 그대로, 밖은 `db_error_unknown`, Promise reject 는 `db_request_failed`. 대기 초과는 `chat_message_save_wait_timeout`(traceId·ms).
- route: 삽입 3곳을 saver 로, `dbErrorSummary` 삭제. 정상 경로는 전과 같이 assistant 저장을 기다린 뒤 `done`(SSE 계약·타이밍 그대로). user 저장은 전처럼 기다리지 않는다 → TTFT 경로 변화 없음(실측 생략 — 첫 토큰 전 코드가 같다).
- 하니스 [test-chat-message-save](../../../../tests/test-chat-message-save.mts) 22건 — 순서 · user 실패+assistant 진행 · 로그 키 고정·문구 없음 · 코드 정규화 · reject 떠돌이 0 · URL 실패 경로 settle · 지연 상한 · 동시 턴 격리 · 중복 로그 없음.
- 전체 46개 통과, tsc·knip·build 통과, eslint 오류 0.
- 남은 위험: `after()` 상한(5s)을 넘는 DB 지연은 로그만 남고 저장 결과를 모른다 / 부분 저장(user 실패·assistant 성공)은 되돌리지 않는다 / route 의 다른 로그(프로필 조회·모델 오류 원문 300자)는 범위 밖 — 별도 점검.
- 배포 후 확인: 정상 턴에서 두 행이 같은 `trace_id` 로 user → assistant 순(KST 조회), `[save]` 줄이 없는지.

## 7. `[turn]` 계측 3개 — `routerMs`·`needsSearch`·`saveMs`

계획: [PLAN_STABILITY_261112](../../../plans/PLAN_STABILITY_261112.md) §3

- `routerMs`: 라우터 노드 소요. 라우터 코드는 안 건드리고 stream-dispatch 가 `on_chain_start`~`on_chain_end`(router)로 잰다. 지름길(`intentFrom=shortcut`) 턴은 0 근처라 분포 볼 때 `intentFrom=router`·`rule` 만 본다. 라우터 제한 시간(§4)의 근거.
- `needsSearch`: 라우터의 검색 필요 판정(`on`/`off`/`other`). `search`(실제 실행)·`sources` 와 나란히 보면 "요청했는데 미실행"·"실행했는데 출처 0건"이 갈린다. vision 으로 가는 턴은 판정이 없어 `other`.
- `saveMs`: assistant 저장 대기. 정상 턴은 저장 뒤 `done` 이라 전체 완료 시간에 든다 — 얼마인지 보이게.
- 셋 다 `turnFields()` 한 곳 → `[turn]`·LangSmith 루트 메타데이터(`needsSearch` 는 불리언). 숫자는 정수·형식 밖은 null/other.
- 하니스: `test-turn-log` 41건(키 집합 갱신 + 5건), `test-tracing` 111건(+2건). 전체 46개·tsc·knip·build 통과, eslint 오류 0.
