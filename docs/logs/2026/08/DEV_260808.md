# DEV_260808 — 업로드 첨부 분석 실패 (영상·대용량 PDF)

> 작성: 2026-08-08
> 증상: 영상 파일을 올리면 **"응답을 받지 못했습니다. 다시 시도해주세요."** / PDF 도 "조금 커지면" 같은 증상
> 성격: 단일 증상 뒤에 **원인 셋**이 겹쳐 있었다. 셋 다 `3.6-flash` 기본 승격(`d439e3d`) 때 생긴 공백이다.

## 요약 (TL;DR)

- **타임아웃이 아니었다.** `gemini-3.6-flash` 는 **임의 URL `fileData` 를 아예 처리하지 못한다**(429 RESOURCE_EXHAUSTED). 업로드 첨부는 Storage 공개 URL 로 나가므로 항상 이 경로다.
- 🔴 **무료티어 한계가 아니다** — **유료 TIER1 키도 동일하게 429.** 티어를 올려도 안 풀린다. (조사 도중 "무료티어 문제"로 단정했다가 정정)
- "타임아웃처럼 보인" 이유: 429 → 키 로테이션 → **12키 × ~12s ≈ 144s** → Vercel 60s 캡 초과 → 텍스트를 한 번도 못 받고 종료. **어떤 키로도 성공하지 못하는 실패를 12번 재시도**하고 있었다.
- "PDF 는 커지면"의 정체는 [useChatStream.ts](../../../../src/hooks/useChatStream.ts) 의 **1MB 임계값** — 넘는 순간 inline → URL 로 경로가 바뀐다.
- 고치는 과정에서 **세 번째 문제**가 드러났다: `SDK_CALL_TIMEOUT_MS = 25s` 가 정상 응답(21~32s)을 끊고 있었다 — YouTube 가 겪었던 회귀와 같은 구조.

## 1. 근본 원인 — 3.6 은 임의 URL fileData 를 못 받는다

### 1-1. 계층 분리부터

서버 코드를 읽는 대신 **Gemini 를 직접 쳐서** 계층을 갈랐다. 우리 코드가 원인인지 모델이 원인인지 먼저 정하지 않으면 추측이 된다.

실제 사용자 파일(`reference/테스트.mp4`, 10초·2.76MB)을 dev `/api/upload` 로 올려 **프로덕션과 같은 Supabase 공개 URL** 을 만들고, 그 URL 로 모델 × 입력 유형 행렬을 측정했다:

| | 텍스트 | YouTube | **업로드 영상** | 인라인 이미지 | 400p PDF(URL) | 400p PDF(inline) |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| **gemini-3.6-flash** | ✅ 6.3s | ✅ 7.5s | **🔴 429** | ✅ 4.8s | **🔴 429** | 🔴 503 |
| gemini-2.5-flash | ✅ 1.5s | ✅ 19.7s | **✅ 21.2s** | ✅ 5.6s | ✅ 31.8s | ✅ 21.2s |

### 1-2. 쿼터 소진이 아니다 — 근거 둘

429(RESOURCE_EXHAUSTED)는 보통 쿼터로 읽힌다. 아니었다:

1. **무료 키 4개 교차** — `API_KEY`~`API_KEY4` 전부 *같은 키가* 텍스트엔 200, 업로드 영상엔 429. 직전 호출이 성공하는 키를 "소진"이라 부를 수 없다.
2. **유료 TIER1 키도 429** — 티어 상향으로 안 풀린다.

즉 **모델 능력 한계**다. 그리고 축이 좁다 — 3.6 은 인라인 이미지도, **YouTube `fileData` 도** 정상이다. 막히는 건 **우리 Storage URL 을 `fileData` 로 줄 때**뿐이다.

> ⚠️ 조사 중간에 "무료티어 한계"로 단정하고 코드 주석에도 그렇게 적었다. 유료 키 확인 후 정정했다. **429 를 보면 쿼터로 읽고 싶어지는 편향**이 있고, 그걸 깨는 건 "같은 키가 직전에 성공했는가"라는 대조군이었다.

### 1-3. 왜 이 경로만 뚫려 있었나

[models.ts](../../../../server/models.ts) 의 능력 테이블이 **틀린 주장**을 하고 있었다:

```ts
"gemini-3.6-flash": { freeTierSearch: false, fastMultimodal: true, fastLongInput: true }
//                                            ↑ 업로드 첨부에는 거짓
```

그리고 강등 조건이 **YouTube 전용**이었다:

```ts
const pinYoutube = isYoutubeRequest && hasVideoData && !selCaps.fastMultimodal;
const pinUrl     = hasUrlContentForModel && !selCaps.fastLongInput;
```

업로드 첨부는 `isYoutubeRequest === false` 라 **어떤 핀에도 안 걸린다.** 기본 모델이 2.5 이던 시절엔 문제가 없었고, 3.6 승격(`d439e3d`) 때 함께 넘어오지 않았다.

### 1-4. 조치 — 축을 하나 추가

`freeTierSearch` 가 이미 쓰는 것과 **같은 패턴**이다.

```ts
// models.ts — 티어 무관. 3.x 는 429.
"gemini-3.6-flash": { …, urlFileData: false },
"gemini-2.5-flash": { …, urlFileData: true  },

// generator.ts
const hasUrlFileData = state.messages.some((m) => Array.isArray(m.content) &&
    m.content.some((p) => p.fileData?.fileUri && !/youtube\.com|youtu\.be/.test(p.fileData.fileUri)));
const pinUrlFileData = hasUrlFileData && !selCaps.urlFileData;
const resolvedModel = (pinYoutube || pinUrl || pinUrlFileData) ? SERVER_MODELS.FLASH : sel;
```

## 2. "PDF 는 조금 커지면" — 1MB 임계값

같은 뿌리인데 **증상이 크기에 따라 갈리는 이유**가 따로 있었다. [useChatStream.ts:196](../../../../src/hooks/useChatStream.ts#L196):

```ts
// 문서: 1MB 미만 base64 inline 허용 (Vercel payload 4.5MB 제한 우회)
if (!isImage && !isVideo && estimatedSize < (1 * 1024 * 1024) && isBase64) {
  finalAttachments.push(attachment);   // ← inline 유지
  continue;
}
// 그 외 → Storage 업로드 → data = URL
```

| 첨부 | 경로 | 3.6 결과 |
|---|---|---|
| PDF < 1MB | inline base64 | 대체로 성공 (단 페이지가 많으면 §2-1) |
| **PDF ≥ 1MB** | Storage URL → `fileData` | **429 — 항상 실패** |
| **영상 (크기 무관)** | 항상 Storage URL | **429 — 항상 실패** |

### 2-1. 작은 PDF 도 "가끔" 실패하던 이유

400페이지(0.41MB, 입력 103k토큰)를 **inline** 으로 보내면 3.6 이 **503 UNAVAILABLE** 을 낸다. 429 와 달리 503 은 기존 코드가 이미 2.5 로 강등하므로(재시도 23s + 21s ≈ 44s) **60s 안에 겨우 들어와 성공**한다.

→ 그래서 "될 때도 있고 안 될 때도 있는" 증상이 나왔다. **429 는 항상 실패, 503 은 자가 회복.** 두 에러의 처리 차이가 증상 차이를 만들고 있었다.

## 3. 🔴 "키 소진"과 "모델 거부"를 구분하지 못했다

### 3-1. 응답에 단서가 없다

먼저 429 본문에 구조적 단서가 있는지 봤다(있으면 휴리스틱이 필요 없다):

```json
{ "error": { "code": 429, "message": "Resource has been exhausted (e.g. check quota).", "status": "RESOURCE_EXHAUSTED" } }
```

`quotaMetric`·`quotaId`·`retryDelay` **전부 없다.** 무료·유료 모두 맨 429다. → 응답만으로는 구분 불가.

### 3-2. 행동으로 구분한다

429 는 두 가지가 같은 얼굴로 온다:

| | 다른 키로 바꾸면 | 올바른 대응 |
|---|---|---|
| ⓐ 그 키의 쿼터 소진 | 성공한다 | 키 로테이션 |
| ⓑ 모델이 요청을 거부 | **똑같이 실패** | **모델 강등** |

기존 코드는 전부 ⓐ 로 처리해 12키를 돌렸다. 구분 기준:

```ts
// 서로 다른 키 2개가 같은 모델에서 429 → ⓑ 로 보고 2.5 로 강등
const modelWide429 = isRateLimit && rateLimitedKeys.size >= Math.min(2, API_KEYS.length);
const justDowngraded = (isUnavailable || isTimeout || modelWide429) && !unavailableDowngrade && isThreeXFlash(resolvedModel);
```

503/timeout 이 이미 쓰던 `justDowngraded` 메커니즘에 **얹기만 했다** — 새 구조를 만들지 않았다.

**임계값 2 의 근거**: ⓐ 를 ⓑ 로 오판해도 비용이 낮다(2.5 도 잘 답하고 더 빠르다). 반대로 ⓑ 를 놓치면 **확정적으로** 60s 를 넘긴다. 비대칭이라 조기 강등이 옳다. 키가 1개뿐이면 로테이션 자체가 불가능하므로 `Math.min(2, API_KEYS.length)` 로 1회 판정한다.

**검증**(핀을 일부러 끄고 429 경로를 태움):

```
Retrying SDK call (attempt 2) reason: 429 | model: gemini-3.6-flash
429 on 2 distinct keys (model-wide, not key quota) on gemini-3.6-flash — downgrading retries to 2.5-flash
Retrying SDK call (attempt 3) | model: 2.5(downgraded)
✅ 43.1s — 정상 답변
```

43s 는 60s 안이지만 여유가 적다. **핀(§1-4)이 1차 방어, 이 강등은 그물**이다.

## 4. 세 번째 문제 — 25s 데드라인이 정상 응답을 끊고 있었다

§3 검증 중 발견. 429 강등 후 PDF 가 2.5 에서 **timeout 으로 계속 재시도**했다:

```
attempt 4~8  reason: timeout | model: 2.5(downgraded)
```

`SDK_CALL_TIMEOUT_MS = 25_000` 인데 400p PDF 는 **21~32s** 가 걸린다. 우리가 정상 응답을 끊고 있었다.

**YouTube 가 겪은 회귀와 완전히 같은 구조다**(`aa9d701` 25s 일률 도입 → `80972c8`·`e189104` 로 57s 예산 복원, 메모리 `youtube-call-timeout-profile`). 그때 만든 예산이 **이름 때문에 업로드 미디어에 적용되지 않았다**:

```ts
const attemptTimeoutMs = isYtVideoTurn ? YOUTUBE_CALL_TIMEOUT_MS : SDK_CALL_TIMEOUT_MS;
//                       ↑ 업로드 영상·PDF 는 여기 안 들어온다
```

→ 상수명을 대상에 맞게 고치고 범위를 넓혔다:

```ts
export const HEAVY_MEDIA_CALL_TIMEOUT_MS = 57_000;
/** @deprecated 이름이 대상을 좁게 말한다 */
export const YOUTUBE_CALL_TIMEOUT_MS = HEAVY_MEDIA_CALL_TIMEOUT_MS;

const isHeavyMediaTurn = isYtVideoTurn || hasUrlFileData;
const attemptTimeoutMs = isHeavyMediaTurn ? HEAVY_MEDIA_CALL_TIMEOUT_MS : SDK_CALL_TIMEOUT_MS;
```

데드라인 소진 후 재시도 차단(`ytPrimaryTimedOut`)도 같은 범위로 넓혔다 — 57s 를 쓰고 또 재시도하면 60s 캡을 확실히 넘긴다.

> **이름이 범위를 좁혔다.** `YOUTUBE_CALL_TIMEOUT_MS` 라는 이름 때문에 "YouTube 전용 예산"으로 읽혔고, 같은 프로파일의 업로드 미디어가 조용히 빠졌다. §1-3 의 `pinYoutube` 와 **같은 실수**다 — 특정 사례로 이름 붙인 규칙이 그 사례에만 적용되는 것.

## 6. 이 세션의 교훈

1. **특정 사례로 이름 붙인 규칙은 그 사례에만 적용된다.** `pinYoutube`·`YOUTUBE_CALL_TIMEOUT_MS` 둘 다 실제로는 "무거운 미디어 턴"의 규칙인데 이름이 YouTube 라 업로드 첨부가 빠졌다. 같은 실수가 **한 파일에서 두 번** 났다.
2. **429 를 쿼터로 읽지 마라.** 대조군("같은 키가 직전에 성공했는가")을 세우기 전엔 알 수 없다. 유료 키 확인 전까지 나는 "무료티어 한계"로 단정하고 있었다.
3. **에러 처리 차이가 증상 차이를 만든다.** 429(강등 없음)는 항상 실패, 503(강등 있음)은 자가 회복 — 그래서 "가끔 된다"로 보였다. 재현이 불안정하면 **에러 코드별 경로**를 먼저 갈라 보는 게 빠르다.
4. **계층을 먼저 가른다.** 서버 코드를 읽기 전에 Gemini 를 직접 쳐서 "모델이 못 하는 것"과 "우리가 잘못하는 것"을 분리했다. 이게 없었으면 타임아웃 튜닝을 하고 있었을 것이다.
