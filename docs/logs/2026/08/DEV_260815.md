# DEV_260815 — 검색 의도분류 누락: "찾아서 정리해보자"가 검색을 끄는 이유

> 작성: 2026-08-15
> 증상: `그럼 모티프 모델 구체적으로 찾아서 정리해보자` → **"실시간 웹 검색 기능이 제공되지 않습니다"**.
> 사용자가 다음 턴에 `검색해서 찾아보자`라고 **"검색"이라는 단어를 직접 쓰자 그제서야** grounding이 붙어 정상 답변.
> 성격: 정규식 한 개의 오발이 아니라, **판정 권한이 3개 레이어에 흩어진 구조**가 만든 필연.

## 요약 (TL;DR)

- 근본 원인은 [intentRules.ts](../../../../server/agent/intentRules.ts) 의 멀티턴 가드 `shouldSuppressSearchForFollowup`.
  `"정리"`라는 단어 하나 때문에 이 발화를 **직전 답변 가공형 follow-up**으로 오판하고 검색을 껐다.
- 억제 해제 조건 `wantsFresh = (temporal || domain) && !pastRef` 에 **`explicit` 태그가 빠져 있다.**
  결과: **"검색해서 정리해줘"조차 검색이 꺼진다.** 사용자가 명시적으로 요청해도 시스템이 뒤집는다.
- 부수 결함: explicit 정규식이 `찾아봐|찾아 줘`만 잡고 **`찾아서`·`찾아줘`(붙여쓰기)·`찾아보자`·`조사`·`알아보자`를 전부 놓친다.**
- 같은 개념("명시적 검색 요청")이 **두 파일에 다른 정규식으로** 존재한다 —
  [intentRules.ts:117](../../../../server/agent/intentRules.ts#L117)(좁음) vs [search-gate.ts:120](../../../../server/agent/nodes/search-gate.ts#L120)(넓음).
  그리고 **좁은 쪽이 관문 역할**을 한다.

## 1. 재현 — 룰 엔진을 그대로 떼어내 돌렸다

서버 로그를 기다리는 대신 [intentRules.ts](../../../../server/agent/intentRules.ts) 의 정규식·판정 함수를 그대로 복사해 순수 함수로 실행했다. LLM도 API 키도 필요 없다 — 이 판정은 전부 결정론이다.

| 발화 | rule | followupRef | 멀티턴 가드 억제 | 실제 화면 |
|---|:---:|:---:|:---:|:---:|
| `그럼 모티프 모델 구체적으로 찾아서 정리해보자` | gray | **true** | **억제** | 검색 안 함 ✅일치 |
| `검색해서 찾아보자` | on(explicit) | false | 통과 | 검색 함 ✅일치 |

두 발화 모두 화면 동작과 일치했다. 갈린 지점은 단 하나 — **`"정리"`라는 단어의 유무**다.

### 1-1. 더 나쁜 케이스

`explicit` 태그가 `wantsFresh` 계산에서 빠져 있다는 걸 확인하고 추가로 돌렸다:

| 발화 | tags | 억제 | 문제 |
|---|---|:---:|---|
| `검색해서 정리해줘` | `[explicit]` | **TRUE** | 🔴 명시적 검색 요청이 무시된다 |
| `출처 찾아서 정리해줘` | `[explicit]` | **TRUE** | 🔴 출처를 달라는데 검색이 꺼진다 |
| `구글에 찾아보고 비교해줘` | `[]` | **TRUE** | 🔴 "구글"·"찾아보"를 아예 못 잡음 |
| `최신 정보 검색해서 정리해줘` | `[temporal, explicit]` | false | ✅ `temporal`이 있어서 우연히 살아남음 |

마지막 행이 핵심이다. **`"최신"`이 우연히 섞여 있었기에 통과했을 뿐**, `explicit`이 구제한 게 아니다.
즉 사용자가 "검색해줘"라고 말하는 것만으로는 이 가드를 통과할 수 없다.

## 2. 왜 이런 코드가 나왔나 — 구조를 봐야 한다

정규식 하나를 고치는 걸로 끝내면 같은 유형이 다시 난다. 실제 병리는 셋이다.

### 2-1. 판정 권한이 3개 레이어에 분산

```
router.ts        → needsSearch (boolean) 산출
  ↓ state
search-gate.ts   → 7개 게이트가 순차적으로 덮어씀
  ↓
generator.ts     → 결과 사용
```

각 레이어가 앞 레이어를 **덮어쓸 수 있고**, 우선순위는 **if문의 물리적 배치 순서**로만 표현돼 있다.
[search-gate.ts](../../../../server/agent/nodes/search-gate.ts) 상단 주석이 우선순위를 산문으로 적어두었다는 사실 자체가 신호다 — 코드가 스스로 말하지 못하니 주석이 대신하고 있다.

### 2-2. 정보 손실이 재분석을 부른다 ← 진짜 원인

`needsSearch`는 **boolean**이다. **"왜 그렇게 판정했는지"가 state를 건너오면서 사라진다.**

그래서 search-gate는 근거를 모른 채 **원문 텍스트를 정규식으로 다시 분석한다**:

- `explicitSearchRequested` — 명시 검색 요청을 **재판정** (라우터가 이미 판정했는데도)
- `prevSearched` — 직전 턴 검색 여부를 **직전 메시지 정규식으로 근사** (기획 9-B A안)
- `isNewSearchQuery` — `classifySearchNeed`를 **다시 호출**

이 재분석들이 원판정과 어긋나는 순간이 버그다. 이번 건이 정확히 그 케이스다.

> **교훈: boolean으로 좁힌 결정을 하위 레이어에 넘기면, 하위 레이어는 반드시 추측을 시작한다.**

### 2-3. 억제 게이트가 사용자 명시 요청을 이길 수 있다

권한 계층이 없으니 "물리 제약(API가 이미지+grounding 거부)"과 "휴리스틱 추측(정리라는 단어가 있네)"이 **같은 층에서 동등하게 경쟁**한다. 나중에 실행되는 쪽이 이긴다.

사용자 의사 표현이 시스템 추측에 지는 건 어떤 경우에도 옳지 않다.

## 3. 확인하지 못한 것 (정직하게)

- **프로덕션 로그 미확인.** 멀티턴 가드가 실제로 발동했음을 증명하려면
  `[LangGraph] Multi-turn follow-up guard — Google Search suppressed` 로그가 필요하다. 확인하지 않았다.
- 가드 발동에는 `prevSearched=true`(직전 human 메시지가 ON 판정) 조건이 필요하다.
  직전 턴 원문을 모르므로, 이번 건이 **가드 오발**인지 **라우터 LLM이 `needs_search=false`를 반환**한 건지 100% 갈라내지 못했다.
- 다만 §1-1의 결함(explicit 태그 누락, 정규식 갭)은 **로그와 무관하게 결정론적으로 재현되는 실재 결함**이다.
  두 갈래 중 어느 쪽이든 고쳐야 한다.

## 4. 테스트 하니스 baseline (2026-08-15)

`scripts/test-search-policy.mts` 신설. **정규식을 복사하지 않고 프로덕션 모듈을 직접 import**한다 —
`test-search-rules.mjs`가 복사본을 채점하느라 드리프트를 숨긴 전례를 반복하지 않기 위해서다(§5 참조).

```
$ npx tsx scripts/test-search-policy.mts

BUG   : 0/4  (0%)     ← 이번 결함. 구현 전 RED가 정상
GAP   : 3/3  (100%)   ⚠️ 아래 주의
GUARD : 5/5  (100%)   ← 회귀 방어
OFF   : 4/4  (100%)
ON    : 3/3  (100%)
TOTAL : 15/19

Part B (정책 엔진 계약 6건): ⏭ SKIP — search-policy.ts 미구현
```

**RED 4건 (전부 같은 구조: 새 검색 요구 + 가공 어휘 동반):**

| 발화 | want | got |
|---|:---:|:---:|
| `그럼 모티프 모델 구체적으로 찾아서 정리해보자` | ON | **OFF** |
| `검색해서 정리해줘` | ON | **OFF** |
| `출처 찾아서 정리해줘` | ON | **OFF** |
| `구글에 찾아보고 비교해줘` | ON | **OFF** |

> ⚠️ **`GAP` 3건이 GREEN인 것에 속으면 안 된다.** `찾아줘`·`조사해줘`·`알아보자`는
> explicit 정규식이 **여전히 못 잡는다.** gray로 떨어진 뒤 **default-on 안전판**에 우연히 구제되고 있을 뿐이다.
> `prevSearched=true`가 되는 순간(= 직전 턴에 검색이 있었던 멀티턴) 전부 RED로 돌아선다.
> 안전판이 결함을 가리고 있는 상태다.

종료코드는 **회귀(GUARD/OFF/ON)가 깨질 때만** 1이다. BUG/GAP의 RED는 구현 전 정상이므로 CI를 오염시키지 않는다.

## 5. 부수 발견 — 검증 하니스가 이미 RED였다

충돌 검토 중 `verify-intentrules-search.mts`를 실제로 돌려봤더니 **20/22 `❌ MISMATCH`**였다.
[PLAN_CHANGES_LATENCY_SEARCH_ROUTING](../../../plans/PLAN_CHANGES_LATENCY_SEARCH_ROUTING.md)은 22/22라고 적고 있었다.

```
❌ exp=off got=gray | 광합성 과정을 설명해줘
❌ exp=off got=gray | TCP 핸드셰이크가 어떻게 작동하는지 설명해줘
```

**프로덕션 버그가 아니다.** [intentRules.ts:101-103](../../../../server/agent/intentRules.ts#L101-L103)이
`설명해/원리/개념`을 강한 OFF에서 **의도적으로 제외**했다(DEV_260624 §5 A안 —
`"gpt 5.5 설명해줘"` 같은 최근 엔티티 설명은 검증 검색이 필요하므로 gray로 위임).
**프로덕션이 옳고 기대값이 낡았다.**

문제는 **왜 아무도 몰랐나**다:

- `test-search-rules.mjs`는 정규식을 프로덕션에서 import하지 않고 **파일 상단에 복사**해 둔다.
  → 프로덕션이 바뀌어도 **자기 복사본을 채점하며 22/22 초록을 유지**한다. 지금도 초록이다.
- 드리프트를 잡으라고 만든 `verify-*.mts`는 RED가 됐지만 **CI에 물려 있지 않아** 아무도 보지 않았다.

> **교훈: 규칙을 복사한 테스트는 규칙이 바뀐 걸 알려주지 못한다.**
> 초록색 테스트가 안전을 뜻하지 않는 경우다 — 무엇을 채점하는지가 먼저다.

**조치 (Step 1, 완료)**: 기대값 2건을 `off → gray`로 정정하고 판정 기준을 "프로토타입과 동일한가"에서
**"사양대로인가"**로 바꿨다. → `22/22, FP 0, 가드 4/4, exit 0` GREEN 복구.

## 5-1. 조치 결과 (Step 4 완료, 2026-08-15)

`search-gate.ts`를 신호 제출 구조로 전환했다. 게이트가 boolean을 덮어쓰지 않는다.

```
$ npx tsx scripts/test-search-policy.mts     exit 0

BUG   : 4/4   ← 해소
GAP   : 3/3   ← 이제 tier 300이 구제한다 (default-on 안전판 의존 해소)
GUARD : 5/5   OFF : 4/4   ON : 3/3
명시요청 탐지 16/16 · 정책 계약 7/7 · 게이트 회귀 19/19
```

`GAP` 3건이 §4의 경고를 벗어났는지 확인이 필요했다 — 안전판이 아니라 실제로 잡히는지.
`prevSearched=true`(안전판이 무력화되는 조건)에서도 ON을 유지한다. tier 300이 잡고 있다.

신설: [search-signals.ts](../../../../server/agent/search-signals.ts) — 텍스트 증거를 신호로 변환하는
순수 함수 레이어. 테스트가 프로덕션 경로를 그대로 실행할 수 있는 것이 이 분리의 목적이다
(`currentEffectiveSearch`가 파이프라인을 흉내내는 대신 `collectTextSearchSignals` + `decideSearch`를 호출한다).

이제 로그 한 줄에 전체 근거가 남는다 — §3에서 "확인하지 못했다"고 적은 종류의 질문이 다시 생기지 않는다:

```
[SearchPolicy] ON by user-explicit(300) "사용자가 검색·출처를 명시 요청" | trace: router-llm=on(100), followup-guard=off(100)
```

의도적 동작 변경 3건(medical_qa+URL, URL+명시요청, 게이트 탈출구 범위)은
[PLAN §5](../../../plans/PLAN_SEARCH_POLICY_260815.md) 표에 기록했다.

## 6. 결론

정규식 2줄 수정으로 이번 증상은 막을 수 있다. 하지만 §2의 구조가 남는 한 같은 유형이 반복된다.

→ **증거(Signal) → 정책(Policy) 2단 분리**로 재설계한다. 계획: [PLAN_SEARCH_POLICY_260815](../../../plans/PLAN_SEARCH_POLICY_260815.md)

핵심은 정규식을 없애는 게 아니다. **정규식을 "결정"에서 "증거"로 강등**시키고,
"누가 누구를 이기는가"를 if문 배치가 아닌 **선언적 데이터(tier)**로 만드는 것이다.
