- 거기서 진짜 결함 1건이 나왔고(홑 달러 노출), 프롬프트 규칙의 **구조적 구멍**을 고쳤다(§4).

## 1. 🔴 main Vercel 에 스테이징 값이 들어가 있었다

인증 브랜치가 요구하는 신규 변수 `NEXT_PUBLIC_SUPABASE_URL`·`NEXT_PUBLIC_SUPABASE_ANON_KEY` 를 등록하면서, 로컬 `.env.local` 의 값을 그대로 옮겼다. 그런데 `.env.local` 은 **스테이징**을 가리킨다.

```
main Vercel (사고 당시):
  SUPABASE_URL                   gaomgqnpsjtabrvwnpad   ← 프로덕션 (예전부터 있던 값)
  NEXT_PUBLIC_SUPABASE_URL       ghdpnuwbvlrxmxcazzci   ← 🔴 스테이징
  NEXT_PUBLIC_SUPABASE_ANON_KEY  role=anon          ref=ghdpnuwbvlrxmxcazzci
  SUPABASE_SERVICE_ROLE_KEY      role=service_role  ref=ghdpnuwbvlrxmxcazzci
```

### 왜 아직 안 터졌나

Vercel 은 env 를 **배포 시점에 함수에 굽는다.** 마지막 프로덕션 배포(1h 전)가 env 등록(36m 전)보다 앞서 있어서, 돌고 있는 함수는 변경 이전 스냅샷을 쓰고 있었다. 발견 시점에 **재배포 금지**를 먼저 확정한 이유다.

### 배포됐다면 무엇이 깨졌나

- `SUPABASE_SERVICE_ROLE_KEY` 는 **인증 머지 전 현재 main 코드도 이미 읽는다**([server/supabase.ts:10](../../../../server/supabase.ts#L10) → create-signed-url · parse-document). 프로덕션 URL + 스테이징 서명 키 = 서명 불일치 → **파일 업로드·문서 파싱만 실패.** 채팅은 멀쩡해서 원인이 env 라는 걸 알아채기 어렵다.
- 머지 후엔 클라이언트와 `createRouteClient` 가 통째로 스테이징을 본다 → 대화는 스테이징에, 서버 일부는 프로덕션에. **에러 없이 조용히 갈라진다.**

### 조치

| 변수 | 조치 | 근거 |
|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | **삭제** | 지우면 폴백으로 `SUPABASE_KEY`(82일째 프로덕션에서 쓰던 값)를 쓴다. dev 는 이 변수 없이 15일 돌았다 — **검증된 경로**다. 값 교체보다 삭제가 낫다 |
| `NEXT_PUBLIC_SUPABASE_URL` | 프로덕션 값으로 교체 | `SUPABASE_URL` 과 같은 ref 여야 한다 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 프로덕션 anon 키로 교체 | |

### 교훈 — 이름이 같으면 출처가 사라진다

세 프로젝트가 **같은 변수 이름**을 쓴다. 그래서 값만 보면 어디 것인지 판별이 안 되고, 복사·붙여넣기 한 번에 사고가 난다. 값 자체가 20자 랜덤 ref 라 눈으로도 안 걸러진다.

→ 런북 §E-2 에 **대조 절차**를 체크리스트로 넣었다. 두 가지를 본다:

```bash
# 1) URL 두 개의 ref 가 같은가 (SUPABASE_URL ↔ NEXT_PUBLIC_SUPABASE_URL)
# 2) 키의 role·ref 디코드 — 네트워크 안 탐
echo '<키>' | cut -d. -f2 | base64 -d 2>/dev/null | grep -oE '"(role|ref)":"[^"]*"'
#    → "role":"anon"  "ref":"gaomgqnpsjtabrvwnpad"
```

`role` 확인이 특히 중요하다. service_role 키를 `NEXT_PUBLIC_` 에 넣으면 **RLS 를 전부 우회하는 키가 브라우저 번들에 실린다.**

## 2. 부수 발견 — `VITE_` 레거시에 service_role 키가 있었다

env 비교 중 발견. main 에만 있던 두 변수:

```
VITE_SUPABASE_ANON_KEY   →  이름은 anon 인데 payload 는 role=service_role
VITE_SUPABASE_URL        →  ref 는 프로덕션도 스테이징도 아닌 제3의 옛 프로젝트 axpvmgndefueicehdetu
```

`VITE_` 접두사는 Vite 시절 "클라이언트 번들에 굽는다"는 뜻이었다. 그때 빌드된 적이 있다면 **RLS 우회 키가 브라우저로 배포됐던** 셈이다.

현재 코드 영향은 없다 — 두 브랜치 모두 `VITE_` 참조 0건, `import.meta.env` 는 [PLAN_NEXTJS_MIGRATION](../../../plans/PLAN_NEXTJS_MIGRATION.md) 문서에만, `vite.config`·`index.html` 은 트래킹된 파일에 없다. Next.js 는 `NEXT_PUBLIC_` 만 번들에 굽는다.

**Vercel 에서 삭제 완료.** 단 삭제가 키를 무효화하지는 않는다 — 그 프로젝트가 살아 있으면 **rotate 가 별도로 필요**하다(런북 §5-2).

미사용 변수 `JINA_API_KEY`(참조 0건)·`HOSPITAL_KEY`(코드는 `PHARM_KEY` 사용)도 같은 항목으로 남겼다. 컷오버 blocker 아님.

## 3. dev 화면 검증 — DEV_260801 이 남긴 4건

### 3-1. ⚠️ 수식 — 테스트 케이스가 잘못돼 있었다

DEV_260801 §5 가 지정한 프롬프트는 `경사면 힘 분석 그림으로 설명해줘` 였다. 돌려보니 응답에 **`$$` 가 하나도 없었다.** KaTeX 경로가 아예 실행되지 않았다.

버그가 아니다. [prompt.ts](../../../../server/agent/prompt.ts) 가 "simple expressions 는 plain Unicode 도 acceptable" 이라고 허용하고 있고, `mg sinθ` 정도는 실제로 유니코드가 더 읽기 좋다. 모델이 그 조항을 따른 것이다.

**문제는 케이스 선정이다.** 경사면 문제는 분수·적분·합이 안 나와서 LaTeX 를 강제하는 조건(`fractions, summations, integrals…`)에 걸리지 않는다. 몇 번을 돌려도 KaTeX 가 안 걸린다.

→ 케이스를 `정규분포 확률밀도함수 설명해줘` 로 교체. 분수·제곱근·지수·적분·그리스 문자가 전부 나온다.

**재실행 결과 — 세 위치 모두 통과:**

| 위치 | 예 |
|---|---|
| 인라인 | `평균이 $$\mu$$이고 …` → 문장 중간 정상 |
| 블록 | `$$f(x) = \frac{1}{\sigma\sqrt{2\pi}} e^{…}$$` → 분수·제곱근·지수 중첩 정상 |
| 표 셀 | `\| $$x$$ \| 확률변수 \|` → 정상 |

표 셀은 프롬프트가 "된다"고 주장만 하고 실측된 적이 없던 항목이었다. 이번에 닫혔다.

### 3-2. ✅ 마크다운 강조 — 최악 조건 통과

같은 응답에서 원래 버그의 재현 조건이 여러 번 나왔고 전부 굵게 렌더됐다:

```
**정규분포(Normal Distribution)**의        닫는 ** 앞 `)` + 뒤 한글조사
**확률밀도함수(…, PDF)**는                  동일
**'밀도'**를                                닫는 ** 앞 작은따옴표 + 뒤 한글
약 **95.45%**가                             `%` + 조사 — 최초 신고 형태
```

[DEV_260801 §3-4](DEV_260801.md)·[§3-4-1](DEV_260801.md) 의 두 수정(remark-cjk-friendly 도입 + 전처리 정규식 제거)이 실제 응답에서 확인됐다.

### 3-3. ✅ 극장 매칭 — 두 케이스 다 통과

- `강남 영화 상영시간표` → 롯데시네마 섹션이 **"'강남'에는 지점이 없습니다"** 로 표시. CGV·메가박스는 강남 지점 정상.
- `광주 영화 상영시간표` → **CGV 광주상무**. 경기광주로 새지 않았다.

[DEV_260801 §3-3-1](DEV_260801.md) 3단 수정이 확인됐다.

### 3-4. ✅ `/privacy`·`/terms`

HTTP 200, `CONTACT_EMAIL` 실제 주소로 반영. `CHANGE_ME` 잔존 0건.

> 배포 직후 첫 확인에서는 옛 값이 나왔다 — **커밋만 하고 푸시가 안 된 상태**였다. `origin/dev` 를 확인해서 바로 갈렸다. 배포 검증 전에 `git log origin/<branch>` 를 먼저 보는 게 맞다.

## 4. 🔴 여기서만 잡힌 결함 — 홑 달러 노출

`정규분포…` 응답의 마지막 문단:

```
구간 $[a, b]$에 속할 확률은 …
      ↑ 홑 달러 → 화면에 원문 그대로 노출
```

[ChatMessage.tsx:703](../../../../components/ChatMessage.tsx#L703) 이 `singleDollarTextMath: false` 라 홑 달러는 수식이 아니다. 같은 응답의 나머지 40여 개는 전부 `$$` 를 제대로 썼는데 여기 한 번만 샜다.

### 왜 코드로 막지 않았나

세 가지 방법이 다 지금보다 나쁘다:

| 방법 | 문제 |
|---|---|
| `singleDollarTextMath: true` | `$100`·`$5` 통화 표기가 전부 수식이 된다. 통화는 **검색 결과·크롤링 문서에서도 들어와** 프롬프트로 통제 불가 |
| 전처리로 `$…$` → `$$…$$` | [§3-4-1](DEV_260801.md) 에서 두 번 데인 패턴. `"가격은 $100에서 $200 사이"` 에서 `$100에서 $` 가 수식이 된다. 게다가 이번 케이스(`$[a, b]$`)엔 백슬래시가 없어 **좁은 규칙으로는 못 잡고, 넓히면 통화가 깨진다** |
| 프롬프트 강화 | 채택 (아래) |

드물고 가벼운 결함(읽을 수는 있고 기호만 보임)을 흔하고 무거운 결함(가격·환율 질문마다 깨짐)으로 교환할 이유가 없다. `singleDollarTextMath: false` 는 그 트레이드오프를 의식하고 고른 값이고, 이번 관찰은 그 선택의 근거에 가깝다.

### 프롬프트의 구조적 구멍

원인을 보니 강조가 부족한 게 아니라 **규칙의 축이 잘못돼 있었다.**

```
기존:  Write ALL mathematical notation
       (fractions, summations, integrals, Greek letters, subscripts/superscripts)
       in LaTeX wrapped in DOUBLE dollar signs
```

**내용 기준** 규칙이다. `[a, b]` 는 분수도 적분도 그리스 문자도 아니다 → 모델 입장에선 "그 목록에 없으니 MUST 대상이 아니다" 로 읽는 게 자연스럽다. 실제로 샌 것도 이 부류뿐이었다.

게다가 마지막 줄의 "simple expressions 는 plain Unicode 도 acceptable" 이 **"간단한 건 느슨하게 해도 된다"** 는 도피처로 읽힌다.

### 수정 — 축을 "내용"에서 "구분자"로

```
THE RULE IS ABOUT THE DELIMITER, NOT ABOUT WHETHER THE CONTENT "COUNTS AS" MATH.
If you type a `$` for any reason other than a currency amount, it MUST be a double `$$`.
```

"이게 수식인가?" 를 판단할 필요를 없앴다. 추가로 **새는 부류를 명시**했다(전부 이번에 관찰된 유형 — 짧고 기호가 아닌 조각):

```
구간·범위     $[a, b]$   → $$[a, b]$$
집합·튜플     ${1, 2}$, $(x, y)$
문장 중 변수   $x$, $n$, $f(a)$
조건·비교      $x > 0$, $n \ge 1$
```

유니코드 허용은 **유지**하되(표 셀에선 실제로 더 읽기 좋다), 홑 달러의 근거로 오독되지 않게 못 박았다:

```
this is a choice between `$$...$$` and plain Unicode — never a license to use a single `$`
```

**⚠️ 프롬프트 변경은 검증이 확률적이다.** 배포 후 같은 질문을 두세 번 돌려 재발 여부를 봐야 한다.

## 5. 이 세션의 교훈

1. **"통과"와 "검증이 성립함"은 다르다.** §3-1 은 응답이 정상이라 통과처럼 보였지만, 검증하려던 코드 경로는 실행조차 안 됐다. 테스트가 **무엇을 실행시켰는지**를 먼저 확인해야 한다.
2. **규칙이 안 지켜지면 강조를 더하기 전에 규칙의 구조를 본다.** §4 의 원인은 "덜 강하게 말해서" 가 아니라 "판단 기준을 모델에게 넘겨서" 였다.
3. **이름이 같으면 출처가 사라진다.** §1 은 사람의 실수가 아니라 이름 설계의 결과다. 대조 절차를 절차로 만들어야 재발이 막힌다.
4. **배포 검증 전에 `origin/<branch>` 부터 본다.** §3-4 에서 "고쳤는데 안 보임" 의 정체는 미푸시였다.
5. **삭제와 무효화는 다르다.** §2 의 키는 Vercel 에서 지워도 살아 있다. rotate 가 별도로 필요하다.

### SQL 두 개에 대한 메모

`cutover-prod.sql` 은 `auth-mvp-schema.sql` 을 **복제하지 않는다.** 340줄을 복사해두면 원본이 바뀔 때 갈라지고, 그건 `ChatMessage.tsx` 에서 렌더러 목록이 4번 중복 선언돼 있는 것과 같은 실수다([PLAN_CHATMESSAGE_REFACTOR](../../../plans/PLAN_CHATMESSAGE_REFACTOR_260801.md)). rename 과 트랜잭션 경계만 제공하고 본문은 붙여넣게 했다.

`verify-prod.sql` 은 **두 항목을 자동 판정에서 뺐다.** Supabase 가 프로젝트 생성 시 `alter default privileges … grant all … to anon` 을 걸어두기 때문에, 정상 적용 상태에서도 anon 권한이 붙을 수 있다. 기대값을 0 으로 박으면 **가짜 FAIL** 이 뜬다 — 유지보수 창에서 가짜 경보만큼 나쁜 게 없다. 참고 조회로 분리하고 이유를 파일에 적었다.

> **둘 다 실제 DB 에서 실행해보지 않았다**(Supabase MCP 미인증). 구문 검사만 했다. 컷오버 전에 **스테이징에서 verify 를 리허설**해 쿼리 자체의 오류를 걸러낼 것 — 기대값은 "2번(`_legacy` 백업)만 FAIL, 나머지 13개 PASS" 다.
