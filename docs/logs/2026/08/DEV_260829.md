# 후속 턴에서 grounding redirect URL 이 본문에 그대로 노출되던 문제

> 날짜: 2026-08-29
> 범위: Gemini grounding 인용(`gemini-citations.ts`), 히스토리 구성(`history.ts`), 스트리밍 sanitize(`app/api/chat/route.ts`), 무거운 미디어 타임아웃 강등(`generator.ts` §7)

## 1. 최종 결론

8월 24일에 넣은 Gemini 인용 번호화([DEV_260824 §5](DEV_260824.md#5-gemini-grounding-인용-번호화))가 **자기 자신을 먹이는 되먹임 고리**를 만들었다.

마커가 박힌 답변이 DB에 저장되고, 그 본문이 **그대로** 다음 턴의 히스토리로 모델에 되돌아간다. 모델은 그 포맷을 흉내 내 자기 검색 결과 URL을 본문에 맨 괄호로 쓰고, 그 위에 서버가 `groundingSupports` 기준으로 진짜 마커를 또 얹는다. 결과가 `[1](A)(A)` — 앞은 알약 배지로 정상 렌더링되고 **뒤의 맨 괄호는 마크다운 자동링크가 되어 화면에 보라색 생 URL로 뜬다.**

세 곳을 고쳤다. ① 히스토리에 마커를 싣지 않는다(원인) ② 본문에 남은 맨 redirect URL을 지운다(안전망) ③ 스트리밍 sanitize의 규칙을 나머지와 맞춘다(별건으로 발견한 잠재 결함).

검증 중 **무거운 미디어 턴 타임아웃에서 강등 재시도가 막혀 있던 별건**이 하나 더 나와 함께 고쳤다(§7).

🔴 **사용자 인식과 실제 원인이 달랐다.** 제보는 "3.7 쓸 때 발생"이었지만 3.7은 `freeTierSearch:false`라 검색 턴이 **2.5로 강등**되므로([models.ts](../../../../server/models.ts) MODEL_CAPS, [generator.ts](../../../../server/agent/nodes/generator.ts) `SEARCH_FALLBACK_MODEL`) 그 답변을 만든 것은 2.5-flash다. 3.5를 골라도 같은 경로다. 방아쇠는 모델이 아니라 **마커가 섞인 히스토리를 받는 후속 검색 턴**이다.

## 2. 증상

모바일 화면에서 문장 끝 알약 배지 `[1]` 바로 뒤에 `(https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQ…)`가 통째로 보였다. 리다이렉트 토큰이라 사람이 읽을 수 없는 200자짜리 문자열이 본문을 밀어냈다.

## 3. 원인 추적

### 3.1 저장된 원문을 본다

DB에서 그 답변(`chat_messages` `a18bbfc0-c0dd-4b60-97ae-3ef8dc495702`, 2026-08-24 23:06)을 꺼내 URL을 출처 이름으로 치환하면 모양이 드러난다.

```text
…정보 작전(Intelligence Operation, IO)을 의미합니다.[1](<1:namu.wiki>)(<1:namu.wiki>)[2](<2:wikipedia.org>)(<2:wikipedia.org>)[3](<3:nordvpn.com>)(<3:nordvpn.com>)
…포함합니다.[4](<4:fortinet.com>)(<4:fortinet.com>)
…공격적인 행위입니다.[5](<5:aks.ac.kr>)(<출처 목록에 없는 URL>)[3](<3:nordvpn.com>)(<출처 목록에 없는 URL>)
```

마커 14개 **전부** 뒤에 괄호 URL이 하나씩 더 붙어 있다. 마크다운에서 `[1](A)`는 링크로 소비되고 남은 `(A)`는 텍스트 → remark-gfm 자동링크 → 화면의 그 보라색 URL이다.

### 3.2 뒤쪽 괄호는 우리 코드가 만든 것이 아니다

근거 둘:

1. 괄호 URL 중 일부는 저장된 `grounding_sources`에 **없는** redirect URL이다. [gemini-citations.ts](../../../../server/agent/gemini-citations.ts)는 `citationNumber`가 붙은 uri만 삽입하고 그 목록을 그대로 sources로 돌려주므로, 출처에 없는 URL은 삽입 경로로 나올 수 없다.
2. 레포 전체에서 맨 괄호 URL(`(${uri})`)을 쓰는 코드가 없다 — 마커는 전부 `[N](uri)` 형태다.

배치도 들어맞는다. 모델이 `…의미합니다.(A)(B)`처럼 쓰면 `groundingSupports`의 segment 경계가 그 괄호들 **사이**에서 끊기므로, 서버 마커가 각 괄호 앞에 꽂혀 정확히 `[1](A)(A)[2](B)(B)`가 된다.

> 중간에 "인용 함수가 두 번 돌았나"를 의심해 실제 3.7 응답에 `applyGeminiCitations`를 두 번 먹여 봤는데, 그 경우는 `[1](A)[2](B)[1](A)[2](B)`처럼 **블록째** 복제된다. 관측된 교차 배열과 다르므로 기각했다.

### 3.3 후속 턴에서만 난다

같은 세션에서 첫 답변은 redirect URL 63개 · 중복 0, **두 번째(후속) 답변만** 28개 중 14쌍 전부 중복이었다. 8월 전체로 넓혀도 같다.

| 구분 | grounding 답변 수 | 중복 발생 |
|---|---|---|
| 세션의 **첫** grounding 턴 | 11 | 0 |
| 후속 grounding 턴 | 2 | 1 |

### 3.4 되먹임 지점

[history.ts](../../../../server/agent/history.ts) `buildHistoryMessages`가 이전 답변을 `new AIMessage(msg.content)`로 **마커까지 그대로** 실어 보낸다. 마커는 서버가 심은 표시지 모델이 쓴 문장이 아닌데, 모델 입장에서는 자기가 직전에 그렇게 썼다는 증거로 보인다. 8월 24일 이전에는 본문에 URL이 없었으므로 이 고리 자체가 없었다 — **인용 번호화가 도입한 회귀**다.

## 4. 수정

### 4.1 히스토리에 마커를 싣지 않는다 (원인)

`stripCitationLinksForHistory`를 신설해 `buildHistoryMessages`가 봇 메시지를 모델에 넘기기 전에 `[N](url)`을 제거한다.

```ts
const CITATION_LINK = /\s?\[\d+(?:,\s*\d+)*\]\(https?:\/\/[^\s)]+\)/g;
```

숫자 라벨만 지운다 — `[약품정보](url)`와 YouTube 타임스탬프 `[[01:23](url&t=83)]`는 라벨이 숫자가 아니라 그대로 남는다. 화면과 DB의 마커는 손대지 않으므로 사용자가 보는 인용은 그대로다.

### 4.2 본문에 남은 맨 redirect URL 제거 (안전망)

`stripBareGroundingUrls`를 추가하고 `applyGeminiCitations`의 **두 return 경로 모두**(supports가 없는 조기 return 포함)에 적용했다. `](` 뒤에 오는 URL, 즉 우리 마커의 목적지만 남기고 괄호형·노출형을 지운다.

```ts
.replace(new RegExp(String.raw`\s?(?<!\])\((?:${GROUNDING_REDIRECT_URL})\)`, 'g'), '')
.replace(new RegExp(String.raw`\s?(?<!\]\()${GROUNDING_REDIRECT_URL}`, 'g'), '');
```

대상은 `vertexaisearch.cloud.google.com/grounding-api-redirect/…`로 한정한다. 사람이 읽을 수 없는 불투명 리다이렉트라 본문 노출은 언제나 버그이고, 모델이 인용한 일반 URL(`https://example.com/news`)은 살려야 하기 때문이다.

> 🔴 **순서가 계약이다.** 제거는 마커를 심은 **뒤**에만 한다. 먼저 지우면 `segment.endIndex`(UTF-8 바이트 오프셋)가 어긋나 한글 문장 한가운데가 잘린다 — [DEV_260824 §5](DEV_260824.md#5-gemini-grounding-인용-번호화)의 그 계약 그대로다.

### 4.3 스트리밍 sanitize 규칙 정합 (별건)

[route.ts](../../../../app/api/chat/route.ts)의 LangChain 스트리밍 경로만 **`(?!\()` lookahead가 빠져** 있었다. 같은 파일 `on_chain_end`(242행 부근)와 `gemini-citations.ts`는 이미 lookahead를 쓰고 있었으므로 한 파일 안에서 규칙이 갈라져 있던 셈이다. 이 경로로 `[N](url)`이 흐르면 `[N]`만 지워지고 `(url)`이 남아 — §3.1과 **같은 화면**이 된다.

고치는 과정에서 결함이 하나 더 드러났다. **청크 경계**다.

```text
chunk1: "…문장입니다.[1]"   chunk2: "(https://…) 다음"
```

기존 순서는 `strip → 보류 판정`이라 chunk1의 `[1]`이 그 자리에서 지워지고 chunk2의 `(url)`만 남는다. 셋을 바꿨다.

- **보류를 strip보다 먼저** 한다 — 뒤에 `(`가 올지 모르는 상태에서 지우지 않는다
- 보류 패턴에 **닫힌 대괄호**를 포함(`/\s?\[\d*(?:,\s*\d*)*\]?$/`) — 열린 `[1`뿐 아니라 완성된 `[1]`도 붙잡는다
- 스트림 끝 flush에도 strip 적용 — 뒤에 아무것도 안 오는 것이 확정된 시점이라 그때는 지우는 게 맞다

## 6. 교훈

- **출력에 심은 표시는 입력으로 돌아온다.** 서버가 본문을 가공해 저장하면 그 가공물이 다음 턴 히스토리가 된다. 표시를 심는 변경에는 "이게 다시 모델에게 보이는가"가 따라붙어야 한다.
- **재현이 안 될 때는 저장된 원문을 본다.** 모델을 직접 호출해 재현하려던 시도는 계속 실패했고(확률적이다), 결론은 DB 원문의 `[1](A)(A)` 배열과 "출처 목록에 없는 URL"이라는 두 증거에서 나왔다.
- **같은 규칙이 세 곳에 흩어져 있으면 하나는 반드시 뒤처진다.** route의 스트리밍 경로만 lookahead가 빠져 있었다. 하니스가 소스에서 규칙을 뽑아 재검증하도록 한 이유다.

## 7. 곁가지 — 무거운 미디어 타임아웃에서 강등 재시도가 막혀 있던 문제

인용 수정을 UI 로 확인하던 중(YouTube 후속 턴 케이스) `YouTube 영상 분석 서비스가 일시적으로
불안정합니다` 가 나왔다. 인용 수정과는 무관한 별건이지만 원인이 명확해 함께 고쳤다.

### 7.1 재현

`tests/manual/probe-youtube.mts` 로 route.ts 와 동일하게 **fileData 파트를 넣어** 실제 영상 분석
경로를 태운다. 🔴 이 파트를 빼면 검색 grounding 으로 답해 버려서(내용이 그럴듯해 더 헷갈린다)
진단이 안 된다 — 첫 시도에서 이걸로 한 번 헛돌았다.

```text
[SearchPolicy] OFF by multimodal(400) "현재 턴 멀티모달 — API가 grounding 거부"
[LangGraph] Starting SDK stream | model: gemini-3.7-flash | useGoogleSearch: false
[LangGraph] heavy media timeout after 90000 ms — no budget for retry/fallback, stopping
[LangGraph] SDK path failed for intent: general — falling back to LangChain (no streaming)
```

19초 영상 실측: 3.7 은 **90s 타임아웃 2회 · 성공 2회(15.5s·35.8s)** 로 간헐적이고, 같은 영상을
2.5 는 **17.3s** 에 처리했다. 즉 재시도하면 건질 수 있는 실패였다.

### 7.2 원인 — 없어진 캡을 근거로 폴백을 막고 있었다

```ts
// 무거운 미디어 턴 timeout은 이미 예산 대부분 소진 → 또 다른 시도/폴백은 60s 캡 초과.
if (isHeavyMediaTurn && isTimeout) { ...; break; }
```

그 60s 는 이미 없다. [route.ts](../../../../app/api/chat/route.ts) 는 `maxDuration = 300` 이고,
**같은 파일의 `HEAVY_MEDIA_CALL_TIMEOUT_MS` 주석이 이미** "강등 재시도까지 90×2=180s < 300s 로
예산 안에 든다"고 적고 있다(DEV_260808 §9). 상수는 새 근거로 고쳐 놓고 **이 분기만 옛 근거로
남아** 있었다 — 한 파일 안에서 근거가 갈라진 형태다.

### 7.3 수정

`heavyMediaTimeoutAction()` 을 [generation-config.ts](../../../../server/agent/nodes/generation-config.ts)
에 순수 함수로 빼고(하니스가 import 할 수 있게) 분기를 교체했다.

- 첫 타임아웃이고 아직 강등 전이면 → **2.5 로 1회 강등 재시도**
- 이미 강등했거나 처음부터 2.5 면 → 정지 (누적 폭주 방지)
- **키 로테이션은 계속 막는다** — 타임아웃은 키 쿼터가 아니라 모델 측 혼잡이라 키만 바꾸면
  90s 를 또 태운다. 바꿀 가치가 있는 건 모델이다

### 7.4 검증

배선은 상수를 3s 로 낮춰 **강제로** 태워 확인했다(간헐적이라 자연 발생을 기다릴 수 없다).

```text
[LangGraph] heavy media timeout after 3000 ms on gemini-3.7-flash
            — downgrading to gemini-2.5-flash for one retry (budget 6000ms < maxDuration 300s)
[LangGraph] Starting SDK stream | model: gemini-2.5-flash
```

이어서 상수를 원복하고 **실제 조건**으로 3.7 × 3회(11분 영상):

| run | 경과 | 경로 |
|---|---|---|
| 1 | 124.8s | 3.7 503 → 기존 강등 → 성공 |
| 2 | 108.2s | 3.7 503 → 기존 강등 → 성공 |
| 3 | **135.9s** | **3.7 90s 타임아웃 → 새 강등 재시도 → 성공** |

run 3 이 수정 전이라면 에러 문구가 나가던 자리다. 3회 모두 에러 없음.

회귀는 `test-thinking-config.mts` 46 → **53**(+7): 3.5/3.6/3.7 각각 "첫 타임아웃은 강등 · 강등
뒤에는 정지", "이미 2.5 면 강등할 곳이 없다".

> ⚖️ **트레이드오프**: 실패가 에러(90s)에서 정답(~135s)으로 바뀌는 대신 사용자가 더 기다린다.
> 300s 예산 안이고 SSE heartbeat(8s)가 연결을 유지하므로 받아들였다. 90s 를 낮춰 총 대기를

## 8. 남은 항목

- 이미 저장된 과거 답변에는 중복 URL이 남아 있다(8월 표본에서 1건). 화면에는 계속 보이지만 §4.1로 **모델에게는 더 이상 안 간다** — 백필 여부는 보류
- 모델이 맨 괄호로 쓰는 일반 URL(redirect가 아닌)은 그대로 둔다. 출처로서 의미가 있을 수 있어 일괄 제거는 하지 않았다
