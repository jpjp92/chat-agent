# URL Fetch 장애 후속 검증 및 공급자 정책 확정

> 날짜: 2026-08-23  
> 범위: GeekNews, Wikidocs, Brunch, OpenAI Web Search, ScrapingBee, browserless, Jina, Puppeteer/Cheerio

## 1. 최종 결론

URL 수집 장애는 하나의 원인이 아니었다.

1. GeekNews는 오래된 `Chrome/120` User-Agent를 거부했다. `Chrome/141`로 바꾸면 유료 공급자 없이 direct fetch가 된다.
2. Wikidocs는 Cloudflare challenge 때문에 direct, Jina, 일반 Puppeteer/browserless로는 안정적으로 읽히지 않는다.
3. 기존 ScrapingBee 키는 trial 1,000 credits를 초과해 `401`을 반환했다. 교체한 키와 `render_js=true + premium_proxy=true + country_code=kr` 조합은 Wikidocs 신규 글을 통과했다.
4. OpenAI Web Search는 검색에 색인된 일부 과거 Wikidocs 글은 읽지만 신규·미색인 글의 실시간 fetch를 대신하지 못했다. 모델을 바꿔도 같은 Web Search 접근 한계가 유지됐다.
5. Brunch 실주소는 현재 범용 폴백에서 성공한다. `/@other/999`는 회귀 하니스가 URL 불일치를 검증하려고 만든 가짜 URL이므로 실사이트 장애 표본으로 쓰면 안 된다.

현재 운영 정책은 다음과 같다.

```text
Wikidocs: cache → ScrapingBee render/premium/KR → browserless → 실패 안내
일반 URL: cache → direct → ScrapingBee static → ScrapingBee render/premium/KR → browserless → 실패 안내
OpenAI URL fallback: 기본 OFF, OPENAI_URL_FALLBACK_ENABLED=true일 때만 최후단에서 실행
ScraperAPI: 체인에서 제외
```

## 2. 사이트별 실측

| 사이트/URL | 방법 | 결과 | 판정 |
|---|---|---|---|
| GeekNews `topic?id=32713` | direct, Chrome/120 | 403 · 10 bytes | 낡은 UA 차단 |
| GeekNews `topic?id=32713` | direct, Chrome/141 | 200 · 169ms · `article` · 본문 7,604자 | 기본 경로로 채택 |
| GeekNews `topic?id=32713` | browserless `/unblock` | 200 · 4.4s · 본문 7,604자 | direct 실패용 보조 수단 |
| ZDNet 표본 | direct, Chrome/141 | 200 · 137ms · 본문 2,541자 | direct 정상 |
| Brunch `/@ghidesigner/532` | Node direct | `redirect count exceeded` | direct 불가 |
| Brunch `/@ghidesigner/532?codex_doc_probe=260823` | 로컬 `/api/fetch-url` | 200 · 8.89s · 본문 4,507자 · `provider=scrapingbee-static` | 범용 폴백 정상 |
| Brunch `/@other/999` | 실 URL 호출 | 502 | 테스트용 가짜 URL이므로 실패 정상 |
| Wikidocs `/blog/@aidevelopermm/29145/` | direct | 403 Cloudflare challenge | direct 불가 |
| 같은 Wikidocs 글 | ScrapingBee render/premium/KR | 200 · 5.66s · `article` · 본문 12,460자 · cost 25 | Wikidocs 1순위로 채택 |
| 같은 Wikidocs 글 | 변경 후 로컬 `/api/fetch-url` | 200 · 6.10s · 본문 13,085자 · fresh fetch | 종단 배선 정상 |

Brunch의 쿼리 파라미터는 캐시를 우회해 현재 공급자를 확인하기 위한 진단용이었다. Supabase `url_cache.provider`가 `scrapingbee-static`으로 저장된 것을 확인했다. 기존 쿼리 없는 캐시에는 과거 `browserless` 성공 결과가 남아 있었으므로, 화면 성공만 보고 현재 공급자를 추정하지 않았다.

## 3. Wikidocs 공급자 비교

### 3.1 실패한 경로

- direct Node fetch: `403`, `cf-mitigated: challenge`
- 일반 Puppeteer/Browserless: Cloudflare `Just a moment` 또는 403
- residential 옵션을 준 Browserless 표본: 동일하게 challenge
- Cheerio: 브라우저가 아니므로 받은 challenge HTML 이상의 정보를 만들 수 없음
- Jina Reader: HTTP 자체는 200이어도 본문이 `Performing security verification`인 보안 페이지
- ScrapingBee premium/JS에서 `country_code=kr`을 빼거나 조합을 달리한 표본: 500 또는 timeout

### 3.2 성공한 ScrapingBee 조합

```text
render_js=true
premium_proxy=true
country_code=kr
```

신규 키로 `/blog/@aidevelopermm/29145/`를 호출한 결과 HTTP 200, 약 5.66초, 본문 12,460자, `article`, `spb-cost=25`였다. 따라서 Wikidocs는 static과 direct를 생략하고 이 조합부터 시작한다.

기존 키의 실패 원인은 사이트가 아니라 계정이었다. 대시보드에서 `1,006 / 1,000` credits를 확인했고 API는 `401 Monthly API calls limit reached: 1000`을 반환했다. 라우터는 이제 401/402/429를 일반 본문 실패와 별도로 로깅한다.

## 4. OpenAI Web Search 검증

### 4.1 파라미터 수정

`gpt-5-mini`에 `reasoning.effort=minimal`과 `web_search`를 함께 보내면 400이 발생했다.

```text
The following tools cannot be used with reasoning.effort 'minimal': web_search
```

모델 capability를 `low`로 수정한 뒤 API 요청 자체는 완료됐다. 응답의 HTTP 200은 OpenAI Responses API가 완료됐다는 뜻이지, 대상 Wikidocs가 HTTP 200을 반환했다는 뜻이 아니다.

### 4.2 URL별 결과

| URL | 모델 | 결과 |
|---|---|---|
| Wikidocs `/156176` | GPT-5 mini, low | 실행 시점에 따라 실패/성공; 검색 색인 의존 |
| Wikidocs `/blog/@jaehong/8745/` | GPT-5 mini, low | 성공 · 본문 4,082자 · 약 25.6s · 10,619 tokens |
| Wikidocs `/blog/@jaehong/27125/` | GPT-5 mini, low | 실패 · `OPENAI_WEB_FETCH_FAILED` |
| Wikidocs `/blog/@aidevelopermm/29145/` | GPT-5 mini, low | 실패 · status completed/200이나 본문 없음 · 4,977 tokens |
| 같은 신규 글 | GPT-5.6 Luna, reasoning none | 실패 · 4,738 tokens · 약 2.06s |

과거 글 `/8745/`는 검색 결과에 본문이 색인돼 있었고 신규 두 글은 정확 URL 검색 결과가 없었다. 따라서 OpenAI는 브라우저형 실시간 스크래퍼가 아니라 색인된 문서를 일부 회수하는 보조 수단으로만 판단한다. 모델 교체로 해결되지 않았으므로 현재 기본값은 OFF다.

```text
OPENAI_URL_FALLBACK_ENABLED=false
```

구현과 회귀 하니스는 향후 재평가를 위해 유지한다. 명시적으로 `true`를 설정한 환경에서만 ScrapingBee와 browserless가 모두 실패한 뒤 호출한다.

## 5. 현재 라우팅과 남은 항목

### Wikidocs

```text
cache → ScrapingBee render/premium/KR → browserless → (OpenAI OFF) → FETCH_ERROR
```

### GeekNews

현재 코드는 일반 URL 체인을 사용하지만 Chrome/141 direct가 성공하므로 정상 시 유료 공급자를 호출하지 않는다.

```text
cache → direct → 성공
direct 실패 시 현재 구현: ScrapingBee static → render → browserless
```

검증상 더 싼 전용 순서는 `direct → browserless`지만, `news.hada.io` 호스트 특례는 아직 구현하지 않았다.

### Brunch

```text
cache → direct(redirect loop) → ScrapingBee static(검증 성공) → render → browserless
```

### 남은 위험

- 일반 URL 최악 예산은 direct 10s + static 15s + render 40s + browserless 30s로 95s다.
- 클라이언트 제한 65s보다 길어 공급자가 모두 느리게 실패하면 클라이언트가 먼저 중단할 수 있다.
- `url_cache`가 다시 사라지거나 쓰기 실패하면 모든 요청이 유료 공급자를 타므로 캐시 오류 로그를 유지해야 한다.
- Chrome/141 UA도 시간이 지나면 낡는다. 특정 사이트만 다시 403이면 최신 UA A/B를 먼저 수행한다.

## 7. 채팅 모델 선택지 확장

URL fetch용 OpenAI 실험과 채팅 모델 선택은 분리했다. URL 원문 fetch는 색인 의존 문제 때문에
기본 OFF지만, 일반 채팅용 Responses API는 별도 어댑터로 연결했다.

현재 선택 목록:

| 공급자 | 모델 | 상태 | 비고 |
|---|---|---|---|
| Google | Gemini 3.7 Flash | 선택 가능 | 기본 모델 전환 전 관찰 단계 |
| Google | Gemini 3.6 Flash | **기본값 유지** | 기존 운영 기준선 |
| OpenAI | GPT-5.4 mini | 선택 가능 | `reasoning.effort=none`, `store=false` |
| OpenAI | GPT-5.6 Luna | 선택 가능 | `reasoning.effort=none`, `store=false` |
| 이전 모델 | Gemini 3.5 / 2.5 Flash | 선택 가능 | 스크롤 아래 별도 그룹 |

OpenAI 채팅 어댑터는 Responses API를 사용하며 텍스트·이미지·웹 검색·출처 변환을 지원한다.
`OPENAI_API_KEY_TIER1`은 서버 환경변수에서만 읽고 요청에는 `store=false`를 명시한다.

라이브 테스트 결과:

| 모델 | 결과 | 응답 시간 |
|---|---|---:|
| GPT-5.4 mini | 성공 | 약 1.19s |
| GPT-5.6 Luna | 성공 | 약 2.67s |

라이브 테스트는 비용이 발생하므로 `npm test`에서 제외하고 `npm run test:openai-live`로만 실행한다.

## 8. 현재 모델 라우팅 정책과 구현 차이

목표 정책은 다음과 같다.

```text
텍스트·URL 본문·웹 검색·이미지·일반 intent → 사용자가 선택한 모델 유지
YouTube 자막 확보 → 자막 텍스트를 선택한 모델로 처리
YouTube 원본 영상·업로드 영상/오디오 → Gemini 2.5 capability fallback
GPT 쿼터/API 오류 → Gemini 자동 전환 금지, 사용자 안내
로컬 도구 intent → 장기적으로 선택 공급자의 function calling 사용
```

하지만 현재 구현은 완전히 공급자 독립적이지 않다.

- 초기 intent router는 선택 모델과 무관하게 Gemini 2.5 Flash Lite를 사용한다.
- `/api/chat`이 스트림 시작 전 `API_KEYS.length`를 검사한다.
- generator도 OpenAI 분기 전에 Gemini `getNextApiKey()`를 호출한다.
- 약품·약국·병원·동물병원·법령·영화·스포츠·날씨 intent는 아직 Gemini LangChain 도구 경로다.

따라서 **Gemini 키가 모두 소진된 뒤 GPT로 수동 전환해도 텍스트 요청이 막힐 수 있다.** 반대 방향인
GPT 소진 후 Gemini 전환은 Gemini 키가 정상이라면 다음 요청부터 가능하다. GPT-5.4 mini와 GPT-5.6
Luna는 같은 OpenAI 프로젝트의 크레딧·지출·사용량 한도를 공유하므로, 영구 한도 소진이면 GPT 모델만
바꿔도 복구되지 않는다. 모델별 RPM/TPM 제한일 때만 다른 GPT 선택이 도움이 될 수 있다.

상세 후속 계획은 [PLAN_MULTI_PROVIDER_ROUTING_260823](../../../plans/PLAN_MULTI_PROVIDER_ROUTING_260823.md)에 둔다.

## 9. 오류 정보 공개 정책

공급자 오류 원문은 서버 로그와 사용자 UI를 분리했다.

```text
서버 로그: model, status, code, type, name, raw message
사용자 UI: 등록된 ko/en/es/fr 안내 문구만 노출
```

UI에서 차단한 기술 문자열 예:

- `LLM returned empty response`
- `No API keys found in server environment`
- `Server error: 429`
- OpenAI/Gemini가 반환한 원문 오류 메시지와 내부 오류 코드

OpenAI 영구 소진 분류에는 다음 코드를 포함한다.

- `insufficient_quota`
- `credit_balance_exhausted`
- `organization_spend_limit_exceeded`
- `project_spend_limit_exceeded`
- `organization_usage_limit_exceeded`

일시적 429는 영구 소진과 분리해 잠시 후 재시도 안내를 표시한다. 게스트 메시지 제한은 기술 오류가
아니라 로그인 모달 전환 신호이므로 기존 동작을 유지한다.

## 10. 모델 선택·첫 화면 UI 정리

- 모델 메뉴를 `Google Gemini` / `OpenAI` / `이전 모델` 그룹으로 분리했다.
- 기본 펼침 높이에는 Google과 OpenAI 그룹을 모두 보여주고 이전 모델은 스크롤해서 확인한다.
- 모바일은 높이를 `60vh`로 제한한다.
- 모델 메뉴 스크롤은 인디고/바이올렛 계열 커스텀 스타일을 적용했다.
- 공급자 구분은 강한 배경색 대신 Gemini=인디고, OpenAI=에메랄드의 섹션 점·라벨·hover·체크에만 적용했다.
- 사이드바 스크롤은 별도 4px 반투명 스타일로 분리했다.
- 첫 화면 추천 칩을 기능명 중심에서 목적 중심으로 변경했다.

| 이전 | 변경 |
|---|---|
| 실시간 검색 | 최신 AI 뉴스 |
| 영화 상영표 | 오늘 볼 영화 |
| 약 정보 | 약 복용 확인 |
| 코드 작성 | Python 자동화 |

Python 예시는 `Python으로 엑셀 파일의 중복된 행을 제거하는 코드 작성해줘`로 바꿨고, 네 언어의
의미를 동일하게 맞췄다.

## 16. 약품 성분명 fallback 안내 누출 수정

### 증상과 원인

`류마티스 관절염에 좋은 약물` 다음 `우파다시티닙? 이건?`이라고 물으면 본문 설명은 정상인데 마지막에
식약처 알약식별 DB 미조회와 웹 검색 할당량 소진, 제품명·이미지 제공 불가 안내가 붙었다. 이는 전역
오류 UI가 아니라 `search_drug_info`의 내부 fallback 지시를 모델이 자연어로 재서술한 결과였다.

결함은 세 가지가 겹쳤다.

- 성분명·약물 계열도 제품명 전용 MFDS `item_name`으로 조회해 0건을 미등재 제품처럼 해석
- 약품 Google Search가 `DEFAULT_CHAT_MODEL` 3.6을 사용했지만 capability 표상 3.6 무료 Search는 미지원
- fallback 지시문이 DB·쿼터 상태를 사용자에게 말하는 문장으로 구성돼 route의 literal marker 제거를 우회

### 수정

- `search_drug_info` 스키마에 필수 `query_kind=product|ingredient_or_class` 추가
- 성분·일반명·기전·약물 계열은 MFDS 제품 조회를 건너뛰고 검색 근거 기반 Markdown으로 처리
- 정확한 판매 제품명만 MFDS 데이터가 있을 때 `json:drug` 카드 생성
- 내부 DB 범위, 검색 실패, API 키, 쿼터, fallback 상태를 사용자에게 반복·재서술하지 않는 순수 정책을
  `server/agent/drug-fallback-policy.ts`로 분리
- 약품 Google Search 모델을 `gemini-2.5-flash`로 고정하고 429 발생 키를 RPM/RPD cooldown 처리한 뒤
  남은 키로 회전
- Google leg 실패 후 DDG가 실제 실행돼 결과가 없었다면 전체 검색 장애·쿼터 소진으로 과장하지 않음

### 검증과 로컬 잔여

- 신규 `tests/test-drug-fallback.mts`: **15/15 통과**
- 전체 `npm test`: 통과, 기존 intent/search/알약 카드 회귀 없음
- `npm run typecheck`: 통과

로컬 종단 확인은 새 대화에서 ① `류마티스 관절염에 좋은 약물` ② `우파다시티닙? 이건?` 순으로
보내 마지막에 MFDS·쿼터·제품 이미지 안내가 붙지 않는지 본다. 대조군으로 구체적인 판매 제품명을
질문해 기존 `json:drug` 카드가 유지되는지도 함께 확인한다.

첫 로컬 종단 확인에서는 내부 실패 안내가 사라진 것을 확인했다. 다만 성분 후속 답변이 적응증·용량·부작용을
과도하게 나열했고, 사용자 입력 `우파다시티닙`과 국내 공식 표기 `유파다시티닙`의 차이를 설명하지 않았다.
이에 성분/계열 후속 답변은 직접 답변 뒤 최대 3개 짧은 섹션으로 제한하고, 사용자가 용량을 묻지 않았다면
적응증별 숫자 용량을 나열하지 않도록 했다. 검색 근거에 공식 표기 차이가 확인되면 첫 문장에서 한 번만
교정하도록 보강했다.

후속 검토에서 특정 `우파다시티닙 → 유파다시티닙` 매핑을 프롬프트 예시로 고정하면 사례 과적합과
상투적 응답을 유발할 수 있다는 점을 반영했다. 프로덕션 프롬프트·도구 설명에서는 두 명칭을 모두 제거하고,
성분명 입력을 그대로 검색한 뒤 반환된 근거가 다른 공식 한글명을 확인해 줄 때만 교정하는 일반 정책으로
변경했다. 근거가 없으면 모델 기억만으로 특정 오타 교정을 단정하지 않는다.

## 17. Gemini/OpenAI Search 공급자 프롬프트 매핑

### 문제

실제 API 배선은 Gemini의 `tools: [{ googleSearch: {} }]`와 OpenAI Responses의
`tools: [{ type: "web_search" }]`로 이미 분리돼 있었다. 그러나 두 경로가 공유하는 시스템 프롬프트는
항상 `'google_search' tool`, `Google Search is ACTIVE`라고 적혀 있었다. GPT 요청에서는 선언된
`web_search`와 프롬프트가 불일치해 검색·citation 판단이 흔들릴 수 있는 구조였다.

### 수정

- 순수 프로필 `server/agent/search-provider.ts` 추가
  - Gemini 검색 ON: `provider=Google Search`, `tool=googleSearch`
  - OpenAI 검색 ON: `provider=OpenAI Web Search`, `tool=web_search`
  - 검색 OFF: `provider=None`, `tool=none`, `enabled=false`
- Gemini SDK는 `decideGoogleSearch`의 실제 결과를 기준으로 매 요청의 system instruction에 프로필 주입
- OpenAI Responses 요청 빌더는 `useWebSearch`와 모델 capability를 기준으로 OpenAI/none 프로필 주입
- 공통 출처 방어와 `medical_qa` 힌트에서 Google 전용 표현을 제거하고 “이번 요청에 선언된 hosted web
  search capability” 기준으로 통일
- 사용자 선택 모델이 GPT여도 미디어 capability fallback으로 Gemini가 실행되는 턴은 실제 Gemini 요청의
  검색 상태를 기준으로 매핑

## 18. OpenAI 웹 검색 인용을 클릭 가능한 번호 UI로 정리

### 문제

OpenAI 웹 검색 답변은 문장 뒤에 `(orthoinfo.org)` 같은 긴 도메인 링크를 반복했고, 하단에는
`web_search_call.action.sources`의 조회 후보까지 모두 배지로 표시해 실제 인용 수보다 훨씬 많은 출처가
나왔다. 서버가 Responses의 `url_citation` annotation에서 URL과 제목만 평탄화하면서
`start_index`/`end_index`와 “실제 인용인지 단순 조회 후보인지” 구분을 버린 것이 원인이었다.

### 수정

- `url_citation`을 출현 순서대로 중복 제거해 동일 URL에 같은 `citationNumber` 부여
- 본문의 도메인형 Markdown 인용을 짧은 클릭 가능 링크 `[N]`으로 변환
- Markdown 링크 문자열이 없는 Responses 형식은 annotation의 `end_index` 뒤에 번호 링크 삽입
- `utm_*` 추적 파라미터와 fragment를 제거한 정규 URL을 본문·배지·DB에 공통 사용
- annotation이 존재하면 실제 인용된 출처만 하단 배지에 표시하고, 검색 후보 전체는 기본 UI에서 제외
- 하단 배지에도 `[N]`을 표시해 본문 번호와 대응; 일반 URL과 YouTube 출처 표시는 기존 유지
- 인라인 번호에 새 창 링크, 출처 제목 tooltip, `aria-label`, 키보드 focus ring 추가

기존 `grounding_sources` JSON 컬럼에 선택 메타데이터를 추가하므로 DB migration은 필요 없다. SSE의
sources 이벤트와 세션 재조회도 같은 객체를 보존한다.

## 20. 새 채팅에 이전 추천 문구가 복원되는 draft 상태 수정

- 데스크톱 중앙 입력창과 하단 입력창이 공통 `handleSendWithPrefillReset`을 사용하도록 변경

- 메시지 전송 진입 시 부모 prefill을 소진해 이후 재마운트 복원을 차단
- `npm run typecheck`, `git diff --check`: 통과

  시간으로 정렬하되 마지막 기준 데이터가 없으면 임의의 고유 순위 대신 공동 순위로 표시한다.
- 30명 표의 내부 세로 스크롤은 전체 순위 출력 정책과 양립하지만, sticky header와 불필요한 가로
  스크롤 제거는 UI 후속 항목으로 남긴다.

### 약국 카드 멀티턴 — 내부 지시문 노출 실패

재현 순서:

1. `전주시 덕진구에서 지금 영업 중인 약국 찾아줘` → 10개 중 영업 중 9개 카드 정상
2. `내가 안덕원로 사는데 가장 가까운 약국은?` → 안덕원로 재조회, 한사랑약국이 첫 항목으로 정상
3. `영업중인건 한사랑 약국뿐이네 여기로 가야겠다` → 새 검색으로 잘못 분류된 뒤 다음 문장이 UI 노출
   - `...약국 정보를 찾을 수 없습니다. [지시사항]: 제공된 search_web 툴을 사용하여...`

확정된 코드 경로:

1. 결과 확인·이동 의사인 3턴이 `pharmacy_search`로 다시 분류됐다.
2. 함수 인자에 세부 주소와 약국명이 함께 들어가 공공데이터 필터 결과가 0건이 됐다.
3. `pharmacy-tool.ts`의 0건 분기가 사용자 데이터와 내부 후속 지시를 하나의 문자열로 반환한다.
4. `local-tool-registry.ts`에서 약국은 `resultMode: fast-pass`다.
5. `generateOpenAIChat()`은 fast-pass 결과가 비어 있지 않으면 내용을 검증하지 않고 그대로 반환한다.

따라서 모델이 시스템 프롬프트를 자발적으로 공개한 문제가 아니라, **서버가 내부 제어 문구를 사용자에게
직접 전달 가능한 도구 결과에 섞은 trust-boundary 결함**이다. 성공 결과에도 `[지시사항]`이 들어 있지만
`json:pharmacy` 파서가 카드만 렌더링해 우연히 가리고 있었고, 0건에는 렌더러 블록이 없어 그대로 보였다.
병원·동물병원 no-result에도 같은 패턴이 있어 함께 정리해야 한다.

수정 기준:

- 카드 후속 코멘트/확인/선택은 general, 다른 위치·조건을 명시한 조회만 pharmacy_search로 분리
- 성공 도구 결과는 bare `json:pharmacy` 블록, 0건은 `pharmacies: []` 카드 또는 typed result로 반환
- fast-pass 경계에서 내부 지시 표식을 거부하는 defense-in-depth 추가
- first lookup·도로명 refine·코멘트·다른 지역·0건·지시문 비노출 회귀 테스트

## 22. 법령 카드 멀티턴에서 설명 요청이 같은 카드로 반복되는 문제

### 재현

1. `도로교통법 제44조 알려줘` → 현행 제44조 ①~⑥항 카드 정상
2. `음주운전에 관한 법률인데 시나리오별로 설명해줄 수 있어?` → 시나리오 설명 대신 제44조 카드 재출력

두 번째 함수 호출의 query에도 `음주운전에 관한 법률을 시나리오별로 설명해줘. 도로교통법 제44조 관련`이
정상 전달됐다. 따라서 사용자 문장이나 멀티턴 히스토리가 소실된 문제가 아니라, 설명 요청까지 원문 조회
경로로 보내는 intent/result-mode 설계가 원인이다.

### 확정된 코드 경로

1. `router.ts`의 `law_search` 설명이 `legal interpretation requests`까지 같은 intent로 분류한다.
2. `intentRules.ts`도 법률명·`제N조`를 포함하면 요청 동사와 관계없이 `law_search`로 잡는다.
3. `prompt.ts`의 law focus는 `lawTool`을 반드시 호출하고 결과를 수정·요약하지 말고 그대로 출력하라고 한다.
4. OpenAI `local-tool-registry.ts`에서 law는 `resultMode: fast-pass`라 선택 GPT가 조문을 설명할 합성 단계가 없다.
5. state에는 `weatherFollowup`·`movieContext`와 달리 `lawContext`/`lawFollowup`/`activeCards.law`가 없다.

즉 모델의 순간적인 의도 파악 실패가 아니라 **원문 조회와 법률 Q&A가 하나의 fast-pass intent에 합쳐진
구조적 결함**이다. 프롬프트에 `시나리오별` 예시 하나를 추가하는 방식으로는 요약·비교·쉽게 설명·사례 적용
등 다른 표현에서 반복되므로 해결되지 않는다.

### 수정 설계

- `law_search`: 법령 목록·법률 본문·특정 조문 원문 조회 전용, 카드 fast-pass 유지
- `law_qa`: 설명·요약·비교·시나리오·적용 질문 전용, law API 결과를 선택 모델이 합성
- 첫 턴부터 법률 설명을 요청하면 `law_qa → law API → selected model synthesis`
- 카드 후 설명이면 저장된 `json:law`/`lawContext`를 우선 사용해 재호출과 카드 중복 방지
- 현재 카드에 없는 처벌 조문·예외가 필요할 때만 추가 조회하고, 답변 문장마다 근거 조·항과 source URL 연결
- 판례·구체 사건의 위법성 결론처럼 Open API가 제공하지 않는 범위는 지어내지 않고 한계를 명시

### 회귀 기준

- `도로교통법 제44조 원문 보여줘` → 카드 1회
- `이걸 시나리오별로 설명해줘` → 카드 없이 제44조 각 항 기반 설명
- `음주측정 거부 처벌도 알려줘` → 필요한 처벌 조문 추가 조회 후 합성
- `이번에는 근로기준법 제60조 보여줘` → 새 법령 카드
- `쉽게 요약해줘`·`사례로 비교해줘`·`무슨 뜻이야?` 표현에서도 카드 반복 없음

## 23. 위치·법률 카드 멀티턴과 fast-pass 출력 경계 수정

약국에서 확인된 결함을 약국·병원·동물병원의 공통 카드 수명주기 문제로 수정했다.
`card-followup.ts`는 새 조회, 표시 카드 상세 질문, 선택·감사·확인, 무관한 주제 전환을 구분한다.
클라이언트는 최근 20개 메시지의 `json:pharmacy|hospital|vet|law` 블록과 가장 최근 카드 종류를
`activeCards`·`cardContexts`로 전송하며, 서버 히스토리 창 스캔은 구버전 폴백으로 유지한다.

- 카드 질문과 확인 코멘트는 `general + cardFollowup`, 검색 OFF로 전환한다.
- generator는 표시 카드 데이터만 근거로 텍스트 응답하고 카드 재출력과 없는 정보 추측을 금지한다.
- 다른 지역·도로·기관 요청만 기존 조회 intent로 새 카드를 만든다.
- 날씨·영화·코드·법률 등 다른 주제로 이동하면 위치 카드가 발화를 가로채지 않는다.

법령은 `law_search` 원문 fast-pass와 `law_qa` 근거 합성으로 분리했다. 첫 턴 설명 요청은 law API를
조회한 뒤 선택 모델이 합성하고, 표시 카드 범위 안의 설명은 저장된 카드 원문으로 답한다. 처벌·예외처럼
추가 조문이 필요한 요청만 API를 다시 호출하며 조문에 없는 판례·예외·사건 결론을 만들지 않는다.
Gemini LangChain 경로에서는 `law_qa`의 중간 `json:law` tool event를 SSE에서 숨겨 최종 설명이 카드에
가려지지 않도록 했다.

출력 경계도 함께 수정했다.

- 약국·병원·동물병원·법령·영화·날씨 도구는 `[지시사항]` 없이 bare fenced JSON만 반환한다.
- 0건·API 오류는 빈 배열과 사용자용 `notice` 카드로 반환해 원시 오류·환경변수명을 숨긴다.
- OpenAI fast-pass는 내부 지시 표식과 예상 카드 타입을 검증해 위반 출력을 거부한다.
- 클라이언트 `activeCards`·`cardContexts`는 서버에서 허용 타입·boolean·단일 JSON 블록·크기·JSON 문법을 검증하고 재직렬화한다.
- 빈 결과 렌더러는 안전한 `notice`를 표시한다.

약국·병원·동물병원·법령 UI 종단 멀티턴은 로컬 수동 확인 대상으로 남긴다.

## 24. 도로명 약국 검색 공급자 차이와 영업 상태 모순 수정

로컬 재검증에서 같은 후속 질문 `내가 안덕원로 사는데 가장 가까운 약국은?`에 공급자별 차이가
확인됐다.

- Gemini 선택 화면: 도로명 주소 검색을 지원하지 않는다며 시·군·구 검색만 가능하다고 거절
- GPT-5.4 mini: `keyword="안덕원로"`로 약국 함수를 호출해 주소 일치 카드를 정상 출력
- GPT 후속 `안덕원로 근처는 모두 문닫았네?`: payload의 모든 `is_open_now`가 `false`인데도
  `hours_today` 문자열을 보고 일부가 영업 중이라고 잘못 답변

첫 차이는 화면에 표시된 Gemini 3.7 자체의 검색 능력 차이가 아니다. 외부 API 카드 intent는 비용·속도
정책상 선택 모델과 별개로 Gemini 2.5 Flash LangChain tool-router를 사용하며, 이 경로가 도구 선택을
`AUTO`에 맡긴 상태였다. 약국 도구는 이미 주소 문자열의 부분 일치 필터를 지원했지만 prompt와 tool
description에 도로명 지원 계약이 약해 모델이 호출 전 자체 거절했다.

수정:

- 약국·병원·동물병원 등 단일 로컬 카드 intent의 첫 호출은 Gemini `tool_choice`와
  `allowedFunctionNames`로 도메인 함수를 강제한다. ToolMessage 이후에는 강제를 해제해 `law_qa` 합성
  재귀를 막는다.
- 위치 카드 도구의 빈 결과는 더 이상 `search_web`로 넘기지 않으므로 약국·병원·동물병원 경로에서
  불필요한 웹 검색 도구를 제거했다.
- 약국 prompt/schema/description에 도로명·세부 주소·동·약국명 `keyword` 지원을 명시하고,
  “시·군·구만 검색 가능”이라는 잘못된 거절을 금지했다.
- 도로명 결과는 주소 일치 목록이지 거리순이 아니다. 사용자 좌표와 거리 계산이 없으면 정확한
  `가장 가까운 약국`으로 단정하지 않고 카드에 안내 문구를 표시한다.
- 약국 payload에 `checked_at`을 추가했다. 후속 합성 전 서버가 `is_open_now` boolean으로 영업 중·종료
  수와 이름을 `PHARMACY_CARD_FACTS`로 계산하며, `hours_today`는 예정 시간일 뿐 현재 상태보다 우선할
  수 없도록 했다.

검증: `tests/test-card-followup.mts` **30/30**, `npm run verify` 전체 통과. 알려진 기존 관측 항목인
`목성의 위성은 몇 개야? → general` 1건 외 신규 회귀는 없다.
