# DEV_260531 — general intent 검색 라우팅 (needsSearch)

> 작성일: 2026-05-31  
> 기획: [PLAN_LATENCY_SEARCH_ROUTING.md](../../../plans/PLAN_LATENCY_SEARCH_ROUTING.md) · 변경요약: [PLAN_CHANGES_LATENCY_SEARCH_ROUTING.md](../../../plans/PLAN_CHANGES_LATENCY_SEARCH_ROUTING.md)

## 배경 / 목적

`general` intent에서 **검색이 불필요한 질문(코드·번역·개념설명·계산 등)에도 Google Search가 항상 켜져** 불필요한 2-track(Stage1 2.5+search → Stage2 3.5 synthesis) 경로를 타며 지연이 발생.

→ `general`에 한해 **검색 필요 여부(needsSearch)** 를 판정해, 필요한 질문(날씨·뉴스·최신·인물·시세 등)만 Search를 켠다.  
기존 13-intent 분류·tool 로직·image/url/video/renderer/medical 분기는 **전부 보존**.

핵심 전제: 검색 필요 여부는 13-intent와 **직교(orthogonal)**. `general`만 모호하므로 `general`에서만 판정.

---

## 설계 (3-게이트 + 멀티턴 가드)

| 신호 | 판정 | 처리 |
|---|---|---|
| 강한 OFF (코드/번역/창작/계산/개념) | `off` | Search off |
| 강한 ON (시의성/실시간/명시검색/인물근황/순위/기업지표) | `on` | Search on |
| 회색지대 | `gray` | router LLM(lite) `needs_search` 판정 → 누락 시 **default-on** |

- **default-on 안전판**: 판정 누락/회색지대 시 `true` → 기존(항상 검색)과 동일하게 폴백.
- **멀티턴 가드**: 직전 턴 검색됨 + 현재 메시지가 follow-up 가공형(요약·정리·비교·방금 등)이면 재검색 억제. 단 "더 최신 걸로" 같은 **새 최신요구(temporal/domain ON & not past-ref)** 는 ON 유지.
- **prevSearched 근사(A안)**: grounding 마커가 히스토리에 영속되지 않으므로(route.ts가 content만 복원), **직전 human 메시지에 `classifySearchNeed` 재적용 → ON이면 prevSearched≈true**.

## 수정 파일

### 1. `server/agent/intentRules.ts` (검색 판정 로직 신규)
```ts
export type SearchDecision = "on" | "off" | "gray";
export const classifySearchNeed = (text: string): SearchDecision => ...;
export const isFollowupReference = (text: string): boolean => ...;
export const isPastReference = (text: string): boolean => ...;
export const shouldSuppressSearchForFollowup = (currentText, prevSearched): boolean => ...;
```
- `SEARCH_OFF_PATTERNS`(7), `SEARCH_ON_PATTERNS`(temporal·domain·explicit·person·ranking·finance), `FOLLOWUP_REF_PATTERN`, `PAST_REF_PATTERN` 추가.
- 기존 export(`classifyIntentByRules`, `hasMedicalIntentKeyword` 등) 불변.

### 2. `server/agent/state.ts` (`needsSearch` 필드)
```ts
needsSearch: Annotation<boolean>({
    reducer: (x, y) => y ?? x,   // ?? 필수 — boolean이라 || 금지 (false 보존)
    default: () => true,          // default-on 안전판
})
```
> **주의**: reducer에 `||`를 쓰면 `false`가 default(`true`)로 덮인다. 반드시 `??`.

### 3. `server/agent/nodes/router.ts` (needsSearch 산출)
- router LLM 프롬프트 출력에 `needs_search` 추가 → `{"intent":"...","needs_search":true}` (intent 판정과 **동일 콜**, 추가 LLM 호출 없음).
- `general`에 한해: rule이 `on`/`off`면 그 값, `gray`면 LLM `needs_search`, 둘 다 없으면 `true`.
- 반환에 `needsSearch` 포함. fast-path(YouTube/drug)는 early-return 유지(generator 게이트가 별도 제어).

### 4. `server/agent/nodes/generator.ts` (게이트 6·7)
- renderer 게이트 직후, **`intent==='general' && useGoogleSearch===true`**("순수 general")일 때만:
  - 게이트7: `useGoogleSearch = state.needsSearch`
  - 게이트6: 직전 human으로 `prevSearched` 근사 → `shouldSuppressSearchForFollowup`이면 `useGoogleSearch = false`
- image/url/video/renderer는 이미 `useGoogleSearch=false`라 제외, medical_qa는 `intent!=='general'`이라 제외 → **기존 동작 무손상**. `useGoogleSearch=false`면 기존 로직상 single-pass 자동 전환.

## 추가 버그픽스 (동일 세션, 테스트 중 발견)

### 5. `generator.ts` — 3.5-flash MALFORMED_FUNCTION_CALL 빈응답 → 2.5 폴백

**증상**: `gemini-3.5-flash` single-pass(`useGoogleSearch=false`, tool 없음)에서도 `finishReason: MALFORMED_FUNCTION_CALL` + 빈 텍스트. minimal thinking 재시도 후에도 동일.

**원인**:
- systemInstruction에 JSON/구조화 출력 지시가 있어 3.5-flash가 function-call 토큰을 흉내내다 깨짐.
- `thinkingLevel: "low"` → thinking에서 토큰을 소진하면 빈 텍스트가 남는 경우 발생.
- 기존 코드는 `finishReason === 'SAFETY'`만 특별 처리, MALFORMED는 `throw 'SDK returned empty response text'` → LangChain 폴백 → LangChain은 `bindTools`로 또 function-call 시도 → 또 empty.

**수정** (`server/agent/nodes/generator.ts`, single-pass 빈응답 블록):
```ts
if (finishReason === 'MALFORMED_FUNCTION_CALL' && effectiveModel !== SEARCH_FALLBACK_MODEL) {
    // 2.5-flash로 1회 폴백 (tool 없이, thinkingBudget:0)
    const mfRetry = await genai.models.generateContent({ model: SEARCH_FALLBACK_MODEL, ... });
    responseText = mfRetry.text?.trim() ?? '';
}
```
- `MALFORMED`일 때만 동작 → 기존 경로(SAFETY/정상응답) 무영향.
- 2.5-flash는 이 패턴에서 MALFORMED 거의 없음.

### 6. `generator.ts` — Two-track stage1(2.5+search) empty → 키교체 1회 재시도

**증상**: `Two-track stage1 returned empty grounded text` → LangChain 폴백 → 또 빈응답 → `LLM returned empty response` 사용자 에러.

**원인**:
- 2.5-flash + googleSearch가 grounding은 하면서 텍스트만 비우는 간헐적 케이스 존재.
- 기존 코드는 stage1 empty 시 즉시 `throw` → LangChain 폴백(bindTools → 또 깨짐)으로 낙하.
- stage1에 재시도 로직이 전혀 없었음.

**수정** (`server/agent/nodes/generator.ts`, stage1 empty 직후):
```ts
if (!stage1Text) {
    // 키 교체 후 stage1 1회 재시도
    const s1RetryKey = getNextApiKey() ?? sdkApiKey;
    const s1Retry = await new GoogleGenAI({ apiKey: s1RetryKey }).models.generateContent({
        model: SEARCH_FALLBACK_MODEL, tools: [{ googleSearch: {} }], ...
    });
    stage1Text = s1Retry.text?.trim() ?? '';
}
if (!stage1Text) throw new Error('Two-track stage1 returned empty grounded text');
```
- 성공 시 정상 stage2 진행, 실패 시에만 기존 throw.

**"왜 자주"의 결론**:
- needsSearch=true → 3.5 free-tier 불가 → 항상 two-track (2.5+search × 2회 호출) → 빈응답 확률 누적.
- 수정 #5·#6 적용 후 테스트: MALFORMED 없음, stage1 empty 없음, 두 턴 모두 정상 성공 확인.

**검증**: `npx tsc --noEmit` → **0 errors** (두 수정 모두)

### 8. 사이드바 세션 정렬 버그 수정 — Supabase 트리거 `trigger_session_updated_at`

**증상**: 새로고침 시 가장 최근에 메시지를 보낸 세션이 아닌, 마지막으로 타이틀이 업데이트된 세션이 상단에 배치됨. 특히 새 세션에서 첫 번째 문서 첨부 전송 후 새로고침하면 해당 세션이 최상단으로 이동.

**원인 분석**:
- `sessions/route.ts` GET은 `order('updated_at', { ascending: false })`로 정렬
- `chat_sessions.updated_at`은 `updateSessionTitle` PATCH 호출 시에만 갱신됨 (`useChatStream.ts:441`)
- `updateSessionTitle`은 `latestHistory.length <= 2` 조건(첫 번째 교환)에서만 호출
- 후속 메시지는 `updated_at`을 갱신하지 않으므로 순서가 고정

**수정**: Supabase에 `trigger_session_updated_at` 트리거 추가 — `chat_messages INSERT` 이벤트 시 해당 `session_id`의 `chat_sessions.updated_at`을 `NOW()`로 자동 갱신. 앱 코드 변경 없음, DB 레벨에서 원자적으로 처리.

```sql
CREATE OR REPLACE FUNCTION update_session_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  UPDATE chat_sessions SET updated_at = NOW() WHERE id = NEW.session_id;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trigger_session_updated_at
AFTER INSERT ON chat_messages
FOR EACH ROW EXECUTE FUNCTION update_session_updated_at();
```
