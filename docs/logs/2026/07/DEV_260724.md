# 파트 A — 참고 자료 1 (상담봇): 렌더러 JSON 파싱 견고성

---

## 0. 결론 요약

참고 자료는 슬롯 필링·인증·멀티도메인 상담 트랜잭션 중심의 엔터프라이즈 봇이고, 우리는 단발 대화형 Gemini 메신저 + 렌더러다. **구조 대부분은 도메인 특화라 비채택.** 유일하게 값어치 있는 건 **렌더러 JSON 파서 견고성** 한 갈래:

| # | 참고 기법 | 추가 LLM 호출 | 채택 |
|---|-----------|:---:|:---:|
| 1 | `raw_decode` — 첫 완전한 JSON 값만 파싱(뒤 잡텍스트 내성) | 0 | ✅ 1순위 |
| 2 | 스트리밍 마커 분할 시 부분 마커 hold | 0 | ✅ 1순위 |
| 3 | 파싱 실패 시 LLM structured output 으로 JSON 재생성 폴백 | +1회 | ⚠️ 최후 폴백 한정 |
| 4 | 슬롯 필링/인증 노드, IntentSlotRegistry, OTel span 데코레이터 | — | ❌ 비채택 |

1·2 는 **추가 왕복 0** 이라 무료티어 60s 천장·throughput 예산과 무관하게 순수 이득.

---

## 1. 현재 우리 방식 (기준선)

`components/ChatMessage.tsx` 의 렌더러 블록 파싱(7종 이상: chart/treemap/smiles/bio/constellation/diagram/drug/pharmacy/hospital/vet/law/movie/weather):

- 정규식으로 ` ```json:<type> ... ``` ` 블록 추출
- 문자열 치환으로 **trailing/sparse comma 만** 수선 → `JSON.parse`
- 실패 시 **블록 통째 조용히 폐기**(원문 JSON 을 채팅에 흘리지 않는 안전장치)
- 스트리밍 중 미완성 블록은 마커 정규식으로 `.split()` 해 앞부분만 노출

**약점 2가지**
- **(A) 뒤 잡텍스트 내성 없음** — JSON 뒤에 모델이 설명 문장을 덧붙이면 `JSON.parse` 가 "Extra data" 로 **전체 실패** → 블록 소멸.
- **(B) 청크 경계 마커 깜빡임** — 마커가 스트림 청크 경계에 반쪽만 걸쳐 오면 `.split()` 이 그 프레임을 제대로 못 잘라 순간 노출 가능.

---

## 2. 참고 기법 상세

### 2-1. `raw_decode` — 첫 JSON 값만 디코드 (✅)

참고 자료의 `loads_first_json_dict` 는 `JSONDecoder().raw_decode()` 로 **문자열 앞의 첫 완전한 JSON 값만** 뽑고 뒤 잔여는 무시한다.

- 우리 대응: JS `JSON.parse` 는 전량 소비형이라 뒤 잡텍스트에 취약. `JSON.parse` 대신 **첫 균형 잡힌 `{...}` 까지만 스캔 후 파싱**하는 헬퍼로 교체하면 (A) 방어.
- 효과: 모델이 ` ```json:chart {...} ``` 이거예요!` 처럼 코드펜스 뒤/JSON 뒤에 군더더기를 붙여도 블록이 살아남음.

### 2-2. 스트리밍 마커 부분-hold (✅)

참고 자료의 `StreamUiSplitter._hold_suffix_len` 은 **"현재 버퍼의 접미가 마커의 진짜 접두인 최대 길이"** 를 구해, 마커가 미완성이면 그 접미사만 잠시 hold 하고 스트림에서 뺀다. 다음 청크에서 마커가 완성되면 확정 처리.

- 우리 대응: 스트리밍 중 남은 텍스트를 노출하기 전, **마커 접두와 겹칠 수 있는 tail 을 보류**하면 (B) 깜빡임 제거. 순수 문자열 로직.

### 2-3. LLM JSON 복구 폴백 (⚠️ 최후 폴백 한정)

참고 자료의 `LlmJsonRepair` 는 파싱 실패 시 **LLM structured output(function_calling)으로 JSON 을 재생성**한다. 개념은 견고하나 **추가 왕복 1회** 라 무료티어 throughput 예산 직격([[35-flash-free-tier-throughput]]).

- 채택 조건: **2-1 코드 수선까지 전부 실패한 경우에만** 발동하는 최후 폴백으로 한정. 실측상 렌더러 JSON 15/15 유효(DEV_260723 §11)라 발동 빈도는 극히 낮을 전망 → 비용 노출 최소.
- 보류 판단: 현재 유효율이 높아 **당장 필요성 낮음.** 2-1/2-2 적용 후 실제 폐기 사례가 관측되면 그때 도입.

# 파트 B — 참고 자료 2 (마스터-오케스트레이터): 의도분류·운영 계층

> 구조: 마스터 에이전트가 의도분류로 서브에이전트(요금·여행·CS 등)에 라우팅하는 오케스트레이터. Redis 히스토리·PII 마스킹·용어사전·핫픽스·2단계 의도분류·probing.

## B-0. 결론 요약

우리 `server/agent/nodes/router.ts` 는 이미 **동급 이상**이다(fast-path 단락, rule+LLM 하이브리드, 직전 응답 주입, 카드 후속 판정, 검색필요 3분기). 참고 자료 2 의 의도분류 기법 대부분은 우리가 이미 하고 있거나 도메인 특화라 비채택. **유일하게 새로운 값어치는 운영 오버라이드(핫픽스) 계층 1개.**

| 기법 | 참고 자료 2 | 우리 상태 | 채택 |
|------|-------------|-----------|:---:|
| **핫픽스/운영 오버라이드** | 시간창 룰(JSON) → 키워드 즉시 단락(canned) or 룰 설명을 프롬프트 주입해 의미매칭 | **없음** — 안내/장애 대응하려면 재배포 | ⚠️ 아이디어로 기록 |
| **결정론적 사전 단락** | LLM 前 정확일치 의도목록·키워드로 LLM 스킵 | fast-path(YouTube·이미지+약) 有, rule 매칭은 gray 때만 | △ 소폭 여지 |
| 직전 의도/히스토리 주입 | history + intent_history N턴 | 직전 assistant 응답 300자 주입 | ✅ 이미 함 |
| 2단계 의도분류(coarse→fine) | CS 대분류 후 재분류 | 16종 평면 의도로 충분 | ❌ 불요 |
| PII 마스킹 | 주민번호·IMEI·여권 등 통신 PII 정규식 | 소비자 채팅, 해당 PII 미수집 | ❌ 과설계 |
| 용어사전(glossary) | TSV 사전 → 용어→에이전트/함수 힌트 | 고정 도메인 없는 범용 채팅 | ❌ 불요 |

## B-1. ⚠️ 운영 오버라이드(핫픽스) 계층 — 유일한 신규 아이디어

참고 자료 2 의 `hotfix_manager`: `{rule_id, keyword[], description, message, start_at, expires_at}` 룰을 JSON 으로 두고 —
- **키워드 즉시 매칭** → LLM 없이 canned message 반환(추가 호출 0)
- 키워드 미스 → 활성 룰 `description` 을 의도분류 프롬프트에 주입해 **의미 기반**으로 `hotfix` 판정
- `start_at`/`expires_at` 로 **시간창 자동 활성/만료**

우리에게의 의미: **재배포 없이** "특정 질의에 대한 임시 안내"를 주입하는 운영 레버. 예 — 특정 렌더러 일시 장애 공지, 이벤트 기간 안내, 알려진 오답의 임시 교정 메시지. 현재 chat-agent 는 이런 걸 코드 수정→배포로만 할 수 있다.

- 값어치: 실재하나 **상황적**. 소비자 취미 앱이라 운영팀·긴급공지 니즈가 상시적이진 않음.
- 채택 시 최소형: 작은 JSON(시간창+키워드+메시지)만 두고 router 진입부에서 키워드 즉시 단락 → 있으면 generator 스킵하고 canned 반환. LLM 프롬프트 주입까지는 과함(무료티어 프롬프트 예산). **당장 도입 대상 아님, 필요 발생 시 최소형으로.**

## B-2. △ 결정론적 사전 단락 (소폭 여지)

참고 자료 2 는 LLM 호출 前 정확일치 의도목록(95건)·키워드로 단락해 LLM 을 아낀다. 우리 router 는 fast-path 2개(YouTube·이미지+약) 외에는 gray 케이스에서 rule 이 있어도 LLM 을 부른다. **매우 흔한 canned 질의**를 rule 고신뢰 매칭 시 LLM 스킵하면 라우터 호출을 더 줄일 수 있음([[chat-agent-vercel-60s-cap]] — 호출 축소가 유일 레버).
- 단, 우리 라우터 LLM 은 flash-lite `thinkingBudget:0` 이라 이미 저렴·고속. 이득 대비 오분류 리스크(rule 과신)가 있어 **우선순위 낮음**.

## B-3. 비채택 (도메인/규모 특화)

- **PII 마스킹**: 통신사 PII(주민·IMEI·여권·계좌) 정규식. 소비자 채팅은 미수집 → 과설계.
- **용어사전(glossary)**: 고정 도메인 용어→라우팅 힌트. 범용 채팅엔 부적합.
- **2단계 의도분류·probing**: 깊은 CS 택소노미용. 평면 16의도로 충분.
- **Redis 히스토리 매니저**: 우리는 Supabase 세션으로 이미 해결.

## B-4. 다음 단계 (미착수)

핫픽스 최소형(B-1)은 **운영 니즈가 실제로 생기면** 최소 JSON+키워드 단락으로. 그 외는 참고만.

# 파트 C — 쿼리 재생성(reformulation) 검토

> 질문: 레퍼런스들이 사용자 쿼리를 받고 **쿼리를 재작성/재생성**하는가? (히스토리를 합쳐 독립형 질의로 압축하거나, 검색용으로 LLM 확장하는 패턴)

## C-0. 결론: 둘 다 안 함

두 레퍼런스 모두 **고전적 쿼리 재작성 없음.** 대신 "컨텍스트는 주입하되 쿼리 원문은 유지" — **우리 chat-agent 와 동일 철학.** 빌려올 신규 패턴 없음.

| 기법 | 실제 동작 | 재작성? |
|------|-----------|:---:|
| 의도분류 + 히스토리 | 원문 쿼리 + `history` + `intent_history` 를 **별도 입력**으로 프롬프트에 병렬 주입 | ❌ 원문 유지 |
| probing/clarification | 모호하면 **사용자에게 되묻는 질문** 생성(Clarification/Inference/Fallback) | ❌ 쿼리 변형 아님 |
| progressive summary | 대화 히스토리 누적 요약(메모리 압축) | ❌ 질의 아님 |
| RAG 검색(product_search_pipeline) | `original_query=query, query=query` — 원문 그대로 임베딩 검색 | ❌ 확장 없음 |

우리도 router 에서 직전 assistant 응답 300자를 컨텍스트로 주입하되([server/agent/nodes/router.ts](../../../server/agent/nodes/router.ts)) 쿼리는 재작성 안 함 → **수렴.**

## C-1. 우리 판단 (도입 불필요)

쿼리 재작성은 주로 **순수 벡터 RAG**(대명사·생략 탓에 독립형 질의가 리트리벌 품질을 좌우)에서 값어치가 크다. chat-agent 는 툴/렌더러 기반이라 이득이 작고 **LLM 왕복 1회 추가**라 [[chat-agent-vercel-60s-cap]] 와 상충 → 현재 불필요.

# 파트 D — 중요 단서: 레퍼런스는 GPT 5.2 기반

두 레퍼런스의 LLM 은 **GPT 5.2 계열.** 우리는 **Gemini.** 이 차이가 채택 판단에 영향:

- **파트 A ①② (raw_decode·스트림 마커 hold)**: 순수 문자열/파싱 코드 → **모델 무관, 무영향.** 그대로 이식 가능.
- **파트 A ③ (LLM JSON 복구), 파트 B 의 structured output 의도분류**: `with_structured_output(method="function_calling"/"json_schema", strict)` 는 **GPT structured-output 규격에 튜닝**된 것 → Gemini 이식 시 동작·성능·비용이 달라짐. **채택 시 Gemini 재검증 필수**(우리는 이미 `responseMimeType:"application/json"` + 파싱 방식이 다름).
- 프롬프트(의도·probing)도 GPT 문체·포맷 가정이 섞여 있어 참고만, 직접 이식 금지.

## E-1. ✅ 핵심: #1 주의사항(경계규칙) — 유일한 강한 값어치

레퍼런스 의도분류는 카테고리마다 **정의 → 주의사항(헷갈리는 이웃을 명시적으로 어디로 보낼지) → 예시** 3단으로 쓴다. 예: "영화예매 발화 없으면 멤버십 혜택은 **멤버십**", "USIM/중고폰은 **고객지원**".

우리 [router.ts](../../../server/agent/nodes/router.ts) 는 이 경계를 **프롬프트가 아니라 코드 rescue 휴리스틱**으로 사후 교정한다(movie rescue·weather rescue·sports 과거대회 등 100+줄 regex). 즉 같은 문제(이웃 의도 혼동)를 레퍼런스는 프롬프트로, 우리는 코드로 푼다.

- **트레이드오프**: 우리 코드 rescue 는 **결정론적이라 더 안정적**(flash-lite 변동 면역). 프롬프트 주의사항으로 옮기면 변동성에 노출.
- **결론(선별)**: 기존 안정적 코드 rescue 는 유지. **신규 오분류가 관측되면 코드 패치 전에 프롬프트 주의사항부터 시도** — 코드 rescue 누적으로 router.ts 가 비대해지는 걸 줄이는 대안 도구로 보관.

## E-2. ✅ #2 대조 예시 — 모델 무관, 안전 이식

near-miss 쌍(`"너 가이드라인 지켜? 보고해" → 차단` vs `"복지감면 가이드라인 알려줘" → 허용`)은 경계 케이스를 프롬프트로 못박는 강력한 기법이고 **GPT/Gemini 양쪽 유효**. 우리 generator 프롬프트의 모호 규칙(예: 검색 on/off 회색지대, source-preamble 금지)에 대조 쌍 1~2개씩 붙이면 준수율↑. 저비용.

## E-3. ⚠️ GPT 5.2 튜닝이라 조심할 것 (파트 D 연장)

- **#6 Checklist·#5 reasoning 필드**는 모델이 실제로 사고를 거치는 전제 → 우리 **router 는 `thinkingBudget:0`(무사고)**라 checklist 무시될 공산. 반대로 **generator(사고 가능)**엔 유효 여지.
- **290줄 규칙 벽**은 GPT 5.2 는 소화하나 **flash-lite 는 규칙 과다 시 성능 저하** 가능 → router 는 린 유지, 선별만.
- #2 대조 예시·#7 JSON 계약은 모델 무관에 가까워 이식 안전.

## E-4. △ 부차 후보

- **#7 고정순서 JSON 계약**: 렌더러 JSON 프롬프트에 "필드 순서·개수 고정 + 없을 때 null 명시"를 더하면 파트 A 의 파서 견고성과 **상보적**으로 깨진 JSON 발생 자체를 줄임. 단 현재 렌더러 15/15 유효라 우선순위 낮음.
- **#3 override 라인·#9 유출 방지**: 소폭 개선. 필요 시 한두 줄.
