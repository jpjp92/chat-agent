## §1. 배경 / 문제

현재 챗봇엔 **전용 날씨 툴이 없음.** "오늘 날씨 어때?"는:

1. [intentRules.ts:108](../../../server/agent/intentRules.ts#L108)에서 `domain` 태깅 → [router.ts:106](../../../server/agent/nodes/router.ts#L106) `search:true` 트리거
2. **Google Search grounding**(SDK 경로)으로 실시간 검색
3. [prompt.ts:10-35](../../../server/agent/prompt.ts#L10)의 지시대로 LLM이 마크다운 표(현재+5일 이모지 표)를 **직접 생성**

**문제점:**
- **느림** — grounding 왕복 + LLM 표 생성으로 15s+. [Vercel 60s 천장](../../../CLAUDE.md) 압박
- **부정확** — 숫자를 LLM이 grounding 텍스트에서 뽑아 씀 → 할루시네이션·stale 위험
- **비구조적** — 카드가 아니라 매번 재생성되는 마크다운 표

키(`OPENWEATHER_API_KEY`·`KMA_API_KEY`)는 이미 `.env`에 보유. 배선만 안 된 상태.

## §3. 격자좌표: 하드코딩 → 공식

레퍼런스는 24개 도시 `nx/ny`를 [`KMA_CITIES` 표](../../../reference/news/app/api/weather/route.ts#L199)에 하드코딩(→ 24개 도시 제약). 대신:

- **`dfsXyConv(lat,lon)` LCC 공식**(Lambert Conformal Conic, ~30줄, 오프라인·결정론적) 채택 시 표 폐기 + **전국 커버**.
- 파이프라인: `도시명 → OpenWeather geocoding(이미 있음, lat/lon) → dfsXyConv → nx/ny → KMA`.
- **단** `shortRegId`(육상예보)·`stnId`는 공식 없음(코드표 파일만) → **육상예보(`getLandFcst`) 생략 권장**. 카드 본체 무관 + notes는 규칙기반 `weatherNotes`로 충분 + **KMA 호출 3→2종(33%↓)**.

**KMA API Hub 쿼터**: 20,000회/일(00시 KST 리셋)·5GB. 2종/조회 → ~10,000 KR조회/일로 넉넉. 캐싱(Supabase TTL, `url_cache` 테이블 패턴 차용)이 쿼터 방어선.

## §7. 강수량 표시 정책 + KMA PCP 파싱 (2026-07-06 추가)

**계기**: 라이브 news 프로젝트에서 route.ts+Weather.tsx 수정 — "현재 관측 0mm 대신 **오늘 예상 강수량** 표시" + "KMA 강수량 문자열을 놓치지 않게". **2026-07-06 `git pull`로 실제 diff 확인**(commit `e8fe197`) → 아래 §7-2/7-3의 예측이 실제 구현과 일치 확인됨.

### 7-1. 왜 "현재 관측"이 아니라 "오늘 예상"이어야 하나

KMA 초단기실황 `RN1`(1시간 누적 강수)은 **지금 세게 오는 중이 아니면 거의 0** — 비 예보가 있어도 0 표시. 실측 대조:
- 2026-07-05 23시 서울 초단기실황: `RN1=0`, `PTY=0` (관측상 무강수)
- 같은 시각 서울 단기예보(`getVilageFcst`): `PTY=1`(비), `POP 30~60%`, `PCP 2.0~13.0mm` → **오늘 비 옴**
- OWM 현재: `보통 비 rain.1h=1.52mm` (모델·보간이라 KMA 관측보다 실시간·광역)

→ **카드 강수 지표 = 오늘 예상(POP% + 예상 mm)을 primary, "지금" 상태는 PTY/description 병기.** `PTY>0 && RN1==0`(비인데 0mm)은 "약한 비/곧 비" 문구 처리.

**✅ 라이브 프로젝트 실제 채택(commit `e8fe197`)**: `current>0 → "Xmm 현재"`, `elif expected(daily[0])>0 → "Xmm 예상"`, `else "0mm"` (둘 다 보존, 라벨로 구분). StatItem "강수량"+"강수확률" 분리 신설, 5일 카드에 `강수량` 줄 추가. `kmaNotes`도 `RN1>0 ? "최근 1시간 강수량" : "오늘 예상 강수량"`. → **"현재 우선 + 예보 fallback"이 실무적으로 더 정확**(지금 실제로 오면 그 값이 진실).

### 7-2. KMA PCP 문자열 파싱 로버스트니스 (실제 버그 포인트)

라이브 확인 — PCP 원본 문자열 + 레퍼런스 `numericValue`(`replace(/[^\d.-]/g,'')`) 결과:

| PCP 원본 | numericValue | 판정 |
|---|---|---|
| `강수없음` | 0 | ✅ |
| `3.0mm` | 3 | ✅ |
| `1.0mm 미만` | 1 | △ 과대 |
| `30.0~50.0mm` | **null** (`30.050.0`→NaN) | ❌ **강수량 소실** |
| `50.0mm 이상` | 50 | ✅(우연) |

범위 문자열(`A~Bmm`)에서 소수점 2개가 붙어 `NaN→null` → **폭우 예보 때 강수량 통째로 사라짐.**

**✅ 확정 — 라이브 프로젝트 실제 수정(commit `e8fe197`)이 이 버그를 정확히 고침.** `numericValue`를 firstNumber 정규식 + 분기로 교체:
```
없음 포함        → 0        (기존 정확일치 → .includes('없음'))
"A~Bmm"         → (A+B)/2  ← 중간값
"Cmm 미만"       → C/2      ← 절반
"Cmm 이상"/"Cmm" → C        (firstNumber = /-?\d+(?:\.\d+)?/ 추출)
```
→ **우리 포팅 시 이 파서 그대로 차용** ([reference/news/app/api/weather/route.ts](../../../reference/news/app/api/weather/route.ts#L318) `numericValue`).

### 7-3. 결론

수정 방향(예보 강수 표시 + PCP 파싱 강화) **타당 → 우리 이식에 반영.** WeatherRenderer 체크리스트에 "강수=오늘 예보 기준 + PCP 범위 문자열 파싱" 엣지케이스 추가.

## §9. 라우터 모델 비교 실측 — flash-lite vs flash (날씨 intent + 후속 판단)

**계기**: 날씨 통합 시 라우터가 (1) 날씨 분류 (2) 후속 "카드 해석 vs 재조회"를 정확히 가르는지, 현재 `ROUTER_MODEL=flash-lite`([server/models.ts:14](../../../server/models.ts#L14))를 flash로 상향해야 하는지.

**방법**: [scripts/test-router-weather.ts](../../../scripts/test-router-weather.ts) — 실제 [router.ts](../../../server/agent/nodes/router.ts) 프롬프트에 `weather` intent 추가, `temp:0`·`thinkingBudget:0` 동일. 16케이스(기본 분류·멀티도시·카드해석 후속·재조회 후속·오발방지 컨트롤) × 2모델 × 2런. 503/429(무료티어 throughput)는 키 로테이션 재시도로 걷어냄.

**결과** (깨끗한 런):

| 모델 | 정확도 | 유일 실패 |
|---|---|---|
| **flash-lite** (현재) | 15/16 (94%) | `"습도가 높은 편이야?"` → weather (기대 general), 2런 다 틀림(안정적 오답) |
| **flash** | 16/16 (100%) | 없음 |

- 레이턴시: 깨끗한 콜은 둘 다 ~1s. flash-lite 평균이 높게 나온 건 무료티어 난기류(재시도)일 뿐 내재 차이 아님.
- **핵심 인사이트**: flash-lite가 틀리는 유일 유형 = **"카드 해석 후속인데 날씨 키워드(습도) 포함"**. 명확한 재조회(부산/내일/모레 = 도시·시간 토큰)와 키워드 없는 해석(우산/빨래)은 **둘 다 100%**.

**판단: 라우터 상향 불필요 — flash-lite 유지 + 결정론 양방향 가드.**
```
weatherContext 활성 시:
  · 새 도시명/시간어(부산·내일·모레…) 있음 → weather 강제 (재조회)
  · 새 도시/시간 없음                    → general 강제 (카드 해석)  ← flash-lite 유일 실패 교정
```
- `"습도가 높은 편이야?"`는 새 도시/시간 없음 → general 강제로 결정론 교정 → **flash-lite + 가드 ≈ flash 100%**.
- 라우터는 매 턴 serial-blocking 1콜([TODO §278](../../TODO.md))이라 전역 flash 상향은 모든 대화 비용·지연↑. 단일 edge case에 그 대가 불필요.
- movie식 후속 가드([router.ts:165](../../../server/agent/nodes/router.ts#L165) `!state.movieContext` 패턴)를 weather에 적용하는 방향과 동일.

> 후속: 이 가드 설계 + 멀티 도시 지원(도시 리스트 추출→병렬 호출→카드 배열)을 [PLAN_WEATHER_TOOL_260706](../../plans/PLAN_WEATHER_TOOL_260706.md)에 섹션으로 반영 예정.
