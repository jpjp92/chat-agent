```
정식  c9b813f1-…          ← 게스트 uuid 그대로 승격
```

## 2. 🐛 로그아웃 시 "연결 실패" 번쩍임

**증상**: 로그아웃하면 "연결에 실패했습니다" 에러 화면이 한 프레임 뜬 뒤 리다이렉트되어 게스트로 돌아왔다.

**원인**: `signOut()` 이 `supabase.auth.signOut()` → `onAuthStateChange(SIGNED_OUT)` → `setCurrentUser(null)` 을 유발한다. 이때 `isAuthLoading` 은 이미 false 라 App 의 `!currentUser && !isAuthLoading` **에러 화면**([App.tsx](../../../App.tsx))이 참이 된다. `window.location.reload()` 가 즉시가 아니라, 그 프레임이 보인다. **에러 화면이 "인증 진짜 실패"와 "방금 로그아웃함(의도적 null)"을 구분하지 못한 게 근본.**

**수정**:
- `useAuthSession` 에 `isSigningOut` 상태 추가 → 로그아웃 중엔 App 이 에러 대신 **"로그아웃 중" 로딩**(`LoadingScreen`, children 없이 → 애니메이션 점이 말줄임 대신)을 그린다.
- `signOut` 을 `try/finally` 로 견고화 → 네트워크 signOut 이 실패해도 **캐시 정리 + 리로드는 항상** 실행(로그아웃 중 갇힘 방지).

> 이 버그는 최근 변경이 만든 게 아니라 signOut/에러화면 상호작용에 원래 있던 것. **실제 흐름을 태워야만 보이는** DEV_260714 §4 계열 — dev 선검증이 값을 한 사례.

## 3. 충돌 재시도에서 계정을 두 번 고르는 체감

**증상**: 대화 있는 게스트가 이미 쓰인 Google 계정을 링크 → `identity_already_exists` → 충돌 모달 "기존 계정으로 로그인" → **Google 계정을 또 고른다.** "두 번 로그인하는" 느낌.

**분석**: 충돌 감지(1차 링크 트립)와 기존 계정 로그인(2차 signIn 트립)은 **서로 다른 OAuth 요청**이라 구조상 트립 둘이 불가피. 다만 2차에도 `prompt=select_account` 가 걸려 있어 **방금 고른 계정을 또 고르게** 만들던 게 문제.

**수정**: `oauthOptions(chooseAccount = true)` 로 파라미터화. **충돌 재시도(`onSignIn`)에서만 `chooseAccount:false`** → `select_account` 를 빼 Google 이 자동 통과. 첫 링크·0개게스트 로그인·계정 전환은 계정 선택이 필요하므로 그대로 켠다.

**한계(문서화)**: `select_account` 를 빼도, **브라우저에 Google 계정이 여러 개 로그인**돼 있으면 Google 이 자체 판단으로 계정 선택창을 띄운다(우리가 강제하는 게 아님). 완전 제거는 `login_hint:이메일` 이 유일한데, **충돌 에러 리다이렉트에 이메일이 실려오지 않아** 그 계정이 뭔지 코드가 알 수 없다. 이메일을 직접 입력받는 건 선택창 클릭보다 더 번거로워 실익 없음. → **"충돌(엣지) × 계정 여러 개(엣지)" 교집합에서만 한 번 더 묻는 것은 감수.** 계정 하나인 대다수 사용자는 자동 통과.

## 3-2. 🐛 시나리오 2(빈 게스트 직행)가 죽은 코드였다

**증상**: "대화 0개 게스트 → 바로 로그인"이 발동 안 하고, 빈 게스트도 linkIdentity 를 타 계정 소진 시 충돌.

**근본 원인**: 새 게스트는 로드 시 **빈 'New Chat' 세션이 자동 생성**된다([useChatSessions.ts](../../../src/hooks/useChatSessions.ts) — DB 세션 0개면 `createNewSession`). 그래서 `sessions.length` 는 항상 ≥1, `sessions.length === 0`(DEV_260715 의 분기 조건)이 **영영 거짓** → signInWithOAuth 경로가 한 번도 안 탔다.

**수정**: 신호를 세션 개수 → **"빈 기본 세션이 아닌 게 있나"** 로 교체.
```js
const guestHasData = sessions.some(s => !(s.title === 'New Chat' && s.messages.length === 0));
onLink={guestHasData ? linkGoogle : signInWithGoogle}
sessionCount={guestHasData ? sessions.length : 0}   // 빈 게스트면 "대화 N개" 칩도 숨김
```

**피한 함정**: 처음엔 `profiles.message_count` 로 판정하려 했으나, 그건 **프로필 로드 시점 값이라 대화 직후에도 stale(0)** 이다. 그걸 썼으면 **대화한 게스트가 signInWithOAuth 로 빠져 고아가 되는**(linkIdentity 로 막으려던 바로 그) 버그를 되살렸다. 게스트 데이터는 전부 브라우저 안에 있으므로 **클라이언트 `sessions` 가 실시간 진실**. `useChatStream` 이 `sessions[].messages` 를 갱신하고, `useChatSessions:131` 에 이미 같은 술어가 있어 패턴도 일관.

## 4. 부수 발견 — 함수 리전 iad1 (Supabase 는 서울)

dev 배포 Vercel 로그에서 `/api/sessions` 가 **iad1(워싱턴)** 에서 실행돼 GET 이 ~900ms. **Supabase 는 서울(ap-northeast-2)** 이라 서울유저→US함수→서울DB 로 태평양을 두 번 건너는 최악 케이스였다. Supabase 붙는 라우트 중 iad1 이던 것: sessions·upload·create-signed-url·sync-drug-image·fetch-url (chat·parse-document 는 이미 icn1). 코드에 `preferredRegion='icn1'` 를 5개 라우트에 추가하고 커밋(`a7a8636`)했다.

**🔴 그런데 커밋 후 로그도 여전히 iad1 이었다.** `Received in Seoul (icn1)` (엣지 수신)인데 `Routed to Washington, D.C. (iad1)` (함수 실행). **원인 = 무료(Hobby) 티어에서는 코드의 per-function `preferredRegion` export 가 무시된다** — per-function 멀티리전은 Pro+ 전용. Hobby 는 **프로젝트 전역 단일 리전**만 지정 가능.

**실제 해결(2026-07-19, 사용자 적용 완료)**: Vercel `chat-agent-dev` 프로젝트 → **Settings → Functions → Function Region 을 `Seoul (icn1)` 단일 선택**. 이게 무료 티어에서 먹히는 유일한 방법이고, 모든 함수에 일괄 적용된다. 저장 후 **재배포부터** 적용. 코드의 `preferredRegion` export 는 무해하므로 유지(Pro 승격 시 자동 의미 발생).

> 교훈: **"코드에 `preferredRegion` 넣으면 리전이 바뀐다"는 무료 티어에서 거짓.** 무료 티어의 리전 스위치는 대시보드 단일 리전 설정 하나뿐. 다음에 "코드에 넣었는데 왜 iad1?" 로 헤매지 말 것.

## 4-1. 부수 발견 — 테스트 스크립트 프로덕션 가드 오탐

스테이징을 dev DB 로 승격(`SUPABASE_URL = STG_SUPABASE_URL`)하면서, `check-auth-users.ts` 등의 `if (STG_SUPABASE_URL === SUPABASE_URL) abort` 가드가 **오탐**한다(둘이 같아짐). 원 의도는 프로덕션 보호였는데 상대 비교라 깨졌다. **더 나은 가드 = 대상 URL 이 프로덕션 ref(`gaomgqnpsjtabrvwnpad`)가 아님을 절대 확인.** 이번엔 일회성 스크립트에 절대 가드를 넣어 우회. 커밋된 스크립트의 가드 갱신은 백로그(PLAN_AUTH_DEV_ROLLOUT §3).
