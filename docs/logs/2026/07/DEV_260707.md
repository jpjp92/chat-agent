# DEV_260707

> wikidocs 블로그 URL 요약 실패(502) 근본 원인 규명 및 수정
> — `isSecurityBlock`이 본문의 `'cloudflare'` 단어를 CF 챌린지로 오판해 **정상 fetch를 실패로 뒤집던** 버그

---

## §1. 배경 / 증상

특정 wikidocs 블로그 URL 요약이 실패하고 아래 안내만 반환:

```
해당 URL의 원문을 가져오지 못했습니다: https://wikidocs.net/blog/@jaehong/8007
이 URL은 보안 확인, CAPTCHA, 접근 제한 등으로 서버에서 본문을 읽을 수 없습니다.
```

- `https://wikidocs.net/blog/@jaehong/8007/` → **매번 실패**(502)
- `https://wikidocs.net/blog/@rudah96/22356/`, `https://wikidocs.net/31695` → 잘 됨

같은 wikidocs.net·같은 블로그 경로 구조인데 특정 URL만 결정적으로 실패 → "블로그 형태가 안 된다"는 착시.

프로덕션 Vercel 로그: `POST /api/fetch-url` **502, 53s**, External APIs에 ScrapingBee·browserless·scraperapi **3종 모두 호출됨**(= 폴백 체인이 끝까지 돌고 전부 실패).

---

## §2. 진단 과정 (systematic-debugging)

**provider별 실측**(로컬, `@jaehong/8007`):

| Provider | 결과 |
|---|---|
| ScrapingBee (render_js+premium) | ✅ 200 · 본문 4,862자 · ~5s |
| browserless `/unblock` | ❌ 본문 0자 (en-US 셸만 반환) |
| scraperapi (render) | ❌ 45s 타임아웃 |

→ **wikidocs 블로그는 실질적으로 ScrapingBee 단일 의존**(나머지 둘은 이 페이지에서 무력). 프로덕션 53s = ScrapingBee 실패 + browserless(~5s) + scraperapi 타임아웃(45s)과 정합.

**착시 규명**:
- `@rudah96/22356`·`31695`가 "되는" 것은 상당 부분 **`url_cache` HIT**(각각 2026-07-07·2026-06-26 scrapingbee 성공분 잔존) → provider 미호출.
- 초기 재현 스크립트가 `bodyLen`만 측정하고 **실제 라우트의 `isSecurityBlock`/`isBoilerplateOnly` 검사를 생략**해 "로컬은 성공"으로 오인.

**근본 원인 확정**: 실제 `isSecurityBlock`을 ScrapingBee 응답 본문에 적용하니 `@jaehong/8007`만 `true`. 트리거 매칭 결과:

```
SECURITY TRIGGER MATCHED: ["cloudflare"]
context: ...는 ID를 만들 수 있을까? ... Astro Technology Company, Cloudflare에 합류하다 ...
```

페이지 `<main>` 안 **관련글 목록의 글 제목 "Astro Technology Company, Cloudflare에 합류하다"** 때문에 본문에 `cloudflare` 문자열 포함 → `isSecurityBlock`이 CF 챌린지로 오판 → provider 성공을 null(실패)로 뒤집음 → 체인 끝까지 실패 → 502. `@rudah96`은 본문에 해당 단어 없어 통과.

## §3. 변경

**app/api/fetch-url/route.ts** — `isSecurityBlock`에서 광범위한 단어 매칭 제거, 챌린지 페이지 고유 문구로 대체.

```diff
- t.includes('cloudflare') || t.includes('cf-ray') ||
+ t.includes('attention required! | cloudflare') || t.includes('sorry, you have been blocked') ||
+ t.includes('cloudflare ray id') ||
```

근거: `'cloudflare'`/`'cf-ray'`는 **정상 콘텐츠에도 흔히 등장**(관련 기사·cdnjs 언급 등)해 오판을 냄. 실제 CF 챌린지 페이지는 `'just a moment'`, `'verifying you are not a bot'`, `'보안 확인 수행 중'` 등 **이미 존재하는 구체 문구**로 잡히며, 여기에 blocked 페이지 고유 문구(`attention required! | cloudflare` / `sorry, you have been blocked` / `cloudflare ray id`)를 명시적으로 보강.

**부수 효과**: 같은 오판이 direct-fetch 경로([route.ts:180](../../../app/api/fetch-url/route.ts#L180) `isSecurityBlock(html)`)에서 Cloudflare CDN·cdnjs를 쓰는 정상 사이트를 불필요하게 render 폴백으로 밀어내던 문제도 해소.

## §4. 검증

- `npx tsc --noEmit` → **0 errors**.
- 수정 predicate 단위 검증(5종): jaehong 본문·정상 CDN 언급 기사 → `false`(오판 제거) / 실제 CF "Just a moment"·blocked 페이지·한글 챌린지 → `true`(탐지 유지). 현행은 앞 2종에서 오판(`true`), 수정본 5/5 정확.
- 실제 ScrapingBee 응답 재검증: `@jaehong/8007` `ROUTE PASS=false → true`(본문 4,862자 정상 반환), `@rudah96/22356` `true` 유지(회귀 0).

캐시에는 실패가 저장되지 않아 **삭제할 stale 캐시 없음** — 배포 후 재요약 시 성공·캐시 저장.

## §5. 남은 취약점 (백로그 후보)

- **wikidocs 블로그의 실질 redundancy 부재**: browserless(본문 0)·scraperapi(타임아웃)가 이 페이지 유형을 못 받침 → ScrapingBee가 실제로 실패(크레딧 소진·bad window)하면 여전히 502. ScrapingBee 1회 재시도 또는 wikidocs 블로그용 browserless 렌더 보강 검토.
- **`isSecurityBlock` 문자열 매칭 방식의 근본 취약성**: 추출 본문 대상 substring 매칭은 콘텐츠 오판 소지 상존. 챌린지 판정은 가능하면 HTTP status·응답 크기·title 등 구조 신호 우선 검토.
