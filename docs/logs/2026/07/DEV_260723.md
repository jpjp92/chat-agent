# DEV_260723 — 암묵 캐싱 실측 · gemini-3.6-flash 도입 리스크 평가

> 작성: 2026-07-23
> 두 갈래: **(A) 암묵 캐싱 실측**(§1-5) — 명시적 캐싱 불필요 확인. **(B) gemini-3.6-flash 도입 평가**(§6-10) — 성능·fallback·의도 전 경로 실측.
> 신규 스크립트 6종: implicit-cache · 36-vs-35 · 36-fallback-probe · 36-image-stress · 36-youtube · 36-url-summary · 36-renderer-json.

## 요약 (TL;DR)

- **암묵 캐싱**: 코드에 명시적 캐싱 0건이나 암묵 캐싱이 프리픽스 78~98% 자동 할인 → **명시적 캐싱 도입 불필요**(§1-5).
- **3.6 성능**: 텍스트 전 쿼리 ~24% 빠름(§6), 렌더러 JSON 10/10·최속(§9-1). 3.6 은 3.5 의 **무료티어 멀티모달·긴입력 throughput 붕괴를 대부분 해소**.
- **3.6 fallback**(4축 실측): **검색만 2.5 강등 필요**(무료티어 429), **이미지·영상·URL 은 직접 처리**(3.6 이 2.5 동급~우수). 503/timeout 반응형 강등이 안전망(§7-8).
- **의도 커버리지**: 렌더러 JSON 안전, 툴 함수호출은 구조상 2.5 고정이라 3.6 무관(§9).
- **Phase A 실그래프 검증**(§11): 서버 코드 변경(능력 테이블+게이트) 적용 후 실그래프로 3.6 검증 — 렌더러 15/15·멀티턴 5/5·tool_code 유출 0·검색 강등 실증. 🟢 **기본 승격 안전**.
- **결정**: 🟢 **Phase A 통과 → Phase B(클라 옵션·기본 승격)로.** 상세 §10-11.

## 1. 왜 측정했나

- 프로덕션 3모델(`gemini-3.5-flash` 기본 · `gemini-2.5-flash` · `gemini-2.5-flash-lite`)은 매 `generateContent` 호출에 **~45KB systemInstruction(≈10.4K 토큰)을 fresh 로 전달**한다. 명시적 컨텍스트 캐싱(`caches.create`/`cachedContent`)은 코드 전체에 없다.
- Gemini 2.5/3.x 는 **동일 프리픽스 반복 시 자동으로 암묵 캐싱**을 적용해 입력 토큰을 할인해줄 수 있는데, 코드에 `usageMetadata` 로깅이 없어 **실제로 먹는지 미관측**이었다.
- 프로덕션에 로깅을 넣기 전에 **테스트 스크립트로 선측정**.

## 2. 방법

동일한 큰 프리픽스(prod systemInstruction + 고정 컨텍스트 대화) + 매 콜 미세하게 다른 꼬리 질문을 순차 반복 호출 → 각 응답 `usageMetadata.cachedContentTokenCount` 관측. `cached>0` 이면 암묵 캐시 히트.

```
npx tsx --import ./scripts/_loader-server-only-shim.mjs scripts/test-implicit-cache.ts
# 옵션: CACHE_TEST_TIER=free|paid  CACHE_TEST_MODELS=all|3.5|2.5|2.5-lite  CACHE_TEST_REPEATS=N
```

## 3. 결과 — 유료 티어(Tier1), 프리픽스 prompt≈10,425 토큰

| 모델 | 첫 콜(populate) | 반복 콜 | 캐시율 | 비고 |
|---|---|---|---|---|
| **gemini-3.5-flash** | miss (0/10425) | **HIT 8157/10425** | **78.2%** (3/4) | 프리픽스 일부만 캐시 |
| **gemini-2.5-flash** | miss | HIT 10220/10425 | **98.0%** (1/4) | 히트 타이밍 지터 |
| **gemini-2.5-flash-lite** | miss | HIT 10220/10425 | **98.0%** (3/4) | 안정적 |

- 첫 콜(캐시 채움) 이후 반복 콜에서 `cachedContentTokenCount` 가 붙는다 → **코드 한 줄 없이 프리픽스 할인 수령 중.**
- 🔴 **3.5 는 78%만 캐시**(8157/10425), 2.5 계열은 98%(10220/10425). 3.5 의 캐시 블록 granularity 가 달라 프롬프트 뒷부분 일부를 안 잡는다. **프로덕션 기본이 3.5 라 이 차이는 알아둘 값.**
- 2.5-flash 가 1/4 만 히트한 건 캐시 TTL·populate 타이밍 지터(반복 간격·부하 의존)이지 미동작이 아니다.
- 지연: 캐시가 붙어도 latency 개선은 미미(3.5 2950→1986ms). **암묵 캐싱은 latency 보다 비용(입력 토큰 회계) 절감**이 본질.

## 4. 결과 — 무료 티어(프로덕션 실환경)

```
#1  196362ms  prompt=10425  cached=0   ← 첫 콜이 196초, 300s 타임아웃에 반복 콜 잘림
```

- 무료 티어 첫 콜이 **196초**. [[35-flash-free-tier-throughput]] 붕괴 프로파일 극단 재확인.
- 암묵 캐싱은 **플랫폼 기능이라 티어 무관** 동일 적용되지만, **무료 티어 지연은 프롬프트 처리가 아니라 스로틀링이 지배** → 캐싱으로 못 구한다. 방향이 안 맞음.

## 5. 결론

**명시적 컨텍스트 캐싱 도입은 불필요.**
1. 암묵 캐싱이 이미 프리픽스의 **78~98% 를 할인** 중 → 명시적 캐싱 추가해도 입력 토큰 절감 여지 거의 없음.
2. 명시적 캐싱은 `caches.create` 왕복·TTL 관리가 추가돼 [[chat-agent-vercel-60s-cap]] 환경에서 순손해 위험.
3. 무료 티어 병목은 캐시가 아니라 throughput — 캐싱은 무관.

**후속(선택)**: prod [generator.ts](../../../../server/agent/nodes/generator.ts) 의 `generateContent` 응답부에 `usageMetadata.cachedContentTokenCount` 한 줄 로깅 → 실트래픽 캐시율 상시 관측. (도입 여부 미결)

## 6. gemini-3.6-flash vs 3.5-flash 비교

> 계기: `gemini-3.6-flash`(2026-07 출시, "더 빠르고 저렴한 frontier급 · 에이전틱/코드/공간추론 강점") 등장 → 프로덕션 기본(3.5)과 교체 판단.
> 스크립트: `scripts/test-36-vs-35-flash.ts` 신규. 조건: prod systemInstruction(~45KB) + `thinkingLevel:"minimal"`(prod 설정) + maxOutputTokens 2048. 대표 쿼리 4종 × 2런 × 2모델 = 16콜, 유료(Tier1). **2회 재현 일관.**

### 쿼리별 지연(ms) — 2런 평균

| 쿼리 | 3.6-flash | 3.5-flash | 3.6 우위 |
|---|---|---|---|
| 추론(이발사 역설) | ~2,220 | ~3,020 | **27% 빠름** |
| 코드(Kadane) | ~1,800 | ~2,350 | **23% 빠름** |
| 공간/에이전틱(격자 경로) | ~3,330 | ~3,830 | 13% 빠름 (출력 2배) |
| 사실(세종시 2문장) | ~1,600 | ~2,580 | **38% 빠름** |
| **전체 평균** | **~2,237ms** | **~2,944ms** | **🟢 3.6 이 ~24% 빠름** |

### 관측

- 🟢 **3.6 이 전 쿼리에서 일관되게 빠르다** — 평균 **~24% 지연 단축**(2,237ms vs 2,944ms). Vercel 60s 캡 여유에 직접 기여.
- **3.6 이 오히려 출력이 더 많다**(평균 out 235 vs 150 토큰). 특히 공간/에이전틱 쿼리에서 641/515 vs 208/251 — **더 상세하면서도 더 빠름**. "빠른 대신 짧게 답한 것" 아님.
- **품질**: 4쿼리 전부 양쪽 정답. 이발사 역설·Kadane(빈 배열 처리 포함)·격자 경로수(6가지, 조합식 유도) 모두 정확. 3.6 의 공간 추론 답이 더 풍부.
- `think=0`(minimal), `finish=STOP` 전부 — 2048 토큰 내 미절단.
- prompt 토큰은 동일 쿼리에서 양 모델 같음(같은 systemInstruction). 이번 비교는 **캐시 없는 콜**(cached=0)이라 순수 처리속도 대조.

### 판단

**기본 모델을 3.6-flash 로 교체 검토할 만함.** 근거: ① 전 쿼리 ~24% 빠름(60s 캡 여유) ② 출력 품질 동등 이상 ③ "저렴" 표방(단가는 별도 확인 필요). **미확인 항목**: 무료 티어 throughput(§4 처럼 붕괴 여부)·429 빈도, 실제 단가, 렌더러 JSON/툴콜 경로 회귀, 암묵 캐시율(3.5 는 78%였음 §3). → 교체 전 무료 티어 재측정 + 렌더러/툴콜 스모크 필요.

## 7. 3.6 옵션 추가 검토 — 무료티어 fallback 필요성 실측

> 목표: 3.6 을 모델 옵션에 추가 시, **검색·이미지·영상에서 3.5 처럼 2.5 로 강등**해야 하는지 실측.
> 스크립트: `scripts/test-36-fallback-probe.ts` 신규.

### 현재 3.5 fallback 플로우 (검토 결과)

3.5 는 사실상 **"텍스트/추론 전용"** 모델이고, 아래는 전부 **2.5 로 강등**된다([generator.ts](../../../../server/agent/nodes/generator.ts)):

| 경로 | 3.5 → 강등 | 근거 |
|---|---|---|
| `resolvedModel` 핀([:115](../../../../server/agent/nodes/generator.ts#L115)) | YouTube 영상 턴·URL 본문 턴 → **2.5** | 무료티어 3.5 영상 60s 초과·URL throughput 나쁨 |
| 검색(`useGoogleSearch && needsSearchFallback`, [:236](../../../../server/agent/nodes/generator.ts#L236)) | **2.5 단일패스 grounding** | 🔴 3.5 Search 무료티어 미지원 |
| 이미지/영상(`isMediaTurn`) | **2.5** | 무료티어 3.5 멀티모달 60s 초과 |
| 503/timeout(`unavailableDowngrade`) | **2.5** | throughput 좋은 2.5 |
| `MALFORMED_FUNCTION_CALL` | **2.5 1회** | 3.5 멀티턴 함수호출 토큰 오류 |

강등 판정은 전부 `resolvedModel === SERVER_MODELS.FLASH_3_5` 하드코딩 → 3.6 추가 시 **"3.x 계열" 판정으로 일반화** 필요.

### 실측 — 무료티어(프로덕션 실환경), per-call 90s 타임아웃

| 축 | 3.6-flash | 3.5-flash | 2.5-flash | 결론 |
|---|---|---|---|---|
| **A. 텍스트**(툴X) | ✅ 3,187ms | — | ✅ 3,971ms | 3.6 정상, 60s 여유 |
| **B. 검색 grounding** | 🔴 **429** | 🔴 429 | ✅ grounding=4 (4,227ms) | **3.6=3.5, 2.5 강등 필수** |
| **C. 이미지**(40KB PNG) | ✅ 3,057ms | — | ✅ 4,435ms | 3.6 이번엔 빠름(추가검증 필요) |

*(유료 티어 대조: A/B/C 전부 OK, 3.5·3.6 검색도 grounding=5 성공 → **B 의 429 는 무료티어 전용 제약**임이 확정. 키 소진 아님 — 같은 키로 2.5 grounding 직후 성공.)*

### 판정

- 🔴 **B(검색) 확정**: `gemini-3.6-flash` + Google Search 는 무료티어에서 **즉시 429**(3.5 와 완전 동일). → **3.6 도 검색 시 2.5 로 강등해야 함.** `needsSearchFallback`/`is3xModel` 을 3.6 포함으로 일반화.
- 🟢 **C(이미지) 확정 — 강등 불필요**(§7-2 스트레스로 해소): 4해상도(작은 스샷~3000×2000 폰사진급)×2런 결과 **3.6 avg 3,327ms·max 5,363ms·<60s 0건 초과·실패 0** — **2.5와 완전 동급**. 반면 **3.5 는 avg 57.6s·max 83s·503 3회** — 이 붕괴가 "이미지→2.5 핀"의 근거였다. **3.6 은 이 문제가 없으므로 이미지를 직접 처리해도 됨**(3.6 의 우수한 이미지 추론을 살릴 수 있음). 드문 503 은 기존 `unavailableDowngrade`(503/timeout→2.5) 반응형 경로가 안전망.
- **YouTube 영상축**: heavy 라 미측정. 3.5 처럼 2.5 핀 유지하고 별도 수동 검증.
- **A(텍스트)**: 3.6 무료티어 정상(3.2s). 단 free-tier throughput 변동(§4 의 196s)이 있으므로 503/timeout→2.5 강등 경로도 3.6 포함 일반화 필요.

## 8. 3.6 fallback 최종 설계 (실측 종합 — 4축 완료)

네 축(검색·이미지·영상·URL)을 무료티어에서 실측한 결과, **3.6 이 3.5 처럼 강등이 필요한 건 검색뿐**이다. 이미지·영상·URL 은 3.6 이 fallback 대상(2.5)과 동급이거나 더 빠르다.

| 경로 | 3.5 현행 | **3.6 (실측 확정)** | 근거 (3.6 / 3.5 무료티어) |
|---|---|---|---|
| **검색 grounding** | → 2.5 강등 | **→ 2.5 강등 (동일)** | 🔴 429 / 429 (§7-B) |
| **이미지/멀티모달** | → 2.5 핀 | **🟢 직접 처리 (핀 제거)** | 3.3s / 57.6s·503 (§7-2) |
| **YouTube 영상** | → 2.5 핀 | **🟢 직접 처리 (핀 제거)** | 6.8s / 503 실패 (§7-3) |
| **URL 요약** | → 2.5 핀 | **🟢 직접 처리 (핀 제거)** | 5.4s / 503·90s (§7-4) |
| **503/timeout** | → 2.5 강등 | **→ 2.5 강등 (동일)** | 혼잡 안전망(3.6 도 드물게 503 가능) |
| **MALFORMED** | → 2.5 1회 | **→ 2.5 1회 (동일)** | 함수호출 토큰 오류 대응 |

**핵심**: 3.6 의 유일한 하드 강등은 **검색→2.5**(429). **이미지·영상·URL 은 전부 직접 처리** — 3.6 이 fallback 대상보다 동급~우수(3.5 는 이 셋 다 503/붕괴). 503/timeout 반응형 강등이 모든 엣지의 안전망.

> 사용자 가설("3.6 도 검색·영상·이미지 전부 2.5 강등 필요")은 **검색만 맞고 영상·이미지·URL 은 반증됨** — 그 셋에서 3.6 은 fallback 대상보다 우수. **3.6 은 3.5 의 무료티어 약점(멀티모달·긴입력 throughput 붕괴)을 대부분 해소한 모델**이라는 게 4축 실측의 결론.

### 다음 단계 (코드 변경 — 미착수)

- **핀은 3.6 예외**(직접 처리): `resolvedModel` YouTube·URL 핀(115-119줄), `isMediaTurn` 핀(236줄) — 3.5 만 2.5 로, 3.6 은 통과.

## 9. 의도별(intent) 커버리지 — 렌더러 JSON · 툴 경로

4축(§7-8)은 SDK path 입력 처리였다. 의도별로 **처리 경로가 갈리므로**, 3.6 이 실제로 쓰이는 나머지 경로를 점검.

### 9-1. 렌더러 JSON (SDK path, 3.6 사용) — 안전 확정

렌더러 의도(astronomy·data_viz·chemistry·biology·physics)는 구조화 JSON(`json:constellation/chart/smiles/bio/diagram`)을 뱉는다. 3.5 에 minimal thinking 을 강제한 이유가 "JSON reasoning 이 thinking budget 을 소진해 **빈응답**"([generation-config.ts:37](../../../../server/agent/nodes/generation-config.ts#L37))이라, 3.6 도 유효 JSON 을 안정 생성하는지가 관건. 스크립트: `scripts/test-36-renderer-json.ts`(블록존재+타입일치+JSON.parse 검증).

| 모델 | 유효 JSON | avg | 의도별(astr/data/chem/biol/phys) |
|---|---|---|---|
| **3.6-flash** | **10/10** | **3,170ms** | 2/2 · 2/2 · 2/2 · 2/2 · 2/2 |
| 3.5-flash | 10/10 | 5,056ms | 2/2 전부 |
| 2.5-flash | 10/10 | 3,991ms | 2/2 전부 |

*(유료 티어. 무료 티어 런은 도중 **일일 quota 429 소진**(모델 무관, 오늘 무료 콜 다수)으로 chem·biol·phys 무효 — 단 소진 전 astronomy·data_viz 는 3.6 4/4 유효, 3.5 는 503. 유효성은 모델 능력이라 티어 무관하므로 유료 결과가 결정적.)*

- 🟢 **3.6 이 전 렌더러 의도에서 유효 JSON 100% + 최속(3.2s)** — 빈응답/malformed 0. **렌더러 취약성 우려는 3.6 에서 발현 안 됨.** 렌더러 안전.

### 9-2. 툴 함수호출 경로 (drug_info·drug_id·sports) — 3.6 미사용, 테스트 불요

LangChain path 는 `pathModel = isToolIntent ? 2.5 : resolvedModel`([langchain-path.ts:83](../../../../server/agent/nodes/langchain-path.ts#L83)). **모든 툴 의도(FAST_PASS + SYNTH_TOOL=drug·sports)는 모델 선택과 무관하게 2.5 로 함수호출**한다. → **3.6 은 툴 함수호출에 아예 관여 안 함** — MALFORMED 우려는 3.6 에 해당 없음, 별도 테스트 불필요.
- `is3xLcModel`(84줄)은 **비툴 의도가 SDK 완전실패로 LangChain 폴백**될 때만 발동(resolvedModel=3.5). 3.6 추가 시 이 폴백 경로에 3.6 포함 여부만 결정하면 됨(엣지).

### 9-3. 나머지 의도

- **FAST_PASS**(pharmacy·hospital·vet·movie·law·weather): LangChain 2.5 고정 → 3.6 무관.
- **medical_qa**: 검색 강제 ON → 무료티어 3.6 은 429 로 2.5 강등 → §7-B 검색축에 포함.
- **general**: §6 텍스트 비교에 포함.

**의도 커버리지 결론**: 3.6 이 실제 쓰이는 경로 중 미검증이던 **렌더러 JSON 은 안전 확정**. 툴 함수호출은 구조상 2.5 고정이라 3.6 무관. → **§8 fallback 설계 + 렌더러 안전**으로 3.6 도입의 경로별 리스크 점검 완료.
