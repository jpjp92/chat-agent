## §1. 배경 / 문제

DEV_260628에서 모델 선택기를 입력창 우측에 통합하며 컴포저를 **1행 3열 그리드**로 구성:

```
grid-cols-[auto_1fr_auto]
   └ [+]     └ textarea(1fr)   └ [모델선택 · 🎤 · ↑]
```

- 모델 선택기("Gemini 2.5 Flash ▾", 폭 ~130px)가 **오른쪽 열을 상시 점유**.
- textarea(`1fr`)는 버튼이 실제로 있는 맨 아랫줄뿐 아니라 **모든 줄에서** 그 열을 비켜감 → 여러 줄 입력 시 우측 세로 띠가 통째로 死공간.
- 사용자 리포트: 긴 텍스트가 박스 중간에서 꺾이고 오른쪽이 크게 빔 → "입력창이 좁아 보임".

## §2. 변경

**components/ChatInput.tsx** — 컴포저를 **반응형 하이브리드**로 재구성. DOM 복제 없이 CSS만으로 모바일=1행/데스크톱=2단 분기.

> 1차엔 `flex flex-col`로 전 화면 2단화했으나, 모바일은 애초에 폭 문제가 없고(모델 선택기가 헤더에 있음) 2단이 세로 공간을 더 먹고 하단 행이 허전해짐(모델 자리 공백). → 모바일은 기존 1행을 복원하는 **flex-wrap 하이브리드**로 확정.

| 영역 | 변경 |
|---|---|
| 폼 컨테이너 | `grid grid-cols-[auto_1fr_auto] items-end` → `flex flex-wrap items-center justify-between gap-y-1` |
| textarea | `flex-1 min-w-0 sm:basis-full sm:order-first` — 모바일은 `flex-1`로 인라인(1행), 데스크톱은 `basis-full+order-first`로 첫 줄 전체 폭 차지 → 나머지가 둘째 줄로 wrap |
| `[+]`·컨트롤 | 각각 폼 직속 flex 자식(`flex-shrink-0`). 모바일=textarea 좌/우 인라인, 데스크톱=wrap된 둘째 줄에서 `justify-between`으로 좌/우 |
| 줄바꿈 | `wordBreak: 'break-all'` → `'normal'` (일반 텍스트 글자 단위 끊김 해소; 초장문 토큰은 `overflowWrap: 'anywhere'` 로 강제) |
| 패딩 | `py-1 sm:py-1.5` + `min-h-[40px] sm:min-h-[48px]`, 드래그 오버레이 rounded 정합 |

변경 없음:
- 모델 선택기 `hidden md:block` **유지** → 모바일은 헤더 모델선택 그대로.
- 드롭다운 방향 로직(`welcome ? top-full : bottom-full`), STT/첨부/드래그 핸들러, 높이 자동조절(`adjustHeight`) 모두 그대로.

**원리**: flex-wrap 한 줄에 3자식(`[+]`·textarea·컨트롤). 모바일은 textarea `flex-1`이 남는 폭을 흡수해 1행 유지(justify-between 무효). 데스크톱은 textarea `basis-full`이 첫 줄을 통째로 먹어 `[+]`·컨트롤이 둘째 줄로 밀리고, `order-first`로 textarea가 시각상 맨 위. 둘째 줄은 `justify-between`으로 `[+]` 좌 · 컨트롤 우.

## §4. 사이드바 제목 편집 밑줄 보정

**문제**: 모바일에서 사이드바 채팅 제목을 편집할 때 밑줄(input `border-b`)이 행 오른쪽 끝까지 뻗어 너무 길게 보임. 웹은 문제 없음.

**원인**: **components/ChatSidebar.tsx** 편집 input이 `flex-1`로 행 전체 폭을 채움. 비편집 제목 `<span>`은 `pr-5`로 우측 여백을 두지만 편집 input엔 없어 밑줄이 끝까지 감. 밑줄은 border라 padding으로는 안 줄고 **margin**으로만 짧아짐.

**수정**: `flex-1` → `flex-1 min-w-0 mr-8 sm:mr-0`
- `mr-8`(2rem) — 모바일 밑줄이 행 끝 전에서 멈추도록 우측 거터 확보.
- `sm:mr-0` — 웹(sm+)은 현행 유지(문제 없다고 리포트됨).
- `min-w-0` — 긴 제목 입력 시 flex 오버플로 방지.
- 기능(입력·Enter/Esc·blur 저장) 불변.

## §5. 유튜브 요약 실패 회귀 — 자체 데드라인 48s→57s

**증상**: 모바일에서 유튜브 URL 요약 시 ~48초 뒤 "일시적으로 불안정합니다" 메시지만 옴. 웹/이전엔 정상.

**Vercel 로그 근거**: `POST /api/chat` 200, **Execution 48.38s / Max 1m**, 외부 호출은 `gemini-2.5-flash:generateContent` **단일** 건. → Gemini 측 429/500/503 재시도 캐스케이드가 아니라 **우리가 건 48초 `AbortSignal.timeout`이 발화**한 것.

**흐름** (`server/agent/nodes/generator.ts`):
1. 영상 턴(`isYtVideoTurn`)은 2.5-flash 단일 호출에 `YOUTUBE_CALL_TIMEOUT_MS`(=48s) 데드라인.
2. 48s abort → `isYtVideoTurn && isTimeout` → `ytPrimaryTimedOut=true` → break → 3.5 폴백 스킵.
3. `runLangChainPath`에서 `!useLangChain && !sdkSuccess && isYoutubeRequest && hasVideoData` → "YouTube 영상 분석 서비스가 일시적으로 불안정합니다" 반환(HTTP 200).

**근본 원인**: **회귀**. `aa9d701` 이전엔 SDK 경로에 per-call 타임아웃이 없어 유튜브가 Vercel 60s 캡 직전(~59s)까지 예산을 다 쓸 수 있었고 잘 됐음. `aa9d701`(25s 일률)이 끊었고 → `80972c8`/DEV_260627 §5가 48s로 완화했지만 **원래 ~59s 예산보다 좁아** 정상 상한(~48s)을 살짝 넘긴 호출을 잘랐다. maxDuration(60s)은 계속 그대로 → 병목은 **우리가 스스로 건 데드라인**.

**수정(중간 조치)**: `YOUTUBE_CALL_TIMEOUT_MS` 48_000 → **57_000**. 낭비되던 48→60s 창을 회수. **단, 이건 미봉책이었다** — 57s로 올려도 더 긴 영상은 여전히 실패(§7).

## §7. 유튜브 요약 근본 해결 — `mediaResolution: LOW` (핵심)

**57s로도 실패**: 상향 배포 후 다른 영상(`GeeLWGdymQM`)에서 **57.68s / Status 0**(200도 아닌 하드 실패). 데드라인만 올린 게 문제를 뒤로 미뤘을 뿐, 근본이 아니었음.

**진짜 병목 실측** (`.env.local` Tier1 키로 직접 generateContent 호출, `usageMetadata` 측정):

| 설정 | 소요 | 입력(prompt) 토큰 | 출력 토큰 |
|---|---|---|---|
| 기본 해상도(현행) | **93.7s** | **315,695** | 1,943 |
| **`mediaResolution: LOW`** | **32.1s** | **110,243** (-65%) | 869 |

→ **병목은 출력이 아니라 영상 입력 토큰**. 이 영상 하나가 기본 해상도로 **31만 토큰**이라 인제스트에 시간이 다 감. 출력은 이미 ~1,900 토큰이라 **maxOutputTokens를 8192→4096으로 줄여도 무효**(모델이 그보다 적게 생성). LOW 해상도가 프레임당 토큰을 대폭 줄여 입력을 11만으로 낮춤.

**수정**: `generator.ts` — `isYtVideoTurn`일 때 generateContent config에 `mediaResolution: 'MEDIA_RESOLUTION_LOW'` 주입(single-pass + minimal-retry). 요약은 화질 무관이라 품질 손실 없음(길이만 다소 짧아짐).

**앱 실측(로컬)**: 기본 57s 타임아웃 → **LOW res로 무료티어 22.9s / 유료 Tier1 17.7s** 정상 요약 반환.

**(참고) 시도했다가 제거한 접근 — 유료 Tier1 키 라우팅**: 무료티어 throughput 의심으로 `API_KEY_TIER1`(env에 있으나 `/^API_KEY\d*$/`에 안 걸려 미로드였음)을 유튜브 턴에 라우팅해봄. Tier1이 무료보다 ~10s 빠르긴 했으나(raw 29.6 vs 39.9s), **LOW res 적용 후엔 무료도 22.9s로 충분**해 불필요 → 코드·config·토글 전부 제거. **필요 시 다시 쓸 수 있는 지렛대로 기록**(TODO/메모리): env에 유료 키를 별도 로드(`API_KEY_TIER1`)해 무거운 경로만 라우팅하면 throughput을 살 수 있음.

### §7.1 남은 한계 — **긴 영상은 LOW res로도 60s 캡 초과** (fps 하향은 역효과)

LOW res가 중간 길이 영상은 구제하나, **더 긴 영상**(`iRm8SQvm38Y`)은 여전히 실패(앱 58~59s 타임아웃, 2회 재현). Tier1 키로 직접 실측:

| 설정 | 소요 | 입력 토큰 | 출력 |
|---|---|---|---|
| LOW res, 기본 fps | **56.6s** | 164,313 | 1,275 |
| LOW res + `videoMetadata.fps` 0.5 | 73.5s | 107,726 | 1,611 |
| LOW res + fps 0.2 | 80.9s | 73,717 | 1,354 |

- **핵심 교훈: fps 하향은 토큰을 줄이지만 오히려 더 느리다** — Gemini가 비표준 fps로 영상을 **재샘플링하는 오버헤드**가 토큰 절감분보다 큼. `videoMetadata.fps`는 유튜브 요약 지연 최적화에 **쓰지 말 것**. LOW res 기본 fps가 최적.
- 이 영상은 LOW res로도 입력 164K 토큰 / raw 56.6s(유료 Tier1 기준). 앱 오버헤드까지 더하면 60s 초과 → **Vercel 무료티어 60s 하드캡의 물리적 한계**([[chat-agent-vercel-60s-cap]]). 타임아웃·키티어·fps 모두 소진.
- **결론**: LOW res로 도달 범위를 넓혔지만(중간 길이 다수 구제), 매우 긴 영상은 무료티어에서 근본적으로 불가. 근본책은 Vercel 유료(함수 300s) 뿐 — 비용 결정 보류. (선택) 실패 UX 개선(빠른/명확한 안내)·유튜브 전용 경량 프롬프트로 경계선 영상 소폭 추가 구제 여지는 TODO.
