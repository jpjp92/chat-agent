## 1. 무엇을 했나

닉네임을 localStorage에 넣고 `service_role` 키로 모든 테이블을 만지던 구조를 걷어내고, **Supabase Auth를 단일 신원 소스로** 세웠다. TODO의 장기 계획 L1~L4를 개별 단계로 밟지 않고 **L3+L4 직행**했다 — L1(자체 토큰 테이블)은 Supabase Auth를 쓰는 순간 폐기될 코드라 만들 이유가 없었다.

핵심은 **게스트도 진짜 계정**이라는 것이다. Anonymous Sign-in으로 uuid를 발급받으므로 가입 없는 즉시 사용 UX는 그대로인데, 데이터는 처음부터 DB에 RLS로 보호되며 들어간다. Google 로그인은 **`linkIdentity`로 같은 uuid에 신원을 덧붙이는** 방식이라 게스트 시절 대화가 그대로 승계된다.

> 🔴 활성 세션이 있는데 `signInWithOAuth`를 부르면 **다른 uuid로 로그인**되어 게스트 대화가 주인 없이 남는다. 세션이 있으면 반드시 `linkIdentity`. 이 프로젝트가 존재하는 이유가 이 한 줄이다.
>
> Supabase의 Automatic Linking은 **이메일 매칭**으로 동작하는데 익명 유저에겐 이메일이 없다 → 자동 연결이 원리적으로 불가능. 대시보드 **Manual Linking 활성화가 선택이 아니라 전제조건**이다.

세션 전달은 **Bearer 토큰**이다. `@supabase/ssr` 쿠키가 아니다 — 앱이 `ssr: false`이고 [PLAN_NEXTJS_MIGRATION](../../../plans/PLAN_NEXTJS_MIGRATION.md) §2가 RSC 최적화를 금지하고 있어, 쿠키 세션은 얻을 게 없이 미들웨어·콜백 라우트만 늘린다.

## 4. 자동 테스트가 놓친 버그 3개 — 전부 실제 OAuth 리다이렉트에서만 드러났다

이 섹션이 이 로그의 핵심이다. 40건이 초록불인 상태에서 실제로 Google 로그인을 눌러보니 **버그가 세 개** 나왔다.

### a. 프로필 승격이 절반만 됐다 — `linkIdentity`는 `raw_user_meta_data`를 채우지 않는다

`is_guest`는 `false`로 잘 바뀌는데 이름·아바타가 `사용자_FF8F` + 기본 이미지 그대로였다. 원인: 동기화 트리거가 `auth.users.raw_user_meta_data`를 읽고 있었는데, **`linkIdentity` 경로에서는 Google의 name/avatar가 거기 들어오지 않는다**. `auth.identities.identity_data`에만 있다. 실측:

```
user_metadata: { "email_verified": true }            ← 이름도 사진도 없다
identities:    [{ provider: "google", name: "Juan Park", avatar_url: "..." }]
```

**identity 스위트가 10/10인데도 못 잡은 이유**: 픽스처가 `admin.createUser({ user_metadata })`였다. 그건 **SIGNUP 경로**를 흉내낸 것이고, 버그는 **LINK 경로**에 있었다. 픽스처가 현실과 다른 지점이 정확히 버그가 사는 지점이었다.

수정 — `auth.identities` INSERT에 트리거를 걸고 `identity_data`를 읽는다(`auth-mvp-identity-sync.sql`). 덤으로 `coalesce(p.avatar_url, ...)`가 아무것도 덮어쓰지 못하던 것도 고쳤다(게스트 기본 unsplash URL이 이미 들어 있어 `coalesce`가 항상 그걸 골랐다) → `chatagent_is_default_avatar()` 술어로 "기본값이면 교체" 판정. INSERT 트리거는 소급 발화하지 않으므로 백필 UPDATE도 같이 넣었다.

### b. 리다이렉트 에러를 무시하고 있었다 — 예외가 아니라 **URL 쿼리 파라미터**로 온다

이미 다른 계정에 붙은 Google 계정을 연결하면 `identity_already_exists`가 나는데, 모달은 아무 반응이 없었다. 로그를 보니 같은 에러가 두 번 — 사용자는 **조용한 무한 재시도**에 갇혀 있었다.

OAuth 실패는 **두 채널로 온다**:
- 리다이렉트 **전** 거부(manual linking 꺼짐 등) → 예외를 던진다
- 리다이렉트 **후** 거부 → `/?error=server_error&error_code=identity_already_exists`로 **돌아온다**. 브라우저가 떠났다가 왔으므로 잡을 예외가 애초에 존재하지 않는다.

수정 — `consumeOAuthError()`가 마운트 시 쿼리/해시에서 에러 코드를 회수하고 URL을 청소한다. `identity_already_exists`면 충돌 분기를 띄운다("이 Google 계정은 다른 계정에 연결됨 → 그 계정으로 로그인, 단 현재 게스트 대화는 승계되지 않음").

### c. 🔴 프라이버시 — 세션 캐시가 유저 간에 샜다

로그아웃 후 새 게스트(`사용자_579E`)로 들어갔더니 사이드바에 **이전 유저(Juan Park)의 대화 제목이 그대로 보였다.** `chat_sessions_cache_v1`이 **전역 키**였고 `signOut()`이 지우지 않았다.

**RLS는 DB를 지키지만 localStorage는 못 지킨다.** 본문은 못 읽지만 제목 목록은 그 자체로 유출이다.

수정 — 캐시에 `ownerId`를 각인하고, `userId`가 캐시의 주인과 다르면 즉시 폐기 + 비우기. `signOut()`도 `clearSessionsCache()`를 먼저 부른다.

## 5. UI 정리

- **`초기화` 버튼 제거.** git 히스토리를 확인해보니 이 버튼은 **DB 행을 지운 적이 한 번도 없었다** — 하는 일이 `sb-*` 키 삭제, 즉 **이름만 다른 로그아웃**이었다. 로그아웃이 있으니 남길 이유가 없다.
- **로그인 진입점** — 헤더 CTA를 빼면서 로그아웃한 유저가 로그인하려면 메시지 5개를 태워 한도 모달을 봐야 하는 상황이 됐다. 설정 모달에 계정 섹션을 넣어 해소.
- **모달 카피 단순화** — 자발적 진입(save)의 설명줄을 삭제하고 제목을 실제 혜택으로 바꿨다. 기존 문구("지금은 이 브라우저에만 대화가 남아 있습니다")는 **사실이 아니다** — 게스트도 익명 계정이 있어 대화는 이미 DB에 있다. 로그인해야만 생기는 값은 **다른 기기에서 잇기**뿐. 이제 제목=혜택 · 칩=구체적 약속(대화 N개) · 버튼=행동으로 셋이 각자 다른 일을 한다. 한도 모달의 설명은 "왜 막혔는가"라는 정보가 있으므로 유지.

## 6. 남은 것

- **프로덕션 이관** — SQL 3종 적용, 대시보드 3종 토글(Anonymous / Manual Linking / Google), Google Cloud에 운영 콜백 URI + JS 원본, Supabase Redirect URLs.
- **IDOR-3** (Storage) — `upload` / `create-signed-url` / `parse-document`는 아직 admin 클라이언트 + 형식 검증뿐. 근본해결은 유저별 prefix `${user.id}/...` + RLS.
- Google 동의 화면에 앱 이름이 아니라 `*.supabase.co`가 뜬다 → Supabase Custom Domain(유료) 외엔 방법 없음. 보류.
- 크로스 디바이스(§5-3)는 미검증이나 §5-2와 구조가 동일.
- Kakao · 이메일+비밀번호 — Google 연결 후엔 그 이메일이 이미 검증된 상태라 `updateUser({ password })`가 깔끔하게 동작한다.
