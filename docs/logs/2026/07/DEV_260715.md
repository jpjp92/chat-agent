## 1. 무엇을 했나

인증 MVP는 **게스트 승계**(guest → Google → 같은 uuid)를 풀었지만, 써보니 **로그인 자체**가 세 군데서 막혀 있었다. 모달에 연결(link)만 있고 로그인(sign-in)이 없던 게 한 뿌리다.

| # | 증상 | 수정 |
|---|---|---|
| P1 | 브라우저에 로그인된 Google 계정이 묻지도 않고 선택된다 | link·signIn 양쪽에 `queryParams: { prompt: 'select_account' }` |
| P2 | 이미 계정 있는 사용자가 **실패를 거쳐야** 로그인된다(왕복 → 충돌 → 그제서야 버튼) | 대화 0개면 `linkIdentity` 대신 `signInWithOAuth` 로 직행 |
| P3 | 로그인 상태에서 계정 전환 수단이 없다 | 설정 › 계정에 "다른 계정으로 로그인" |

P2가 특히 아픈 이유: **캐시를 지운 사용자가 정확히 이 경우다.** 세션이 사라져 새 게스트(대화 0개)가 되고, 하려는 건 "원래 내 계정 로그인"인데 앱은 "이 게스트를 연결"을 시도했다 충돌로 튕겼다.

## 3. 🔴 철칙을 정확하게 다시 썼다

MVP 내내 가장 자주 인용된 주석:

> ~~"활성 세션이 있으면 signInWithOAuth 금지"~~ → **"승계할 게스트 데이터가 있을 때 금지"**

원 문장은 목적(게스트 대화가 고아가 되는 것을 막기)을 **세션의 존재로 잘못 일반화**했다. 대화 0개 게스트나 이미 정식인 사용자에겐 고아가 될 게 없으므로 `signInWithOAuth` 가 금지가 아니라 **정답**이다. 이 구분을 주석에 못 박지 않으면 다음 사람이 옛 규칙만 보고 §2 의 분기를 버그로 오해해 되돌린다.

계정 전환(P3)이 로그아웃 선행 없이 되는 이유도 여기 있다: 세션이 새 계정으로 교체돼도 원래 계정의 대화는 그 uuid 에 그대로 남아 다시 로그인하면 돌아온다. 그리고 계정이 바뀌면 [DEV_260714](DEV_260714.md) §4-c 에서 넣은 **ownerId 불일치 가드**가 발화해 이전 계정 제목 캐시를 폐기한다 — 계정 전환에도 그대로 맞아 추가 작업이 없었다.

## 4. 검증

- `tsc --noEmit` **0**.
- **수동 3건 대기** — 이 변경은 전부 실제 OAuth 리다이렉트에서만 드러나므로 자동 테스트로 못 본다([DEV_260714](DEV_260714.md) §4 교훈).
  - a. 대화 **있는** 게스트 → 선택창 뜸 → 링크·승계(회귀). 선택창이 안 뜨면 `linkIdentity` 가 `queryParams` 를 안 흘려보내는 것(플랜 §6 의 유일한 가정).
  - b. 대화 **0개** 게스트 → **충돌 없이** 바로 로그인.
  - c. 로그인 상태 → 계정 전환 → 사이드바 **완전 교체**(이전 제목 잔존 0 = ownerId 가드 발화 확인).
