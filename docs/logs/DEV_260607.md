# DEV_260607

## 1. 작업 개요

멀티턴 대화 UI에서 **턴(turn) 사이 간격**이 좁다는 피드백 → `ChatMessage.tsx` 메시지 버블 하단 마진 조정.

---

## 2. 문제 인식

스크린샷(모바일, `chat-gem.vercel.app`) 리뷰 결과:

- AI 응답 → 다음 유저 메시지(새 턴 시작) 사이의 시각적 구분이 부족.
- **유저 메시지 ↔ AI 응답 사이 간격**은 문제없음 — 같은 턴 내 흐름이므로 붙어 있어야 자연스러움.
- 데스크톱 웹은 이미 충분. **모바일에서만 조정 필요.**

---

## 3. 현황 분석

| 파일 | 클래스 | 설명 |
|------|--------|------|
| `components/ChatArea.tsx:40` | `space-y-2` | 메시지 리스트 컨테이너, 아이템 간 8px |
| `components/ChatMessage.tsx:694` | `mb-8` | 각 메시지 버블 하단 마진 32px |

유저 메시지 · AI 응답 모두 동일한 `mb-8` → 턴 사이 구분이 없음.

---

## 4. 수정 (최종)

1차 수정 후 추가 피드백 2건을 반영해 총 3단계로 최종 확정.

### 4-1. 1차: AI 응답 하단 마진 분리

**`components/ChatMessage.tsx:694`**

```diff
- mb-8
+ ${isUser ? 'mb-8' : 'mb-16 sm:mb-8'}
```

AI 응답에 모바일 64px / 데스크톱 32px 하단 마진 부여.

### 4-2. 2차: AI 응답 상단 마진 추가 + `space-y-2` 제거

**문제**: 2번째 턴의 유저 메시지 → AI 응답 간격이 1번째 턴보다 좁아 보임.

**원인**: `ChatArea.tsx`의 `space-y-2`가 자식 요소에 CSS 선택자 specificity (0,3,0)로 `margin-top: 8px`을 적용해, 직접 지정한 `mt-8` (specificity 0,1,0)을 덮어쓰고 있었음.

**수정**:

`components/ChatArea.tsx:40` — `space-y-2` 제거

```diff
- <div className="flex min-h-0 flex-col space-y-2 pt-4">
+ <div className="flex min-h-0 flex-col pt-4">
```

`components/ChatMessage.tsx:694` — AI 메시지에 모바일 상단 마진 추가

```diff
- ${isUser ? 'mb-8' : 'mb-16 sm:mb-8'}
+ ${isUser ? 'mb-8' : 'mt-8 mb-16 sm:mt-0 sm:mb-8'}
```

→ 유저→AI 간격: 32px + 32px = **64px** / AI→유저 간격: 64px → 양방향 대칭.

### 4-3. 3차: 간격 소폭 축소 (최종)

간격이 과도하게 크다는 피드백 → 값 하향 조정.

```diff
- mt-8 mb-16 sm:mt-0 sm:mb-8
+ mt-4 mb-10 sm:mt-0 sm:mb-8
```

**최종 모바일 간격 (확정)**

| 구간 | 계산 | 결과 |
|------|------|------|
| 유저 메시지 → AI 응답 (within-turn) | `mb-8`(32px) + `mt-4`(16px) | **48px** |
| AI 응답 → 유저 메시지 (turn boundary) | `mb-10`(40px) | **40px** |
| 데스크톱 전체 | `sm:mt-0 sm:mb-8` | 32px (기존 동일) |

---

## 5. 영향 범위

- 변경 파일: `components/ChatMessage.tsx` 1줄, `components/ChatArea.tsx` 1줄
- 데스크톱 레이아웃 변화 없음 (`sm:mt-0 sm:mb-8`)
- `space-y-2` 제거로 메시지 간 암묵적 8px 패딩 없어짐 — 각 메시지 `mb-*` 값이 전체 간격 제어의 단일 소스가 됨

## 6. Notion DEV Records 동기화 점검 및 정리

### 6-1. 문제

Notion `DEV Records`에 커밋 내용이 자동 업데이트되지 않는 것으로 보임.

확인 결과 이 구성은 GitHub webhook이 아니라 로컬 Git hook 기반이었다.

| 구성 | 역할 |
|------|------|
| `.git/hooks/post-commit` | 커밋 후 `docs/notion/sync-notion-dev-records.mjs` 실행 |
| `docs/notion/sync-notion-dev-records.mjs` | 최근 git commit을 Notion DB page로 생성 |
| `docs/notion/.synced-hashes.json` | 로컬 중복 방지 캐시 (`.gitignore` 대상) |

기존 hook은 `node ... > /dev/null 2>&1 &`로 실행되어 실패 로그가 완전히 사라지는 구조였다.

### 6-2. 원인

1. **Notion 날짜 payload 오류**
   - 기존 payload가 `start: 2026-06-07T15:57:34+09:00`와 `time_zone: Asia/Seoul`을 동시에 전달.
   - 현재 Notion API는 `time_zone` 명시 시 `start/end`에 non-zero UTC offset을 허용하지 않음.
   - 결과: `invalid date`로 page 생성 실패.

2. **Notion SDK v5 data source API 변화**
   - page 생성은 `parent.database_id`로 가능.
   - DB query는 `notion.databases.query`가 아니라 `notion.dataSources.query`.
   - DB metadata의 `data_sources[0].id`를 사용해야 함.

3. **중복 방지 기준 부족**
   - 로컬 캐시가 유일한 기준이면 `.synced-hashes.json`이 비거나 오래됐을 때 중복 page 생성 가능.
   - 과거 일괄 동기화분은 짧은 commit hash URL(`.../commit/f1a9cafc`)이 섞여 있었고, 최신 생성분은 full hash URL 사용.

### 6-3. 수정

**`docs/notion/sync-notion-dev-records.mjs`**

- repo root 기준으로 `.env`와 `git log`를 읽도록 `REPO_ROOT` 도입.
- Notion date payload에서 `time_zone` 제거.
- `notion.databases.retrieve()`로 `data_sources[0].id` 자동 감지.
- `notion.dataSources.query()` 기반 중복 조회 추가.
- 중복 조회 시 full hash URL과 short hash URL을 모두 검사.
- 기존 Notion 행을 Git 커밋 메타데이터로 보정하는 유지보수 옵션 추가:

```bash
node docs/notion/sync-notion-dev-records.mjs --update-existing-times
node docs/notion/sync-notion-dev-records.mjs --update-existing-times --dry-run
```

**`.git/hooks/post-commit`**

- 최근 10개 커밋을 재시도하도록 변경.
- `.git/notion-post-commit.log`에 실행 로그를 남기도록 변경.
- 한 번 실패해도 다음 커밋 때 누락분이 회복될 수 있게 함.

### 6-4. Notion 데이터 정리

| 완전 중복 그룹 | 0 |
| 완전 중복 page | 0 |

URL만 같고 제목이 다른 `autoeval` 항목은 삭제하지 않음.

#### 기존 chat-agent 행 시간 보정

기존 `chat-agent` 커밋 URL 행을 Git 실제 커밋 내역으로 역추적하여 Notion `날짜`와 `참고링크`를 보정.

|------|------|
| 업데이트 대상 | 110 |
| 업데이트 성공 | 110 |

보정 내용:

- 날짜만 있던 기존 행을 시간 포함 값으로 업데이트.
- short hash commit URL을 full hash commit URL로 정규화.
- `.synced-hashes.json` 캐시도 full hash 기준으로 보강.

### 6-5. Notion 뷰 정렬

`DEV Records`의 3개 뷰 모두 `날짜` 내림차순 sort 적용.

| 뷰 | 타입 | 정렬 |
|----|------|------|
| `Default view` | table | `날짜` descending |
| `📅 캘린더` | calendar | `날짜` descending |
| `📋 상태별 보드` | board | `날짜` descending |

API 조회 기준으로 ascending/descending 결과가 정상적으로 다르게 나오는 것 확인.

주의:

- calendar view는 날짜 칸 배치라 sort 변경 체감이 작음.
- board view는 `상태` 그룹 내부 정렬이라 UI에서 변화가 약하게 보일 수 있음.
- Notion 응답의 sort property는 내부 ID `b>y_`로 표시되지만 실제 속성명은 `날짜`.

### 6-6. 검증

```bash
node docs/notion/sync-notion-dev-records.mjs --last 5 --dry-run
node docs/notion/sync-notion-dev-records.mjs --update-existing-times --dry-run
git diff --check
```

결과:

- 최근 5개 커밋 모두 중복 스킵.
- 기존 chat-agent 커밋 행 보정 후보 0개.
- Notion 날짜 descending 조회: 최신 커밋부터 시간순 정렬 확인.
- `git diff --check` 통과.
